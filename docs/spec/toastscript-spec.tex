\chapter{Preface}

Welcome to the \textbf{ToastScript Language Specification}---the definitive guide
to every feature, command, operator, and idiom in the TōSh shell.

\textbf{TōSh} is a modern, object-oriented shell built on .NET 10 and the Common
Language Runtime (CLR). It replaces traditional text-stream pipelines with
\emph{structured object pipelines}, giving you rich types, tab completion, and
CLR interop right at the command line.

This document covers:

\begin{itemize}
  \item The complete language syntax---variables, operators, control flow,
        functions, modules, classes, records, enums, and events.
  \item Every built-in command (over 200), with signatures, descriptions,
        and runnable examples.
  \item The type system, including CLR type aliases, shell records, callables,
        type conversion, and truthiness rules.
  \item Pipeline mechanics, redirection, process substitution, and
        background jobs.
  \item Configuration, startup files, and prompt customization.
  \item A \emph{Cookbook} of practical recipes for everyday tasks.
\end{itemize}

\begin{tipbox}[Who Is This For?]
Whether you are evaluating TōSh for the first time, writing your first
\code{profile.tosh}, or building complex automation scripts, this
specification is your single source of truth.
\end{tipbox}

\subsection*{Conventions}

\begin{description}[style=nextline]
  \item[\texttt{monospace}] Shell commands, code, and identifiers.
  \item[\textit{italic}] Placeholder values you supply.
  \item[\texttt{[brackets]}] Optional arguments.
  \item[\texttt{arg \dots}] One or more repetitions.
  \item[\texttt{a\,|\,b}] Choose one of the alternatives.
\end{description}

\section*{Conformance}
\label{sec:conformance}

This document is both a description and a contract. Most of it explains *why* a rule is
what it is, and that explanation is deliberate --- a rule whose reason is lost gets
"tidied" away by the next reader. But an implementation has to know which sentences bind
it, so this section says how to tell.

\subsection*{What binds an implementation}

\begin{description}[style=nextline]
  \item[\textbf{Statements of behaviour are normative.}] A sentence saying what a construct
        \emph{is} or what an operation \emph{does} --- "a \code{str} is a sequence of
        UTF-16 code units", "arithmetic on \code{null} raises" --- states a requirement. An
        implementation that answers differently is not conforming.
  \item[\textbf{Examples are normative in their results.}] Where a listing carries a
        comment giving a value, that value is required. The examples in this document are
        run against the implementation before they are written down.
  \item[\textbf{\code{must} and \code{must not} mark a requirement} that might otherwise be
        read as advice.] They add emphasis, not force: a plain statement of behaviour binds
        just as much.
  \item[\textbf{\code{may} marks a genuine choice}] left to the implementation. Where this
        document says an implementation \emph{may}, two conforming implementations are
        permitted to differ, and a program that depends on which is not portable.
\end{description}

\subsection*{What does not}

\begin{description}[style=nextline]
  \item[\textbf{Rationale.}] Text explaining why a rule was chosen, what was rejected, or
        what went wrong before, constrains nothing. It is here because the reasons are
        harder to recover than the rules.
  \item[\textbf{A \emph{Known defect} box.}] These describe behaviour that is true today
        and \emph{intended to change}. They name the item tracking the change. An
        implementation is never required to reproduce one, and a program should not rely
        on one.
  \item[\textbf{Notes, tips and asides}] that restate or illustrate a rule stated
        normatively elsewhere.
\end{description}

\begin{notebox}
Where this document and the implementation disagree, that is a defect in one of them and
neither is automatically right. Several rules here were written from the implementation's
behaviour and then found to be wrong about it; the specification is kept honest by a
corpus that runs its claims, not by its own authority.
\end{notebox}

\section{What Is TōSh?}

TōSh (short for \emph{ToastScript}) is a Linux-first interactive shell and
scripting language. It is built on the .NET 10 CLR, meaning every value that
flows through a pipeline is a \textbf{real object}---not a flat string.

\begin{itemize}
  \item \textbf{Structured pipelines.} Commands emit lists, records, dates,
        file-system entries, and arbitrary CLR objects. Downstream commands
        filter, transform, and aggregate with full type awareness.
  \item \textbf{CLR integration.} Call any .NET method, inspect types, load
        assemblies, and even invoke native (unmanaged) libraries via built-in
        FFI.
  \item \textbf{Familiar surface.} If you know Bash, PowerShell, or Nushell,
        much of TōSh will feel natural: pipes, redirection, globs,
        \code{\$variables}, \code{if}/\code{for}/\code{while}, and function
        definitions all look close to what you expect.
  \item \textbf{Rich features.} Pattern matching with guards, destructuring,
        first-class functions, event handlers, module system, classes, records,
        enums, and a built-in TUI toolkit.
\end{itemize}

\section{Quick Start}

\begin{lstlisting}[title={Your first TōSh session}]
# List files, filter, and sort
ls -la | where _.Type == file | sort Size | reverse | first 5

# Variables and string interpolation
var name = "World"
echo $"Hello, {$name}!"

# Functions
func greet(who: string) {
    writeline $"Welcome, {$who}."
}
greet "Toast"

# Pipeline with structured data
ps -ef | where _.Cpu > 5.0 | sort Cpu | reverse | first 10
\end{lstlisting}

\section{Design Philosophy}

\begin{enumerate}
  \item \textbf{Objects, not text.} Parsing output into columns is a relic.
        Every TōSh command returns typed objects.
  \item \textbf{Progressive disclosure.} Basic usage is simple; advanced
        features (modules, FFI, TUI) are there when you need them.
  \item \textbf{Linux-native.} Built for Linux with first-class support for
        systemd, procfs, and POSIX signals.
  \item \textbf{Correctness.} Strong typing with helpful error messages.
        \code{pipefail} by default.
\end{enumerate}

\section{Comments}
\ikw{comment}

TōSh supports regular comments, block comments, and documentation comments:

\begin{lstlisting}
# This is a comment
echo hello  # Inline comment

##{
This block comment may span lines.
}##

## Adds two numbers.
## @param a first value
## @param b second value
## @returns the sum
func add(a, b) { return ($a + $b) }
\end{lstlisting}

\code{\#} begins an ordinary single-line comment.  \code{\#\#\{...\}\#\#}
is a block comment.  Consecutive \code{\#\#} documentation comments attach to
the next function, class, module, record, enum, event, or class member and feed
hover, completion, signature-help, and \code{help} metadata.

\subsection{When \code{\#} Is a Comment}
\label{sec:hash-boundary}

A lone \code{\#} opens a comment only when it \emph{stands alone as a word}: it
must begin a word --- be at the start of a line or preceded by whitespace ---
\emph{and} be followed by whitespace or the end of the line.  Anywhere else it
is an ordinary bareword character:

\begin{lstlisting}
# a comment                 # '#' begins a word, space follows
echo hello  # a comment     # same, mid-line
#                           # a lone '#' at end of line is an empty comment

echo #ff0000                # bareword "#ff0000" -- no quoting needed
echo issue#42               # bareword "issue#42"
echo http://host/page#frag  # bareword, fragment intact
echo C#                     # bareword "C#"
\end{lstlisting}

The word-start half of the rule is the POSIX shell rule: \code{bash} and
\code{zsh} also refuse to start a comment mid-word, which is why
\code{echo issue\#42} prints \code{issue\#42} in both.  Requiring whitespace to
follow as well is what TōSh adds, and it is what lets \code{\#ff0000} go
unquoted.

\begin{notebox}
\code{\#\#} is unconditional.  Doc comments and \code{\#\#\{...\}\#\#} blocks
keep their meaning wherever they appear, so a divider line such as
\code{\#\#\#\#\#\#\#\#\#\#} still reads as a doc comment.  The one further
exception is \code{\#!} at byte offset zero, which is a shebang.
\end{notebox}

\begin{warnbox}[Migration note --- July 31, 2026]
Earlier builds treated \code{\#} as a comment opener everywhere, so
\code{echo issue\#42} printed \code{issue} and silently discarded the rest of
the line.  Comments written \code{\#comment} with no following space are now
barewords; write \code{\# comment} instead.  The formatter normalises the
spelling, and no comment in the TōSh tree needed changing.
\end{warnbox}

\section{Identifiers}

Identifiers start with a letter or underscore and may contain letters, digits,
underscores, and hyphens:

\begin{lstlisting}
var my_count = 10
var total-items = 42
func process-batch() { ... }
\end{lstlisting}

\begin{notebox}
Hyphens are allowed in identifiers, which is unusual among programming
languages but natural for shell commands (\code{read-file}, \code{group-by}).
\end{notebox}

\subsection{Escape Sequences}

Double-quoted strings support these escapes:

\begin{tabular}{ll}
\toprule
\textbf{Sequence} & \textbf{Meaning} \\
\midrule
\code{\textbackslash n} & Newline \\
\code{\textbackslash t} & Tab \\
\code{\textbackslash r} & Carriage return \\
\code{\textbackslash\textbackslash} & Literal backslash \\
\code{\textbackslash"} & Literal double quote \\
\code{\textbackslash 0} & Null character \\
\bottomrule
\end{tabular}

An unrecognised escape is preserved verbatim, including its backslash:
\code{"\textbackslash d+"} contains the three characters
\code{\textbackslash}, \code{d}, and \code{+}.  This makes common regex
forms work without doubled slashes:

\begin{lstlisting}
"a1" =~ "\d"       # true
"file.cs" =~ "\.cs$"  # true
\end{lstlisting}

Single-quoted strings are raw: backslashes never introduce escapes and the
next single quote closes the string.  Use \code{\$'...'} for ANSI-C escapes
such as \code{\textbackslash x1b}, or switch quote forms when the text itself
contains a single quote.

\begin{warnbox}[Migration note --- July 25, 2026]
Earlier builds decoded escapes inside ordinary \code{'...'} strings and
silently removed the backslash from unknown escapes in \code{"..."} and
\code{\$"..."}.  Ordinary single quotes are now raw, and every
escape-processing form preserves unknown escape pairs.  Replace an ordinary
single-quoted string with \code{\$'...'} when the old escape processing was
intentional.
\end{warnbox}

\subsection{Quotes Inside a Word}

A quote need not begin a word to be quoting.  Quote characters are removed
wherever they are \emph{balanced within a single word}, and what they enclose is
protected from splitting and from glob expansion:

\begin{lstlisting}
/usr/bin/grep --include="*.cs" ...   # grep sees --include=*.cs
--opt="a"b"c"                        # one argument, --opt=abc
--opt="a b"                          # one argument, --opt=a b
x"*"y                                # literal x*y, not expanded
\end{lstlisting}

An \textbf{unbalanced} quote is an ordinary character and the word still splits at
whitespace, so \code{don't} and \code{5"} keep their marks.  A literal quote in a
word is spelled by quoting the whole word, \code{"--opt=\textbackslash"x\textbackslash""},
or with the other quote character, \code{'"'}.

\subsection{String Interpolation}
\ikw{interpolation}

Interpolated strings (\code{\$"..."}) embed expressions inside
\code{\{...\}} delimiters:

\begin{lstlisting}
var user = "Alice"
echo $"Hello, {$user}!"             # Variable
echo $"2 + 2 = {2 + 2}"             # Expression
echo $"Files: {ls | where _.Type == file | count}"  # Pipeline
echo $"Today is {(date now).DayOfWeek.ToString()}"              # Member access
\end{lstlisting}

A hole is \textbf{one value} unless it contains a pipeline.  An expression renders
its value; a pipeline joins its results with a single space:

\begin{lstlisting}
var xs = [1, 2, 3]
$"{$xs}"                      # [1, 2, 3]   -- an expression, one value
$"{$xs | where { $_ > 1 }}"   # 2 3         -- a pipeline, joined
\end{lstlisting}

The distinction is a \code{|} the reader can see in the source, rather than a
property of whatever the value turned out to be.

\begin{lstlisting}[title={Multi-line interpolated string}]
var report = $"""
Name:  {$name}
Items: {$items | count}
Total: {$items | sum Price}
"""
\end{lstlisting}

\section{Numeric Literals}

\begin{lstlisting}
42          # int (System.Int32)
3.14        # double (System.Double)
1_000_000   # underscores for readability
0xFF        # hexadecimal
0b1010      # binary
0o777       # octal
4i          # imaginary literal (Complex: 0 + 4i)
-2.5i       # imaginary literal (Complex: 0 - 2.5i)
\end{lstlisting}

An integer literal takes the narrowest type that holds it --- \code{int}, then
\code{long}, then \code{ulong} --- and the rule is the same in every base, so
\code{0xFFFFFFFFFFFFFFFF} is a \code{ulong} and not a truncated \code{int}. A
literal too large for \code{ulong} is an error rather than a silently different
number.

A suffix pins the type where inference is not what is wanted:

\begin{lstlisting}
100u        # uint  (ulong when too large for uint)
100L        # long
100UL       # ulong
\end{lstlisting}

Suffixes are case-insensitive, and \code{lu} is accepted alongside \code{ul}.

\subsection{Format and Alignment}

An interpolation hole may carry an alignment and a format clause,
\code{\{expr,align:format\}}:

\begin{lstlisting}
$"pi is {$n:F2}"          # pi is 3.14
$"hex {$i:X}"             # hex 2A
$"[{$i,6}]"               # [    42]   right-aligned in six columns
$"[{$i,-6}]"              # [42    ]   left-aligned
$"{$when:yyyy-MM-dd}"     # 2026-08-16
\end{lstlisting}

The clause selects a rendering other than the value's default, and is applied
invariantly --- \code{\$"\{3.14159:F2\}"} is \code{3.14} on every machine, not
\code{3,14} on one whose locale uses a comma.

A clause the value cannot honour is \textbf{an error}.  \code{\$"\{\$name:F2\}"}
where \code{\$name} is a string reports \code{tosh.runtime.invalid\_format\_clause}
and names the clause.  A clause is an explicit instruction, and ignoring an
explicit instruction is worse than refusing it: a silently dropped clause makes a
program succeed while producing text nobody asked for.

On the \code{dotnet} target a clause outside the portable core reaches the value's
own formatter, so every .NET format string continues to work.  A program that
stays inside the core set renders identically on every target; one that goes
outside it has made a target-specific choice.

Only separators at the top level of the hole are clauses: inside parentheses,
brackets, braces or a string they belong to the expression.  A conditional's
colon is recognised as its own, so \code{\$"\{\$x > 0 ? "a" : "b"\}"} needs no
parentheses --- though a conditional that wants a format clause does:
\code{\$"\{(\$x > 0 ? 1.5 : 2.5):F1\}"}.

\section{Collection Literals}

Record, dictionary, and set literals use the paired delimiters
\code{\{|~...~|\}}, \code{\{\%~...~\%\}}, and \code{\{:~...~:\}},
respectively.  The two characters in each opening or closing delimiter must
be adjacent.  Their empty spellings are \code{\{||\}}, \code{\{\%\%\}}, and
\code{\{::\}}.  Plain \code{\{~...~\}} remains block syntax.

\begin{lstlisting}
# Lists
[1, 2, 3]
["a", "b", "c"]

# Records
{| name = "Alice", age = 30 |}
{| ($key) = "dynamic" |}          # computed property name
{| ...$base, enabled = true |}    # record spread

# Dictionaries with arbitrary keys
{% "left" => 1, "right" => 2 %}

# Sets
{: 1, 2, 2, 3 :}

# Tuples
("x", 42)

# Spread in list literals
[0, ...$items, 99]
\end{lstlisting}

\section{Special Literals}
\ikw{null}\ikw{true}\ikw{false}

\begin{lstlisting}
true         # Boolean true
false        # Boolean false
null         # Null reference

# Durations (parsed as TimeSpan)
5s
100ms
2m30s

# ISO temporal instants (parsed as DateTimeOffset)
2026-03-27
2026-03-27T14:30
2026-03-27T14:30:45Z
2026-03-27T14:30:45.1234567-04:00

# IP addresses (parsed as System.Net.IPAddress)
192.168.1.1
::1
2001:db8::1

# Quantities with units (backtick syntax)
100`m        # 100 meters (Length)
9.8`m/s^2    # acceleration
5`kg         # 5 kilograms (Mass)
\end{lstlisting}

Intrinsic temporal literals deliberately accept only these ISO-style shapes:
\code{yyyy-MM-dd}, \code{yyyy-MM-ddTHH:mm},
\code{yyyy-MM-ddTHH:mm:ss}, and the seconds form with one through seven
fractional digits.  Date-time forms may omit a zone or end in \code{Z} or a
numeric \code{+HH:mm}/\code{-HH:mm} offset.  Explicit commands such as
\code{date parse} may accept additional human-oriented input, but that
permissive parser is never used to guess the type of a bareword.

IPv4 literals likewise require four explicit decimal octets from 0 through
255, without leading zeroes.  IPv6 uses its ordinary colon notation.
Consequently, dotted numeric text such as \code{1.2.3} is neither a date nor
an abbreviated IPv4 literal.

\begin{warnbox}[Migration note --- July 25, 2026]
Earlier builds let the CLR's culture-oriented date and abbreviated-IPv4
parsers guess the type of expression barewords.  Text such as \code{1.2.3}
could therefore become a date in 2003 or the address \code{1.2.0.3}.
Intrinsic literals are now exact.  Quote human-oriented input as text or pass
it to an explicit parser such as \code{date parse}.
\end{warnbox}

\subsection*{Aliases and CLR types of the same name}
\label{sec:alias-case}

The aliases are matched without regard to case, so \code{INT} and \code{Int}
both name \code{System.Int32}.  Several aliases share a name with a different
CLR type---\code{file} is \code{FileInfo} while \code{System.IO.File} is the
static helper class, and \code{array} is \code{object[]} while
\code{System.Array} is the class carrying \code{IndexOf} and \code{Sort}.

The spelling decides which one a \emph{member access} reaches.  An alias is
canonically lower-case, so a capitalised head names the CLR type:

\begin{lstlisting}
File.ReadAllText("/etc/hostname")   # System.IO.File
Array.IndexOf([1, 2, 3], 2)         # System.Array
\end{lstlisting}

Everywhere a type is \emph{named} rather than used---annotations, \code{cast},
and \code{new}---the alias wins regardless of case, so \code{var f: file} and
\code{var f: File} both bind \code{FileInfo}:

\begin{lstlisting}
var f: file = (new FileInfo("/etc/hostname"))
var a: array = [1, 2]               # object[], not System.Array
new array(1, 2, 3)                  # the shell's array type
\end{lstlisting}

Fully qualifying the name is always unambiguous, in either position.

\subsection*{Array types}
\label{sec:array-types}

A postfix \code{[]} names a CLR array of the element type, so \code{string[]}
is \code{System.String[]}.  It is accepted anywhere a type is: parameter and
return annotations, variable and class-member declarations, and \code{cast}.
The suffix repeats for jagged arrays (\code{string[][]}) and may be followed
by \code{?}.

\begin{lstlisting}
func names(paths: string[]) -> string[] {
    return $paths
}

var files: string[] = ["a.txt", "b.txt"]
var grid: int[][]   = [[1, 2], [3, 4]]
var typed = (cast string[] ["a", "b"])
\end{lstlisting}

\begin{notebox}
\code{T[]} is an array; \code{list<T>} is a \code{System.Collections.Generic.List<T>}.
Both are available and they are different types --- \code{array} remains the
untyped spelling, equivalent to \code{object[]}.
\end{notebox}

\begin{notebox}
Only an \emph{empty} bracket pair is a type suffix.  In a \code{native}
signature a bracket holds a fixed inline capacity instead ---
\code{buffer[256]}, \code{double[3]} --- and those keep that meaning.
\end{notebox}

\section{Shell-Specific Types}

Beyond CLR types, TōSh introduces several shell-native types:

\subsection{StorageSize}

A value type representing byte quantities with human-friendly display:

\begin{lstlisting}
var small = 10kb             # StorageSize of 10 kB (10,000 bytes)
var large = 2.5mb            # StorageSize of 2.5 MB (2,500,000 bytes)
echo ($large > $small)       # true
ls | where Size > 100kb      # filter files larger than 100 kB
ls | sort Size               # sort by StorageSize
\end{lstlisting}

\begin{notebox}
Storage-size suffixes \code{b}, \code{kb}, \code{mb}, \code{gb}, \code{tb}, \code{pb}
use SI decimal factors (1 kb = 1{,}000 bytes). Binary suffixes \code{kib}, \code{mib},
\code{gib}, \code{tib}, \code{pib} use powers of 1{,}024.  These suffixes are
\emph{expression-context literals}: they parse to \code{StorageSize} values in
expressions (\code{var x = 10kb}, \code{(10kb > 5mb)}) but remain plain strings
when passed as raw command arguments (\code{echo 10kb}).  Suffix matching is
case-insensitive and mandatory; a malformed or overflowing suffix form in
expression position never silently falls back to a string.
\end{notebox}

\subsection{TemporalAmount / TimeSpan}

Duration values with natural syntax:

\begin{lstlisting}
5s                       # 5 seconds
100ms                    # 100 milliseconds
2m30s                    # 2 minutes 30 seconds
sleep 1s
\end{lstlisting}

\subsection{ToshRange}
\ikw{range}

Lazy sequences defined by start, optional step, and end:

\begin{lstlisting}
1..10                    # 1, 2, 3, ..., 10
1..2..10                 # 1, 3, 5, 7, 9 (step of 2)
10..1                    # 10, 9, 8, ..., 1 (auto-descending)
-2..2                    # -2, -1, 0, 1, 2
\end{lstlisting}

Range starts, steps, and ends are signed 32-bit integers.  A literal
fractional bound such as \code{1.5..3} produces
\code{tosh.parser.range\_requires\_integer}; negative integer bounds are
ordinary ranges.

\subsection{IShellRecordObject}

The interface for structured records---produced by commands like \code{ls},
\code{ps}, \code{stat}, and record literals:

\begin{lstlisting}
{| name = "Alice", age = 30 |} # Anonymous record
ls | first | get-props          # List property names
\end{lstlisting}

\subsection{IShellCallable}

The interface for callable objects---lambdas, function references, partial
applications, curried functions, and composed functions:

\begin{lstlisting}
var fn = func(x) => ($x * 2)
invoke $fn 21                   # 42
var callback = &greet           # Function reference
\end{lstlisting}

\subsection{LazySequence}
\ikw{lazy}

\code{LazySequence} is the runtime representation for lazy pipeline-friendly
sequences.  Infinite ranges, generator comprehensions, and iterator commands
such as \code{iterate}, \code{recur}, \code{cycle}, \code{repeat}, and
\code{repeatedly} can produce values without materialising the entire sequence.
Items are evaluated on demand and memoised as the sequence is traversed.

\begin{lstlisting}
1.. | first 5                         # 1, 2, 3, 4, 5
0..2.. | first 5                      # 0, 2, 4, 6, 8
iterate 1 func(x) => ($x * 2) | first 6
recur (0, 1) func(a, b) => ($a + $b) | first 8
($x * $x <| for x in 1..) | first 5   # generator comprehension
\end{lstlisting}

\subsection{Vector}
\ikw{Vector}\ikw{vec}

\code{Vector} is a shell-native dense vector of \code{double} values.  Create
vectors with the \code{vec} command, \code{new Vector(...)}, or static factory
methods such as \code{Vector.zeros}, \code{Vector.ones}, \code{Vector.fill},
\code{Vector.range}, and \code{Vector.random}.  Vectors render compactly as
\code{[1, 2, 3]} even though they implement \code{IEnumerable<double>}.

\begin{lstlisting}
var v = vec 1 2 3
var w = Vector.range(1, 3)
Vector.dot($v, $w)
Vector.cross((vec 1 0 0), (vec 0 1 0)) | raw
Vector.normalize($v) | raw
$v.Length
$v.Magnitude
\end{lstlisting}

\subsection{Matrix}
\ikw{Matrix}\ikw{mat}

\code{Matrix} is a shell-native dense matrix of \code{double} values.  Create
matrices with \code{mat}, \code{new Matrix(...)}, or factories such as
\code{Matrix.zeros}, \code{Matrix.ones}, \code{Matrix.fill},
\code{Matrix.identity}, and \code{Matrix.random}.  Matrix multiplication uses
\code{*}; element-wise multiplication is available as
\code{Matrix.hadamard(left, right)}.

\begin{lstlisting}
var a = mat [1, 2] [3, 4]
var b = Matrix.identity(2)
($a * $b) | raw
Matrix.transpose($a) | raw
Matrix.determinant($a)
Matrix.inverse($a) | raw
($a * (vec 1 1)) | raw
\end{lstlisting}

\subsection{Complex}
\ikw{Complex}\ikw{complex}

\code{Complex} wraps \code{System.Numerics.Complex} with shell type metadata,
compact rendering, casts, imaginary literals, and static helpers.  Use
\code{complex}, \code{new Complex(...)}, numeric casts, string casts, or
imaginary literals such as \code{4i}.

\begin{lstlisting}
var z = complex 3 4
var w = 4i
($z + $w) | raw
Complex.conjugate($z) | raw
Complex.magnitude($z)
Complex.phase($z)
Complex.from-polar(2, Math.PI / 2) | raw
echo "3-4i" | cast complex | raw
\end{lstlisting}

\subsection{Quantity (Unit System)}
\label{sec:quantities}

TōSh includes a dimensional-analysis unit system inspired by CAS calculators.
A \emph{quantity} is a numeric value paired with a physical unit. Unit literals
use backtick syntax: the number is immediately followed by a backtick and the
unit expression with no intervening whitespace. The conventional U+00B0 degree
sign is the one adjacency shorthand and does not require a backtick.

\begin{lstlisting}
100`m            # Length -- 100 meters
5`kg             # Mass -- 5 kilograms
9.8`m/s^2        # Acceleration
2.5`kWh          # Energy (SI prefix + unit)
90°              # Angle -- 90 degrees
20°C             # Absolute temperature -- 20 degrees Celsius
\end{lstlisting}

\subsubsection{Syntax}

\begin{center}
\begin{tabular}{r c L{10.5cm}}
$\langle$quantity-literal$\rangle$ & ::= & $\langle$decimal-real$\rangle$\textasciigrave{}$\langle$unit-expr$\rangle$ $|$ $\langle$decimal-real$\rangle$\textdegree{}$\langle$angle-tail$\rangle$? $|$ $\langle$decimal-real$\rangle$\textdegree{}(\texttt{C}$|$\texttt{F}$|$\texttt{R}) \\
$\langle$unit-expr$\rangle$ & ::= & $\langle$unit-term$\rangle$\,((\texttt{*}$|$\texttt{/})\,$\langle$unit-term$\rangle$)$^{*}$ $|$ \texttt{1/}$\langle$unit-term$\rangle$\,((\texttt{*}$|$\texttt{/})\,$\langle$unit-term$\rangle$)$^{*}$ \\
$\langle$unit-term$\rangle$ & ::= & $\langle$unit$\rangle$\,(\texttt{\^{}}\,$\langle$int$\rangle$)? \\
$\langle$angle-tail$\rangle$ & ::= & (\texttt{*}$|$\texttt{/})\,$\langle$unit-term$\rangle$\,((\texttt{*}$|$\texttt{/})\,$\langle$unit-term$\rangle$)$^{*}$ $|$ \texttt{\^{}}\,$\langle$int$\rangle$ \\
$\langle$unit$\rangle$ & ::= & $\langle$si-prefix$\rangle$?\,$\langle$base-unit$\rangle$ \\
\end{tabular}
\end{center}

\noindent
Here $\langle$decimal-real$\rangle$ is a signed or unsigned decimal floating
literal (including exponent notation and the ordinary digit-separator rules),
not a radix integer, imaginary literal, or storage suffix. Unit expressions may
contain multiplication (\code{*}), division (\code{/}), and integer exponents
(\code{\^{}}), but no grouping parentheses. SI prefixes from quecto through
quetta are resolved only for unit definitions that opt into prefixes.

\noindent
The degree shorthand uses the exact degree sign: \code{90°} is an angle, while
\code{20°C}, \code{68°F}, and \code{540°R} are temperatures. Kelvin never takes
a degree sign. Bare \code{C} and \code{F} retain their electrical meanings
(coulomb and farad), so backtick temperature aliases are written
\code{degC}, \code{degF}, and \code{degR}. Only the angle form may take a
compound tail (for example \code{90°/s}); absolute scales such as \code{°C/s}
are invalid.

\subsubsection{Arithmetic}

Quantities support the standard arithmetic operators. Dimensional analysis is
applied automatically---adding incompatible dimensions is an error:

\begin{lstlisting}
100`m + 50`m          # 150 m   (Length)
100`km + 500`m        # 100.5 km (auto-converts to larger unit)
100`m / 20`s          # 5 m/s   (Speed)
5`kg * 9.8`m/s^2     # 49 N    (Force)
100`m + 5`kg          # ERROR: dimension mismatch
\end{lstlisting}

\noindent
Multiplication and division use base values and return a canonical unit for the
derived dimension; addition and subtraction preserve the left operand's display
unit. Dividing equal dimensions yields an ordinary numeric scalar. Absolute
Celsius, Fahrenheit, Rankine, and Kelvin values are temperature points; until
temperature-difference units are introduced, arithmetic on those points is
rejected rather than silently applying an affine offset as though it were a
scale. Conversion and comparison remain supported.

\subsubsection{Unit Conversion}

The idiomatic conversion form reuses \code{as}; a leading backtick on the right
marks a unit target rather than a type target:

\begin{lstlisting}
2`mi as `ft           # 10560 ft
2`hr as `s            # 7200 s
10`m/s as `mph        # approximately 22.3694 mph
20°C as `°F           # 68 °F
\end{lstlisting}

\noindent
The method forms \code{value.To("ft")} and \code{value.ConvertTo("ft")} are
equivalent and are convenient for CLR interop or a dynamically selected target.
The target must describe the same dimension.

\noindent
Comparison operators also use base-value comparison with dimension checking:

\begin{lstlisting}
1`km > 500`m          # true  (1000 m > 500 m)
5`s == 5000`ms        # true
\end{lstlisting}

\subsubsection{Bridge Promotion}

When a plain \code{TimeSpan} or \code{StorageSize} is combined with a unit
quantity, TōSh automatically promotes it:

\begin{lstlisting}
5s + 10`s             # 15 s   (TimeSpan promoted to Duration)
\end{lstlisting}

\noindent
Typed script and function boundaries also parse external strings such as
\code{"5km"}, \code{"2hr"}, and \code{"10m/s"} when the declared type is a
quantity category. Friendly annotations include \code{quantity}, \code{length},
\code{mass}, \code{temperature}, \code{datasize}, \code{speed}, \code{energy},
\code{power}, and the other named categories. The existing \code{duration} alias
continues to mean calendar-aware \code{TemporalAmount}; fixed physical time uses
\code{DurationQuantity} or \code{timequantity}.

\subsubsection{Members}

\section{Type Conversion}
\label{sec:conversion}

TōSh performs automatic type conversion in many contexts via its
\code{TypeConversion} engine. Conversion is attempted in order:

\begin{enumerate}
  \item \textbf{Identity.} Same type---no conversion needed.
  \item \textbf{Null to nullable.} \code{null} converts to any nullable type.
  \item \textbf{Numeric widening.} \code{int}~\textrightarrow~\code{long}~\textrightarrow~\code{double}, etc.
  \item \textbf{String parsing.} Strings are parsed to the target type
        (\code{"42"}~\textrightarrow~\code{int}, \code{"true"}~\textrightarrow~\code{bool}).
  \item \textbf{Collection coercion.} Lists can convert to arrays, sets, etc.
  \item \textbf{CLR implicit/explicit operators.} If the target type defines
        conversion operators, they are used.
\end{enumerate}

\begin{lstlisting}
# Explicit cast
echo "42" | cast int       # String -> Int32

# Implicit in typed parameters
func double-it(n: int) => $n * 2
double-it "21"             # "21" auto-converts to 21
\end{lstlisting}

\subsection*{Narrowing is refused, not truncated}

A conversion to an integral type succeeds when the value has nothing to lose
and is refused when it does.  Nothing narrows silently:

\begin{lstlisting}
7.0 as int                 # 7
"7.0" as int               # 7   - the string spells the same number
7.9 as int                 # error: would discard its fractional part
"7.9" as int               # error: the same, for the same reason
\end{lstlisting}

\noindent The rule is about the \emph{value}, not the type: a \code{double}
narrows perfectly well when it holds a whole number.  A numeric string follows
whatever rule the number it spells would follow, so the spelling never decides
the outcome.

\begin{tipbox}
The refusal names the fix.  Round explicitly with \code{Math.Round},
\code{Math.Floor}, \code{Math.Ceiling} or \code{Math.Truncate}, and the
conversion then has nothing to discard.
\end{tipbox}

\subsection*{Casting to a declared type}
\label{sec:cast-declared}

\code{cast} also targets a type declared in ToastScript, including one nested
inside a class.  The target name is resolved against the CLR first and the
declarations second, so an existing script that casts to a CLR type keeps
doing so even if a declaration later takes the same name.

An \textbf{enum} converts from either a member name or a backing value, which
is the reverse of the conversion that turns a member into its number:

\begin{lstlisting}
enum Fuel : int { Mox = 3, Uranium = 8 }

cast Fuel 8                 # Uranium
cast Fuel "Mox"             # Mox   (member names are matched case-insensitively)
cast int Fuel.Uranium       # 8     (the round trip closes)
cast Fuel (cast int Fuel.Uranium)   # Uranium

class Reactor { enum Fuel : int { Mox = 3 } }
cast Reactor.Fuel 3         # Mox
\end{lstlisting}

Every other declared kind---class, struct, record, union, interface,
trait---converts only from a value that already \emph{is} one, subclasses
included.  \code{cast} does not construct:

\begin{lstlisting}
class Base { prop X = 7 }
class Derived extends Base { }

var d = new Derived()
(cast Base $d).X            # 7 - a Derived is a Base
cast Base 5                 # error: cast converts only a value that already is one
\end{lstlisting}

\noindent Two failures are distinguished, because they call for different
fixes.  A name that resolves to no type at all raises
\code{tosh.runtime.unknown\_cast\_target}---a misspelling, or a declaration
that has not been \code{require}d yet.  A name that resolves but a value that
will not convert raises \code{tosh.runtime.cast\_failed}, and for an enum the
message lists the members that do exist.

\section{Type Annotations}
\label{sec:annotations}

An annotation names the type a value must have: on a variable
(\code{var x: T}), a parameter (\code{func f(a: T)}), a return
(\code{-> T}) or a class member (\code{prop P: T}).  It is checked when the
value is produced, and a value that does not already have the type is put
through the conversions of \S\ref{sec:conversion} before being rejected.

Annotations differ from \code{cast} in when they run rather than in what they
accept: \code{cast} converts at the point you write it, an annotation converts
every value that arrives at the annotated position.

\subsection*{What satisfies an annotation}

\textbf{A subclass satisfies its base class.}  This holds in every annotated
position, not only in variables:

\begin{lstlisting}
class Shape  { prop Kind: string = "shape"  }
class Circle extends Shape { prop Kind: string = "circle" }

var s: Shape = new Circle()            # circle
func describe(v: Shape) -> string => $v.Kind
describe (new Circle())                # circle
func make() -> Shape => new Circle()   # a Circle is a Shape
\end{lstlisting}

\noindent The relation runs one way only.  \code{var c: Circle = new Shape()}
raises \code{tosh.type.mismatch}: every Circle is a Shape, and no Shape is
necessarily a Circle.

\textbf{A function type is written \code{func(...) -> r}}, naming what a
callable accepts and returns.  Parameters are types rather than
\code{name: type} pairs, because this describes a signature rather than
declaring one:

\begin{lstlisting}
func dbl(x: int) -> int => $x * 2

func apply(g: func(int) -> int, v: int) -> int => $g($v)
apply &dbl 21                          # 42

var f: func(int) -> int = &dbl
\end{lstlisting}

\noindent The return may itself be a function, and the form is
right-associative --- \code{func(int) -> func(int) -> int} is a function
returning a function:

\begin{lstlisting}
func adder(n: int) -> func(int) -> int {
    return func(x: int) -> int => $x + $n
}
var add10: func(int) -> int = (adder 10)
add10(32)                              # 42
\end{lstlisting}

\noindent When the value arrives it is checked for being callable and for
accepting that many arguments; a value that is not callable, or whose arity
cannot match, is rejected with
\code{tosh.runtime.annotation\_conversion\_failed}.  The parameter \emph{types}
are checked where the call is compiled rather than where the value is stored.

A bare \ikw{func} is the vaguer claim ``some callable'', and accepts any
callable regardless of shape.  A lambda that annotates its own parameters and
return needs no second description:

\begin{lstlisting}
var lam = func(x: int) -> int => $x + 1    # typed: func(int) -> int
var any = func(x) => $x + 1                # untyped: stays dynamic
\end{lstlisting}

\textbf{A tuple type is a parenthesised list} of element types, and may be
written wherever any other annotation may:

\begin{lstlisting}
var pair: (int, string) = (1, "a")

func split() -> (int, string) {
    return (2, "b")
}

func second(p: (int, string)) -> string => $p.Item2
\end{lstlisting}

\noindent Arity and elements are both checked: a tuple of the wrong length, or
one whose element cannot become the declared element type, is rejected with
\code{tosh.runtime.annotation\_conversion\_failed}.  Elements may be any type,
including another tuple, and the \code{[]} and \code{?} suffixes apply to the
whole:

\begin{lstlisting}
var nested: (int, (string, bool)) = (1, ("x", true))
var rows: (int, string)[]         = [(1, "a"), (2, "b")]
var maybe: (int, string)?         = null
\end{lstlisting}

\noindent A single parenthesised type is that type rather than a one-element
tuple --- \code{(int)} is \code{int} --- and \code{()} is the empty tuple type,
satisfied by the empty tuple \code{()}.

\textbf{An interface or trait names a contract}, and an annotation naming one
accepts any class that declares it with \ikw{fulfills} or \ikw{uses}.  A
contract declared on a base class counts for its subclasses:

\begin{lstlisting}
interface Drawable { func Draw() -> string }
class Box   fulfills Drawable { func Draw() -> string => "box" }
class Crate extends  Box      { }

func render(d: Drawable) -> string => $d.Draw()
render (new Box())                     # box
render (new Crate())                   # box - inherited from Box

trait Named { prop Name = "anon" }
class Widget uses Named { }
func label(n: Named) -> string => $n.Name
label (new Widget())                   # anon
\end{lstlisting}

\noindent The contract must be \emph{declared}.  A class with a structurally
identical member but no \ikw{fulfills} clause is rejected with
\code{tosh.type.mismatch}, because an annotation that accepted it would be duck
typing with extra syntax, and the annotation would document nothing.

\subsection*{Where an annotation's name is resolved}

A type name in an annotation is resolved against the scope that \emph{declares}
the annotation, not the scope that happens to be executing when the value
arrives.  A class inside a module therefore names itself, a sibling, or a
module-local refinement type by its bare name, with no module path:

\begin{lstlisting}
export partial module Geometry {
    export type Unit = double where (_ >= 0.0 and _ <= 1.0) coerce Math.Clamp(_, 0.0, 1.0)
    export class Node { prop Label: string = "n" }

    export class Tree {
        prop Root : Node = new Node()      # a sibling, unqualified
        prop Alpha: Unit = 0.25            # a module-local refinement type
        static func Empty() -> Tree => new Tree()   # the declaring class itself
    }
}

(Geometry.Tree.Empty()).Root.Label         # n
var t = new Geometry.Tree()
$t.Alpha = 5.0
$t.Alpha                                   # 1 - the refinement still coerces
\end{lstlisting}

\noindent This matters because member annotations are checked when the member
\emph{runs}, by which time the module scope that declared the class is no
longer on the engine's stack.  Resolution against the declaring module is what
makes the bare name mean what it reads as.  Qualified names
(\S\ref{sec:module-qualified-types}) work from anywhere and are unaffected.

\section{Value Rendering}
\label{sec:value-rendering}

\textbf{Rendering} is the operation that turns a value into a string.  It is what
an interpolation hole produces, what \code{\$x as string} produces, and what a
value's text is inside a diagnostic or on its way to a redirect target.

Rendering is \textbf{not display}.  Display is how TōSh paints a value on a
terminal --- tables, colour, column widths, display profiles, themes.  Display may
call rendering; rendering never calls display and never consults display
configuration.  A Tōast program therefore produces the same strings in every
host, on every target, under every configuration: \code{\$"\{x\}"} in a program
with no shell and no terminal produces exactly what it produces in an interactive
session.

Rendering is \textbf{total}.  Every value renders, and no value renders as a
failure --- a diagnostic that could not render the value it is about would be
worse than an imperfect string.  The one exception is a format clause the value
cannot honour, which is an error (\S\ref{sec:strings}).

\subsection{Scalars}

\begin{longtable}{L{5.5cm}L{7.5cm}}
\toprule
\textbf{Value} & \textbf{Renders as} \\
\midrule
\endhead
\code{null} & \code{null} \\
\code{true}, \code{false} & \code{true}, \code{false} \\
integer & decimal digits, \code{-} if negative, no separators, no suffix \\
floating & the shortest form that round-trips \\
NaN & \code{NaN} \\
infinity & \code{Infinity}, \code{-Infinity} \\
negative zero & \code{-0} \\
\code{char} & the character, unquoted \\
\code{date} & \code{yyyy-MM-dd HH:mm:ss} \\
\bottomrule
\end{longtable}

Rendering is \textbf{invariant}: a machine whose locale uses a comma decimal
separator still renders \code{3.14}.  There are no thousands separators --- a
program that wants \code{1,000,000} asks for it with a format clause.

Negative zero keeps its sign, because \code{-0} and \code{0} are different values
and a rendering that collapsed them would make output depend on how a zero was
reached.  A floating \code{3.0} renders \code{3}, which is indistinguishable from
the integer: the shortest round-tripping form is the useful one, and the type
distinction is available through a clause when it is wanted.

A \code{date} is rendered with its own clock reading.  No timezone conversion is
applied to a value that stated no timezone.

\subsection{Strings}

A string renders as its own characters at the top level, and \textbf{quoted and
escaped when nested inside a container}:

\begin{lstlisting}
$"{"hi"}"                 # hi
$"{["a b", "c"]}"         # ["a b", "c"]
\end{lstlisting}

The asymmetry is deliberate.  At the top level the caller is putting text into a
sentence; nested, they are looking at a structure, and unquoted elements make it
ambiguous --- \code{["a b", "c"]} would be indistinguishable from three elements,
and the string \code{"null"} from the value \code{null}.

\subsection{Containers}

Every container renders in \textbf{its own literal syntax, at every depth}:

\begin{lstlisting}
[1, 2, 3]                 # list
[]                        # empty list
{% "a" => 1 %}            # dictionary
{: 1, 2 :}                # set
{| Name = "a", N = 1 |}   # record
(1, "a")                  # tuple
1..3                      # range
\end{lstlisting}

A container renders the same way wherever it sits --- as a whole hole, as an
element of another container, as a dictionary value, or as a record field.  No
CLR type name ever appears in a rendering.  A range renders as a range rather
than as the list it would produce.

Rendering is bounded: beyond a fixed maximum depth a container renders as an
elision, and a value already being rendered further up the chain renders as an
elision rather than recursing.  Neither is an error.

\subsection{Named values}

An enum member renders as its member name --- \code{Color.Red} is \code{Red}.  A
flags value renders the member names its bits cover, comma-separated.

A class or struct renders as its type name followed by its readable state,
\code{Point \{ X = 1, Y = 2 \}}, which is what distinguishes it from a record.

A type controls its own rendering by implementing the \code{Display} trait:

\begin{lstlisting}
trait Display { func render() -> string }

class Temperature uses Display {
    prop Celsius: dec = 0
    func render() -> string => $"{$this.Celsius}degC"
}
\end{lstlisting}

A declared \code{ToString} is honoured as well, so types written before the trait
existed keep rendering as their authors intended.  \code{Display} is what this
specification teaches; \code{ToString} is what it tolerates.

\section{Truthiness}
\label{sec:truthiness}

TōSh uses one truthiness protocol whenever a value is tested as a condition.
The same rules apply to \code{if}/\code{while}/\code{until}, conditional
expressions, comprehension and match guards, event \code{when} guards,
\code{not}/\code{and}/\code{or}, and standard-library predicates such as
\code{where}, \code{any}, \code{all}, and \code{assert}.

\begin{longtable}{L{4.8cm}L{4.1cm}L{4.1cm}}
\toprule
\textbf{Type} & \textbf{Truthy} & \textbf{Falsy} \\
\midrule
\endhead
\code{bool} & \code{true} & \code{false} \\
\code{null} & --- & Always falsy \\
\code{byte} through \code{UInt128}, native integers, \code{BigInteger} & Non-zero & Zero \\
\code{Half}, \code{float}, \code{double} & Non-zero (including infinity) & Positive/negative zero, NaN \\
\code{decimal} & Non-zero & Zero \\
\code{Complex} & Non-zero with no NaN component & Zero or either component is NaN \\
\code{string} & Non-empty & Empty \\
\code{ICollection}, synchronous \code{IEnumerable} & Non-empty & Empty \\
Everything else & Always truthy & --- \\
\bottomrule
\caption{Truthiness rules}
\label{tab:truthiness}
\end{longtable}

\begin{notebox}
Count-bearing collections are tested through their count.  A general
synchronous \code{IEnumerable} is probed with one \code{MoveNext} call and
the temporary enumerator is disposed.  This can observably advance a
deliberately single-pass enumerable; test such a value once and retain the
result when that distinction matters.
\end{notebox}

Truthiness is not an explicit cast.  For example, the non-empty string
\code{"false"} is truthy, while converting that string to \code{bool} produces
\code{false}.  Logical operators always return a boolean and preserve
short-circuit evaluation; they do not return one of their operands.

Refinement \code{where} predicates are the intentional exception: they are
validation contracts and must return an actual \code{bool}.  Refinement
\code{if <guard> coerce} guards use the broad truthiness rules above.


\section{Refinement Types}
\label{sec:refinement}
\ikw{coerce}

A \emph{refinement type} constrains an existing type with one or more
predicates.  Values that fail a predicate are either repaired via a
\code{coerce} clause or rejected at runtime.

\subsection*{How a value is admitted}

Conversion into a refined slot follows one algorithm, and every step of it
is normative:

\begin{enumerate}
  \item Convert the value to the refinement's base type.
  \item Run any guarded \code{if <guard> coerce} clauses, in declaration
        order, threading each result into the next.
  \item Test the predicates.  If they hold, the value is admitted.
  \item Otherwise run the unguarded \code{coerce} clause, if there is one.
  \item \textbf{Convert the coercer's result to the base type again.}
  \item Test the predicates again.  If they hold the value is admitted;
        otherwise it is rejected with
        \code{tosh.runtime.refinement\_failed}.
\end{enumerate}

\noindent Step 5 is what keeps the base type a guarantee rather than a
hope.  A predicate tests the \emph{value} and says nothing about its type,
so without it a coercer returning another type would be admitted:
\code{Math.Clamp} resolves to an overload returning a floating-point
number, and \code{type TimeoutMs = int where (\_ > 0 and \_ <= 300000)
coerce Math.Clamp(\_, 0, 300000)} would leave a \code{double} in a slot
declared \code{int} --- but only on the coerced path, so the ordinary case
looked correct.

\noindent Step 6 is equally load-bearing: a coercer is not trusted merely
because it returned.  A coercer that cannot repair a value leaves it
rejected, which is the correct outcome for \code{TimeoutMs = 0} above,
whose coercer clamps to a lower bound the predicate still refuses.

\subsection*{Block Form}

\begin{lstlisting}
type PositiveInt = int {
    where _ > 0
}

type NormalizedPath = string {
    if (_ contains "\\") coerce (replace "\\" "/" _)
    where _ starts-with "/"
    coerce "/"
}
\end{lstlisting}

The body may contain any combination of the three clause forms:

\begin{description}
  \item[\code{where <predicate>}] A constraint predicate.  The value (bound to
    \code{\_}) must evaluate to the boolean value \code{true} after all
    coercions have been applied; other truthy values are rejected. Multiple
    \code{where} clauses are evaluated as a conjunction.

  \item[\code{if <guard> coerce <expr>}] A conditional normalisation that fires
    \emph{before} predicate evaluation.  When \code{guard} is truthy, \code{expr}
    replaces the value.  Useful for always-on normalization such as trimming
    whitespace or canonicalizing path separators.

  \item[\code{coerce <expr>} (no guard)] A fallback that fires only when one or
    more \code{where} predicates have already failed.  The expression receives
    the failing value as \code{\_} and produces a replacement.  Predicates are
    then re-evaluated against the replacement; if they still fail the refinement
    is rejected.
\end{description}

\begin{tipbox}
Think of the three forms as three phases: \emph{normalise} (\code{if X coerce
Y}) then \emph{validate} (\code{where}) then \emph{repair} (\code{coerce}).
\end{tipbox}

\subsection*{Inline Form}

\begin{lstlisting}
type Port = int where (_ >= 1 and _ <= 65535)

# With an inline fallback: clamp to range if out of bounds
type Port = int where (_ >= 1 and _ <= 65535) coerce 80
\end{lstlisting}

\subsection*{Refinements on Parameters and Variables}

Refinement types compose with the standard type annotation syntax:

\begin{lstlisting}
# Function parameter
func serve(port: int where _ > 0) { ... }

# Variable declaration
var name: string where _ != ""

# Inline predicate (anonymous refinement)
var count: int where _ >= 0 = 0
\end{lstlisting}

\subsection*{Execution Order}

When a value is checked against a refinement type:

\begin{enumerate}
  \item All \code{if <guard> coerce <expr>} clauses fire in declaration order;
    when the guard is truthy, \code{expr} replaces the value.
  \item All \code{where} predicates evaluate against the (possibly normalised) value.
  \item If any predicate fails and an unconditional \code{coerce} clause exists,
    its expression runs and replaces the value.
  \item Predicates are re-evaluated against the coerced value.
    Pass \textrightarrow{} success.  Fail \textrightarrow{} runtime error.
\end{enumerate}

\midrule

\medskip

Equality is decided by the first of these that applies:

\begin{enumerate}
  \item \textbf{Records and dictionaries} compare by name and value. Insertion order
        is not part of a record's identity, so \code{\{| a = 1, b = 2 |\}} equals
        \code{\{| b = 2, a = 1 |\}}.
  \item \textbf{Two non-string sequences} compare element-wise, in order.
  \item \textbf{An enum member} equals another member of the same enum, and equals its
        own backing value, so \code{E.Mid == 1} holds for a numeric-backed enum.
  \item \textbf{An integer against a floating value} compares \emph{exactly}: they are
        equal when the floating value is finite, has no fractional part, and is the same
        number. It is never decided by converting the integer to a float, because that
        conversion can lose digits --- see \S\ref{sec:numeric-equality}.
  \item \textbf{Conversion.} One operand is converted to the other's type. Both
        directions are attempted, so the answer never depends on which operand was
        written first, and a conversion that succeeds decides the result even when the
        converted values differ.
  \item \textbf{CLR operator fallback.} If neither conversion applies, the values are
        not language-native numbers, and an operand's CLR type declares a compatible
        public static \code{op\_Equality} method, that method decides the result.
  \item \textbf{Otherwise} the values are compared with \code{Equals} --- a compiled
        \code{Equals} method, then record fields, then \code{object.Equals}.
\end{enumerate}

Ordered comparison applies the language's enum, string, and conversion rules first,
then \code{IComparable}.  If those rules do not support the pair, it consults the
corresponding CLR operator method (\code{op\_LessThan},
\code{op\_LessThanOrEqual}, \code{op\_GreaterThan}, or
\code{op\_GreaterThanOrEqual}) before reporting that the values cannot be ordered.

The conversion step is the one that surprises: \code{1 == "1"} is \code{true}. It
applies only across \emph{different} types --- two strings compare exactly, so
\code{"ABC" == "abc"} is \code{false}. Where a conversion is itself indifferent to
case the equality inherits that, which is the whole reason \code{true == "TRUE"}
holds: parsing a bool ignores case. There is no textual fallback behind it, and the
difference is visible on an enum, whose conversion is by member name and \emph{is}
case-sensitive --- \code{E.Low == "Low"} is \code{true} while \code{E.Low == "LOW"}
is \code{false}.

\begin{lstlisting}
enum E { Low, High }

echo (1 == 1)              # true
echo (1 == "1")            # true  (a string operand is coerced)
echo (1.0 == "1")          # true
echo (true == "TRUE")      # true  (converting "TRUE" to bool ignores case)
echo ("ABC" == "abc")      # false (two strings compare exactly)
echo (E.Low == "Low")      # true  (converting to an enum member is by name)
echo (E.Low == "LOW")      # false (that conversion is case-sensitive)
echo (1 == "one")          # false (no coercion is possible)
echo ("abc" < "def")       # true (by code point)
echo ("a" < "B")           # false ('B' is 66, 'a' is 97)
echo (10kb > 5kb)          # true (StorageSize comparison, both are literals)
echo (10kb > 5mb)          # false
\end{lstlisting}

\subsection{Numbers, \code{null} and Instances}
\label{sec:numeric-equality}

\paragraph{Numbers compare by value, across widths.}
\code{1 == 1.0} holds, and so does \code{(1 as long) == (1 as int)}: a number's width
is not part of what it is. Where the two operands are an integer and a floating
value, the comparison is \emph{exact} --- and this is the one place the rule has to
be stated rather than left to the conversion step, because a 64-bit integer above
$2^{53}$ has no exact \code{double}:

\begin{lstlisting}
var a = 9007199254740993 as long   # 2 ** 53 + 1
var c = 9007199254740992 as long   # 2 ** 53
echo ($a == ($c as double))        # false -- they are different numbers
echo ($c == ($c as double))        # true
\end{lstlisting}

Deciding this by conversion would make \code{==} intransitive: \code{\$a} and
\code{\$c} would each equal the same \code{double} while differing from each other,
and a relation where \code{\$x == \$y} and \code{\$y == \$z} do not give \code{\$x == \$z} cannot
back a dictionary, a \code{distinct}, or a cache.

\paragraph{\code{NaN} equals itself.}
\code{\$n == \$n} is \code{true} for a \code{NaN}, which is deliberately \emph{not}
IEEE~754's rule for \code{==}. Equality here is the relation collections are built
on, and it has to be reflexive: under the IEEE rule a \code{NaN} placed in a
dictionary could never be found again, not even with the identical value. Signed
zeroes go the other way and follow IEEE: \code{0.0 == -0.0} is \code{true}, though
the two render differently (\S\ref{sec:value-rendering}).

\paragraph{\code{null} equals only \code{null}.}
\code{null == null} is \code{true}, and \code{null} equals nothing else --- not
\code{0}, not \code{""}, not \code{false}. This is the one place \code{null} is
better behaved than in ordering, where it is outside the relation entirely
(\S\ref{sec:ordering}).

\paragraph{A class instance is equal only to itself, unless the class says otherwise.}
Two instances with identical property values are \emph{not} equal:

\begin{lstlisting}
class P(x: int) { prop X: int = $x }
echo ((new P(1)) == (new P(1)))    # false -- two distinct objects
\end{lstlisting}

A class that wants value equality declares it, and the declaration is what \code{==}
then uses:

\begin{lstlisting}
class Q(x: int) {
    prop X: int = $x
    func equals(other) -> bool => ($this.X == $other.X)
}
echo ((new Q(1)) == (new Q(1)))    # true
\end{lstlisting}

This is the opposite default from a \code{record}, and deliberately: a record is a
bag of values and is compared as one, while a class has identity --- two accounts
holding the same balance are not the same account.

\subsection{Key Equality}
\label{sec:key-equality}

\code{==} is \emph{coercive}: it converts across types so that \code{1 == "1"} holds,
which is what a shell wants when a value has come back from a command as text. That
convenience has a cost, and the cost is why collections do not use it.

\paragraph{Coercion makes \code{==} intransitive.}

\begin{lstlisting}
echo ("1" == 1)         # true
echo (1 == "1.0")       # true
echo ("1" == "1.0")     # false   -- two strings compare exactly
\end{lstlisting}

Three values, two of which are equal to a third and not to each other. A relation like
that has no equivalence classes, so there is nothing for a hash table to put in a
bucket, and a container built on it answers differently depending on the order things
were put in.

\paragraph{So containers use a second, stricter relation: \emph{key equality}.}
Dictionary keys, \code{distinct}, \code{sort -u}, set literals, \code{group-by} and
\code{frequencies} all ask whether two values are \textbf{the same value}, not whether
one can be converted into the other:

\begin{itemize}
  \item \textbf{Numbers} are the same key when they are the same number, whatever their
        width: \code{1}, \code{1 as long} and \code{1.0} are one key. Comparison is
        exact, by the rule in \S\ref{sec:numeric-equality}.
  \item \textbf{A string} is a key only to the same string, compared by code point.
        \code{"1"} and \code{1} are \emph{different keys}, though \code{==} calls them
        equal.
  \item \textbf{\code{null}}, \code{true} and \code{false} are each their own key.
  \item \textbf{An enum member} is a key with the members of its own enum, and not with
        its backing number.
  \item \textbf{Records and dictionaries} are the same key when they hold the same names
        and the same values, in any order --- matching \code{==}.
  \item \textbf{Collections} are the same key when their elements are, in order.
  \item \textbf{A class instance} is a key only to itself, unless the class declares
        \code{equals}; see below.
\end{itemize}

Key equality is transitive, so a dictionary holds one entry per key, a lookup does not
depend on insertion order, and \code{distinct} returns the same answer whatever order
its input arrived in.

\begin{notebox}
A value can be \code{==} to a key it does not match \emph{as} a key. This is deliberate:
\code{\$d["1"]} does not find the entry stored under \code{1}. Convert explicitly ---
\code{\$d["1" as int]} --- when that is what was meant.
\end{notebox}

\paragraph{A class that declares \code{equals} should declare \code{hash}.}
Key equality uses a class's own \code{equals} when it has one. A hash has to agree with
it --- two values that are equal must hash alike --- and the class is the only thing that
knows how. Declaring \code{hash} alongside \code{equals} is what makes such a class a
usable key:

\begin{lstlisting}
class Point(x: int, y: int) {
    prop X: int = $x
    prop Y: int = $y
    func equals(other) -> bool => ($this.X == $other.X and $this.Y == $other.Y)
    func hash() -> int => ($this.X * 31 + $this.Y)
}
\end{lstlisting}

A class declaring \code{equals} and \emph{not} \code{hash} is still correct as a key ---
every instance simply shares one hash, and the container falls back to comparing them
one by one. It is correctness at the cost of speed, never a wrong answer.

\subsection{Ordering}
\label{sec:ordering}

Equality asks whether two values are the same. \emph{Ordering} --- \code{<},
\code{>}, \code{<=}, \code{>=} --- asks which comes first, and it is a narrower
question, because not every pair of values has an order.

\paragraph{Strings order by code point.}
\code{"a" < "B"} is \code{false}, because \code{B} is code point 66 and \code{a} is
97. This is deliberately \emph{not} the order a person would file the two words
under, and the reason is portability: culture-aware collation gives different
answers on different machines --- under a Swedish collation \code{"z" < "ä"} is
true and under an American one it is false --- so a program's meaning would depend
on the locale of the machine running it. A shell command that presents values to a
reader may order them for reading; see \code{sort} (\S\ref{ref:sort}). The
\emph{language} orders them the one way that is the same everywhere.

Ordering is therefore consistent with equality: two strings that are not
\code{==} are strictly ordered one way or the other, and only strings that are
\code{==} compare as neither less nor greater.

\paragraph{Numbers order across widths.}
\code{1 < 2.5} holds; the operands are converted to a common type first, in either
direction, so the answer never depends on which side a value was written. A
\code{StorageSize} orders against another \code{StorageSize} and against a plain
number, by bytes: \code{1kb < 2000} is \code{true}.

\paragraph{An enum member orders by its backing value}, against another member of
the same enum and against a plain number. Members of \emph{different} enums are not
one ordered domain and comparing them raises.

\paragraph{\code{null} is unordered.}
Every ordered comparison involving \code{null} is \code{false} --- including
\code{null < null}. \code{null} is not smaller than everything, it is outside the
order, so \code{\$x < \$y} being \code{false} does not imply \code{\$x >= \$y}. Compare
against \code{null} with \code{==} instead.

\paragraph{Some pairs have no order, and say so.}
Rather than inventing one, these raise:

\begin{itemize}
  \item \textbf{Booleans.} \code{true} is not greater than \code{false}. Use
        \code{==}, or \code{and}/\code{or}.
  \item \textbf{A string against a non-string.} \code{"10" < 9} would otherwise have
        to choose silently between lexicographic and numeric order, and either choice
        is wrong half the time. Convert explicitly --- \code{("10" as int) < 9}.
  \item \textbf{Members of two different enums}, as above.
\end{itemize}

\begin{notebox}
An ordering that raises is doing the same job as one that answers: it reports that
the question has no answer, at the point it was asked, rather than returning a
\code{false} that reads as "no" and means "not applicable".
\end{notebox}

\subsection{Overflow}
\label{sec:overflow}

\paragraph{Integer arithmetic does not overflow.}
It \emph{promotes}. When a result leaves the range of the types that produced it, the
value widens to an arbitrary-precision integer rather than wrapping into a wrong
answer:

\begin{lstlisting}
var m = 2147483647 as int   # int.MaxValue
echo ($m + 1)               # 2147483648   -- exact, not -2147483648
echo ($m * 2)               # 4294967294
echo (2 ** 62)              # 4611686018427387904
\end{lstlisting}

Wrapping is the behaviour most languages inherit from the machine, and it turns a
number that was merely large into a number that is merely wrong --- usually negative,
usually far from where the mistake happened. There is no \code{checked} spelling here
because there is nothing to check for.

\code{**} follows the same rule when both operands are integers and the exponent is not
negative, because raising to a power is repeated multiplication and has no business
losing precision where multiplying would not. A fractional or negative exponent is a
different operation and gives a \code{double}. Very large exponents are the one bound:
past a million, the result is floating point, because an exact answer would be a number
whose \emph{digits} do not fit in memory.

\paragraph{A declared type is still a promise.}
The promotion is a property of the arithmetic, not a licence to store anything anywhere.
A variable annotated \code{int} holds an \code{int}, and a result that will not fit is
reported at the assignment:

\begin{lstlisting}
var x: int = 2147483647
echo ($x + 1)               # 2147483648 -- the expression is exact
$x = $x + 1                 # error: the value does not fit 'int'
\end{lstlisting}

Conversion is the same: \code{300 as byte} raises rather than silently keeping
\code{44}.

\paragraph{A literal keeps the digits it was written with.}
A number with a fractional part is a \code{double}, unless writing it as one would lose
digits --- then it is a \code{decimal}, which holds about 28 significant figures where a
\code{double} holds about 17:

\begin{lstlisting}
echo ((1.5).GetType().Name)                   # Double
echo ((2.718281828459045).GetType().Name)     # Double  -- 16 digits, all kept
echo ((1.0000000000000001).GetType().Name)    # Decimal -- the last digit needs one
echo (1.0000000000000001 == 1.0)              # false
\end{lstlisting}

The cost is that a literal's \emph{type} depends on how many digits it has, which is
worth knowing before it surprises. The alternative was a suffix, and the natural letters
are taken: \code{1.5m} is one and a half \emph{minutes} and \code{1.5d} is one and a half
\emph{days}. The two types interoperate --- \code{decimal + double} is a \code{decimal},
and comparison and rendering work across them --- so a widened literal is not stranded.

Arithmetic is unaffected: \code{0.1 + 0.2} is \code{0.30000000000000004}, because both
operands are still \code{double}s.

\paragraph{Floating point follows IEEE~754.}
Overflow gives an infinity rather than an error, \code{1.0 / 0.0} is \code{Infinity},
and \code{0.0 / 0.0} is \code{NaN} --- which is equal to itself here
(\S\ref{sec:numeric-equality}). \emph{Integer} division by zero raises, because there is
no integer answer to give.

\subsection{What \code{null} Means}
\label{sec:nullability}

\code{null} is the absence of a value, and every operator is specified for it rather
than left to inherit one. The rule throughout is the same: an operation that has no
sensible answer for a missing value \textbf{reports that}, and the author asks for
propagation where they want it.

\paragraph{Truthiness.} \code{null} is falsy. \code{if (\$x)} does not run its body,
\code{not null} is \code{true}, and \code{\$x ?? fallback} yields the fallback.

\paragraph{Comparison.} \code{null == null} is \code{true} and \code{null} equals
nothing else (\S\ref{sec:numeric-equality}). Ordered comparison is different: \code{null}
is \emph{outside} the order, so every one of \code{<}, \code{>}, \code{<=}, \code{>=}
against it is \code{false}, \code{null < null} included (\S\ref{sec:ordering}). As a
container key, \code{null} is its own key (\S\ref{sec:key-equality}).

\paragraph{Arithmetic raises.} \code{null + 1}, \code{null - 1} and \code{null * 2} all
report that the operator requires non-null operands. So does \code{null + "a"}: a
missing value must not turn into empty text and vanish into concatenated output. Write
\code{(\$x ?? "") + "a"} when that is the intent.

\paragraph{Reaching into \code{null} raises, and \code{?.} is how to ask otherwise.}
Reading a member, calling a method and indexing all report a null receiver:

\begin{lstlisting}
var x = null
$x.Length          # error: Cannot read member 'Length' of null
$x.ToString()      # error: Cannot invoke an instance method on null
$x[0]              # error: Cannot index into null

$x?.Length         # null
\end{lstlisting}

\begin{notebox}
Member access used to answer \code{null} silently, for \emph{any} member name --- so a
misspelled member on a null value reported nothing, while the same misspelling on a
string raised. It also left \code{?.} meaning nothing, since both spellings behaved
identically.
\end{notebox}

\paragraph{Membership asks a real question.} \code{null} can be looked for in a
collection and found: \code{null in [1, null]} is \code{true}, and so is
\code{[1, null] contains null}. A \emph{string} does not contain it ---
\code{"abc" contains null} is \code{false} --- because a string contains text, and
\code{null} is not text.

\subsection{Errors and \code{catch}}
\label{sec:exception-semantics}

\paragraph{Anything can be thrown, and arrives unchanged.}
\code{throw} takes a value, not only an error, and \code{catch} binds whatever was
thrown:

\begin{lstlisting}
try { throw "a plain string" } catch (e) { ... }   # $e is that string
try { throw 42 }               catch (e) { ... }   # $e is 42
try { throw new Error("boom") } catch (e) { ... }  # $e.Message is "boom"
\end{lstlisting}

There is no typed \code{catch}: one \code{catch} receives everything, and a handler
distinguishes what it got with \code{is}.

\paragraph{\code{Error} is the base for declared error types.}
A class declared \code{extends Error} is an \code{Error}, at any depth of inheritance,
which is what lets a handler tell a raised error from an arbitrary thrown value:

\begin{lstlisting}
class AppError extends Error { }

try { ... } catch (e) {
    if ($e is Error) { ... }   # true for AppError, false for a thrown string
}
\end{lstlisting}

\paragraph{A raised runtime error is a diagnostic.}
Dividing by zero, indexing out of range, or reaching a member of \code{null} raises a
\emph{diagnostic} rather than an \code{Error}. It carries a message and is catchable, and
it is \textbf{not} \code{is Error}:

\begin{lstlisting}
try { (1 / 0) } catch (e) {
    echo ($e is Error)     # false -- a diagnostic, not a declared error
    echo ($e.Message)      # "Division by zero."
}
\end{lstlisting}

The distinction is intended: one is the language reporting that an operation had no
answer, the other is a program raising something deliberately.

\paragraph{\code{Failure} is either of them.}
Three names describe what a \code{catch} caught, and none of them borrows from the host:

\begin{lstlisting}
try { ... } catch (e) {
    echo ($e is Failure)      # anything the language raised
    echo ($e is Error)        # a program raised it
    echo ($e is Diagnostic)   # the language raised it
}
\end{lstlisting}

\code{Error} and \code{Diagnostic} are the two kinds of \code{Failure}, and nothing is
both. A value that was merely \code{throw}n --- a string, a number --- is \emph{none} of
the three, which is what keeps \code{Failure} meaning "something went wrong" rather than
"something was thrown".

\begin{notebox}
Catch broadly with \code{\$e is Failure}; ask the narrower question only where the answer
changes what the handler does. A handler that means "any failure" and writes
\code{\$e is Error} will silently ignore every division by zero.
\end{notebox}

\paragraph{\code{finally} always runs, and \code{throw} re-raises.}
A \code{finally} block runs whether its body completed, raised, or was caught further out,
and an inner \code{finally} runs before an outer \code{catch} sees the error. Re-raising is
\code{throw \$e} with the caught value.

\code{try} is a statement, not an expression: a value is carried out of it by assigning to
a variable declared before it.

\subsection{Type Tests}
\label{sec:type-tests}

\code{\$x is T} asks whether a value is a \code{T}, and it walks the type graph: a
declared class matches its own name, its bases, its interfaces and its traits, and a CLR
value matches its type, the types it derives from, and the interfaces it implements.

\begin{lstlisting}
class Base { }
class Leaf extends Base { }
echo ((new Leaf()) is Base)     # true
echo (5 is ValueType)           # true
echo ([1, 2] is IEnumerable)    # true
\end{lstlisting}

\paragraph{A bare name asks about \emph{this} language; a qualified one asks about the host.}
This is the one place the two differ, and it is deliberate. A \code{str}, a record and a
dictionary are single values rather than sequences (\S\ref{sec:collection-shape}), so a
bare sequence test answers accordingly --- even though a \code{string} does implement
\code{IEnumerable} underneath:

\begin{lstlisting}
echo ("abc" is IEnumerable)                        # false -- a str is one value
echo ("abc" is System.Collections.IEnumerable)     # true  -- asking about the host
echo ("abc" | count)                               # 1     -- and the pipeline agrees
\end{lstlisting}

A namespace-qualified name is an explicit question about the .NET type graph, and
answering it any way but literally would mislead code written to bridge to it. The rule
applies only to \emph{sequence} tests: \code{"abc" is string} and
\code{"abc" is IComparable} are unaffected, because neither asks whether the value is a
sequence.

\subsection{Collection Shape}
\label{sec:collection-shape}

A pipeline carries \emph{items}. Whether a collection is one item or many is decided by
two rules.

\paragraph{Which values are sequences.}
An array, a set and a range are sequences: piping one sends its elements. A dictionary, a
record and a string are single values: piping one sends the value itself.

\begin{lstlisting}
echo ([1, 2, 3] | count)              # 3  -- three items
echo ({: 1, 2, 3 :} | count)          # 3
echo (1..3 | count)                   # 3
echo ({% "a" => 1, "b" => 2 %} | count)  # 1  -- one value
echo ({| a = 1, b = 2 |} | count)     # 1
echo ("abc" | count)                  # 1
\end{lstlisting}

A dictionary and a record are values with named parts rather than sequences of them,
which is why they count as one. Their parts are reached by name, or by iterating
\code{.Keys}.

\paragraph{Who decides that a collection is a sequence.}
The \textbf{producer} does, and the rule is one sentence: a collection \textbf{written} as
an expression is a sequence, and a collection \textbf{returned by a call} is a value.

Written --- a literal, a variable holding one, a range, a property read, a
constructor --- so its elements are sent:

\begin{lstlisting}
echo ([1, 2, 3] | count)              # 3
echo (1..3 | count)                   # 3
echo (new array(1, 2, 3) | count)     # 3  -- constructing writes a value
echo ([[1, 2], [3]] | count)          # 2  -- two items, each an array
\end{lstlisting}

Returned by a call --- a command, a function, a method, a generator --- so it is sent as
one item, however the call is spelled:

\begin{lstlisting}
func a() { yield [1, 2, 3] }
func f() { return [1, 2, 3] }
class C { func m() { return [1, 2, 3] } }
var c = new C()

echo (echo [1, 2, 3] | count)         # 1  -- a command
echo (a | count)                      # 1  -- a generator
echo (f() | count)                    # 1  -- a function
echo ($c.m() | count)                 # 1  -- a method
\end{lstlisting}

A \emph{property} read is on the written side, not the called side: \code{\$c.Items} is
the collection in the way a variable is one, and it is the calling that produces a new
value.

The consequence worth stating is what \emph{cannot} happen: the shape of a value does not
depend on how much data follows it. A generator yielding one array and the same generator
yielding two hand downstream the same first item, so adding a second batch never changes
what the first batch meant.

\paragraph{A function that produces nothing contributes nothing.}
A call contributes to a pipeline exactly the values it produced. A function that falls off
its end, returns bare, or ends in an expression that yields nothing has produced no value,
and contributes none --- it does not contribute a null standing in for one.

\begin{lstlisting}
func f() { }                          # produces nothing
func g() { return }                   # produces nothing
func v() -> void { writeline "hi" }   # writes; produces nothing
func h() { return null }              # produces one value, which is null

echo (f | count)                      # 0
echo (g | count)                      # 0
echo (v | count)                      # 0
echo (h | count)                      # 1
\end{lstlisting}

Returning \code{null} is therefore not the same as producing nothing, and which of the two
happened can depend on a branch taken at run time:

\begin{lstlisting}
func maybe(x) { if ($x) { return 1 } }
echo (maybe true | count)             # 1
echo (maybe false | count)            # 0
\end{lstlisting}

The distinction is observable \emph{only} in a pipeline. In every other position --- an
assignment, a subexpression argument, a comparison --- a function that produced nothing
reads as \code{null}:

\begin{lstlisting}
var x = f()
echo ($x == null)                     # true
\end{lstlisting}

\paragraph{Null and return annotations.}
A return annotation refuses \code{null} unless it is nullable: \code{-> string} rejects it
and \code{-> string?} accepts it. \code{dynamic} accepts it, because \code{dynamic} is the
opt-out from annotation checking and cannot itself be a check that only some values pass.

\paragraph{How many values a command yields.}
One per argument. \code{echo 1 2} yields two values, not one joined string, for the same
reason \code{echo \$xs} yields one: each \emph{argument} is a value, and joining them
would make the number of values depend on how they were spelled rather than on how many
there were.

\begin{lstlisting}
echo (echo 1 2 | count)               # 2  -- two arguments, two values
echo (echo 1 | count)                 # 1
echo (echo $xs | count)               # 1  -- one argument, holding a collection
echo (echo ...$xs | count)            # 3  -- spread, so one value per element
\end{lstlisting}

This is what keeps \code{echo} consistent with the producer rule above rather than an
exception to it: a collection handed to a command is one argument and so one value, and
\code{...} is how it becomes several.

\code{...} (\S\ref{sec:pipeline-spread}) turns any value into a sequence, which is how a
collection produced by a command is spread when that is what was wanted:

\begin{lstlisting}
echo (echo ...[1, 2, 3] | count)          # 3
echo (echo ...(a) | count)                # 3  -- a generator's collection, spread
\end{lstlisting}

\begin{notebox}
\textbf{Rationale.} Shape used to be decided by counting: a collection arriving as the
only item was expanded, and a collection arriving beside others was not. That made a
collection's meaning depend on how many of them there were --- \code{a | count} answered
3 and \code{b | count} answered 2 for the same first value --- and nothing at the call
site could say which reading was intended.

It also cost an item. Deciding ``is this the only one?'' requires reading one item further
than the consumer asked for, so a generator was advanced once more than necessary and any
side effect of that step happened for an item nobody requested. A mark placed by the
producer needs no lookahead to read.

The first version of this rule was \emph{syntactic} rather than semantic: every expression
head was a sequence. That made \code{f() | count} answer 1 and \code{\$c.m() | count}
answer 3 for a function and a method returning the identical collection --- a difference
the author could not see, because it came from how the head parsed rather than from
anything written. The sentence above replaced it, and the distinction it draws is between
writing a collection and calling for one.

Changing this was affordable only once \code{...} existed to spell the old meaning, which
is why \S\ref{sec:pipeline-spread} came first.
\end{notebox}

\subsection{Text and Unicode}
\label{sec:unicode}

A \code{str} is a sequence of \textbf{UTF-16 code units}. Everything else in this
section follows from that one sentence, including the parts that surprise.

A code unit is written with \code{\textbackslash uHHHH}, four hex digits, and a byte with
\code{\textbackslash xHH}. Both work in an ordinary double-quoted string and in an
ANSI-C string (\code{\"..."}) alike. A character outside the Basic Multilingual Plane is
written as the \emph{surrogate pair} it is made of, which is the model made visible ---
the waving-hand character U+1F44B is
\code{"\textbackslash uD83D\textbackslash uDC4B"}.

A backslash before a letter that names no escape is kept as written, so
\code{"\textbackslash q"} is two characters. Note that \code{\textbackslash t},
\code{\textbackslash n} and the rest \emph{do} resolve in a double-quoted string, so a
Windows path written with single backslashes does not survive one:
\code{"C:\textbackslash path\textbackslash to"} contains a tab.

\paragraph{\code{Length} counts code units, not characters.}

\begin{lstlisting}
echo ("abc".Length)                        # 3
echo ("\u00E9".Length)                     # 1  -- precomposed e-acute
echo ("\uD83D\uDC4B".Length)               # 2  -- one character, two code units
echo ("\uD83D\uDC68\u200D\uD83D\uDC69".Length)
                                           # 5  -- two people and a joiner
\end{lstlisting}

\paragraph{Indexing can therefore yield half a character.}

\begin{lstlisting}
var w = "a\uD83D\uDC4Bb"
echo ($w.Length)             # 4
echo ($w[0])                 # a
echo ($w[1])                 # an unpaired surrogate -- not valid text
echo ($w[3])                 # b
\end{lstlisting}

\begin{notebox}
This is a sharp edge and it is deliberate. Counting scalar values instead would make
\code{\$w[1]} whole, at the cost of \code{O(n)} indexing and a \code{Length} that
disagrees with what the same string reports to every .NET API it is passed to. Counting
\emph{grapheme clusters} --- what a person means by a character --- would cost more
again, and would make the answer depend on which Unicode version the runtime was built
against, so two implementations could disagree about the length of one emoji. That is
the same defect that made culture-sensitive collation unacceptable for ordering
(\S\ref{sec:ordering}), and it is worse in a length than in a comparison.

An implementation on a target whose native strings are UTF-8 must still report these
numbers.
\end{notebox}

\paragraph{Comparison is exact, and does not normalise.}
Unicode can spell the same character more than one way: \code{\"\textbackslash u00E9"} is one code point, and \code{e} followed by a combining acute
(\code{\textbackslash u0301}) is two. They render identically and they are \emph{not}
equal:

\begin{lstlisting}
var combined = "e\u0301"
echo ($combined == "\u00E9")   # false
echo ($combined.Length)        # 2
\end{lstlisting}

Normalisation is available and explicit --- \code{\$s.Normalize()} for NFC,
\code{\$s.Normalize(form)} for another form, \code{\$s.IsNormalized()} to ask:

\begin{lstlisting}
echo ($combined.Normalize() == "\u00E9".Normalize())   # true
echo ($combined.Normalize().Length)                    # 1
\end{lstlisting}

\begin{notebox}[The trap this leaves]
macOS hands out filenames decomposed and Linux usually composed, so \emph{the same
filename} read on two machines can compare unequal, sort apart, and count as two
distinct values. Normalise both sides when comparing text that came from different
sources.

Normalising implicitly was the alternative, and it costs either a pass on every
comparison --- inside sorts and dictionary lookups, where it would dominate --- or a
rewrite of the bytes at construction, which stops a filename round-tripping back to the
filesystem that produced it. An explicit call keeps comparison exact and predictable and
leaves the choice where the information is.
\end{notebox}

\paragraph{A string is one value, not a collection of characters.}
\code{reverse}, \code{sort} and the other pipeline commands treat a \code{str} as an
atom, so reversing a string containing an astral character leaves it whole rather than
scrambling it into unpaired surrogates.

\subsection{Chained Comparison}
\label{sec:chained-comparison}

Relational comparisons chain.  Writing \code{a < b < c} means
\code{(a < b) and (b < c)}, matching ordinary mathematical notation:

\begin{lstlisting}
echo (1 < 2 < 3)          # true
echo (3 < 2 < 1)          # false
echo (1 <= 1 <= 1)        # true
echo (1 < 2 < 3 < 4)      # chains of any length
\end{lstlisting}

Two guarantees make a chain different from writing the conjunction out
by hand:

\begin{itemize}
  \item Each operand is evaluated \emph{at most once}.  In
        \tosh{1 < (next) < 3} the \code{next} call happens a single
        time, whereas the hand-written
        \tosh{(1 < (next)) and ((next) < 3)} would call it twice.
  \item Evaluation short-circuits.  Once a pair compares false, the
        remaining operands are never evaluated.
\end{itemize}

Only \code{<}, \code{<=}, \code{>}, \code{>=}, \code{==}, and
\code{!=} chain.  A run containing \code{is}, \code{in},
\code{contains}, or a regex operator keeps the ordinary
left-associative reading.

\section{Operator Precedence}
\label{sec:precedence}

Operators are listed from highest to lowest precedence.

Note that \code{as} and \code{is} sit at opposite ends of the table although both
concern types. \code{as} is a cast: it yields a value, so it binds tighter than
every binary operator and \code{x as int \% 2} means \code{(x as int) \% 2}.
\code{is} is a test: it yields a boolean, so it binds loosely and
\code{1 + 2 is int} tests the sum.

The bitwise operators are spelled as words because the symbols are taken:
\code{\&} runs a pipeline in the background and takes a function reference, and
\code{|} separates pipeline stages. They also sit \emph{tighter} than comparison,
unlike C, so \code{flags band Mask == 0} groups as \code{(flags band Mask) == 0}
--- the way the line reads. Their order relative to one another follows C, which
is not the part that surprises people.

Comparison, type testing and membership share one level and associate to the
left, so \code{true == 1 is int} groups as \code{(true == 1) is int} rather than
\code{true == (1 is int)} --- the two give different answers. Note also that
\code{-2} is a negative \emph{literal} rather than a negation applied to \code{2}:
\code{-2 ** 2} is \code{4}, while \code{-\$x ** 2} with \code{\$x} of \code{2} is
\code{-4}, because \code{**} binds tighter than the unary minus.

\section{Variable Declarations}
\ikw{var}

\begin{lstlisting}
var name = "Alice"              # Inferred type
var age: int = 30               # Explicit type annotation
var items = [1, 2, 3]           # List
var config = {| debug = true |} # Record
\end{lstlisting}

\begin{notebox}
Variables must be declared with \code{var} before use. Assigning to an
undeclared name is an error.
\end{notebox}

\subsection*{Inferred types follow reassignment}

A variable declared without an annotation takes its type from what it holds,
and reassignment updates it.  A use before the reassignment still sees the
earlier type, so the rule is positional rather than whole-of-scope:

\begin{lstlisting}
var x = "hello"
$x.Length                       # 5  - a string
$x = [1, 2, 3]
$x.Length                       # 3  - now an array
\end{lstlisting}

\noindent An \emph{annotated} variable does not re-infer.  The annotation is a
contract, so an assignment that disagrees with it is an error to report rather
than a new type to adopt:

\begin{lstlisting}
var y: int = 10
$y = "nope"                     # error: could not be converted to 'int'
\end{lstlisting}

\noindent A reassignment inside a conditional branch says nothing certain about
the type after it, because the branch may not have run.  The variable becomes
dynamic there rather than adopting a type only one path produces.

\section{Constants}
\ikw{const}

The \code{const} keyword declares an \emph{immutable binding}. The initialiser
may be any expression, is evaluated once where the declaration appears, and the
name is typed by the result. A constant cannot be reassigned, and cannot be
redeclared in the scope that already binds it.

\begin{lstlisting}
const MaxRetries = 3
const AppName = "TōSh"
const StartedAt = (date)      # any expression, evaluated once

echo $MaxRetries     # 3
# $MaxRetries = 5   # error: tosh.runtime.const_reassignment
# var MaxRetries = 5 # error: tosh.runtime.const_redeclaration
\end{lstlisting}

Constants are visible in the same scope and all nested scopes, exactly like
\code{var}, and are resolved by variable lookup in the same way.

\begin{notebox}
\code{const} is deliberately \emph{not} a compile-time constant. Earlier
drafts of this specification described it as one, requiring a literal or
constant expression and folding the value at use sites; the implementation
never did either, and the binding form proved the more useful of the two ---
\code{const StartedAt = (date)} says exactly what it means. A compile-time
constant remains a possible future addition under its own keyword, in which
case the constant-expression rules would be literals, operators over them, and
references to other such constants.
\end{notebox}

Immutability applies to the \emph{binding}, not to the value it holds. A
constant bound to a record or a list still permits its contents to be changed;
what cannot change is which value the name refers to.

\begin{lstlisting}
const Config = {| retries = 3 |}
$Config.retries = 5           # allowed --- the record is mutable
# $Config = {| retries = 5 |} # error --- the binding is not
\end{lstlisting}

Shadowing in a \emph{nested} scope is not redeclaration and stays legal: an
inner block or a function body may bind its own name without disturbing the
constant outside it.

\begin{lstlisting}
const X = 5
if (true) {
    const X = 6               # a different binding, inner scope
    echo $X                   # 6
}
echo $X                       # 5
\end{lstlisting}

\subsection{Tuple Destructuring}
\label{sec:tuple-destructuring}

Parentheses destructure positionally, exactly as brackets do, and read
naturally beside the way a tuple is written:

\begin{lstlisting}
var (x, y) = (1, 2)
echo $x             # 1

const (WIDTH, HEIGHT) = (80, 24)

func min-max() { return (3, 9) }
var (lo, hi) = min-max()

# Existing variables, no declaration
var a = 1
var b = 2
(a, b) = ($b, $a)   # a swap: the value is read in full before either is written
\end{lstlisting}

\noindent \textbf{A tuple's arity is checked; an array's is not.}  An array
is a variable-length collection, so taking a prefix of one is a meaningful
request and stays legal.  A tuple has a fixed, declared shape, so naming the
wrong number of targets for one is a miscount and raises
\code{tosh.runtime.tuple\_assignment\_arity\_mismatch}:

\begin{lstlisting}
var [first, second] = [10, 20, 30, 40, 50]   # fine - a prefix of an array
var (a, b) = (1, 2, 3)                       # error - the tuple has 3 elements
\end{lstlisting}

\noindent \code{const} applies to every name a destructuring binds,
whichever bracket style is used, so \code{const (A, B) = (1, 2)} produces two
constants and not two ordinary variables.

\section{Spread Operator}
\label{sec:spread}
\iop{...}

The spread operator (\code{...}) works in three contexts:

\subsection{Array Spread}

\begin{lstlisting}
var a = [1, 2, 3]
var b = [0, ...$a, 4]    # [0, 1, 2, 3, 4]
\end{lstlisting}

\subsection{Record Spread}

\begin{lstlisting}
var base = {| name = "Alice", role = "user" |}
var admin = {| ...$base, role = "admin", level = 5 |}
# { name = "Alice", role = "admin", level = 5 }
\end{lstlisting}

\subsection{Function Splatting}

\begin{lstlisting}
var args = [1, 2, 3]
some-function ...$args     # Equivalent to some-function 1 2 3
\end{lstlisting}

\subsection{Pipeline Spread}
\label{sec:pipeline-spread}

A spread in pipeline position sends a collection's elements as separate items:

\begin{lstlisting}
var xs = [1, 2, 3]
echo (...$xs | count)              # 3
echo (...$xs | where $_ > 1 | count)   # 2
\end{lstlisting}

It spreads one level, and only what the language calls a sequence
(\S\ref{sec:collection-shape}) --- a record, a dictionary and a string are single values,
so spreading one yields it unchanged rather than taking it apart.

\begin{notebox}
This is the only form in a pipeline where shape is not inferred from the value. Everywhere
else a stage decides whether a collection means itself or its elements; here the author has
said so, at the point of writing. That makes it the spelling to reach for when the default
is not what was meant --- and the reason it is worth having is that a default can be
argued about, while \code{...} cannot be misread.
\end{notebox}

\section{Computed Properties}
\label{sec:computed}

\begin{lstlisting}
var key = "name"
var record = {| ($key) = "Alice", age = 30 |}
echo ($record.name)        # Alice

# Dynamic key from expression
var dynkey = "item-count"
var record2 = {| ($dynkey) = 42 |}
echo ($record2.item-count) # 42
\end{lstlisting}

\section{Function References}
\label{sec:funcref}

Prefix a function name with \code{\&} to get a reference to it:

\begin{lstlisting}
func double(x) => $x * 2
var fn = &double
invoke $fn 21              # 42

# In pipelines
[1, 2, 3] | map &double   # [2, 4, 6]
\end{lstlisting}

\section{Scoping}
\label{sec:scoping}

TōSh uses \textbf{lexical scoping} with a scope stack. Each block
(\code{\{...\}}) creates a new scope. Variables are visible in their
declaring scope and all nested scopes.

\subsection{Visibility Modifiers}
\ikw{shy}\ikw{global}\ikw{export}

\begin{longtable}{lL{9cm}}
\toprule
\textbf{Modifier} & \textbf{Behavior} \\
\midrule
\endhead
(none) & Visible in current scope and nested scopes \\
\code{shy} & Private to the declaring scope (e.g.\ module-internal, class-private) \\
\code{global} & Visible across all scopes for the entire session \\

\section{Match Expressions}
\ikw{match}

\code{match} is a powerful pattern-matching expression.  Arms use
\code{pattern => result} syntax.

\subsection*{Pattern Forms}

\begin{tabular}{lL{7.5cm}}
\toprule
\textbf{Form} & \textbf{Matches when} \\
\midrule
\code{<literal>} & Value equals the literal (\code{"file"}, \code{42}, \code{true}). \\
\code{\_ <op> <value>} & Comparison holds; \code{\_} stands for the matched value.  Supported: \code{>}, \code{>=}, \code{<}, \code{<=}, \code{==}, \code{!=}, \code{=\textasciitilde}, \code{!\textasciitilde}. \\
\code{\_ is <type>} & Runtime type check (\code{\_ is string}, \code{\_ is int}). \\
\code{\_} (bare) & Always matches; wildcard catch-all. \\
\code{default} & Always matches; conventional alternative to bare \code{\_}. \\
\midrule
\multicolumn{2}{l}{\textit{Destructuring forms --- these bind names the arm and its guard can read}} \\
\midrule
\code{Name(a, b)} & Value is a \code{Name} --- a union variant, record or struct --- and binds its declared fields in order.  The paren must abut the name: \code{Ok (v)} with a space is still a command and its argument. \\
\code{Name \{ f \}} & Binds field \code{f} by name.  \code{Name \{ f: <pattern> \}} renames (\code{f: got}) or tests (\code{f: "if"}, \code{f: \$want}).  The brace need not abut. \\
\code{[a, b]} & Sequence of exactly that length, each element matched by its own sub-pattern.  A string is not a sequence here. \\
\code{[a, ...rest]} & Sequence of at least that length; \code{rest} binds the remainder as an array, possibly empty.  The rest may sit in the middle: \code{[a, ...mid, z]}.  At most one per pattern. \\
\code{(<p> | <p>)} & Either alternative matches.  Always parenthesised, since \code{|} is the pipeline separator everywhere else.  Every alternative must bind the same names. \\
\code{<p> as name} & Binds the whole value alongside the parts.  Only after a destructuring form --- after a literal, \code{as} is the cast operator. \\
\bottomrule
\end{tabular}

\subsection*{Destructuring Patterns}

Every form above nests: a sub-pattern is a pattern, so patterns compose to any
depth and the forms mix freely.

\begin{lstlisting}[title={Binding a union's fields}]
union Expr {
    Lit(v: int)
    Add(l: Expr, r: Expr)
}

func evaluate(e) => match ($e) {
    Lit(v)    => $v
    Add(l, r) => (evaluate $l) + (evaluate $r)
}
\end{lstlisting}

\noindent This is the shape the \code{switch}-on-\code{\$x.Variant} form in
\emph{Union Definitions} exists to work around.  A typo in a variant name is a
missed arm there and a reported one here; a typo in a field is a runtime member
error there and a diagnostic naming the field here.

\begin{lstlisting}[title={The forms composing}]
match ($node) {
    Item { kind: "if", body }          => (compile $body)   # test one field, bind another
    Item { kind: $expected, body }     => (compile $body)   # test against a variable
    Some(Add(Lit(a), Lit(b)))          => $a + $b           # nested two deep
    (Lit(0) | Lit(1)) as bit           => $bit.v            # either shape, keep the whole
    [first, ...rest]                   => (walk $rest)      # head and remainder
    Add(l, r) if (($l is Lit))         => (fold $l $r)      # a guard sees the bindings
    default                            => 0
}
\end{lstlisting}

\noindent Inside a pattern, a \textbf{plain name binds} and \textbf{\code{\$name}
compares}: \code{Lit(v)} binds whatever the field holds, while \code{Lit(\$want)}
matches only when the field equals \code{\$want}.  \code{\_} discards a position
without binding it.  Bound names are scoped to their arm and are visible to that
arm's guard.

A \textbf{class} destructures by name only.  Its properties may be inherited,
reordered or added without changing what the class means, so there is no order a
positional pattern could rely on --- \code{Circle(r)} is refused, and the
diagnostic offers \code{Circle \{ Radius \}} instead.  Named patterns do reach
inherited properties.

\begin{notebox}
Two rules are checked where the pattern is written rather than where it runs.  A
list pattern may hold only one \code{...}, because a second leaves no
unambiguous split between front and back.  And every alternative of an
or-pattern must bind the same names: \code{(Lit(v) | Add(l, r))} would leave
\code{\$v} unset whenever the \code{Add} side matched, and an unset variable is
not an error anywhere else in the language, so the arm would quietly do
something wrong.
\end{notebox}

Arm bodies may be a single pipeline expression (\code{pattern => expr}) or a
block (\code{pattern => \{ ... \}}).  An optional guard clause
\code{if ((<condition>))} after the pattern skips the arm when the guard
is falsy even if the pattern matched.

The fat-arrow body also accepts the jump statements \code{return},
\code{yield}, \code{throw}, \code{break}, and \code{continue} directly,
so generators and short-circuit returns can be expressed without an
explicit block:

\begin{lstlisting}
func emit-codes(events) {
    for $e in $events {
        match ($e.kind) {
            "ack" => yield $e
            "fatal" => throw $e.message
            default => continue
        }
    }
}
\end{lstlisting}

\code{match} is an expression: its value is the result of the matched arm.
When used as a statement the result is discarded (side effects still apply).

Value patterns match by equality; comparison patterns use \code{\_} as a placeholder for the matched
value and support \code{>}, \code{>=}, \code{<}, \code{<=}, \code{=\textasciitilde}, and \code{is}:

\begin{lstlisting}
# Value patterns (match by equality)
var kind = "file"
var label = match ($kind) {
    "file" => "it is a file"
    "dir"  => "it is a directory"
    default => "something else"
}

# Comparison patterns (use _ as a placeholder for the matched value)
var category = match ($score) {
    _ >= 90 => "A"
    _ >= 80 => "B"
    _ >= 70 => "C"
    default  => "F"
}

# Type-check patterns
var typelabel = match ($x) {
    _ is string => "string value"
    _ is int    => "integer value"
    default      => "other type"
}
\end{lstlisting}

\begin{lstlisting}[title={Match with guards}]
# Guards use `if ((<condition>))` after the pattern
match ($n) {
    0          => echo "zero"
    _ > 0 if (($n is int)) => echo "positive integer"
    _ > 0      => echo "positive"
    default    => echo "negative"
}
\end{lstlisting}

\section{Type Narrowing}
\label{sec:narrowing}

Testing a value's type with \ikw{is} \emph{narrows} it: for the branch guarded
by the test, the value is known to have the tested type, and its members are
reachable without a cast.  Both \code{if} and a \code{match} arm narrow, and
they narrow identically:

\begin{lstlisting}
class Node { prop Kind : string = "node" }
class Leaf extends Node { prop Value: int = 7 }

func describe(n: Node) -> string => match ($n) {
    _ is Leaf => $"leaf {$n.Value}"     # Value belongs to Leaf, not Node
    default   => $n.Kind
}

func viaIf(n: Node) -> string {
    if ($n is Leaf) { return $"leaf {$n.Value}" }
    return $n.Kind
}
\end{lstlisting}

\noindent Narrowing applies to the arm or branch only.  Outside it the value
has its declared type again, and a member that exists on neither the declared
nor the narrowed type is still reported.

\begin{notebox}
This is what makes a visitor over a class hierarchy writable: every pass over
an AST is a \code{match} whose arms test node types and then read the members
those types add.
\end{notebox}

\section{Try / Catch / Finally}
\ikw{try}\ikw{catch}\ikw{finally}

\begin{lstlisting}
# Plain catch - no variable bound
try {
    var data = read-file "config.json" | from json
    process $data
} catch {
    writeline "An error occurred while loading config"
} finally {
    writeline "Cleanup complete"
}

# Named catch - binds the thrown value or exception object
try {
    throw "something went wrong"
} catch (err) {
    writeline $"Caught: {$err}"
}

# Runtime errors expose a .Message field
try {
    var x: int = "not a number"
} catch (err) {
    writeline $"Unexpected: {$err.Message}"
}
\end{lstlisting}

\code{catch} accepts either no variable, \code{catch \{ ... \}}, or one
variable in parentheses, \code{catch (err) \{ ... \}}.  TōSh currently has one
catch block per try statement; filter exception kinds inside the catch body
with \code{is}, \code{match}, or regular conditionals.

\section{Defer}
\ikw{defer}

\code{defer} schedules a block to run when the current scope exits, regardless
of how it exits (normal completion, error, or early return). Multiple defers
execute in LIFO (last-in, first-out) order:

\begin{lstlisting}
func process-file(path) {
    var handle = open-file --read $path
    defer { close $handle }

    var data = read-to-end $handle
    # handle is automatically closed when function returns
    return $data
}
\end{lstlisting}

\begin{lstlisting}[title={Defer LIFO ordering}]
func example() {
    defer { writeline "third" }
    defer { writeline "second" }
    defer { writeline "first" }
}
example()   # Output: first, second, third
\end{lstlisting}

A defer is registered only when execution reaches its declaration.  For
example, a defer written after a \code{return} or an escaping
\code{throw} is not registered.  On scope exit, every registered cleanup
is attempted exactly once in reverse registration order, even when a
newer cleanup fails.  Values yielded by cleanup pipelines are discarded;
direct side effects such as file writes or explicit writer commands still
occur.  Values already produced by the ordinary scope body are preserved.

Failure handling during unwind is deterministic:

\begin{itemize}
  \item If cleanup succeeds, the original completion, jump, cancellation,
        or failure resumes unchanged.
  \item If only one failure exists, TōSh rethrows that original exception
        without an aggregate wrapper.
  \item When failures compete, TōSh raises
        \code{ToshDeferAggregateException}.  Its failure order is the
        scope-body failure first, when present, followed by cleanup
        failures in their actual LIFO execution order.  Nested defer
        aggregates are flattened; unrelated aggregate and diagnostic
        exceptions are not.
  \item A cleanup failure supersedes a pending \code{return},
        \code{break}, or \code{continue}.  The displaced jump is control
        flow, not an entry in the failure list.
\end{itemize}

Cleanup runs in a cancellation-shielded context: cancellation that caused
the scope to exit does not prevent a reached defer from receiving its one
execution attempt.  The original \code{OperationCanceledException}
remains the outward cancellation result; any cleanup failures are retained
in the public defer-failure metadata.  A cleanup that may block should use
an explicit \code{timeout}.

For compatibility, \code{return}, \code{break}, and \code{continue}
executed by a deferred cleanup are local to that cleanup and suppressed.
They neither replace the enclosing scope's pending exit nor prevent an
earlier registered cleanup from running.

\section{Break, Continue, Return, Throw}
\ikw{break}\ikw{continue}\ikw{return}\ikw{throw}

\begin{lstlisting}
# break - exit a loop early
for item in $items {
    if ($item == "stop") { break }
    writeline $item
}

# continue - skip to next iteration
for item in $items {
    if ($item == "skip") { continue }
    writeline $item
}

# return - exit function with value
func find-first(items, predicate) {
    for item in $items {
        if ($predicate($item)) { return $item }
    }
    return null
}

# throw - raise an exception
func validate(value) {
    if ($value == null) {
        throw "Value cannot be null"
    }
}
\end{lstlisting}

\code{throw} also works as an \emph{expression} in any value position---the
false branch of a ternary, the right side of null-coalescing, or a match arm
body.  This lets you encode "this path must not be reached" inline:

\begin{lstlisting}
# Throw in a ternary: one branch produces a value, the other throws
var x = ($valid ? $value : throw "validation failed")

# Throw in null-coalescing: fail immediately if a required value is absent
var conn = $connectionString ?? throw "Connection string is required"

# Throw in a match arm body
var label = match ($input) {
    _ is int    => $"int: {$input}"
    _ is string => $"str: {$input}"
    default     => throw $"Unexpected type: {typeof $input}"
}
\end{lstlisting}


\section{Postfix Conditionals (\code{if} / \code{unless})}
\label{sec:postfix-conditionals}
\ikw{if}\ikw{unless}

A jump statement \textemdash{} \code{return}, \code{yield}, \code{throw},
\code{break}, or \code{continue} \textemdash{} may be followed by a
\emph{postfix conditional} that guards execution.  The form is:

\begin{lstlisting}
return 5  if   $x == 9
return 5  if   $x > 3 and $ready
return 8  unless $ready
yield $i  if   ($i % 2 == 0)
throw "bad" unless (validate $input)
break     if   $done
continue  unless $found
\end{lstlisting}

Semantics:

\begin{itemize}
  \item \code{stmt if cond} executes \code{stmt} only when \code{cond}
        is truthy. It is exactly equivalent to
        \code{if cond \{ stmt \}}.
  \item \code{stmt unless cond} executes \code{stmt} only when
        \code{cond} is falsy. It is exactly equivalent to
        \code{if cond \{ \} else \{ stmt \}}; the original condition
        expression is preserved verbatim (no negation operator is
        inserted).
\end{itemize}

The condition is a full expression, so \code{return 5 if \$x > 3} needs no
parentheses; they remain available for clarity.  The postfix form is recognised only
when the \code{if} or \code{unless} keyword appears on the same logical
line as the jump statement (no implicit statement boundary in between);
this avoids ambiguity with a free-standing \code{if} block on the
following line.  Omitting the condition raises
\code{tosh.parser.expected\_postfix\_condition}.

Postfix conditionals attach \emph{only} to jump statements.  Regular
commands (\code{echo "hi" if \$x}) and assignments
(\code{var x = 1 if \$y}) are not supported \textemdash{} use a block
\code{if} instead.

\end{lstlisting}

\subsection*{Default-Value Semantics}
\label{sec:default-binding}

Defaults follow one protocol for functions, lambdas, methods, and
constructors:

\begin{itemize}
  \item A default is evaluated only when the caller supplies neither a
        positional nor a named argument for that parameter, and it is
        re-evaluated on every such call --- never captured once at
        declaration time.
  \item Defaults evaluate in the callable's own lexical scope, at call
        time, so a default that reads an outer variable observes that
        variable's value when the call happens.
  \item Evaluation proceeds left to right, and a default may reference
        any \emph{earlier} parameter that is already bound.  Referring
        to the parameter's own name, or to a later parameter, raises
        \code{tosh.runtime.unknown\_variable}.
  \item Overload resolution never evaluates a default; only the selected
        overload's defaults run, so a losing candidate produces no side
        effects.
  \item An evaluated default is converted through the parameter's
        annotation and refinement exactly like a supplied argument.  A
        default that cannot be converted raises
        \code{tosh.runtime.parameter\_default\_conversion\_failed}.
\end{itemize}

\begin{lstlisting}
func step(a: int, b: int = $a + 1, c: int = $b + 1) -> string {
    return $"{$a},{$b},{$c}"
}

step 1                     # 1,2,3   -- defaults chain left to right
step(1, c = 99)            # 1,2,99  -- named argument, b still defaults
\end{lstlisting}

\begin{notebox}
Because defaults evaluate at call time, a mutable default expression
produces a fresh value per call.  \tosh{func add(item, into = [])}
therefore starts from a new empty list on every call rather than sharing
one list across calls.
\end{notebox}

\section{Named Arguments and Callable Invocation}

Function calls can use command-style syntax, parenthesized call syntax, or
named arguments.  Named arguments use \code{name = value} inside the call and
may be supplied out of order.

\begin{lstlisting}
func deploy(host, port = 22, user = "root") {
    echo $"{$user}@{$host}:{$port}"
}

deploy "server"
deploy(host = "server", user = "alice")
deploy(user = "alice", port = 2222, host = "server")
\end{lstlisting}

Callable values can be invoked with \code{invoke} or postfix call syntax:

\begin{lstlisting}
var double = func(x) => ($x * 2)
invoke $double 21
$double(21)

var add3 = func(a, b, c) => ($a + $b + $c)
(curry $add3)(1)(2)(39)       # 42
\end{lstlisting}

\subsection*{Functions that produce nothing}

\ikw{void} and \ikw{nothing} are two spellings of one type, and both declare
that the function produces no value.  Because a function's output \emph{is} its
value (see the note below), that is a claim about output rather than about a
return slot:

\begin{lstlisting}
func log(m: string) -> void {
    writeline $"[log] {$m}"     # writes to the console, yields nothing
}

log "starting"                  # prints; contributes nothing
(log "x") | count               # 0
\end{lstlisting}

\noindent A \ikw{void} function may not say what it evaluates to.  Writing
\code{echo}, \ikw{yield}, or \code{return} with an operand inside one is
reported as \code{tosh.compile.void\_function\_produces\_output}, in the same
way a C\# \code{void} method may not \code{return} a value.  \code{echo} emits
a pipeline value and is therefore the shell's form of that statement, while
\code{writeline} writes to the console and yields nothing --- so a
\ikw{void} function still prints, it simply does not produce.

If a \ikw{void} function produces a value by some route the compiler cannot
see, it is reported when it runs, as
\code{tosh.runtime.void\_function\_produced\_value}.  Nothing is discarded
silently.

\begin{notebox}[Implicit Pipeline Return]
A function does not need an explicit \code{return} to produce a value.
All pipeline output emitted by the function body is collected and yielded
as the function's result when the function exits normally.  If a
\code{return} is reached, its operands replace any buffered output:

\begin{lstlisting}
func doubled-items(items) {
    $items | each { _ * 2 }   # output flows out; no 'return' needed
}

var results = (doubled-items [1, 2, 3])   # [2, 4, 6]
\end{lstlisting}

Generator functions (those containing \code{yield}) stream values
progressively instead of buffering them---see
Section~\ref{sec:generators}.
\end{notebox}

\section{Function Overloading}

Functions can be overloaded by arity and typed parameters:

\begin{lstlisting}
func greet() { echo "Hello!" }
func greet(name) { echo $"Hello, {$name}!" }
func kind(value: int) { echo "integer" }
func kind(value: string) { echo "string" }

greet              # Hello!
greet "World"      # Hello, World!
kind 42            # integer
kind "hi"          # string
\end{lstlisting}

\section{Recursion Depth}

TōSh protects the host process with a limit on active ToastScript
execution frames. Functions, methods, lambdas, constructors, and nested
\code{eval}/\code{source} execution participate in the same
asynchronous-flow-local count; compiled ToastScript uses the same
protocol and the same limit.

The limit is not a fixed number. A ToastScript frame costs a chain of
asynchronous state-machine frames on the host stack, so the depth that
fits is a property of the stack the process was given: one frame is
budgeted per 64\,KB, with a floor of 128 and a ceiling of 10{,}000. On
the 8\,MB stack a thread gets by default this yields 128, which is the
limit unless the stack has been enlarged.

Exceeding the limit raises the stable
\code{tosh.runtime.recursion\_limit\_exceeded} diagnostic. It does not
terminate the process, and an interactive session remains usable after
the diagnostic is handled.

The limit may be lowered for a session or persisted in
\code{config.tosh}:

\begin{lstlisting}
$tosh.Config.Shell.MaxRecursionDepth = 64
\end{lstlisting}

Accepted values run from 1 to whatever the current stack allows, and
the diagnostic names the range when a larger value is refused.

To raise the limit rather than lower it, enlarge the stack every thread
is created with. The .NET runtime reads this before any ToastScript
runs, so it is an environment variable rather than a setting:

\begin{lstlisting}
DOTNET_Thread_DefaultStackSize=0x4000000 tosh script.tosh
\end{lstlisting}

64\,MB raises the limit to 1{,}024. The value is hexadecimal, and the
cost is reserved address space rather than memory, so a script that does
not recurse deeply pays nothing for it.

TōSh does not currently perform tail-call elimination, so deeply
recursive algorithms should be rewritten as loops when practical.

\section{Operator Overloading}
\label{sec:operator-overloading}

Classes may overload binary operators by declaring methods whose names are
the operator symbol itself. The method receives the right-hand operand as
its single argument; \code{\$this} refers to the left-hand operand.

\begin{lstlisting}
class Vec {
    prop X: int = 0
    prop Y: int = 0

    func +(other) { var r = new Vec(); $r.X = $this.X + $other.X; $r.Y = $this.Y + $other.Y; return $r }
    func *(scalar) { var r = new Vec(); $r.X = $this.X * $scalar; $r.Y = $this.Y * $scalar; return $r }
    func ==(other) { return $this.X == $other.X and $this.Y == $other.Y }
}

var a = new Vec(); $a.X = 1; $a.Y = 2
var b = new Vec(); $b.X = 3; $b.Y = 4
$a + $b              # Vec { X: 4, Y: 6 }
$a * 3               # Vec { X: 3, Y: 6 }
\end{lstlisting}

The following operator symbols are accepted as method names:

\begin{center}
\begin{tabular}{l l}
\toprule
\textbf{Category} & \textbf{Symbols} \\
\midrule
Arithmetic & \code{+}, \code{-}, \code{*}, \code{/}, \code{//}, \code{\%}, \code{**} \\
Comparison & \code{==}, \code{!=}, \code{<}, \code{<=}, \code{>}, \code{>=} \\
Match      & \code{=\textasciitilde}, \code{!\textasciitilde} \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Resolution order}

When evaluating \code{a OP b} where either operand is a class instance:

\begin{enumerate}
    \item If the left operand defines an \code{OP} method, it is invoked
      with \code{b} as the argument.
    \item Otherwise, if the right operand defines an \code{OP} method, it
      is invoked with \code{a} as the argument (note: \code{\$this} is
      still the right operand).
    \item Otherwise, the standard built-in operator semantics apply.
    \item If no built-in rule supports the operand pair, TōSh looks for the
      corresponding compatible public static CLR \code{op\_*} method on the
      left operand's type, then on the right operand's type when the types differ.
    \item If neither operand supplies one, evaluation raises the ordinary
      incompatible-operand diagnostic naming both types.
\end{enumerate}

The CLR fallback uses \code{op\_Addition}, \code{op\_Subtraction},
\code{op\_Multiply}, \code{op\_Division}, and \code{op\_Modulus} for arithmetic,
and the six conventional equality and ordering names for comparison.  The symbolic
\code{**} and \code{//} operators have no standard CLR operator name and therefore
retain TōSh's built-in and class-overload behavior.  This lookup is also the lookup
used by the \code{Add}, \code{Sub}, \code{Mul}, and \code{Div} type constraints, so
constraint satisfaction and execution cannot disagree about whether an operator exists.

\subsection{Limitations}

\begin{itemize}
    \item Unary operators (prefix \code{-}, \code{not}) are not currently
      overloadable. Only the binary forms above are accepted as method
      names.
    \item Compound-assignment operators (\code{+=}, \code{-=}, etc.) are
      not overloadable directly; they desugar to the binary form, so
      defining \code{+} also covers \code{+=}.
    \item Indexer-style access (\code{a[i]}) is parser-level wired but
      not yet a spec-level guarantee; prefer named methods until indexer
      semantics stabilise.
\end{itemize}

\section{Generator Functions}
\label{sec:generators}
\ikw{yield}

A function that contains a \code{yield} statement is a \emph{generator
function}.  Each call returns a \code{LazySequence}---values are produced on
demand as the sequence is consumed.  A generator may yield any number of times
and may mix \code{yield} with normal control flow.

\begin{lstlisting}
func evens-up-to(n: int) {
    var i = 0
    while ($i <= $n) {
        yield $i
        $i += 2
    }
}

evens-up-to 10 | collect        # [0, 2, 4, 6, 8, 10]
evens-up-to 20 | first 4        # 0, 2, 4, 6
\end{lstlisting}

You can annotate the return type as \code{LazySequence} to make intent clear:

\begin{lstlisting}
func fibonacci() -> LazySequence {
    var a = 0
    var b = 1
    while (true) {
        yield $a
        var next = $a + $b
        $a = $b
        $b = $next
    }
}

fibonacci | first 8             # 0, 1, 1, 2, 3, 5, 8, 13
\end{lstlisting}

\begin{warnbox}[Known Limitation]
Generator functions with unbounded \code{while (true)} loops do not yet cooperate
with early-termination commands such as \code{first}.  The pipeline will run
indefinitely.  Use a finite upper bound in the loop condition, or reach for
built-in lazy sources (\code{iterate}, \code{recur}, \code{cycle}, \code{repeat},
infinite ranges \code{1..}) which do support early termination.
\end{warnbox}

\begin{tipbox}
Finite generator functions integrate naturally with the full pipeline command set:
\code{first}, \code{skip}, \code{where}, \code{map}, \code{collect}, etc.
\end{tipbox}

\section{Asynchrony}

\code{async} and \code{await} are \emph{commands}, not keywords---they are
resolved by the command dispatcher like any other builtin, and they do not
appear in the keyword list for that reason.

\code{async} starts a callable or block in the background and returns a future
handle; \code{await} waits for it and replays its outputs:

\begin{lstlisting}
var f = async { sleep 0.2; echo done }
await $f                      # done
\end{lstlisting}

\subsection*{Awaiting CLR Tasks}

\code{await} also accepts a CLR \code{Task}, \code{Task<T>}, \code{ValueTask},
or \code{ValueTask<T>}, so .NET asynchronous methods work the way a .NET reader
expects.  A task-returning call yields a task, and you await it---the same
explicit model as C\#:

\begin{lstlisting}
using System.Net.NetworkInformation

var p = new Ping()
var reply = await ($p.SendPingAsync("8.8.8.8", 1000))
echo $reply.Status            # Success
\end{lstlisting}

Because a task is a value, work can overlap---start several, then await each:

\begin{lstlisting}
var a = $client.GetStringAsync($first)
var b = $client.GetStringAsync($second)

var one = await $a
var two = await $b            # both requests were already in flight
\end{lstlisting}

A method declared to return plain \code{Task} produces no value, so awaiting it
emits nothing:

\begin{lstlisting}
await (System.IO.File.WriteAllTextAsync($path, $text))
\end{lstlisting}

The \code{Task} helpers are reachable, because a generic method infers its type
arguments from the arguments supplied, as C\# does:

\begin{lstlisting}
var a = Task.FromResult(1)
var b = Task.FromResult(2)
echo (await (Task.WhenAll($a, $b)))   # both results, in order
\end{lstlisting}

Inference here is narrower than the compiler's: there is no best-common-type
step, so a type parameter used in more than one position must bind to one type
or a base of it.  A call that supplies nothing to infer from---
\code{Array.Empty()}, \code{Enumerable.Empty()}---reports
\code{Cannot infer type argument 'T'} naming the parameter it could not
supply, rather than claiming the method has no such overload.

Where inference cannot reach, write the type arguments:

\begin{lstlisting}
Array.Empty<int>()                  # an empty int[]
Enumerable.Empty<string>()
Task.FromResult<int>(7)
Tuple.Create<int, int>(1, 2)
\end{lstlisting}

An instance call takes them in the same position, \code{\$x.m<int>(…)}.

The list must be glued to the method name and closed before the parenthesis,
which is what tells it apart from a comparison: \code{\$A < 5} is still an
ordinary \code{<}.

\begin{notebox}
\code{await} unwraps as many layers as it finds, so a block whose last
expression is an asynchronous call needs only one \code{await}:

\begin{lstlisting}
var f = async { $p.SendPingAsync("8.8.8.8", 1000) }
var reply = await $f          # a PingReply, not a Task
\end{lstlisting}

This is a deliberate difference from C\#, where the equivalent needs
\code{Task.Unwrap}.  A future whose value is a task has no use, and leaving it
unflattened is a trap.
\end{notebox}

A failed task raises its \emph{own} error, not the
\code{AggregateException} wrapper the CLR would surface, so
\code{\$e.Message} inside \code{catch} is the message the operation actually
failed with:

\begin{lstlisting}
try {
    await (System.IO.File.ReadAllTextAsync("/nope.txt"))
} catch (e) {
    echo $e.Message           # Could not find a part of the path '/nope.txt'.
}
\end{lstlisting}

\begin{warnbox}
Reading \code{.Result} or calling \code{.GetAwaiter().GetResult()} on a task
also works, and \emph{blocks the calling thread}.  Prefer \code{await}; the
blocking forms can deadlock.
\end{warnbox}

An un-awaited task displays as what it is, so a forgotten \code{await} is
visible rather than mysterious:

\begin{lstlisting}
$p.SendPingAsync("8.8.8.8", 1000)     # Task<PingReply> (pending)
\end{lstlisting}

\section{Event Handlers}
\ikw{handles}

Functions can be registered as event handlers:

\begin{lstlisting}
func onDirChange(event) handles DirectoryChanged {
    writeline $"Changed to: {$event.NewDirectory}"
}

# With priority and guard
func onBigCommand(event) handles CommandCompleted priority 10
    when { $event.Duration > (timespan 1s) }
{
    writeline $"Slow command: {$event.Duration}"
}

# One-time handler
func onFirstStart(event) handles SessionStarted once {
    writeline "Welcome to your first session!"
}
\end{lstlisting}

The last value emitted by a \code{when} block is tested using the canonical
truthiness rules in Table~\ref{tab:truthiness}.  A block that emits no values
therefore has a falsy guard.

\code{priority} is an ordering rank, and \emph{lower numbers run first}:
a handler declared \code{priority 1} runs before one declared
\code{priority 10}.  Handlers that declare no priority run after every handler
that declares one, in registration order.

\begin{warnbox}
The number is a position in a queue, not an importance.  \code{priority 10}
runs \emph{later} than \code{priority 1}, which is the opposite of how the
word reads in most systems --- give the handler that must run first the
smallest number.
\end{warnbox}

\section{Doc-Comments}

Functions, classes, properties, and methods accept documentation comments
immediately above their declaration.  A doc-comment line begins with \code{\#\#}
(double hash).  At runtime, \code{help <name>} renders the doc-comment:

\begin{lstlisting}
## Adds two numbers together and returns the sum.
## @param=a The first operand.
## @param=b The second operand.
## @returns The sum as an int.
## @example
##   add 3 4    # 7
func add(a: int, b: int) -> int {
    return ($a + $b)
}
\end{lstlisting}

The supported tags are:

\begin{tabular}{lL{8cm}}
\toprule
\textbf{Tag} & \textbf{Purpose} \\
\midrule
\code{@param=<name> <desc>} & Document a named parameter. \code{@param <name> <desc>} is accepted as an equivalent spelling. \\
\code{@returns <desc>} & Describe the return value. \\
\code{@example} & Lines following this tag (still prefixed \code{\#\#}) are shown verbatim as examples in \code{help} output. \\
\code{@deprecated <message>} & Flag the item as deprecated; \code{help} renders a visible warning. \\
\code{@see <ref>} & Cross-reference another command or function. \\
\code{@since <version>} & First release in which the item appeared. \\
\code{@throws <type> <desc>} & Document an exception path the function may raise. \\
\bottomrule
\end{tabular}

\begin{tipbox}
All tags are optional.  A doc-comment containing only prose (no tags) is
perfectly valid and will display as the item's description.
\end{tipbox}

\begin{warnbox}
\code{\#\#} is a doc-comment, not an ordinary comment.  Commenting code out
with \code{\#\#} turns it into documentation, and it will appear in
\code{help} and \code{--help} output.  Use a single \code{\#} to comment
code out.
\end{warnbox}

\subsection*{Naming an input}

\code{@param}, \code{@arg} and \code{@flag} all document one named input and
behave identically; they differ only in reading naturally beside the
declaration they describe.  A function takes parameters, while a script or a
subcommand takes \code{arg}s and \code{flag}s.  Each accepts either separator
--- \code{@arg=name <desc>} and \code{@arg name <desc>} are the same tag.

\subsection*{Scripts and \code{--help}}

A script that declares inputs with \code{arg} or \code{flag} answers
\code{--help} (and \code{-h}) by describing itself, without running its body.
The summary comes from the file-level doc-block, and each input is listed with
the description written above it:

\begin{lstlisting}
## Greets a person by name.

## Who to greet.
arg name: string

## Shout the greeting.
flag loud: bool = false

echo $"Hello, {$name}"
\end{lstlisting}

\begin{lstlisting}
$ greet.tosh --help
Greets a person by name.

Usage: greet.tosh [options] <name>

Arguments:
  name  string  Who to greet.

Options:
  --loud  bool  Shout the greeting.
\end{lstlisting}

Required arguments are written \code{<name>}, optional ones \code{[name]},
and a rest argument \code{[name...]}.  A script that declares its own
\code{help} or \code{h} flag keeps it --- the built-in answer is a default,
never an override --- and arguments after a bare \code{--} are data rather
than a request for help.

\subsection*{Subcommands}

A subcommand may document its inputs in its own doc-block, or leave each
declaration to describe itself.  Where both do, the subcommand's block wins,
so one header can describe everything a subcommand takes:

\begin{lstlisting}
## @summary Build, version-bump, and package.
## @arg=target What to build.
## @flag=fast Skip slow steps.
subcommand publish {
    arg target: string = "all"
    flag fast: bool = false
}
\end{lstlisting}

Overriding is per input rather than wholesale: an input the block does not
mention keeps the description written above its declaration.

\section{Rune Definitions}
\ikw{rune}

Runes are macro-like shell commands whose arguments are captured lazily as
syntax thunks.  They are useful for control-flow helpers that should decide
when, whether, or how often to evaluate their arguments or body blocks.

\begin{lstlisting}
rune do-twice(body) {
    $body
    $body
}

do-twice { writeline "hi" }  # hi, hi
\end{lstlisting}

A rune can be invoked like any command, including with block arguments:

\begin{lstlisting}
rune retry(count, body) {
    for i in 1..$count {
        try {
            $body
            return
        } catch (err) {
            if ($i == $count) { throw $err }
        }
    }
}
\end{lstlisting}

\section{Rune Hygiene}
\ikw{sealed}\ikw{leaky}

Runes are \code{sealed} by default.  A sealed rune evaluates in a hygienic
scope so variables declared inside the rune do not leak back to the caller.
Mark a rune \code{leaky} when it intentionally writes bindings into the caller
scope.

\begin{lstlisting}
rune internal() {
    var hidden = 42
}

leaky rune export-var() {
    var visible = 42
}
\end{lstlisting}

\code{fixed} and \code{lazy} are accepted rune modifiers.  \code{lazy} is the
default evaluation mode; \code{fixed} marks the captured argument behaviour as
fixed for future expansion/runtime policy.

\section{Quote}
\ikw{quote}

\code{quote \{ ... \}} captures syntax as a first-class quoted value instead of
evaluating it immediately.  This is primarily useful inside runes for source
inspection and AST-like metaprogramming.

\begin{lstlisting}
rune show-source(expr) {
    var src = (quote { $expr })
    echo $src
}

show-source (1 + 2)          # contains "1 + 2"
\end{lstlisting}

\section{Built-In Runes}

The runtime currently provides \code{unless} as a built-in rune:

\begin{lstlisting}
unless false { echo "runs" }
unless true  { echo "skipped" }
\end{lstlisting}

\section{Using Statements}
\ikw{using}

Import CLR namespaces for shorter type references:

\begin{lstlisting}
using System.IO             # Import namespace
using System.IO = IO        # Aliased import
\end{lstlisting}

\code{using} is lexically scoped---it only applies in the block where declared.

\section{Require Statements}
\ikw{require}

Load scripts or modules:

\begin{lstlisting}
# Import everything the file exports
require "./utils.tosh"

# Import specific module
require Inventory from "./toastlib.tosh"

# With alias
require Inventory from "./toastlib.tosh" as Inv

# Multiple modules
require { Reporting, Utilities } from "./toastlib.tosh"
\end{lstlisting}

\noindent \textbf{\code{require} imports exports; it does not run the file in
your scope.}  A required file is executed once per session in a scope of its
own, and only declarations marked \code{export} are brought into the caller.
Anything else stays private to the module---which is what makes \code{export}
mean something.

\begin{lstlisting}
# lib.tosh
func helper() { return "private to this file" }
export func shared() { return "importable" }
export var VERSION = 2

# main.tosh
require "./lib.tosh"
shared                # "importable"
echo $VERSION         # 2
helper                # error - not exported
\end{lstlisting}

\noindent Use \code{source} when you do want a file's every declaration in the
current scope; that is the difference between the two.  A file required for its
exports that declares none raises
\code{tosh.runtime.require\_exports\_nothing}, since importing nothing at all
is never the intent and used to happen in silence.

\subsection*{How a relative path is resolved}
\label{sec:relative-load-paths}

Both \code{require} and \code{source} read a relative path as \emph{beside the
file doing the loading}, not beside the working directory, so a script that
loads a sibling behaves the same however it is invoked:

\begin{lstlisting}
# ~/tools/report.tosh
source "./format.tosh"        # always ~/tools/format.tosh
require "./stats.tosh"        # always ~/tools/stats.tosh
\end{lstlisting}

The rule follows the file being executed, so a sourced script reaches its
\emph{own} siblings rather than those of whatever sourced it.

The two differ in what happens when the path is not there.  \code{require}
stops.  \code{source} then tries the working directory, so a path deliberately
written relative to where the shell was invoked still resolves, and a file that
is simply missing is reported against the directory the reader expects.
Absolute paths and \code{\textasciitilde} paths are unaffected by either rule.

\section{Native Library Loading}
\ikw{bind}\ikw{callconv}\ikw{raw}\ikw{from}\ikw{where}

Load and bind native (unmanaged) libraries:

\begin{lstlisting}
bind native "./libcrypto.so" as Crypto {
    func sha256(data: ptr, len: uint64) -> ptr
}
\end{lstlisting}

A bind block may also be written inside a module or a class body, so the
library path is stated once and the bound functions hang off the type that
wraps them:

\begin{lstlisting}
export hermit class SystemFacts {
    shy bind native "libc.so.6" {
        func uname(out buf: UtsName) -> ok
        func sysconf(name: int)      -> count
    }

    shared prop Kernel:   string => SystemFacts.uname().release
    shared prop PageSize: long   => SystemFacts.sysconf(30)
}
\end{lstlisting}

Native members inside a class are always static, and default to \code{shy} ---
the reverse of \code{func} --- so the raw ABI surface stays hidden behind the
typed members written over it.  \code{proud bind} opts back out.

For a single binding that does not justify a block, \code{raw func} names its
library inline with \code{from}:

\begin{lstlisting}
raw func sysconf(name: int) -> count from "libc.so.6"
\end{lstlisting}

\subsection{Parameter Modes}

Parameters default to \code{in} (pass by value).  \code{ref} passes a managed
reference the callee both reads and writes.  \code{out} is written by the
callee and read by nobody, so it is \emph{engine-allocated and does not appear
at the call site}:

\begin{lstlisting}
bind native "libc.so.6" as LibC {
    func gettimeofday(out tv: Timeval, nint) -> int
}

var r = LibC.gettimeofday(0)   # one argument, not two
$r.tv.tv_sec
\end{lstlisting}

\code{cstring} may be passed by reference, which is C's \code{char**}: the
callee replaces the pointer rather than the characters.

\begin{lstlisting}
bind native "libc.so.6" as LibC {
    func strtol(s: cstring, out endptr: cstring, base: int) -> long
    func strsep(ref stringp: cstring, delim: cstring)       -> cstring
}

var r = LibC.strtol("42abc", 10)
$r.ReturnValue    # 42
$r.endptr         # "abc"
\end{lstlisting}

The pointer the callee leaves is \emph{copied} into a string and the bytes
behind it are left alone: TōSh frees only memory TōSh allocated, because the
callee's allocator cannot be known from a shared object.  A caller who must
free the callee's buffer declares \code{ptr} and frees it explicitly.  A managed
\code{string} cannot be passed by reference, since writing one back would mean
guessing the encoding as well as the allocator.

Use \code{out} when the callee fills a structure and reads nothing
(\code{sysinfo}, \code{uname}, \code{gettimeofday}); use \code{ref} when it
reads and writes the same memory (\code{poll}, \code{select}, \code{ioctl}
with \code{TCSETS}).  Passing a native buffer to a \code{ref} parameter writes
the result back into unmanaged memory.

\subsection{Variadic Parameters}

A binding may end in \code{...}, C's variadic tail:

\begin{lstlisting}
bind native "libc.so.6" as LibC {
    func snprintf(dst: ptr, n: long, fmt: cstring, ...) -> int
}

LibC.snprintf($buf, 256, "i=%d s=%s f=%.1f", 42, "hi", 2.5)
\end{lstlisting}

The tail is whatever the call site passes, so the call signature is built from
the actual arguments and cached per shape.  C's default argument promotions
apply, because the callee reads them: anything narrower than \code{int} is passed
as \code{int}, and \code{float} as \code{double}.  Nothing may follow \code{...},
and the fixed parameters before it are still required.

\subsection{Return Conventions}

A native call declares how success is decided.  This is orthogonal to what a
successful call yields.

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Return} & \textbf{Meaning} \\
\midrule
\code{-> ok}    & \code{int}; \code{0} is success, anything else throws \\
\code{-> count} & \code{>= 0} is success \emph{and is the value}; \code{ssize\_t} \\
\code{-> int count} & the same, read at a stated width (\code{int}, \code{long}) \\
\code{-> auto}  & no checking; project the out parameters \\
\code{-> T where (\_)} & custom predicate over the return value \\
\code{-> T}     & raw, unchecked \\
\bottomrule
\end{tabular}
\end{center}

Bare \code{count} marshals the return as \code{ssize\_t}, which is pointer-sized.
Bound to a function that really returns \code{int}, a \code{-1} failure is read at
the wrong width and can arrive as \code{4294967295} --- non-negative, so the
failure goes undetected. Whether that happens depends on what the callee left in
the upper half of the return register, so it varies by library. State the width
when the C function does not return \code{ssize\_t}:

\begin{lstlisting}
func read(fd: int, buf: ptr, n: long) -> count        # ssize_t
func open(path: cstring, flags: int)  -> int count    # int32_t, -1 detected
\end{lstlisting}

\code{where} is the same keyword, placeholder and meaning as a refinement
type, with \code{\_} bound to the native return value.  \code{ok} and
\code{count} are that clause with its two commonest predicates given names ---
the convention is still stated explicitly at the declaration site.

A checked call spends its return value on the success decision, so the out
parameter becomes the result: with exactly one, it is yielded directly; with
several, a record keyed by parameter name; an unchecked call yields a record
carrying \code{ReturnValue} alongside them.  With no out parameters at all, a
checked call yields \emph{nothing} --- the return value was spent on the success
decision and there is no result left to project, so \code{LibC.chdir("/tmp")}
emits no pipeline object.  \code{count} is the exception in every position: its
return value is a genuine count that happens to double as the error signal, so
it is still yielded.

\begin{lstlisting}
bind native "libc.so.6" as LibC {
    func sysinfo(out info: SysInfo) -> ok
}

var info = LibC.sysinfo()      # a SysInfo, not a record wrapping one
\end{lstlisting}

Failure throws a \code{NativeError} carrying \code{Errno}, \code{ErrnoName},
\code{Symbol}, \code{Library} and \code{Result}, rendered with the offending
symbol and a \code{strerror} message.

\subsection{Buffers and Arrays}

\code{buffer[n]} collapses C's output-string idiom --- always an adjacent
\code{(pointer, length)} pair --- into one parameter that expands to both ABI
arguments and yields a decoded string:

\begin{lstlisting}
bind native "libc.so.6" as LibC {
    func gethostname(out name: buffer[256])            -> ok
    func readlink(path: string, out buf: buffer[4096]) -> count
    func getloadavg(out avg: double[3], count: int)    -> int where (_ == 3)
}
\end{lstlisting}

With \code{-> count} the returned count supplies the buffer's true length
rather than scanning for a NUL, which is what makes \code{readlink}
safe --- it does not terminate its output.  A typed \code{T[n]} out-parameter
is engine-allocated and comes back as an array.

\subsection{Calling Conventions}

\code{callconv} is a trailing clause on the function it applies to:

\begin{lstlisting}
bind native "user32.dll" as User32 {
    func MessageBoxW(nint, string, string, uint) -> int callconv stdcall
}
\end{lstlisting}

It defaults to \code{cdecl}; \code{stdcall}, \code{thiscall}, \code{fastcall}
and \code{winapi} are also accepted.  An unrecognised name is an error rather
than a silent fallback.

\subsection{Type Restrictions}

\code{cstring} is a borrowed NUL-terminated C string; \code{nint} / \code{nuint}
(or \code{ptr} / \code{uptr}) are pointer-sized values.  Plain \code{string}
works as a parameter but not as a return type, which needs explicit ownership
semantics.  \code{out} and \code{ref} string parameters are rejected for the
same reason and need an explicit pointer type.

\section{Raw Structs}
\ikw{raw}\ikw{struct}\ikw{union}\ikw{pack}\ikw{size}

A \code{raw struct} declares a C memory layout.  It is deliberately a separate
declaration kind from \code{struct}: a tosh struct is a dictionary-backed
object model with computed properties and refinement-typed fields, whereas a
raw struct is a byte layout that becomes a real sequential-layout CLR type.

\begin{lstlisting}
raw struct SysInfo {
    uptime:    long
    loads:     ulong[3]
    totalram:  ulong
    procs:     ushort
    totalhigh: ulong
    mem_unit:  uint
}
\end{lstlisting}

The emitted type is nameable anywhere a native interop type is expected, so
\code{size-of}, \code{offset-of}, \code{alloc}, \code{read-buffer} and native
signatures all accept it.

\textbf{Padding is never declared.}  Sequential layout aligns each field
naturally, exactly as a C compiler does, so a declaration transcribes the
header and omits its \code{pad} / \code{\_\_pad0} / \code{\_\_glibc\_reserved}
members.  In the example above \code{totalhigh} lands at offset~88, not~82,
without any padding field being written.

Array counts are part of the ABI and cannot be inferred, since
\code{char[65]} and \code{char[256]} are different layouts.  \code{cstring[n]}
is an inline character buffer; \code{T[n]} is an inline array.

\begin{lstlisting}
raw struct UtsName {
    sysname:    cstring[65]
    nodename:   cstring[65]
    release:    cstring[65]
    version:    cstring[65]
    machine:    cstring[65]
    domainname: cstring[65]
}
\end{lstlisting}

\code{bool} is rejected in favour of \code{byte}: default marshalling maps it
to a four-byte Win32 \code{BOOL} rather than a C \code{\_Bool}, which would
shift every subsequent field.

Two optional header clauses, both rarely needed.  \code{pack n} sets the
packing; \code{size n} asserts the computed size, turning a mis-transcribed
struct into a declaration-time error rather than silent memory corruption.

\begin{lstlisting}
raw struct Packed pack 1 { a: byte; b: long }   # 9 bytes, not 16
raw struct Checked size 16 { a: long; b: long }
\end{lstlisting}

\code{raw union} places every field at offset zero.

Fields may carry defaults.  These apply when tosh constructs a value and to
\code{ref} parameters, but never to an \code{out} parameter, which arrives
zero-filled --- a CLR struct cannot carry an initializer the marshaller would
run, and seeding one would mask a callee that failed to write.

\begin{lstlisting}
raw struct PollFd {
    fd:      int   = -1
    events:  short = 1
    revents: short
}
\end{lstlisting}

\section{Raw Callbacks}
\ikw{raw}\ikw{callback}

A \code{raw callback} declares the C function-pointer type a native signature
names when the library calls back into TōSh.  Like \code{raw struct} it is a
named declaration rather than an inline type, which is also how C spells these
--- nearly always a \code{typedef}.

\begin{lstlisting}
raw callback Comparator(a: ptr, b: ptr) -> int

bind native "libc.so.6" as LibC {
    func qsort(base: ptr, count: nuint, size: nuint, compare: Comparator) -> void
}

func ascending(a, b) {
    return (read-buffer int32 $a) - (read-buffer int32 $b)
}

LibC.qsort($buf, 8, 4, &ascending)
\end{lstlisting}

The name resolves anywhere a native interop type is expected, and a function
reference (\code{\&name}) is what satisfies it.  \code{callconv} applies as it
does to a \code{func}.

\subsection{Exactly One Value}

A TōSh function yields a stream; a C callback returns a single value.  A
callback that produces anything other than exactly one value is an error rather
than a silent choice, because the failure it would otherwise cause --- a
mis-sorted array from a comparator, an ignored event --- is invisible at the
call site.  A \code{void} callback is the exception: it must produce nothing.

Note that \code{writeline} prints rather than yields, so ordinary tracing inside
a callback does not trip this rule; bare expressions do.

\subsection{Threading}

The engine is single-threaded --- its scope stack is a plain stack, and forks
clone rather than lock --- so a callback is only supported when the library
invokes it on the same thread that called in.  That covers the common cases:
comparators, GLFW's window and error callbacks, and anything dispatched from
inside a call the script itself made.

A callback arriving on a library's own thread (SDL's audio callback, for
example) does \emph{not} run.  It cannot throw either, because unwinding through
native frames is undefined behaviour; instead the violation is recorded and
rethrown once the native call returns, naming both threads.  Failures raised
inside a callback are carried the same way, so a \code{catch} around the native
call sees them.

\subsection{Restrictions}

\code{ref} and \code{out} parameters are rejected: the value would have to be
written back into the caller's memory after the body ran, and a silently ignored
\code{out} is worse than a rejected one.  Declare a pointer and use
\code{read-buffer} / \code{write-buffer} instead.  A \code{buffer[n]} parameter
is likewise rejected --- it is an inbound decoding convention with nothing to
decode here.  The success conventions \code{ok} and \code{count} decide whether
a \emph{call} failed, so they are rejected on a callback, whose return value is
one it produces.

Callbacks are a control plane, not a data plane.  Each invocation re-enters the
engine, which is far more expensive than the C call around it --- fine for
window events and comparisons, unsuitable for per-sample or per-vertex work.

A thunk passed to a library is kept alive for as long as that library is
loaded, so a callee that stores it (GLFW does) keeps working after the
registering call returns.

\section{Module Definitions}
\ikw{module}

\begin{lstlisting}
module Utilities {
    shy func internal-helper() { ... }
    export func banner(title: string) {
        writeline $"=== {$title} ==="
    }
    func default-accessible() { ... }
}

# Usage
Utilities.banner("Report")
\end{lstlisting}

Modules can contain nested types:

\begin{lstlisting}
module Inventory {
    enum StockState { Healthy, Low, Out }
    record Item(Name: string, Quantity: int)
    class Shelf(label: string) { ... }

    func sample-items() {
        return [
            new Item("Widget", 100),
            new Item("Gadget", 5)
        ]
    }
}

# Access via dot notation
var items = Inventory.sample-items()
var state = Inventory.StockState.Healthy
\end{lstlisting}

\subsection*{Module-Qualified Command Dispatch}

Functions exported from a module may also be invoked in command position
using \code{module.function} syntax---no \code{\$} prefix, arguments
separated by whitespace like any other command:

\begin{lstlisting}
module Geometry {
    func area(r) { return 3.14159 * $r * $r }
}

Geometry.area 5            # 78.53975
\end{lstlisting}

This works for any module-name casing, including identifiers that contain
hyphens (\code{kebab-mod.hi}), underscores, or mixed case.  Nested modules
resolve segment-by-segment (\code{outer.inner.fn}).

\subsection*{Module-Qualified Type Names}
\label{sec:module-qualified-types}

A type declared inside a module may be named from outside it by its
qualified path, in every position a type name is accepted---including a
variable's type annotation.  Nested modules resolve segment-by-segment, the
same rule as command dispatch:

\begin{lstlisting}
module Outer {
    module Inner {
        export type SmallInt = int where (_ >= 0 and _ <= 10) coerce 10
        export class Widget { prop Name = "w" }
    }
}

var a: Outer.Inner.SmallInt = 5     # 5
var b: Outer.Inner.SmallInt = 99    # 10 --- the refinement's coercion runs
var w: Outer.Inner.Widget = (new Outer.Inner.Widget())
\end{lstlisting}

The qualified name resolves to the same definition the unqualified name
would, so a refinement type used as a qualified annotation still applies its
predicate and its coercion, and still rejects a value it cannot coerce.

\subsection*{Modules That Shadow CLR Types}

A module may be named after a CLR type---\code{Math}, \code{Console}---and
inside it that name refers to the module.  Its own exports win, and the
shadowed type stays reachable: a member that the module does not export is
looked up on the CLR type of the same name.

\begin{lstlisting}
module Math {
    export func Clamp(a, b, c) { return "module-wins" }
    export func widest() { return Math.Max(3, 7) }
}

Math.Clamp(1, 2, 3)        # module-wins --- the export
Math.widest()              # 7 --- System.Math.Max, not shadowed away
\end{lstlisting}

This matters most inside the module's own body, where the shadowing is
unavoidable: a refinement type declared in \code{module Math} whose coercion
calls \code{Math.Clamp} would otherwise have no way to reach
\code{System.Math}.  A member found on neither the module nor a shadowed type
is still an error rather than a null.

\subsection*{Partial Modules}
\ikw{partial}

A module marked \code{partial} may be declared more than once; the
declarations merge into one module.  Every declaration must carry
\code{partial}---extending a module that was not declared partial raises
\code{tosh.runtime.partial\_mismatch}, matching the rule for classes,
records, and structs.

\begin{lstlisting}
partial module Sys {
    export func alpha() -> string { return "from-a" }
}

partial module Sys {
    export func beta() -> string { return "from-b" }
}

Sys.alpha()                # from-a
Sys.beta()                 # from-b
\end{lstlisting}

Parts merge in declaration order, and each part sees what earlier parts
exported, so a later part can build on an earlier one rather than merely
sit beside it:

\begin{lstlisting}
partial module Sys {
    export func base-name() -> string { return "core" }
}

partial module Sys {
    export func label() -> string { return $"[{(base-name())}]" }
}

Sys.label()                # [core]
\end{lstlisting}

\subsection*{Splitting a Partial Declaration Across Files}

Partial declarations---modules, classes, records, and structs alike---may be
split across separate files and assembled by \code{require}.  Both the bare
and the named import form work, in any order:

\begin{lstlisting}
# sys-core.tosh
partial module Sys {
    export func alpha() -> string { return "from-core" }
}

# sys-extra.tosh
partial module Sys {
    export func beta() -> string { return "from-extra" }
}

# main.tosh
require Sys from "./sys-core.tosh"
require Sys from "./sys-extra.tosh"

Sys.alpha()                # from-core
Sys.beta()                 # from-extra
\end{lstlisting}

The parts share one export table rather than being copied, so every
reference to the module observes the merged state regardless of which file
declared the member being used.

A declaration \emph{without} \code{partial} does not merge---it replaces
any previous declaration of that name, which is what makes redefining a
module or class at the prompt behave as expected.  Members of the replaced
declaration are gone.  This is the reason \code{partial} is required rather
than inferred.

\section{Class Definitions}
\ikw{class}\ikw{prop}

\begin{lstlisting}
class Point(x: double, y: double) {
    prop X: double = $x
    prop Y: double = $y

    # Computed property (evaluated on each access)
    prop Magnitude => (Math.Sqrt(($this.X * $this.X) + ($this.Y * $this.Y)))

    func Distance(other) -> double {
        var dx = $this.X - $other.X
        var dy = $this.Y - $other.Y
        return (Math.Sqrt(($dx * $dx) + ($dy * $dy)))
    }

    shared func Origin() { return new Point(0.0, 0.0) }
}
\end{lstlisting}

\begin{lstlisting}[title={Using classes}]
var p = new Point(3.0, 4.0)
echo $p.Magnitude              # 5
echo (Point.Origin())          # Point

var q = new Point(6.0, 8.0)
echo ($p.Distance($q))         # 5
\end{lstlisting}

Class features:
\begin{itemize}
  \item \textbf{Primary constructor}---parameters after the class name.
    They are in scope for property initializers.
  \item \textbf{Explicit constructors}---a member named after the class,
    \code{ClassName(params) \{ ... \}}.  A class may declare several, and they
    overload on their parameter types.
  \item \textbf{Stored properties}---\code{prop Name: Type = value}.
  \item \textbf{Computed properties}---\code{prop Name => (expr)} (type annotation is inferred).
  \item \textbf{Accessor blocks}---\code{prop Name \{ get ... set ... \}}.  Each
    accessor takes either an arrow body (\code{get => (expr)}) or a brace body
    (\code{get \{ ... \}}), the latter holding as many statements as it needs.
    Inside \code{set}, the incoming value is \code{\$value}.
  \item \textbf{Methods}---\code{func Name(params) \{ ... \}}.
  \item \textbf{Static methods}---\code{shared func Name(params) \{ ... \}} (also accepts \code{static}).
  \item \textbf{Self-reference}---\code{\$this} inside methods.
  \item \textbf{Visibility}---\code{shy} for private members.
  \item \textbf{Instantiation}---\code{new ClassName(args)}.
\end{itemize}

\subsection*{Reaching Members from Inside the Class}
\ikw{this}

A member is always reached through a qualifier, including from the class's own
code.  An instance member is reached through \code{\$this.}, a static one through
the class name:

\begin{lstlisting}
class Counter {
    prop Count: int = 0
    shared prop Limit: int = 10

    func Step() { $this.Count = $this.Count + 1 }   # instance: $this.
    prop AtLimit => ($this.Count >= Counter.Limit)  # static: class name
}
\end{lstlisting}

A bare name in a class body is not a member reference.  It is resolved the way
any other command head is---against builtins, functions, and \code{\$PATH}---so
\code{Count} inside \code{Counter} names no member and reports
\code{tosh.bind.unknown\_command}.  The rule is uniform: a bare name fails from a
static position and an instance one alike, and the diagnostic names the
qualified form to write instead.

This is what allows a class to run shell commands in its methods without its own
members shadowing them: a class declaring \code{prop git} can still call
\code{git status}.

\begin{lstlisting}[title={A primary-constructor parameter is not a member}]
class Point(seed: double) {
    prop X: double = $seed       # in scope here: `$seed` or `seed`
    func Show() { return $seed } # not in scope: initializers only
}

var p = new Point(3.0)
echo $p.X                        # 3
echo $p.seed                     # error: no member 'seed'
\end{lstlisting}

A primary-constructor parameter is in scope in a \emph{stored} property
initializer and in a later parameter's default, and nowhere else in the body.
It does not become a member.  Declare a property from it, as
\code{prop X: double = \$seed} above does, to reach the value from the rest of
the class.

\begin{lstlisting}[title={Where a primary-constructor parameter reaches}]
class P(x: int, y: int = 2) {
    prop A = ($x + $y)        # stored initializer, and a later default: in scope
    prop B => $x              # computed: evaluated per access, after construction
    func g() { return $x }    # method body: same
}
\end{lstlisting}

The reason is when each runs.  A stored initializer runs \emph{while} the value
is being built, with the parameters still bound; a computed property, an
accessor block, a method body and a static initializer all run afterwards, and
a constructor parameter is a local of the construction that was never stored.
Referring to one from those positions reports that it is a constructor
parameter and is not in scope, rather than that the variable is undeclared.

Member access is case-insensitive, so \code{\$p.x} above reaches \code{X}.  A
parameter that differs from a property only in case is therefore easy to mistake
for a reachable one; the two are unrelated.

\subsection*{Chaining to the Primary Constructor}
\ikw{this}

A class may declare a primary constructor and explicit constructors together.
When it does, an explicit constructor reaches the primary one with
\code{\$this(...)}, which must be the first statement in its body:

\begin{lstlisting}
class Point(x, y) {
    prop X = $x
    prop Y = $y

    ## Construct from a single scalar: the same value on both axes.
    Point(size) { $this($size, $size) }
}

(new Point(2, 3)).X        # 2
(new Point(4)).Y           # 4
\end{lstlisting}

The chain binds the primary parameters \emph{before} property initializers run,
which is what lets \code{prop X = \$x} work no matter which constructor was
called.  Without it, an initializer that reads a primary parameter fails when
construction comes in through an explicit constructor, because the primary
parameters were never bound.

\code{\$this(...)} mirrors \code{\$super(...)}: same position rule, same
once-only rule, pointed at this class's own primary constructor rather than its
base class.  The explicit constructor's parameters are visible to the chain
arguments---\code{\$this(\$a + \$b)} is the usual shape---and the arguments are
checked against the primary signature exactly as a direct \code{new} would be.

A chain does not replace the constructor body; the rest of the body runs after
it.  Note also that chaining does not permit an ambiguous pair: a primary and an
explicit constructor of identical signature remain a declaration error, because
a call would still have two candidates and no way to choose.

\subsection*{Constructor Overloads}

Constructors overload on their parameter \emph{types}, not on how many
parameters they take.  Two constructors may share an arity as long as a reader
and the resolver can tell them apart:

\begin{lstlisting}
class G {
    prop X: string = ""
    G(n: int)    { $this.X = $"int:{$n}" }
    G(s: string) { $this.X = $"str:{$s}" }
}

(new G(7)).X               # int:7
(new G("hi")).X            # str:hi
\end{lstlisting}

The primary constructor participates as one more overload, so it may sit beside
explicit constructors of a different signature:

\begin{lstlisting}
class H(x: int) {
    prop X: string = "primary"
    H(s: string) { $this.X = $"str:{$s}" }
}

(new H(7)).X               # primary
(new H("hi")).X            # str:hi
\end{lstlisting}

Two constructors with an \emph{identical} signature are rejected where they are
declared, with \code{tosh.runtime.duplicate\_constructor}---including the case
where an explicit constructor repeats the primary one:

\begin{lstlisting}
class C(x: int) {
    C(y: int) { }          # error: same signature as the primary constructor
}
\end{lstlisting}

The check is a declaration rule rather than a call-site one because such a class
can never be constructed at that signature: the error belongs where the mistake
is, not at every \code{new}.

\subsection{Class Modifiers}
\ikw{sealed}\ikw{hollow}\ikw{hermit}\ikw{strict}\ikw{partial}

Class-level modifiers appear before the \code{class} keyword and control
the class's overall behaviour.

\begin{description}
  \item[\code{sealed}] Prevents the class from being inherited.
    A sealed class cannot appear as a base class.
  \item[\code{hollow}] Marks the class as \emph{abstract}.
    It cannot be instantiated directly; subclasses must override all hollow methods.
  \item[\code{hermit}] Marks the class as \emph{static-only}.
    All members are auto-promoted to shared; constructors are not allowed;
    the class cannot be instantiated.
  \item[\code{strict}] Makes every property in the class \emph{read-only}
    after initialisation, as if each were individually marked \code{fixed}.
  \item[\code{partial}] Allows the class definition to be split across
    multiple declarations, including declarations in separate files
    assembled by \code{require}.  All declarations must carry the
    \code{partial} modifier.  Properties and methods are merged; duplicate
    property names are silently skipped; methods support overloading.
\end{description}

\noindent Example:
\begin{lstlisting}
sealed class Config {
    prop Host = "localhost"
    prop Port = 8080
}

hollow class Shape {
    hollow func area() -> double { }
}

hermit class MathHelper {
    func square(x) { writeline ($x * $x) }
}
MathHelper.square(5)             # 25

strict class Point {
    prop X = 0
    prop Y = 0
}

partial class User { prop Name = "" }
partial class User { func greet() { writeline $"Hi, {$this.Name}" } }
\end{lstlisting}

\subsection{Member Modifiers}
\ikw{shy}\ikw{private}\ikw{shared}\ikw{static}\ikw{fixed}\ikw{readonly}\ikw{vital}\ikw{required}
\ikw{guarded}\ikw{protected}\ikw{overrule}\ikw{override}\ikw{fading}\ikw{obsolete}\ikw{local}
\ikw{raw}\ikw{proud}\ikw{public}\ikw{abstract}\ikw{lazy}

Member-level modifiers appear before \code{prop} or \code{func} inside a
class body.  Several accept a second, C\#-familiar spelling; both forms are
accepted and mean exactly the same thing, so a reader arriving from C\# is not
stopped by vocabulary.  The ToastScript word is listed first throughout.

\begin{description}
  \item[\code{shy} / \code{private}] Hides the member from public inspection and external access.
  \item[\code{shared} / \code{static}] Member belongs to the class rather than an instance.
  \item[\code{fixed} / \code{readonly}] Makes a property read-only after initialisation.
  \item[\code{vital} / \code{required}] Marks a property as required---construction
    fails without a value.
  \item[\code{guarded} / \code{protected}] Restricts access to the defining class
    and its subclasses.
  \item[\code{overrule} / \code{override}] Overrides an inherited method from a parent class.
  \item[\code{lazy}] Defers the property initialiser until first access;
    the result is cached.
  \item[\code{fading} / \code{obsolete}] Marks the member as deprecated; emits a
    warning to stderr on use.
  \item[\code{local}] Restricts visibility to the defining assembly
    (internal).
  \item[\code{raw}] Marks a method for unsafe/native interop.
  \item[\code{proud} / \code{public}] Explicitly marks a member as public
    (no-op, members default to public).
  \item[\code{hollow} / \code{abstract}] (on a method) Declares an abstract method that subclasses must overrule.
    An empty body \code{\{ \}} is required: \code{hollow func name() \{ \}}.
\end{description}

\noindent \textbf{Canonical aliases.}  Every flavored modifier has an
equally-valid canonical alias drawn from the wider .NET / object-oriented
vocabulary; either form is accepted at parse time and produces identical
semantics.  Use whichever reads better in context.  The pairs are:
\code{shy}/\code{private}, \code{proud}/\code{public},
\code{guarded}/\code{protected}, \code{shared}/\code{static},
\code{fixed}/\code{readonly}, \code{vital}/\code{required},
\code{overrule}/\code{override}, \code{hollow}/\code{abstract},
\code{fading}/\code{obsolete}, \code{hermit}/\code{static} (class-level).
The same canonical/flavored equivalence applies to class-level modifiers
(\code{abstract}/\code{hollow}, \code{static}/\code{hermit}).

\noindent Example:
\begin{lstlisting}
class Product {
    vital prop Name: string
    fixed prop Id = 0
    lazy prop Metadata = load_metadata($this.Id)
    shy prop _cache = []
    guarded func validate() { echo "checking" }
    fading prop OldName = "use NewName"
}
\end{lstlisting}

\subsection{Static Members}
\label{sec:static-members}

A property or method marked \code{shared} / \code{static} belongs to the
class rather than to any instance, and is reached through the class name:

\begin{lstlisting}
class Counter {
    static prop Total = 0
    static func describe() { return "counted" }
}

echo Counter.Total          # 0
Counter.Total = 5
echo Counter.Total          # 5
\end{lstlisting}

\noindent \textbf{A static path carries no \code{\$}.}  \code{\$name} refers
to a \emph{variable}; a bare dotted name refers to a \emph{type}.  That rule
already governed reading (\code{Math.PI}, \code{Reactor.Fuel.Mox}), and it
governs assignment identically: \code{Counter.Total = 5} writes a static,
while \code{\$counter.Total = 5} writes a member of the variable
\code{\$counter}.

Because the two spellings are the same shape, the decision cannot be made
before anything runs.  A dotted target left of \code{=} is resolved when the
statement executes, and a variable of that name wins: with
\code{var person = \{| Name = "ada" |\}} in scope,
\code{person.Name = "toast"} reports
\code{tosh.runtime.variable\_reference\_requires\_dollar} and suggests
\code{\$person.Name}, exactly as reading \code{person.Name} always has.  A
head that names neither a type nor a variable reports
\code{tosh.runtime.unknown\_static\_assignment\_target}.

\noindent \textbf{One slot per declaration.}  A static declared on a base
class is a single value shared with every subclass, not a copy per subclass.
Reading and writing agree on where it lives:

\begin{lstlisting}
class Base { static prop S = 1 }
class Derived extends Base { }

Derived.S = 7
echo Base.S                 # 7
echo Derived.S              # 7
\end{lstlisting}

\noindent \textbf{The instance rules apply unchanged.}  A static property
with a \code{set} accessor runs it instead of storing; one with only a
\code{get} accessor is read-only; and \code{fixed static} refuses assignment
after the declaration's own initialiser has run.  A static that answered
differently from an instance property would be a second set of rules for no
reason.

\begin{lstlisting}
class Config {
    fixed static prop Version = "1.0"
    static prop Raw = 0
    static prop Level {
        get { return Config.Raw }
        set { Config.Raw = $value }
    }
}

Config.Level = 3
echo Config.Level           # 3
Config.Version = "2.0"      # error: fixed and cannot be reassigned
\end{lstlisting}

\noindent Assignment reaches nested types and CLR statics by the same path:
\code{Outer.Inner.V = 9} and \code{System.Environment.ExitCode = 2} both
work, the path being split at the longest prefix that names a type.  A CLR
\code{const} or \code{readonly} field is reported as read-only rather than as
missing, since it can still be read.

\section{Generic Classes}
\label{sec:generic-classes}

A class declaration may introduce one or more \emph{type parameters}
inside angle brackets after the class name.  Type parameters can be used
anywhere a type annotation is accepted: primary-constructor parameters,
property types, method parameter and return types, and the
\code{extends} clause of a derived class.

\begin{lstlisting}
class Box<T>(initial: T) {
    prop value: T = $initial
    func unwrap() -> T { return $this.value }
    func set(v: T) { $this.value = $v }
}

var bi = new Box<int>(42)
echo $bi.unwrap()              # 42

var bs = new Box<string>("hi")
echo $bs.unwrap()              # hi
\end{lstlisting}

\subsection*{Instantiation}

\code{new ClassName<arg1, arg2, \ldots>(ctorArgs)} creates an instance
whose type parameters are bound to the supplied CLR types.  The
type-argument list must match the class's declared arity exactly;
mismatches \textemdash{} too few, too many, an empty
\code{<>} list, or omitting the angle brackets entirely on a class
that declares type parameters \textemdash{} raise an instantiation
error.

\subsection*{Strict (no-coercion) bindings}

When a constructor parameter, method parameter, method return value, or
property type is declared as a class type parameter (e.g.\ \code{x: T}),
the engine performs a \emph{strict} \code{IsInstanceOfType} check at
each use site against the bound CLR type --- it does \emph{not} run
the standard value-conversion path that applies to ordinary
annotations.  In particular:

\begin{itemize}
  \item \code{new Box<string>(42)} rejects with
    \code{tosh.runtime.annotation\_conversion\_failed} rather than
    silently stringifying \code{42} to \code{"42"}.
  \item \code{new Box<double>(9)} rejects rather than widening
    \code{int} to \code{double}.
  \item Reassignment to \code{\$this.value} where \code{value: T} is
    bound goes through the same strict check.
\end{itemize}

\noindent Type-parameters whose binding does \emph{not} resolve to a
known CLR type (rare; usually a forward-declared user type) are
treated nominally --- any value is accepted, and the binding only
participates in display.

\subsection*{Inheritance}

A subclass can pass type arguments through to its base, propagate its
own type parameters, or fix the base's parameters to concrete types:

\begin{lstlisting}
class _Point<T1, T2> {
    hollow prop X: T1
    hollow prop Y: T2
}

class Point2D<T1, T2> extends _Point<T1, T2> {
    overrule prop X: T1
    overrule prop Y: T2

    Point2D<T1, T2>(x: T1, y: T2) {
        $this.X = $x
        $this.Y = $y
    }
}

var p = new Point2D<int, int>(3, 4)
echo $p.X                      # 3
\end{lstlisting}

Bindings flow through the inheritance chain: when an instance of
\code{Point2D<int, int>} accesses an inherited member declared on
\code{\_Point}, the engine resolves \code{T1} and \code{T2} against
the base's type-argument list using the child's bindings.

\subsection*{Generic annotations}

Anywhere a type annotation is accepted, the form
\code{ClassName<arg1, arg2, \ldots>} refers to the user-defined
generic class \code{ClassName}.  Annotations with this shape are
recognised before falling through to the CLR type loader (where
multi-arg names like \code{Foo<int, int>} would otherwise produce a
\code{Type.GetType} error treating commas as type/assembly separators).
A value satisfies the annotation when it is a
\code{ToshClassInstance} whose definition (or any ancestor in the
inheritance chain) names \code{ClassName}; the per-instance type-argument
strings are not currently validated against the annotation strings.

\subsection*{Compiled mode}

Generic classes do not emit a CLR shell type at compile time.  Instead,
the compiler registers the class via source-replay and emits
\code{new}-expressions through a typed host overload\\
\code{ToshHost.NewObject(typeName, bareTypeName, string[] typeArgs, object?[] args)}\\
which delegates to the engine's reification path.  This means
generic classes behave identically in REPL and compiled execution.

\subsection*{Type-Parameter Constraints}

A \code{where T: <Constraint>[, <Constraint>\ldots]} clause may follow
the class header to restrict acceptable type arguments.  Built-in
constraints are summarised below; multiple \code{where} clauses may
follow one another to constrain different type parameters.  Unknown
constraint names are accepted conservatively (reserved for future
user-defined constraints).

\begin{center}
\begin{tabular}{L{3.6cm}L{9cm}}
\toprule
\textbf{Constraint} & \textbf{Satisfied by} \\
\midrule
\code{Numeric} / \code{Number} / \code{INumber} &
  \code{int}, \code{long}, \code{short}, \code{byte}, signed/unsigned variants,
  \code{float}, \code{double}, \code{decimal}, \code{Half}, \code{BigInteger} \\
\code{Add} / \code{Sub} / \code{Mul} / \code{Div} &
  Any numeric type, or any CLR type with a matching \code{op\_*} static method \\
\code{Comparable} & Any type implementing \code{IComparable} \\
\code{Eq} & Always satisfied (placeholder) \\
\bottomrule
\end{tabular}
\end{center}

\begin{lstlisting}
class Box<T>(initial: T) where T: Numeric {
    prop value: T = $initial
    func bump(amount) { $this.value = $this.value + $amount }
}

var bi = new Box<int>(10);     $bi.bump(5)     # 15
var bf = new Box<double>(1.5); $bf.bump(2.5)   # 4.0
# new Box<string>("hi")  -> rejected: 'string' does not satisfy 'Numeric'
\end{lstlisting}

The same constraint names also work as right-hand operands for the
\code{is} / \code{is-not} operators on values, so runtime checks reuse
the same registry as compile-time generic-parameter validation:

\begin{lstlisting}
var x = 42
$x is Numeric           # true
$x is Comparable        # true
"hello" is Numeric      # false
$x is-not Numeric       # false
\end{lstlisting}

\section{Inheritance, Interfaces, and Traits}
\ikw{extends}\ikw{fulfills}\ikw{implements}\ikw{uses}

Classes can extend another TōSh class, fulfill one or more interfaces, and use
one or more traits.  \code{implements} is accepted as an alias for
\code{fulfills}.  Parent constructors can be supplied in the \code{extends}
clause or called from the constructor with \code{\$super(...)}.
Construction proceeds exactly once per class layer, from the root base class
to the most-derived class.  The preferred form is
\code{extends Base(args)}.  A direct \code{\$super(args)} call is retained as
an alternative for an explicit constructor, but it must be that constructor's
first executable statement and must not be combined with arguments in the
\code{extends} clause.  If neither form is present, TōSh implicitly invokes a
matching zero-argument base constructor; a base that requires arguments
produces a diagnostic.

\begin{lstlisting}
interface Printable {
    func print()
}

trait Named {
    prop Name = "anonymous"
    func label() { return $this.Name }
}

class Report(title: string) fulfills Printable uses Named {
    prop Title = $title
    func print() { return $this.Title }
}

var r = new Report("Daily")
echo ($r is Printable)        # true
echo ($r is Named)            # true
\end{lstlisting}

\section{Interface Definitions}
\ikw{interface}

Interfaces declare required method signatures.  They cannot be instantiated.
When a class \code{fulfills} an interface, TōSh validates that the class has
each required method by name and arity.

\begin{lstlisting}
interface Runnable {
    func run()
    func stop()
}

class Job fulfills Runnable {
    func run()  { echo "running" }
    func stop() { echo "stopped" }
}
\end{lstlisting}

\section{Trait Definitions}
\ikw{trait}

Traits describe reusable requirements and optional defaults.  A trait may
declare required properties/methods, or provide default property values and
method bodies.  Classes using the trait must supply the required members; any
defaults not already present on the class are injected into the class.

\begin{lstlisting}
trait Timestamped {
    prop CreatedAt = date now
    func age() { return ((date now) - $this.CreatedAt) }
}

class Note uses Timestamped {
    prop Text = ""
}
\end{lstlisting}

A trait member is written the way a class member is: a return type with
\code{->}, a default body with \code{=>} or braces, and a required property with
\code{prop name: Type}.

\begin{lstlisting}
trait Display {
    func render() -> string          # required, with a declared result
    func label() -> string => "?"    # default body
    prop Name: string                # required property
}
\end{lstlisting}

\subsection{What a declared type requires}

A trait's declared types are a \textbf{contract}, checked where the class is
declared rather than where a member is called.

\begin{itemize}
  \item A \textbf{return type} is covariant: the class may return the declared
        type or one derived from it.  Narrowing a result never surprises a caller
        holding the trait.
  \item A \textbf{parameter} must name the same type.
  \item A \textbf{property} must name the same type.  A property is written as
        well as read, so narrowing it is unsound: code holding the trait could
        assign the declared type into what the class narrowed.
  \item An \textbf{undeclared} type on either side agrees with anything.  A trait
        that says nothing constrains nothing, and a class that says nothing has
        not contradicted the trait --- it has only declined to repeat it.
\end{itemize}

An alias and its CLR spelling name one type and agree, so \code{int} satisfies
\code{Int32}.  Interfaces are checked by the same rules; being method-only, the
return and parameter rules are the whole of it for them.

\section{Union Definitions}
\ikw{union}

Unions define closed, tagged reference types.  The runtime representation is an
abstract union base class with one sealed class per variant.  This representation
is used for both flat and recursive unions; there is no implicit value-layout or
\code{struct union} form.  A future value-layout form, if added, must be an explicit
declaration kind rather than changing the layout of an existing \code{union}.

Unit variants (no fields) are accessed as static members.  Variants with fields
are constructed as static calls.  Every union instance exposes \code{Variant}
(also aliased as \code{Tag}) plus any fields declared on its variant.

\begin{lstlisting}
union Result {
    Ok(value: int)
    Error(message: string)
    None
}

var success = Result.Ok(42)
echo $success.Variant        # Ok
echo $success.value          # 42

var failure = Result.Error("not found")
echo $failure.message        # not found

var empty = Result.None
echo $empty.Variant          # None
\end{lstlisting}

A named payload field uses the ordinary \code{name: Type} annotation.  A
type-only positional payload is also accepted and receives the tuple-style name
\code{Item1}, \code{Item2}, and so on.  Construction converts and checks every
annotated payload before the value becomes observable; a refusal names the
union, variant, and field.

Unions may declare type parameters.  A direct type-parameter payload can be
inferred from its value, or all union type arguments can be supplied on the
variant constructor.  An explicit list is required when the selected variant
does not carry enough information to infer every parameter (including a generic
unit variant).  Nested type arguments use the same type-name grammar as generic
classes.

\begin{lstlisting}
union Result<T, E> {
    Ok(T)                 # positional field: Item1
    Error(error: E)       # named field: error
}

union Option<T> { Some(T) None }

var inferred = Option.Some(42) # T is int when every parameter can be inferred
var nested = Result.Ok<list<int>, string>([1, 2])
echo $nested.Item1[0]
\end{lstlisting}

A payload may name the union being declared, so recursive trees are ordinary
union values rather than a special case:

\begin{lstlisting}
union Expr {
    Lit(value: double)
    Add(left: Expr, right: Expr)
}

var expression = Expr.Add(Expr.Lit(1), Expr.Lit(2))
\end{lstlisting}

\subsection*{Pattern Matching on Unions}

Use \code{switch} on the \code{Variant} string to dispatch on the active
variant:

\begin{lstlisting}
func describe(r) {
    switch ($r.Variant) {
        case "Ok"    { echo $"Success: {$r.value}" }
        case "Error" { echo $"Failed: {$r.message}" }
        case "None"  { echo "No value" }
    }
}

describe (Result.Ok 100)        # Success: 100
describe (Result.Error "oops")  # Failed: oops
describe Result.None            # No value
\end{lstlisting}

\subsection*{Type Checking}

Union instances respond to \code{is} checks against their union type:

\begin{lstlisting}
echo ($success is Result)    # true
echo ($success is-not Result)# false
\end{lstlisting}

\section{Struct Definitions}
\ikw{struct}\ikw{fluid}

Structs are shell-defined value types with positional fields and optional class
style members.  By default, struct fields are read-only after construction.
Mark a struct \code{fluid} to make fields writable.  \code{partial} structs can
be split across declarations; every declaration must be marked \code{partial}.

\begin{lstlisting}
struct Point(x: int, y: int) {
    func sum() { return ($this.x + $this.y) }
}

var p = new Point(3, 4)
echo $p.x
echo ($p.sum())              # 7

fluid struct Counter(value: int)
var c = new Counter(0)
$c.value = 1
\end{lstlisting}

\section{Record Definitions}
\ikw{record}

Records are lightweight named types with positional fields:

\begin{lstlisting}
record Item(
    Name: string,
    Quantity: int,
    Category?: string = "General",
    Tint?: string = "White"
)

var widget = new Item("Widget", 50)
var custom = new Item("Gadget", 10, "Electronics", "Blue")
echo $widget.Name        # Widget
echo $custom.Category    # Electronics
\end{lstlisting}

Records feature value equality, optional fields with \code{?}, and default
values.

\section{Nested Types}

A class body may declare a type as well as members.  \code{enum},
\code{class}, \code{struct}, \code{record}, \code{union}, \code{interface}
and \code{trait} are all accepted, and are written exactly as they would be at
the top level:

\begin{lstlisting}
class Reactor {
    enum Fuel : int {
        Mox     = 3
        Uranium = 8
    }

    prop Loaded: Fuel = Fuel.Mox
}

var r = new Reactor()
echo $r.Loaded                          # Mox
echo Reactor.Fuel.Uranium               # Uranium
\end{lstlisting}

Inside the class the qualification is unnecessary --- the code is already in
\code{Reactor} --- so \code{Fuel} and \code{Fuel.Mox} resolve directly in
property initialisers, method bodies and constructors, as the example above
does.  Outside it, the type is reached through the class that declares it.

A nested type is a static member of the class that declares it, so it is
reached through that class --- \code{Reactor.Fuel} --- and its own members
follow by ordinary access: \code{Reactor.Fuel.Uranium}.  The name does not
appear in the scope surrounding the class, which is the point of nesting;
\code{Fuel} alone resolves only inside \code{Reactor}.

A qualified name is also a type name, so a nested class can be constructed and
annotated with it, at any depth:

\begin{lstlisting}
class Outer {
    class Inner { prop V = 7 }
}

var i: Outer.Inner = new Outer.Inner()
echo $i.V                               # 7
\end{lstlisting}

\code{shy} applies as it does to any other member: a shy nested type is
visible inside its declaring class and refused from outside.

\section{Enum Definitions}
\ikw{enum}

\begin{lstlisting}
enum StockState { Unknown, Healthy, Low, Out }

enum Permissions : int {
    None = 0
    Read = 4
    Write = 2
    Execute = 1
}

var state = StockState.Healthy
if ($state == StockState.Low) {
    echo "Reorder needed"
}
\end{lstlisting}

\subsection{Flag Enums}
\ikw{flags}

An enum declared \code{flags} is one whose members are meant to be combined. The
bitwise operators over its members yield a value of the same enum rather than a
number, and that value names itself from the bits it carries:

\begin{lstlisting}
flags enum Permissions : int {
    None    = 0
    Execute = 1
    Write   = 2
    Read    = 4
}

var access = Permissions.Read bor Permissions.Write
echo $access                        # Write, Read
echo ($access as int)               # 6
echo ($access has Permissions.Read) # true
\end{lstlisting}

The name is composed from the underlying value in declaration order, so
\code{band} and \code{bxor} name their results too, and a value whose bits are
not exactly covered by the members falls back to the number.

Without \code{flags} the same expression yields the underlying integer:
combining members is a claim about the type that the author has not made, so the
result is a number and not a member. Combining members of two different enums is
an error either way.

\code{has} tests that \emph{every} bit of the right operand is set in the left,
so a composite flag answers true only when it is wholly present. A zero flag is
vacuously present, matching \code{Enum.HasFlag}.

\section{Extension Methods}
\ikw{extend}

\code{extend} adds methods to a type it does not own.  \code{\$this} is the
receiver.

\begin{lstlisting}
extend Color {
    func ToGl()  -> GlColor => Gfx.ToGl($this)
    func Darken(by: double) -> Color => Gfx.Lerp($this, Black, $by)
}

$tint.ToGl()
$tint.Darken(0.2)
\end{lstlisting}

An extension can only ever \emph{add} a name.  Dispatch reaches it last --- after
the receiver's own methods, after inherited ones, and after a callable held in a
property --- so no call that already worked can change meaning.

Extensions are registered when the declaration runs, so a \code{require}d module
brings its extensions with it.  An extension may declare only methods: it has
nowhere to put state.

\section{Event Definitions}
\ikw{event}\ikw{raise}\ikw{required}

Events are named message types with a fixed set of payload fields.  Any code
that can see the event name can \code{raise} it; any function in scope can
subscribe with \code{handles} (see Section~\ref{ch:functions}).

\textbf{Defining events:}

\begin{lstlisting}
event BuildCompleted {
    Project  = ""
    Duration = (timespan 0s)
    Success  = true
}

# Required event --- error if raised with no handlers registered
required event CriticalError { Message = "", Code = 0 }

# Local event --- automatically unregistered when the declaring scope exits
local event ScopedNotification { Text = "" }
\end{lstlisting}

\textbf{Raising events:}

\begin{lstlisting}
raise $BuildCompleted ({|
    Project  = "MyApp",
    Duration = (timespan 5s),
    Success  = true
|})
\end{lstlisting}

\textbf{Subscribing (in any visible scope):}

\begin{lstlisting}
func on-build(e) handles BuildCompleted {
    if ($e.Success) {
        writeline $"Build OK: {$e.Project} in {$e.Duration}"
    } else {
        writeline $"Build FAILED: {$e.Project}"
    }
}
\end{lstlisting}

Handler modifiers (\code{priority}, \code{when}, \code{once}) control
dispatch order, conditional execution, and single-fire semantics---see
Section~\ref{ch:functions} for the full syntax.  Dispatch order runs from the
lowest \code{priority} number to the highest, with unprioritised handlers
last.

Fields not supplied in the \code{raise} payload keep their declared default
values.  Event fields are read-only inside the handler body.

\label{ch:pipelines}

\section{The Pipeline}

The pipe operator \code{|} connects command stages, sending the output of one
as input to the next:

\begin{lstlisting}
ls -la | where _.Type == file | sort Size | reverse | first 5
\end{lstlisting}

\begin{tipbox}
The current item in pipeline predicates and blocks is \code{\_}. This is
a special implicit variable---you do not need to declare it.
\end{tipbox}

Each stage in a pipeline receives objects (not text). Commands like
\code{where}, \code{sort}, and \code{map} operate on object properties
natively.

\section{Command Substitution}

Capture command output into a variable:

\begin{lstlisting}
var user = $(whoami)            # Capture as string
var count = $(ls | count)       # Capture pipeline result
var files = $(find . -name "*.cs" -type f)
\end{lstlisting}

\section{Subexpressions}

Parentheses group expressions and force evaluation:

\begin{lstlisting}
var result = (2 + 3)
echo (String.Join(" ", ["a", "b"]))
echo ($items | count)
\end{lstlisting}

\section{Ranges}
\iop{..}

\begin{lstlisting}
1..10             # 1, 2, 3, ..., 10 (inclusive)
1..2..10          # 1, 3, 5, 7, 9 (step of 2)
0..5              # 0, 1, 2, 3, 4, 5
10..1             # 10, 9, 8, ..., 1 (auto-descending)
\end{lstlisting}

Ranges are lazy \code{ToshRange} objects implementing
\code{IShellEnumerableObject}.

\section{Comprehensions}
\ikw{where}\ikw{let}

Comprehensions build collections from sequences using a concise
\emph{body}\,\code{<|}\,\emph{clause} syntax.  The clause specifies the
source, an optional filter, and optional intermediate bindings.

\subsection*{Collection Forms}

The opening and closing delimiters determine the output type:

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Syntax} & \textbf{Result type} & \textbf{Evaluation} \\
\midrule
\code{[body <| clause]} & list (array) & eager \\
\code{\{: body <| clause :\}} & set (\code{HashSet}) & eager \\
\code{\{\% key => value <| clause \%\}} & dict & eager \\
\code{(body <| clause)} & \code{LazySequence} & lazy / on demand \\
\bottomrule
\end{tabular}
\end{center}

\begin{lstlisting}
[$x * $x <| for x in 1..5]
# [1, 4, 9, 16, 25]

{: $x * $x <| for x in 1..5 :}
# {1, 4, 9, 16, 25}  -- duplicates removed automatically

{% $x => $x * $x <| for x in 1..5 %}
# {1: 1, 2: 4, 3: 9, 4: 16, 5: 25}

($x * $x <| for x in 1..) | first 5    # lazy -- safe with infinite source
# 1, 4, 9, 16, 25
\end{lstlisting}

\subsection*{Clause Keywords}

\begin{description}
  \item[\code{for name in source}]
    Required.  Iterates \code{source}; the current element is bound to
    \code{name} (no \code{\$} prefix).  Inside the body and subsequent
    clause parts, refer to it as \code{\$name}.

  \item[\code{where condition}]
    Optional filter.  Only items for which \code{condition} is truthy are
    projected through to the body.

  \item[\code{let alias = expr}]
    Optional intermediate binding.  Evaluated once per item after the
    \code{where} filter.  Multiple \code{let} bindings may appear; each is
    visible in subsequent bindings and in the body.

\begin{lstlisting}
[$x <| for x in 1..20 where $x % 3 == 0]
# [3, 6, 9, 12, 15, 18]

[$label <| for x in 1..5 where $x % 2 != 0 let label = $"item-{$x}"]
# ["item-1", "item-3", "item-5"]
\end{lstlisting}
\end{description}

\subsection*{Multi-Clause Forms}

Three syntaxes extend a single \code{for} clause into a multi-variable iteration.

\paragraph{Cartesian product (comma \texttt{,})}
A comma after the source (or its modifiers) introduces a second clause.
Every combination of elements is produced---equivalent to nesting two
\code{for} loops:

\begin{lstlisting}
[($x, $y) <| for x in 1..3, y in ["a", "b"]]
# [(1,"a"), (1,"b"), (2,"a"), (2,"b"), (3,"a"), (3,"b")]

[$x + $y <| for x in [1, 2], y in [10, 20]]
# [11, 21, 12, 22]
\end{lstlisting}

The explicit nested \code{for} keyword produces the same result:

\begin{lstlisting}
[($x, $y) <| for x in 1..3 for y in ["a", "b"]]   # identical
\end{lstlisting}

\paragraph{Parallel / zip (\texttt{||})}
\code{||} between two clauses zips the sources together---one element from
each source per step.  Iteration terminates when the \emph{shorter} source
is exhausted:

\begin{lstlisting}
[$x + $y <| for x in [1, 2, 3] || y in [10, 20, 30]]
# [11, 22, 33]

[$x + $y <| for x in [1, 2, 3] || y in [10, 20]]   # shorter wins
# [11, 22]
\end{lstlisting}

\paragraph{Pattern destructuring (\texttt{(a, b, \ldots)})}
When the source yields tuples or lists, use a parenthesised name list to
bind each element to its own variable:

\begin{lstlisting}
[$a + $b <| for (a, b) in [(1, 2), (3, 4)]]
# [3, 7]

[$a + $b + $c <| for (a, b, c) in [(1, 2, 3), (4, 5, 6)]]
# [6, 15]

# A dictionary is rebuilt by iterating its keys and indexing back into it;
# there is no `entries` command, and piping a dictionary yields the dictionary
# itself rather than its pairs. Note the literal: a dictionary is {% k => v %},
# and the {| ... |} form is a record, which has no `Keys`.
var myDict = {% "a" => 1, "b" => 2 %}
{% $k => ($myDict[$k] * 2) <| for k in $myDict.Keys %}
# {% "a" => 2, "b" => 4 %}
\end{lstlisting}

All four forms compose with \code{where}/\code{let} modifiers and work in
every collection form
(\code{[...]}, \code{\{:~:\}}, \code{\{\%~\%\}}, \code{(~)}).

\section{Live / Streaming Output}
\label{sec:streaming-output}

Long-running commands that emit objects progressively (via \code{yield}
internally) are displayed incrementally in an interactive TTY session.
The REPL automatically promotes a pipeline to \emph{streaming mode} when it
detects a gap of roughly 250\,ms or more between successive output objects.

In streaming mode the REPL renders a live table:

\begin{itemize}
  \item The top border, header row, and mid-border are drawn immediately
        after the first object arrives.
  \item Each subsequent object is appended as a new row in real time.
  \item If a later object causes a column to widen, the entire table is
        redrawn from the top (using cursor-up escape sequences) to keep
        widths consistent.
  \item The closing bottom border is drawn when the command completes or
        is interrupted with \code{Ctrl-C}.
\end{itemize}

\begin{lstlisting}
ping -c 5 www.google.com    # rows appear one per second as replies arrive
tail -f /var/log/app.log    # new rows stream in as lines are written
\end{lstlisting}

Commands that complete quickly (e.g.\ \code{ls}) fall back to the standard
buffered renderer---the gap heuristic ensures short commands are never
artificially slowed. Streaming is automatically disabled when stdout is
redirected to a file or pipe (non-TTY).

\section{Tilde Expansion}
\label{sec:tilde}

A \emph{bareword} argument whose first character is \code{\textasciitilde}
expands to a home directory before the command is invoked.  Unlike glob
expansion, this happens for \textbf{every} command---builtins, user
functions, and external processes alike.  Whether \code{\textasciitilde}
means the home directory is a property of the language, not something each
command decides for itself.

\begin{lstlisting}
echo ~                 # /home/ada
echo ~/projects        # /home/ada/projects
echo ~root             # /root
cd ~                   # changes to the home directory
/bin/echo ~            # the external process receives /home/ada
\end{lstlisting}

Tilde expansion rules:

\begin{itemize}
  \item \code{\textasciitilde} alone, and \code{\textasciitilde/path},
        expand to the current user's home directory.
  \item \code{\textasciitilde name} expands to a configured directory
        alias if one exists, and otherwise to that user's home directory.
        An alias wins, because it was written down on purpose.
  \item A name matching neither is a diagnostic
        (\code{tosh.runtime.unknown\_tilde\_target}) rather than being
        passed through unchanged.
  \item Only \textbf{bareword} arguments are expanded.  Quoted strings
        (\code{"\textasciitilde"}) are never expanded, and neither is a
        variable that happens to hold a tilde---expansion is lexical, so
        it applies to the word as written.
  \item The tilde must be the \emph{first} character of the word.
        \code{notes.txt\textasciitilde} and
        \code{-{}-out=\textasciitilde/x} are left alone.
  \item Tilde expansion runs before glob expansion, so
        \code{\textasciitilde/*.log} searches the home directory.
\end{itemize}

\begin{lstlisting}
# Directory aliases give ~name spellings of your own
$tosh.Config.Shell.Dirs.work = "/srv/projects"
echo ~work/notes.md    # /srv/projects/notes.md

# Quoting is how a literal tilde is written
echo "~"               # prints ~
\end{lstlisting}

\noindent At the start of a command, an expanded tilde is a path like any
other: with \code{auto\_cd} enabled a bare \code{\textasciitilde} changes to
the home directory exactly as a bare \code{/tmp} changes to \code{/tmp}, and
with it disabled both report that the target is a directory rather than a
program.

\section{Glob Expansion}
\label{sec:globs}
\ikw{glob}

When a \emph{bareword} argument to an external process or one of the
builtin commands \code{echo}, \code{write}, \code{writeline}, or
\code{raw} contains the wildcard characters \code{*}, \code{?},
\code{[}, or the extended glob prefix \code{@(}, TōSh expands it
against the file system before the command is invoked.

\begin{lstlisting}
ls *.txt               # expands to all .txt files in $PWD
echo src/**/*.cs       # ** matches any number of path segments
rm build-?.log         # ? matches exactly one character
\end{lstlisting}

Glob expansion rules:

\begin{itemize}
  \item Only \textbf{bareword} arguments are expanded.  Quoted strings
        (\code{"*.txt"}, \code{'*.txt'}) and interpolated strings
        (\code{\$"*.txt"}) are \emph{never} expanded.
  \item If the glob matches no files the literal pattern is passed to
        the command unchanged (no error).
  \item Only commands that implement the implicit-glob contract perform
        expansion.  Pure shell built-ins such as \code{where}, \code{each},
        and \code{sort} do not expand globs---use \code{glob} or
        \code{find} to produce a file list first.
\end{itemize}

\begin{lstlisting}
# Use 'glob' to materialise a list from a pattern in a pipeline
glob "*.log" | where _.Size > 1mb | each { rm $_ }

# Quoted string - no expansion
echo "*.txt"           # prints the literal string *.txt
\end{lstlisting}

\section{Nameof}
\ikw{nameof}\ikw{name-of}

\code{nameof} reports a name as a string, without evaluating it.

\begin{lstlisting}
var x = 42
echo (nameof($x))     # "x"
\end{lstlisting}

Given a member or type path, it reports the \emph{last} segment---the name the
expression asks about---as C\# does:

\begin{lstlisting}
var foo = {| Bar = {| Baz = 1 |} |}
echo (nameof($foo.Bar))       # "Bar"
echo (nameof($foo.Bar.Baz))   # "Baz"

class Counter { shared prop Limit: int = 10 }
echo (nameof(Counter.Limit))  # "Limit"
echo (nameof(Counter))        # "Counter"
\end{lstlisting}

The command form \code{name-of \$foo.Bar} reduces its operand the same way.

A bare name that is also a variable in scope is rejected, since \code{nameof(x)}
beside \code{var x} almost always means \code{nameof(\$x)}:

\begin{lstlisting}
var x = 42
echo (nameof(x))      # error: tosh.runtime.nameof_requires_dollar
\end{lstlisting}

A member path is exempt from that check---its last segment is a member name, and
a variable that happens to share it says nothing about what was written, so
\code{nameof(Counter.Limit)} is valid beside a \code{var Limit}.  An operand with
no name to report, such as a trailing dot, raises
\code{tosh.parser.nameof\_expects\_a\_name}.

\section{Alloc (Native Buffer)}

\begin{lstlisting}
alloc buffer = 1024     # Allocate 1024 bytes of native memory
alloc info = SysInfo    # Or size it from an interop type
\end{lstlisting}

Byte offsets on the buffer helpers are the \code{--at} flag, not a positional
slot:

\begin{lstlisting}
write-buffer $buffer 42 --at 8
read-buffer long $buffer --at 8
read-buffer bytes $buffer --count 16
forget $buffer          # unsets the variable and frees the buffer
\end{lstlisting}

The \code{native-*} names are canonical; \code{alloc}, \code{read-buffer},
\code{write-buffer}, \code{size-of} and \code{offset-of} are blessed aliases.
\code{native-free} deliberately has no short alias, because \code{free} is the
System memory command --- use \code{forget}, which releases the variable and
the buffer together.

With \code{raw struct} and \code{out} parameters, most code needs none of
this: the engine allocates and marshals, and the buffer helpers remain for
genuinely dynamic sizes and raw pointer arithmetic.

See Chapter~\ref{ch:command-catalog} for full native interop commands.

\section{Picking Columns vs Rows}
\label{sec:get-row}

\code{get} and \code{row} form the canonical pipeline-slicing cluster.
\code{get} projects \emph{members} (columns); \code{row} selects
\emph{positions} (rows).  Both are variadic.

\begin{lstlisting}
ls | get Name Size              # column picker -- variadic field projection
ls | get Name                   # single column (yields scalars)
[10,20,30,40,50] | row 2        # row picker -- single index
[10,20,30,40,50] | row 4 0 2    # variadic, yields 50, 10, 30 in requested order
[10,20,30,40,50] | row [3,1,0]  # list literal works too
[10,20,30,40,50] | row 1..3     # contiguous range
\end{lstlisting}

\code{select} and \code{pick} are soft aliases for \code{get}.  Bad
indices in \code{row} throw \code{tosh.row.index\_out\_of\_range}.
\code{row} only materialises the prefix of the pipeline necessary to
satisfy the highest requested index, so it is safe on long but bounded
streams; infinite ranges (\code{row 0..}) are rejected.

\section{Structured Introspection}
\label{sec:introspection}

\code{members} and \code{methods} are the canonical introspection
commands.  Both accept first-argument keywords for filtering and
querying:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Subcommand} & \textbf{Effect} \\
\midrule
\code{has <Name>} & \code{true}/\code{false} for whether the named member exists. \\
\code{get <Name>} & Yields each matching member descriptor (zero-or-more). \\
\code{props}      & Filter to properties only (\code{members} only). \\
\code{fields}     & Filter to fields only (\code{members} only). \\
\code{methods}    & Filter to methods only (\code{members} only). \\
\code{events}     & Filter to events only (\code{members} only; reserved). \\
\bottomrule
\end{tabular}
\end{center}

The keyword may consume a trailing operand; any further arguments are
parsed as type targets, so the piped form and the named-type form are
interchangeable:

\begin{lstlisting}
$obj | members has Length        # bool from a piped instance
$obj | members get FullName      # descriptor record(s)
$obj | members props             # all properties of $obj's type
$obj | methods has ToUpper       # bool

members has Length string        # equivalent: type as trailing arg
methods get ToUpper string       # descriptor for String.ToUpper
\end{lstlisting}

\code{props} and \code{funcs} are top-level shortcuts for
\code{members props} and \code{methods}, respectively.

The verb-form CLR commands (\code{call}, \code{call-method},
\code{get-prop}, \code{get-props}, \code{get-methods}, \code{has-prop},
\code{has-method}, \code{set-prop}, \code{del-prop}) are deprecated
since version \code{26.05.0.10}; they remain registered for backward
compatibility but emit deprecation diagnostics.  Prefer the fluent
member-access syntax (\code{\$obj.Method(\$args)}, \code{\$obj.Prop},
\code{\$obj.Prop = value}) and the introspection cluster above.

\section{System Namespace}

The full \code{System.*} namespace tree is exposed via the CLR resolver
without an \code{import} statement.  This makes \code{System.IO.*} the
canonical handle API for file streams, paths, and binary IO:

\begin{lstlisting}
var fh = System.IO.File.OpenRead "/etc/hostname"
defer { $fh.Dispose() }
var bytes = System.IO.File.ReadAllBytes "/etc/hostname"
var leaf  = System.IO.Path.GetFileName $path
var b64   = System.Convert.ToBase64String $bytes
\end{lstlisting}

\section{Binder Pass}
\label{sec:binder-pass}

Between parse and evaluate, a static binder pass walks the AST and
emits \code{tosh.bind.unknown\_command} diagnostics for command names
that look like typos for registered builtins or aliases (Levenshtein
distance \(\le 1\) for short names, \(\le 2\) for longer).  Same-source
\code{func} declarations are recognised and never flagged.

Strictness depends on context:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Context} & \textbf{Default mode} \\
\midrule
Interactive REPL                 & \code{Warn} (stderr) \\
\code{tosh -c "\ldots"}          & \code{Strict} \\
\code{tosh script.tosh} / \code{source} & \code{Strict} \\
\code{profile.tosh} / \code{autoload/*} & \code{Warn} \\
\bottomrule
\end{tabular}
\end{center}

To bypass the binder entirely (recovery escape hatch; undocumented in
user-facing help), set \code{TOSH\_DISABLE\_BINDER=1}.

\chapter{Scripts and Subcommand Dispatch}
\label{ch:subcommands}
\ikw{subcommand}\ikw{flag}\ikw{arg}\ikw{eager}\ikw{hidden}
% =============================================================================

TōSh has a built-in system for turning a script into a structured CLI tool.
The \code{subcommand} block declares named commands with typed flags and
positional arguments; TōSh handles parsing, validation, and auto-generated
help text automatically.

\section{Subcommand Basics}

A \code{subcommand} block declares one named command.  Its body runs when
the user selects that command on the command line:

\begin{lstlisting}
subcommand greet {
    flag name: string = "World"
    echo $"Hello, {$name}!"
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh myscript.tosh greet            # Hello, World!
tosh myscript.tosh greet --name Alice  # Hello, Alice!
\end{lstlisting}

\subsection*{Arrow form}

A subcommand with parameters and a single-expression body may use the arrow
form.  Parameters in the arrow form are passed directly, not via flags:

\begin{lstlisting}
subcommand greet(name: string) => echo $"Hello, {$name}!"
\end{lstlisting}

\begin{warnbox}
Parameters declared with \code{()} in the arrow form require the
\code{=>} separator.  Using a block body with \code{()} parameters is a
parse error (\code{tosh.parser.subcommand\_params\_require\_arrow}).
\end{warnbox}

\section{Flags and Arguments}

Inside a subcommand body, \code{flag} declares an optional named option and
\code{arg} declares a required positional argument:

\begin{lstlisting}
subcommand deploy {
    arg  host: string
    flag port: int    = 22
    flag user: string = "root"
    flag dry-run: bool = false

    if ($dry-run) {
        echo $"[dry-run] ssh {$user}@{$host}:{$port}"
    } else {
        ssh $"-p{$port}" $"{$user}@{$host}"
    }
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh deploy.tosh deploy myserver
tosh deploy.tosh deploy myserver --port 2222 --user alice
tosh deploy.tosh deploy myserver --dry-run
\end{lstlisting}

\begin{itemize}
  \item \code{flag} values are set with \code{--name value} or \code{--name=value}.
  \item The CLI flag name is exactly the identifier as declared---no
        case folding or kebab-from-snake conversion.  A flag declared
        \code{flag dry-run} is invoked as \code{--dry-run}; \code{flag fooBar}
        as \code{--fooBar}; \code{flag MAX\_RETRIES} as \code{--MAX\_RETRIES}.
  \item Boolean flags may be set with \code{--name} (sets to \code{true}) or
        \code{--no-name} (sets to \code{false}).
  \item \code{arg} values are consumed from the remaining positional tokens in
        declaration order.
  \item \code{--} stops option parsing; all tokens after it are positional.
\end{itemize}

\section{Nested Subcommands}

Subcommands nest to build command trees.  Dispatch descends into the child
whose name matches the first positional token:

\begin{lstlisting}
subcommand git {
    subcommand commit {
        flag message: string = ""
        flag all: bool = false
        echo $"committing: {$message}"
    }

    subcommand push {
        arg remote: string = "origin"
        flag force: bool = false
        echo $"pushing to {$remote}"
    }
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh myscript.tosh git commit --message "initial"
tosh myscript.tosh git push origin --force
\end{lstlisting}

Flags are looked up leaf-to-root: a flag defined on a parent is available to
all its descendants.

\section{Subcommand Modifiers}

Modifiers appear between \code{subcommand} and the name:

\begin{description}
  \item[(none)] Body runs only when this is the chosen leaf of dispatch.
  \item[\code{eager}] Body runs even when execution descends into a child.
    Used for setup work (e.g.\ loading config before a child acts on it).
    May not be combined with \code{hollow}.
  \item[\code{hidden}] Excluded from auto-generated help and ``did you mean''
    suggestions.  Still fully callable.
  \item[\code{hollow}] Pure namespace---body must contain only nested
    \code{subcommand} declarations.  Cannot be instantiated directly.
  \item[\code{vital}] Throws a runtime error if children exist but the user
    did not choose one (instead of showing auto-help).
\end{description}

\begin{lstlisting}[title={eager parent}]
eager subcommand db {
    flag env: string = "production"
    writeline $"Connecting to {$env} database"   # always runs

    subcommand migrate {
        flag dry-run: bool = false
        run-migrations --env $env --dry-run $dry-run
    }

    subcommand seed {
        run-seed-data --env $env
    }
}
\end{lstlisting}

\section{Auto-Help}

Every subcommand automatically supports \code{--help} at any nesting level.
The help output is generated from the \code{flag} and \code{arg} declarations
at the current and ancestor levels.  To opt out of automatic help, declare your
own \code{flag help: bool = false}.

\begin{warnbox}[Doc-comments not yet included in auto-help]
Although \code{\#\#} doc-comments can be written above a \code{subcommand}
block, the current runtime does not attach them to the auto-generated help
output.  Only the structural information (flag names, types, and which
subcommands exist) is shown.  If you need richer descriptions today, write
them in the script body as \code{writeline} output guarded by
\code{if (\$tosh.Script.Help)}.
\end{warnbox}

\begin{lstlisting}[title={Invoking auto-help}]
tosh myscript.tosh --help
tosh myscript.tosh git --help
tosh myscript.tosh git commit --help
\end{lstlisting}

\midrule

\code{tosh.runtime.missing\_script\_argument} & Required positional \code{arg} not provided. \\

\code{tosh.runtime.script\_option\_requires\_value} & Flag that expects a value was given without one. \\

% =============================================================================
\chapter{Overview \& Execution Model}
\label{ch:compile-overview}
% =============================================================================

TōSh runs in two modes: an \emph{interpreter} (\code{ToshEngine}) and an
\emph{ahead-of-time compiler} (\code{Tosh.Compiler}) that emits standard
.NET assemblies. The interpreter is the canonical semantics; the compiler is
a faithfulness-preserving lowering of those semantics onto the CLR. Both
modes share the same lexer, parser, binder, lowerer, and type checker —
only the back end differs.

\section{When each mode runs}
\label{sec:compile-when}

\begin{tabular}{l p{0.65\linewidth}}
\toprule
\textbf{Mode} & \textbf{Triggered by} \\
\midrule
Interpreter (REPL) & \code{tosh}, no positional source. \\
Interpreter (one-liner) & \code{tosh -c "..."}. \\
Interpreter (script) & \code{tosh path/to/script.tosh}. \\
Compiler (CLI) & \code{tosh --compile path.tosh -o out.dll} (\S\ref{ch:compile-cli}). \\
Compiler (MSBuild) & \code{<Project Sdk="Tosh.Sdk">} (\S\ref{ch:compile-msbuild}). \\
\bottomrule
\end{tabular}

\section{Compiler pipeline}
\label{sec:compile-pipeline}

\begin{enumerate}
  \item \textbf{Lex / parse.} Identical to the interpreter; produces a
        \code{ParseResult} with the same syntax tree.
  \item \textbf{Bind / lower.} Identical to the interpreter; produces a
        \code{BoundUnit} containing \code{BoundStatement}s and
        \code{BoundExpression}s.
  \item \textbf{Type check.} The same \code{TypeChecker} runs, but in
        \emph{compile mode} it emits an extra audit pass
        (\code{CheckCompileAnnotations}) for missing or implicit
        \code{dynamic} annotations (\S\ref{ch:compile-types}).
  \item \textbf{Emit.} \code{BoundUnitEmitter} walks the bound tree and
        emits IL into a \code{PersistedAssemblyBuilder}. Each shape is
        gated by a profile/tier check (\S\ref{ch:compile-profiles}).
  \item \textbf{Persist.} The assembly is written to disk; an optional
        reference assembly, apphost wrapper, and single-file bundle are
        produced as requested (\S\ref{ch:compile-cli}).
\end{enumerate}

\section{Parity contract}
\label{sec:compile-parity}

A program that compiles cleanly must, when run, produce the same observable
behaviour as the interpreter would for the same source. Observable here
means: stdout, stderr, exit code, files written by redirection, and values
returned to a hosting C\# caller. Internal scheduling, allocation, and
diagnostics-not-yet-promoted-to-errors are not part of the contract.

The conformance test layer (\S\ref{ch:compile-conformance}) is the
machine-checked expression of this contract.

\begin{tipbox}[Where to look]
The full pipeline lives under \code{src/Tosh.Compiler/} and
\code{src/Tosh.Compiler.Runtime/}. The bound tree the emitter walks is
defined in \code{src/Tosh.Language/Binding/BoundNodes/}.
\end{tipbox}


% =============================================================================
\chapter{Command-Line Interface}
\label{ch:compile-cli}
% =============================================================================

The compiler is invoked through the same \code{tosh} binary that runs the
shell. The first positional argument selects between shell and compile
modes:

\begin{lstlisting}
# Interpret a script.
tosh greet.tosh

# Compile a script to a managed assembly.
tosh --compile greet.tosh -o greet.dll
tosh -C greet.tosh -o greet.dll

# The output path may be left out: this writes greet.dll beside greet.tosh.
tosh --compile greet.tosh
\end{lstlisting}

\section{Flags}
\label{sec:compile-flags}

\begin{tabular}{>{\raggedright\arraybackslash}p{0.34\linewidth} >{\raggedright\arraybackslash}p{0.55\linewidth}}
\toprule
\textbf{Flag} & \textbf{Effect} \\
\midrule
\code{-o PATH}, \code{--output PATH} & Output assembly path. Optional: when it is omitted the assembly is written beside the first input with its extension changed to \code{.dll}. The stem is kept as the assembly name, but the extension is always \emph{replaced} with \code{.dll} --- \code{-o cli} and \code{-o cli.exe} both emit \code{cli.dll} --- because \code{dotnet <file>} recognises no other extension. The native launcher beside it takes the bare stem. \\
\code{--profile NAME} & Compile profile (\code{permissive}, \code{runtime}, or \code{pure}). Default \code{permissive}. May also be written \code{--profile=NAME}. \\
\code{--compile-allow-dynamic}, \code{--allow-dynamic} & Suppress \code{tosh.compile.implicit\_dynamic} diagnostics. Equivalent to opting out of strict-mode for variables whose type the inferrer cannot pin down. \\
\code{--emit-refasm} & Also emit a sibling \code{*.ref.dll} stamped with \code{[ReferenceAssembly]} so C\# / F\# / Roslyn consumers can target the public surface without dragging in private members. \\
\code{--no-apphost} & Skip the native apphost wrapper (Windows: \code{.exe}; Unix: bare). The \code{.dll} is still written and remains runnable via \code{dotnet}. \\
\code{--publish-single-file} & Bundle the .NET runtime and all dependencies into a single self-contained executable. Implies an apphost. \\
\bottomrule
\end{tabular}

\section{Examples}
\label{sec:compile-examples}

\begin{lstlisting}
# Default profile -- accepts every shape the interpreter does.
tosh --compile script.tosh -o script.dll

# Strict -- reject source-replay (Tier 3) shapes.
tosh --compile script.tosh -o script.dll --profile=runtime

# Emit a refasm alongside the implementation assembly.
tosh --compile lib.tosh -o lib.dll --emit-refasm

# Single-file self-contained binary (~70 MB; bundles the runtime).
tosh --compile cli.tosh -o cli --publish-single-file
\end{lstlisting}

\begin{notebox}[Errors]
A \code{--compile} invocation with no source paths fails with
``\code{The '--compile'/'-C' flag requires at least one script path.}''.
Unknown options inside the \code{--compile} arg list fail with
``\code{Unknown option '...' for --compile.}''.
\end{notebox}


% =============================================================================
\chapter{Profiles \& the Tier Model}
\label{ch:compile-profiles}
% =============================================================================

Every compiled shape lives at one of three tiers. The \emph{profile}
selects how strict the compiler is about which tiers it accepts.

\section{Tiers}
\label{sec:compile-tiers}

\begin{tabular}{l p{0.7\linewidth}}
\toprule
\textbf{Tier} & \textbf{Definition} \\
\midrule
1 — native IL & Pure IL with no \code{ToshHost} call at runtime: literals, arithmetic, control flow, top-level user-function calls resolved at IL-emit time, real CLR module-type field reads. \\
2 — runtime-hosted & Real IL but calls into \code{Tosh.Compiler.Runtime.ToshHost} for builtin command dispatch, dynamic member access, qualified lookup, redirection scopes, etc. \\
3 — source-replay & The emitted assembly registers a span of the original tosh source and re-evaluates it through \code{ToshEngine} at runtime. Used for class / record / struct / union / enum / trait bodies, complex module bodies, and block-pipeline arguments. \\
\bottomrule
\end{tabular}

\section{Profiles}
\label{sec:compile-profiles-table}

\begin{tabular}{l c p{0.55\linewidth}}
\toprule
\textbf{Profile} & \textbf{Max tier} & \textbf{Use case} \\
\midrule
\code{permissive} & 3 & Default. Accepts every shape the interpreter does. The compile is guaranteed to succeed if the program parses, binds, and type-checks. \\
\code{runtime} & 2 & Real, redistributable .NET assembly that doesn't carry its own source for re-evaluation. Rejects user-defined types, complex module bodies, and block arguments. \\
\code{pure} & 1 & No \code{ToshHost} calls at runtime, no source replay. Today this is mostly aspirational — even \code{echo} is a Tier-2 builtin — but the profile exists as a forcing function for future ``lift this builtin into IL'' work. \\
\bottomrule
\end{tabular}

\section{\code{RequireTier} semantics}
\label{sec:compile-requiretier}

Internally, every shape emitter calls \code{RequireTier(int tier, string
feature)} before lowering itself. If the requested tier exceeds the maximum
allowed by the active profile, the emitter records a diagnostic of the form

\begin{lstlisting}
profile 'pure' rejects tier 2 feature: builtin command dispatch (statement)
\end{lstlisting}

Diagnostics are deduplicated per \code{(tier, feature)} pair: a program with
fifty calls to \code{ls} in pure profile reports the violation once, not
fifty times.

\section{Parity expectations}
\label{sec:compile-profile-parity}

A profile narrowing is \emph{always conservative}: any program that compiles
under \code{pure} also compiles under \code{runtime} and \code{permissive},
and any program that compiles under \code{runtime} also compiles under
\code{permissive}. Behaviour is identical across profiles when the program
compiles under all three.

\begin{tipbox}[Choosing a profile]
Pick \code{runtime} when you want a redistributable .NET library that does
not need to ship its own source. Pick \code{permissive} during development
or when the program uses class / record / module bodies the runtime profile
rejects today. Pick \code{pure} only in tooling contexts (refasm-only
builds, audit checks) where Tier-2 dispatch is itself the thing under test.
\end{tipbox}


% =============================================================================
\chapter{Type Discipline in Compiled Mode}
\label{ch:compile-types}
% =============================================================================

The type checker runs in every mode, but compile mode adds an
\emph{annotation audit} that the interpreter does not. The audit promotes
weakly-typed shapes to errors so a redistributable assembly cannot expose a
public surface that silently degrades to \code{dynamic}.

\section{The audit rules}
\label{sec:compile-audit-rules}

\begin{tabular}{>{\raggedright\arraybackslash}p{0.42\linewidth} >{\raggedright\arraybackslash}p{0.5\linewidth}}
\toprule
\textbf{Diagnostic} & \textbf{When} \\
\midrule
\code{tosh.compile.missing\_type\_annotation} & A \code{func} has no
return-type annotation, or a parameter has no type annotation. \\
\code{tosh.compile.implicit\_dynamic} & A \code{var} declaration has no
type annotation \emph{and} the inferrer cannot pin down a concrete type from
the initializer. \\
\bottomrule
\end{tabular}

\section{Explicit \code{dynamic} opt-out}
\label{sec:compile-explicit-dynamic}

The audit treats an explicit \code{: dynamic} annotation as an
intentional opt-out. Both of the following are accepted by the audit:

\begin{lstlisting}
func passthrough(x: dynamic) -> dynamic { return $x }

var f: dynamic = (ls)
\end{lstlisting}

The same source without the annotations would fail compile:

\begin{lstlisting}
func passthrough(x) -> dynamic { return $x }
# tosh.compile.missing_type_annotation: parameter 'x' is missing an
# annotation. Use `dynamic` to opt out explicitly.

var x = (ls)
# tosh.compile.implicit_dynamic: variable 'x' has no type annotation
# and the inferrer could not pin down a concrete type.
\end{lstlisting}

\section{The \code{--allow-dynamic} flag}
\label{sec:compile-allow-dynamic}

\code{--compile-allow-dynamic} (alias \code{--allow-dynamic}) suppresses
\code{tosh.compile.implicit\_dynamic}. It does not suppress
\code{tosh.compile.missing\_type\_annotation}: function signatures must
always be either typed or explicitly \code{dynamic}, because they form the
public CLR surface of the compiled assembly.

\section{Implementation note}
\label{sec:compile-types-impl}

The \code{AnnotatedDynamic} flag on \code{BoundVariableDeclaration} records
whether the source carried an explicit \code{: dynamic}. The Lowerer sets
the flag (case-insensitive on the type name); the audit consults it in
\code{CheckVarAnnotation}. Synonyms for explicit dynamic on parameters are
\code{dynamic}, \code{any}, and \code{object}.


% =============================================================================
\chapter{Public CLR Shape}
\label{ch:compile-clr-shape}
% =============================================================================

Compiled tosh source produces a single .NET assembly. The shape is designed
to be consumable from C\#, F\#, and reflection-driven tooling without
re-parsing the source.

\section{Top-level statements}
\label{sec:compile-clr-toplevel}

A top-level user function \code{func greet(name: string) -> string} becomes
a public static method on a class named after the assembly's main type.
Module bodies become nested static classes.

\section{Overloads}
\label{sec:compile-clr-overloads}

When a tosh function name is overloaded, every overload is emitted as a
separate static method under the same CLR name. Argument types come from
the parameter annotations, so overload resolution from C\# follows the
ordinary CLR rules.

\begin{lstlisting}
# tosh
func pick(a: int) -> string => $"one:{$a}"
func pick(a: int, b: int) -> string => $"two:{$a}+{$b}"
\end{lstlisting}

\begin{lstlisting}[language={[Sharp]C}]
// C# consumer
Greet.pick(1);        // "one:1"
Greet.pick(1, 2);     // "two:1+2"
\end{lstlisting}

\section{Name mangling}
\label{sec:compile-clr-mangling}

Tosh identifiers may contain characters the CLR-targeted languages reject —
hyphens are the common case (\code{func to-json}). The emitter rewrites
each illegal character to \code{\_} and prefixes leading digits, then
stamps the original spelling on the resulting member with
\code{[ToshOriginalName("to-json")]}. Tools such as the LSP, the MCP server,
and editor extensions read the attribute to present the original
identifier.

When two top-level types or functions mangle to the same CLR name a
\code{tosh.compile.name\_mangling\_collision} diagnostic fails the build.

\section{User-defined types}
\label{sec:compile-clr-types}

Compiled \code{class}, \code{struct}, \code{record}, \code{enum},
\code{interface}, \code{trait}, and \code{union} declarations are emitted
as public CLR types stamped with \code{[ToshType(Kind, SpanStart,
SpanLength)]}. The span identifies the original declaration in the
registered source so source-replay-backed types can rebind full interpreter
semantics through \code{ToshHost.RegisterTypeFromSource} when needed.

\section{Reference assemblies}
\label{sec:compile-clr-refasm}

\code{--emit-refasm} writes a sibling \code{*.ref.dll} stamped with
\code{[ReferenceAssembly]}. The refasm exposes only the public surface
(types, methods, signatures) and is the recommended target for downstream
C\# / F\# / Roslyn consumers — it isolates them from private-member churn
and reduces incremental rebuild scope.


% =============================================================================
\chapter{Pipelines \& Redirections Under Compile}
\label{ch:compile-pipelines}
% =============================================================================

Pipeline construction and stream redirection are emitted as IL that calls
into \code{Tosh.Compiler.Runtime.ToshHost} (Tier 2). The lowering preserves
both the lazy-by-stage semantics of the interpreter and the deterministic
disposal order of redirection sinks.

\section{Pipeline stages}
\label{sec:compile-pipeline-stages}

A multi-stage pipeline lowers to a chain of \code{RunStage} calls seeded by
either \code{EmptyInput} (top-of-pipeline) or \code{SeedFromValue} (when a
value-typed expression feeds the pipeline):

\begin{lstlisting}
ls -la | where _.Type == "file" | sort-by Size | head 10
\end{lstlisting}

becomes, schematically:

\begin{lstlisting}[language={[Sharp]C}]
var input = ToshHost.EmptyInput();
input = ToshHost.RunStage(ToshHost.ResolveCommand("ls"),     input, ["-la"]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("where"),  input, [_filter]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("sort-by"),input, ["Size"]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("head"),   input, [10]);
ToshHost.DrainStatement(input);
\end{lstlisting}

Each stage is executed lazily: a stage's body does not run until the next
stage pulls from its async enumerable. \code{DrainStatement} (statement
context) and \code{DrainEnumerator} (value context) are the only points
that force evaluation.

\section{Stream redirection}
\label{sec:compile-redirection}

Output redirections (\code{out>}, \code{err>}, \code{o+e>}, and the
\code{>>} append variants) and input redirection (\code{in<}) all lower to
a single \code{ToshHost.BeginRedirection} call wrapping the pipeline body
in a \code{using} (try/finally + Dispose):

\begin{lstlisting}
echo hello out> "log.txt"
\end{lstlisting}

becomes, schematically:

\begin{lstlisting}[language={[Sharp]C}]
using (ToshHost.BeginRedirection(
        streams: [1],         // stdout
        modes:   [0],         // truncate
        targets: ["log.txt"],
        inputPath: null))
{
    /* pipeline body */
}
\end{lstlisting}

Output sinks are flushed and closed in reverse order during \code{Dispose};
\code{Console.Out} / \code{Console.Error} / \code{Console.In} are restored
to their pre-scope readers.

\section{Input redirection}
\label{sec:compile-input-redirection}

Input redirection installs \emph{both} a \code{Console.SetIn(...)} reader
(so commands that read \code{Console.In} — e.g.\ \code{read-line} — observe
the redirected file) and a thread-static input path consulted by
\code{EmptyInput()} (so commands that consume the pipeline input — e.g.\
\code{cat}, \code{wc}, \code{grep}, \code{read-lines} — observe the same
file as a sequence of lines).

\begin{lstlisting}
echo (read-line) in< "in.txt"          # reads via Console.In
cat in< "in.txt"                       # reads via pipeline input
\end{lstlisting}

\section{Nested redirection}
\label{sec:compile-nested-redirection}

\code{RedirectionScope} tracks per-scope state for the streams and sinks it
opened. Each scope only restores state it actually installed: an
output-only nested scope cannot clobber an outer scope's input path on
dispose, and vice versa.

\begin{warnbox}[Pre-existing footgun, now fixed]
The original implementation restored the thread-static input path
unconditionally on dispose. A nested output redirection inside an outer
input redirection would therefore wipe the outer scope's input path,
causing later pipeline-input consumers to see no input. The current
implementation gates the restore on a \code{\_trackedInputPath} flag set
only when the inner scope itself opened an input redirection.
\end{warnbox}


% =============================================================================
\chapter{Function References in Compiled Mode}
\label{ch:compile-funcrefs}
% =============================================================================

The \code{\&name} expression evaluates to an \code{IShellCallable}. In
compiled mode the value is a \code{CompiledMethodReferenceValue} bound
directly to one or more emitted \code{MethodInfo}s, not a late-bound name
lookup.

\section{Single-overload fast path}
\label{sec:compile-funcref-single}

When a function name has exactly one compiled overload the emitter loads
the \code{MethodInfo} via \code{ldtoken} / \code{MethodBase.GetFromHandle}
and calls \code{ToshHost.MakeFunctionReferenceFromMethod(method, name)}.
Invocation reorders named arguments to match the parameter list and calls
the method directly.

\begin{lstlisting}
func inc(n: int) -> int => $n + 1
var f = &inc
$f(41)                # 42
\end{lstlisting}

\section{Overloaded references}
\label{sec:compile-funcref-overload}

When a function name has two or more compiled overloads the emitter emits a
\code{MethodInfo[]} containing each overload and calls
\code{MakeFunctionReferenceFromMethods(methods, name)}. Invocation routes
through \code{InvokeUserOverload}, which scores each candidate against the
supplied argument list and dispatches to the best match.

\begin{lstlisting}
func pick(a: int) -> string => $"one:{$a}"
func pick(a: int, b: int) -> string => $"two:{$a}+{$b}"
var f = &pick
$f(1)            # "one:1"
$f(1, 2)         # "two:1+2"
\end{lstlisting}

\section{Named arguments through references}
\label{sec:compile-funcref-named}

Named-argument calls (\code{\$f(value=42, label="answer")}) are reordered
against the chosen overload's parameter list. Single-overload calls reorder
in \code{BindNamedArguments}; overload-set calls inherit the existing
\code{InvokeUserOverload} reorder pass. Missing optional parameters fall
back to their declared default; missing required parameters surface as the
ordinary arity-mismatch failure.

\section{Late-bound fallback}
\label{sec:compile-funcref-fallback}

For names that the compiler cannot resolve at emit time (e.g.\ a reference
to a builtin command or to a function loaded later through a host) the
emitter emits \code{MakeFunctionReference(name)} instead. The resulting
callable consults the runtime command table at invocation time.


% =============================================================================
\chapter{Other Bound-Shape Emitters}
\label{ch:compile-shapes}
% =============================================================================

Several language constructs lower to dedicated host helpers rather than
inline IL. They are summarised here so the implementation surface is
discoverable.

\section{Records}
\label{sec:compile-shape-records}

\begin{tabular}{l p{0.6\linewidth}}
\toprule
\textbf{Field shape} & \textbf{Lowering} \\
\midrule
\code{name: value} & Plain \code{Ldstr} key + value expression. \\
\code{(\$key): value} & Key expression evaluated, \code{ToString()}, then value (Tier 2). \\
\code{...\$source} & Call to \code{ToshHost.SpreadRecord} with the source on the stack (Tier 2). \\
\bottomrule
\end{tabular}

\begin{lstlisting}
var base = {| name: "alice", age: 30 |}
var ext  = {| ...$base, age: 31, role: "admin" |}
echo $ext.name $ext.age $ext.role     # alice 31 admin
\end{lstlisting}

\section{Tuple destructuring}
\label{sec:compile-shape-tuples}

A statement of the form \code{(\$a, \$b) = expr} lowers to one
\code{DestructureArray(value, count)} call followed by \code{count}
strongly-typed local stores. Missing slots collapse to \code{null}.

\begin{lstlisting}
var a = 0
var b = 0
($a, $b) = [10, 20]
echo $a $b           # 10 20
\end{lstlisting}

\section{\code{throw} as expression}
\label{sec:compile-shape-throw}

A \code{throw expr} in expression position lowers to a
\code{ToshHost.ThrowAsException(value)} call that returns \code{object} so
the rest of the surrounding expression typechecks.

\begin{lstlisting}
var port = $env.PORT ?? throw "PORT is required"
\end{lstlisting}

\section{Other helpers}
\label{sec:compile-shape-other}

\code{ToArray}, \code{IndexOrNull}, \code{IsTruthy},
\code{AsRedirectionPath}, \code{MakeMemberProjection}, and
\code{MakeFunctionReference[FromMethod[s]]} all live in
\code{Tosh.Compiler.Runtime.ToshHost} and are called from the
\code{BoundUnitEmitter} via cached \code{MethodInfo}s.

\chapter{Conformance Test Layer}
\label{ch:compile-conformance}
% =============================================================================

Two test surfaces in \code{tests/Tosh.Tests/CompilerFeatureMatrixTests.cs}
turn the parity contract from \S\ref{sec:compile-parity} into machine-checked
expectations.

\section{Feature matrix}
\label{sec:compile-conformance-matrix}

\code{FeatureCases()} yields one row per language shape with a flag per
profile saying whether the shape should compile cleanly under that profile.
The matrix is the executable form of \S\ref{ch:compile-limits}.

\begin{lstlisting}[language={[Sharp]C}]
yield return FeatureCase(
    id: "redirection.out-file",
    category: "redirection",
    source: "echo hi out> \"x\"",
    permissive: true, runtime: true, pure: false,
    note: "stream redirection requires Tier 2");
\end{lstlisting}

\section{Conformance cases}
\label{sec:compile-conformance-exec}

\code{ConformanceCases()} yields one row per shape that should produce a
specific stdout (and optionally a specific file) under the default profile.
The harness compiles the source, runs the resulting assembly, and asserts
on the captured streams.

\begin{lstlisting}[language={[Sharp]C}]
yield return ExecCase(
    id: "redirection.in-pipeline",
    source: "cat in< \"{TMPFILE}\"",
    stdout: "alpha\nbeta",
    note: "input redirection seeds pipeline-input commands like cat",
    seedFile: "alpha\nbeta\n");
\end{lstlisting}

\section{Adding a row}
\label{sec:compile-conformance-add}

Two-step recipe:

\begin{enumerate}
  \item Add a \code{FeatureCase} or \code{ExecCase} row alongside the
        implementation change. Runtime/Pure flags should reflect the
        \code{RequireTier} call the emitter makes for the new shape.
  \item Run \code{dotnet test tests/Tosh.Tests/Tosh.Tests.csproj
        --filter "FullyQualifiedName~CompilerFeatureMatrixTests"} and
        confirm the row passes for every profile its flags claim.
\end{enumerate}

\begin{notebox}[Console serialisation]
Tests that capture stdout/stderr or install \code{Console.SetIn} share the
xUnit collection \code{ConsoleSerialCollection} so xUnit serialises them.
Concurrent collections that touch \code{Console.\{Out, Error, In\}}
otherwise interleave output and produce flaky equality checks.
\end{notebox}

\subsection{Delimited Column Types}

\code{from csv} and \code{from tsv} infer column types, so numeric columns
arrive ready to compare rather than as text.  Inference is deliberately
narrow---integers, decimals, and \code{true}/\code{false}:

\begin{lstlisting}
Id,Name,Amount,Ratio,Active
001,Alice,150,2.5,true

# Id     -> string  (leading zero: an identifier, not a number)
# Name   -> string
# Amount -> int
# Ratio  -> double
# Active -> bool
\end{lstlisting}

The rules, and what each one protects:

\begin{description}
  \item[Per column, not per cell] A column is typed only when every non-empty
    cell agrees.  One \code{n/a} in a numeric column leaves the whole column
    textual, so values within a column always compare with each other.
  \item[Integers and decimals reconcile] A column of \code{1, 2, 2.5} is
    \code{double}.  Integers narrow to \code{int} where they fit, widening to
    \code{long} only when they must.
  \item[Leading zeros stay text] \code{007} and \code{01234} are identifiers;
    converting them destroys the zero irreversibly.  \code{0} and \code{0.5}
    are ordinary numbers.
  \item[No thousands separators] \code{1,234} is textual---the comma is also
    the delimiter.
  \item[No dates] \code{01/02/26} is three different days depending on locale,
    so date-like columns stay text.  Convert explicitly with \code{cast}.
  \item[Empty cells] Not evidence either way, and become \code{null} in a typed
    column rather than a value that would not compare with its neighbours.
\end{description}

Pass \code{--raw} (or \code{--no-infer}) to switch inference off and receive
every column as text.

\code{from json} needs none of this: JSON declares its own types.
