\chapter{Preface}

Welcome to the \textbf{ToastScript Language Specification}---the definitive guide
to every feature, command, operator, and idiom in the TōSh shell.

\textbf{TōSh} is a modern, object-oriented shell built on .NET 10 and the Common
Language Runtime (CLR). It replaces traditional text-stream pipelines with
\emph{structured object pipelines}, giving you rich types, tab completion, and
CLR interop right at the command line.

This document covers:

\begin{itemize}
  \item The complete language syntax---variables, operators, control flow,
        functions, modules, classes, records, enums, and events.
  \item Every built-in command (over 200), with signatures, descriptions,
        and runnable examples.
  \item The type system, including CLR type aliases, shell records, callables,
        type conversion, and truthiness rules.
  \item Pipeline mechanics, redirection, process substitution, and
        background jobs.
  \item Configuration, startup files, and prompt customization.
  \item A \emph{Cookbook} of practical recipes for everyday tasks.
\end{itemize}

\begin{tipbox}[Who Is This For?]
Whether you are evaluating TōSh for the first time, writing your first
\code{profile.tosh}, or building complex automation scripts, this
specification is your single source of truth.
\end{tipbox}

\section{What Is TōSh?}

TōSh (short for \emph{ToastScript}) is a Linux-first interactive shell and
scripting language. It is built on the .NET 10 CLR, meaning every value that
flows through a pipeline is a \textbf{real object}---not a flat string.

\begin{itemize}
  \item \textbf{Structured pipelines.} Commands emit lists, records, dates,
        file-system entries, and arbitrary CLR objects. Downstream commands
        filter, transform, and aggregate with full type awareness.
  \item \textbf{CLR integration.} Call any .NET method, inspect types, load
        assemblies, and even invoke native (unmanaged) libraries via built-in
        FFI.
  \item \textbf{Familiar surface.} If you know Bash, PowerShell, or Nushell,
        much of TōSh will feel natural: pipes, redirection, globs,
        \code{\$variables}, \code{if}/\code{for}/\code{while}, and function
        definitions all look close to what you expect.
  \item \textbf{Rich features.} Pattern matching with guards, destructuring,
        first-class functions, event handlers, module system, classes, records,
        enums, and a built-in TUI toolkit.
\end{itemize}

\section{Quick Start}

\begin{lstlisting}[title={Your first TōSh session}]
# List files, filter, and sort
ls -la | where _.Type == file | sort Size | reverse | first 5

# Variables and string interpolation
var name = "World"
echo $"Hello, {$name}!"

# Functions
func greet(who: string) {
    writeline $"Welcome, {$who}."
}
greet "Toast"

# Pipeline with structured data
ps -ef | where _.Cpu > 5.0 | sort Cpu | reverse | first 10
\end{lstlisting}

\section{Design Philosophy}

\begin{enumerate}
  \item \textbf{Objects, not text.} Parsing output into columns is a relic.
        Every TōSh command returns typed objects.
  \item \textbf{Progressive disclosure.} Basic usage is simple; advanced
        features (modules, FFI, TUI) are there when you need them.
  \item \textbf{Linux-native.} Built for Linux with first-class support for
        systemd, procfs, and POSIX signals.
  \item \textbf{Correctness.} Strong typing with helpful error messages.
        \code{pipefail} by default.
\end{enumerate}

\section{Comments}
\ikw{comment}

TōSh supports regular comments, block comments, and documentation comments:

\begin{lstlisting}
# This is a comment
echo hello  # Inline comment

##{
This block comment may span lines.
}##

## Adds two numbers.
## @param a first value
## @param b second value
## @returns the sum
func add(a, b) { return ($a + $b) }
\end{lstlisting}

\code{\#} begins an ordinary single-line comment.  \code{\#\#\{...\}\#\#}
is a block comment.  Consecutive \code{\#\#} documentation comments attach to
the next function, class, module, record, enum, event, or class member and feed
hover, completion, signature-help, and \code{help} metadata.

\section{Identifiers}

Identifiers start with a letter or underscore and may contain letters, digits,
underscores, and hyphens:

\begin{lstlisting}
var my_count = 10
var total-items = 42
func process-batch() { ... }
\end{lstlisting}

\begin{notebox}
Hyphens are allowed in identifiers, which is unusual among programming
languages but natural for shell commands (\code{read-file}, \code{group-by}).
\end{notebox}

\subsection{Escape Sequences}

Double-quoted strings support these escapes:

\begin{tabular}{ll}
\toprule
\textbf{Sequence} & \textbf{Meaning} \\
\midrule
\code{\textbackslash n} & Newline \\
\code{\textbackslash t} & Tab \\
\code{\textbackslash r} & Carriage return \\
\code{\textbackslash\textbackslash} & Literal backslash \\
\code{\textbackslash"} & Literal double quote \\
\code{\textbackslash 0} & Null character \\
\bottomrule
\end{tabular}

An unrecognised escape is preserved verbatim, including its backslash:
\code{"\textbackslash d+"} contains the three characters
\code{\textbackslash}, \code{d}, and \code{+}.  This makes common regex
forms work without doubled slashes:

\begin{lstlisting}
"a1" =~ "\d"       # true
"file.cs" =~ "\.cs$"  # true
\end{lstlisting}

Single-quoted strings are raw: backslashes never introduce escapes and the
next single quote closes the string.  Use \code{\$'...'} for ANSI-C escapes
such as \code{\textbackslash x1b}, or switch quote forms when the text itself
contains a single quote.

\begin{warnbox}[Migration note --- July 25, 2026]
Earlier builds decoded escapes inside ordinary \code{'...'} strings and
silently removed the backslash from unknown escapes in \code{"..."} and
\code{\$"..."}.  Ordinary single quotes are now raw, and every
escape-processing form preserves unknown escape pairs.  Replace an ordinary
single-quoted string with \code{\$'...'} when the old escape processing was
intentional.
\end{warnbox}

\subsection{String Interpolation}
\ikw{interpolation}

Interpolated strings (\code{\$"..."}) embed expressions inside
\code{\{...\}} delimiters:

\begin{lstlisting}
var user = "Alice"
echo $"Hello, {$user}!"             # Variable
echo $"2 + 2 = {2 + 2}"             # Expression
echo $"Files: {ls | where _.Type == file | count}"  # Pipeline
echo $"Today is {(date now).DayOfWeek.ToString()}"              # Member access
\end{lstlisting}

\begin{lstlisting}[title={Multi-line interpolated string}]
var report = $"""
Name:  {$name}
Items: {$items | count}
Total: {$items | sum Price}
"""
\end{lstlisting}

Intrinsic temporal literals deliberately accept only these ISO-style shapes:
\code{yyyy-MM-dd}, \code{yyyy-MM-ddTHH:mm},
\code{yyyy-MM-ddTHH:mm:ss}, and the seconds form with one through seven
fractional digits.  Date-time forms may omit a zone or end in \code{Z} or a
numeric \code{+HH:mm}/\code{-HH:mm} offset.  Explicit commands such as
\code{date parse} may accept additional human-oriented input, but that
permissive parser is never used to guess the type of a bareword.

IPv4 literals likewise require four explicit decimal octets from 0 through
255, without leading zeroes.  IPv6 uses its ordinary colon notation.
Consequently, dotted numeric text such as \code{1.2.3} is neither a date nor
an abbreviated IPv4 literal.

\begin{warnbox}[Migration note --- July 25, 2026]
Earlier builds let the CLR's culture-oriented date and abbreviated-IPv4
parsers guess the type of expression barewords.  Text such as \code{1.2.3}
could therefore become a date in 2003 or the address \code{1.2.0.3}.
Intrinsic literals are now exact.  Quote human-oriented input as text or pass
it to an explicit parser such as \code{date parse}.
\end{warnbox}

\section{Shell-Specific Types}

Beyond CLR types, TōSh introduces several shell-native types:

\subsection{StorageSize}

A value type representing byte quantities with human-friendly display:

\begin{lstlisting}
var small = 10kb             # StorageSize of 10 kB (10,000 bytes)
var large = 2.5mb            # StorageSize of 2.5 MB (2,500,000 bytes)
echo ($large > $small)       # true
ls | where Size > 100kb      # filter files larger than 100 kB
ls | sort Size               # sort by StorageSize
\end{lstlisting}

\begin{notebox}
Storage-size suffixes \code{b}, \code{kb}, \code{mb}, \code{gb}, \code{tb}, \code{pb}
use SI decimal factors (1 kb = 1{,}000 bytes). Binary suffixes \code{kib}, \code{mib},
\code{gib}, \code{tib}, \code{pib} use powers of 1{,}024.  These suffixes are
\emph{expression-context literals}: they parse to \code{StorageSize} values in
expressions (\code{var x = 10kb}, \code{(10kb > 5mb)}) but remain plain strings
when passed as raw command arguments (\code{echo 10kb}).  Suffix matching is
case-insensitive and mandatory; a malformed or overflowing suffix form in
expression position never silently falls back to a string.
\end{notebox}

\subsection{TemporalAmount / TimeSpan}

Duration values with natural syntax:

\begin{lstlisting}

100ms                    # 100 milliseconds
2m30s                    # 2 minutes 30 seconds
sleep 1s
\end{lstlisting}

\subsection{ToshRange}
\ikw{range}

Lazy sequences defined by start, optional step, and end:

\begin{lstlisting}

\subsection{LazySequence}
\ikw{lazy}

\code{LazySequence} is the runtime representation for lazy pipeline-friendly
sequences.  Infinite ranges, generator comprehensions, and iterator commands
such as \code{iterate}, \code{recur}, \code{cycle}, \code{repeat}, and
\code{repeatedly} can produce values without materialising the entire sequence.
Items are evaluated on demand and memoised as the sequence is traversed.

\begin{lstlisting}

\end{lstlisting}

\section{Type Conversion}
\label{sec:conversion}

TōSh performs automatic type conversion in many contexts via its
\code{TypeConversion} engine. Conversion is attempted in order:

\begin{enumerate}
  \item \textbf{Identity.} Same type---no conversion needed.
  \item \textbf{Null to nullable.} \code{null} converts to any nullable type.
  \item \textbf{Numeric widening.} \code{int}~\textrightarrow~\code{long}~\textrightarrow~\code{double}, etc.
  \item \textbf{String parsing.} Strings are parsed to the target type
        (\code{"42"}~\textrightarrow~\code{int}, \code{"true"}~\textrightarrow~\code{bool}).
  \item \textbf{Collection coercion.} Lists can convert to arrays, sets, etc.
  \item \textbf{CLR implicit/explicit operators.} If the target type defines
        conversion operators, they are used.
\end{enumerate}

\begin{lstlisting}
# Explicit cast
echo "42" | cast int       # String -> Int32

# Implicit in typed parameters
func double-it(n: int) => $n * 2
double-it "21"             # "21" auto-converts to 21
\end{lstlisting}

\section{Truthiness}
\label{sec:truthiness}

TōSh uses one truthiness protocol whenever a value is tested as a condition.
The same rules apply to \code{if}/\code{while}/\code{until}, conditional
expressions, comprehension and match guards, event \code{when} guards,
\code{not}/\code{and}/\code{or}, and standard-library predicates such as
\code{where}, \code{any}, \code{all}, and \code{assert}.

\begin{longtable}{L{4.8cm}L{4.1cm}L{4.1cm}}
\toprule
\textbf{Type} & \textbf{Truthy} & \textbf{Falsy} \\
\midrule
\endhead
\code{bool} & \code{true} & \code{false} \\
\code{null} & --- & Always falsy \\
\code{byte} through \code{UInt128}, native integers, \code{BigInteger} & Non-zero & Zero \\
\code{Half}, \code{float}, \code{double} & Non-zero (including infinity) & Positive/negative zero, NaN \\
\code{decimal} & Non-zero & Zero \\
\code{Complex} & Non-zero with no NaN component & Zero or either component is NaN \\
\code{string} & Non-empty & Empty \\
\code{ICollection}, synchronous \code{IEnumerable} & Non-empty & Empty \\
Everything else & Always truthy & --- \\
\bottomrule
\caption{Truthiness rules}
\label{tab:truthiness}
\end{longtable}

\begin{notebox}
Count-bearing collections are tested through their count.  A general
synchronous \code{IEnumerable} is probed with one \code{MoveNext} call and
the temporary enumerator is disposed.  This can observably advance a
deliberately single-pass enumerable; test such a value once and retain the
result when that distinction matters.
\end{notebox}

Truthiness is not an explicit cast.  For example, the non-empty string
\code{"false"} is truthy, while converting that string to \code{bool} produces
\code{false}.  Logical operators always return a boolean and preserve
short-circuit evaluation; they do not return one of their operands.

Refinement \code{where} predicates are the intentional exception: they are
validation contracts and must return an actual \code{bool}.  Refinement
\code{if <guard> coerce} guards use the broad truthiness rules above.


\section{Refinement Types}
\label{sec:refinement}
\ikw{coerce}

A \emph{refinement type} constrains an existing type with one or more
predicates.  Values that fail a predicate are either repaired via a
\code{coerce} clause or rejected at runtime.

\subsection*{Block Form}

\begin{lstlisting}
type PositiveInt = int {
    where _ > 0
}

type NormalizedPath = string {
    if (_ contains "\\") coerce (replace "\\" "/" _)
    where _ starts-with "/"
    coerce "/"
}
\end{lstlisting}

The body may contain any combination of the three clause forms:

\begin{description}
  \item[\code{where <predicate>}] A constraint predicate.  The value (bound to
    \code{\_}) must evaluate to the boolean value \code{true} after all
    coercions have been applied; other truthy values are rejected. Multiple
    \code{where} clauses are evaluated as a conjunction.

  \item[\code{if <guard> coerce <expr>}] A conditional normalisation that fires
    \emph{before} predicate evaluation.  When \code{guard} is truthy, \code{expr}
    replaces the value.  Useful for always-on normalization such as trimming
    whitespace or canonicalizing path separators.

  \item[\code{coerce <expr>} (no guard)] A fallback that fires only when one or
    more \code{where} predicates have already failed.  The expression receives
    the failing value as \code{\_} and produces a replacement.  Predicates are
    then re-evaluated against the replacement; if they still fail the refinement
    is rejected.
\end{description}

\begin{tipbox}
Think of the three forms as three phases: \emph{normalise} (\code{if X coerce
Y}) then \emph{validate} (\code{where}) then \emph{repair} (\code{coerce}).
\end{tipbox}

\subsection*{Inline Form}

\begin{lstlisting}
type Port = int where (_ >= 1 and _ <= 65535)

# With an inline fallback: clamp to range if out of bounds
type Port = int where (_ >= 1 and _ <= 65535) coerce 80
\end{lstlisting}

\subsection*{Refinements on Parameters and Variables}

Refinement types compose with the standard type annotation syntax:

\begin{lstlisting}
# Function parameter
func serve(port: int where _ > 0) { ... }

# Variable declaration
var name: string where _ != ""

# Inline predicate (anonymous refinement)
var count: int where _ >= 0 = 0
\end{lstlisting}

\subsection*{Execution Order}

When a value is checked against a refinement type:

\begin{enumerate}
  \item All \code{if <guard> coerce <expr>} clauses fire in declaration order;
    when the guard is truthy, \code{expr} replaces the value.
  \item All \code{where} predicates evaluate against the (possibly normalised) value.
  \item If any predicate fails and an unconditional \code{coerce} clause exists,
    its expression runs and replaces the value.
  \item Predicates are re-evaluated against the coerced value.
    Pass \textrightarrow{} success.  Fail \textrightarrow{} runtime error.
\end{enumerate}

\subsection*{Diagnostics}

\begin{tabular}{lL{7.5cm}}
\toprule
\textbf{Code} & \textbf{Trigger} \\
\midrule
\code{tosh.runtime.refinement\_failed} & Value did not satisfy a \code{where} predicate after all coercions. \\
\code{tosh.runtime.refinement\_requires\_boolean} & A \code{where} predicate returned a non-boolean value. \\
\bottomrule
\end{tabular}

\begin{warnbox}[Limitation]
Generic instantiation of refinement types (e.g.\ \code{list<PositiveInt>})
is not supported by the annotation resolver.  For per-element validation,
use \code{each \_ as PositiveInt} in a pipeline instead.
\end{warnbox}

\section{Comparison Operators}
\iop{==}\iop{!=}\iop{<}\iop{>}\iop{<=}\iop{>=}

\begin{tabular}{cl}
\toprule
\textbf{Operator} & \textbf{Meaning} \\
\midrule
\code{==} & Equal \\
\code{!=} & Not equal \\
\code{<}  & Less than \\
\code{>}  & Greater than \\
\code{<=} & Less than or equal \\
\code{>=} & Greater than or equal \\
\bottomrule
\end{tabular}

\medskip

Equality cascades through: \code{object.Equals}, \code{IComparable},
structural equality for records, and finally reference equality. Comparison
operators attempt \code{IComparable} first, then fall back to string
comparison.

\begin{lstlisting}
echo (1 == 1)              # true
echo ("abc" < "def")       # true (lexicographic)
echo (10kb > 5kb)          # true (StorageSize comparison, both are literals)
echo (10kb > 5mb)          # false
\end{lstlisting}

\subsection{Chained Comparison}
\label{sec:chained-comparison}

Relational comparisons chain.  Writing \code{a < b < c} means
\code{(a < b) and (b < c)}, matching ordinary mathematical notation:

\begin{lstlisting}
echo (1 < 2 < 3)          # true
echo (3 < 2 < 1)          # false
echo (1 <= 1 <= 1)        # true
echo (1 < 2 < 3 < 4)      # chains of any length
\end{lstlisting}

Two guarantees make a chain different from writing the conjunction out
by hand:

\begin{itemize}
  \item Each operand is evaluated \emph{at most once}.  In
        \tosh{1 < (next) < 3} the \code{next} call happens a single
        time, whereas the hand-written
        \tosh{(1 < (next)) and ((next) < 3)} would call it twice.
  \item Evaluation short-circuits.  Once a pair compares false, the
        remaining operands are never evaluated.
\end{itemize}

Only \code{<}, \code{<=}, \code{>}, \code{>=}, \code{==}, and
\code{!=} chain.  A run containing \code{is}, \code{in},
\code{contains}, or a regex operator keeps the ordinary
left-associative reading.

\iop{and}\iop{or}\iop{not}\iop{||}\iop{\&\&}

\code{collection contains value} is exactly the operand-reversed spelling
of \code{value in collection}.
\end{notebox}

\section{Constants}
\ikw{const}

The \code{const} keyword declares a compile-time constant. Constants must be
initialised with a literal or constant expression, cannot be reassigned, and
are always typed by their initialiser.

\begin{lstlisting}
const MaxRetries = 3
const AppName = "TōSh"
const Pi = 3.14159265358979

echo $MaxRetries     # 3
# $MaxRetries = 5   # error: cannot assign to a constant
\end{lstlisting}

Constants are visible in the same scope and all nested scopes, exactly like
\code{var}, but the name resolves to the literal value at use sites rather
than through a variable lookup.

\section{Match Expressions}
\ikw{match}

\code{match} is a powerful pattern-matching expression.  Arms use
\code{pattern => result} syntax.

\subsection*{Pattern Forms}

\begin{tabular}{lL{7.5cm}}
\toprule
\textbf{Form} & \textbf{Matches when} \\
\midrule
\code{<literal>} & Value equals the literal (\code{"file"}, \code{42}, \code{true}). \\
\code{\_ <op> <value>} & Comparison holds; \code{\_} stands for the matched value.  Supported: \code{>}, \code{>=}, \code{<}, \code{<=}, \code{==}, \code{!=}, \code{=\textasciitilde}, \code{!\textasciitilde}. \\
\code{\_ is <type>} & Runtime type check (\code{\_ is string}, \code{\_ is int}). \\
\code{\_} (bare) & Always matches; wildcard catch-all. \\
\code{default} & Always matches; conventional alternative to bare \code{\_}. \\
\bottomrule
\end{tabular}

Arm bodies may be a single pipeline expression (\code{pattern => expr}) or a
block (\code{pattern => \{ ... \}}).  An optional guard clause
\code{if ((<condition>))} after the pattern skips the arm when the guard
is falsy even if the pattern matched.

The fat-arrow body also accepts the jump statements \code{return},
\code{yield}, \code{throw}, \code{break}, and \code{continue} directly,
so generators and short-circuit returns can be expressed without an
explicit block:

\begin{lstlisting}
func emit-codes(events) {
    for $e in $events {
        match ($e.kind) {
            "ack" => yield $e
            "fatal" => throw $e.message
            default => continue
        }
    }
}
\end{lstlisting}

\code{match} is an expression: its value is the result of the matched arm.
When used as a statement the result is discarded (side effects still apply).

Value patterns match by equality; comparison patterns use \code{\_} as a placeholder for the matched
value and support \code{>}, \code{>=}, \code{<}, \code{<=}, \code{=\textasciitilde}, and \code{is}:

\begin{lstlisting}
# Value patterns (match by equality)
var kind = "file"
var label = match ($kind) {
    "file" => "it is a file"
    "dir"  => "it is a directory"
    default => "something else"
}

# Comparison patterns (use _ as a placeholder for the matched value)
var category = match ($score) {
    _ >= 90 => "A"
    _ >= 80 => "B"
    _ >= 70 => "C"
    default  => "F"
}

# Type-check patterns
var typelabel = match ($x) {
    _ is string => "string value"
    _ is int    => "integer value"
    default      => "other type"
}
\end{lstlisting}

\begin{lstlisting}[title={Match with guards}]
# Guards use `if ((<condition>))` after the pattern
match ($n) {
    0          => echo "zero"
    _ > 0 if (($n is int)) => echo "positive integer"
    _ > 0      => echo "positive"
    default    => echo "negative"
}
\end{lstlisting}

\section{Try / Catch / Finally}
\ikw{try}\ikw{catch}\ikw{finally}

\begin{lstlisting}
# Plain catch - no variable bound
try {
    var data = read-file "config.json" | from json
    process $data
} catch {
    writeline "An error occurred while loading config"
} finally {
    writeline "Cleanup complete"
}

# Named catch - binds the thrown value or exception object
try {
    throw "something went wrong"
} catch (err) {
    writeline $"Caught: {$err}"
}

# Runtime errors expose a .Message field
try {
    var x: int = "not a number"
} catch (err) {
    writeline $"Unexpected: {$err.Message}"
}
\end{lstlisting}

\code{catch} accepts either no variable, \code{catch \{ ... \}}, or one
variable in parentheses, \code{catch (err) \{ ... \}}.  TōSh currently has one
catch block per try statement; filter exception kinds inside the catch body
with \code{is}, \code{match}, or regular conditionals.

\section{Defer}
\ikw{defer}

\code{defer} schedules a block to run when the current scope exits, regardless
of how it exits (normal completion, error, or early return). Multiple defers
execute in LIFO (last-in, first-out) order:

\begin{lstlisting}
func process-file(path) {
    var handle = open-file --read $path
    defer { close $handle }

    var data = read-to-end $handle
    # handle is automatically closed when function returns
    return $data
}
\end{lstlisting}

\begin{lstlisting}[title={Defer LIFO ordering}]
func example() {
    defer { writeline "third" }
    defer { writeline "second" }
    defer { writeline "first" }
}
example()   # Output: first, second, third
\end{lstlisting}

A defer is registered only when execution reaches its declaration.  For
example, a defer written after a \code{return} or an escaping
\code{throw} is not registered.  On scope exit, every registered cleanup
is attempted exactly once in reverse registration order, even when a
newer cleanup fails.  Values yielded by cleanup pipelines are discarded;
direct side effects such as file writes or explicit writer commands still
occur.  Values already produced by the ordinary scope body are preserved.

Failure handling during unwind is deterministic:

\begin{itemize}
  \item If cleanup succeeds, the original completion, jump, cancellation,
        or failure resumes unchanged.
  \item If only one failure exists, TōSh rethrows that original exception
        without an aggregate wrapper.
  \item When failures compete, TōSh raises
        \code{ToshDeferAggregateException}.  Its failure order is the
        scope-body failure first, when present, followed by cleanup
        failures in their actual LIFO execution order.  Nested defer
        aggregates are flattened; unrelated aggregate and diagnostic
        exceptions are not.
  \item A cleanup failure supersedes a pending \code{return},
        \code{break}, or \code{continue}.  The displaced jump is control
        flow, not an entry in the failure list.
\end{itemize}

Cleanup runs in a cancellation-shielded context: cancellation that caused
the scope to exit does not prevent a reached defer from receiving its one
execution attempt.  The original \code{OperationCanceledException}
remains the outward cancellation result; any cleanup failures are retained
in the public defer-failure metadata.  A cleanup that may block should use
an explicit \code{timeout}.

For compatibility, \code{return}, \code{break}, and \code{continue}
executed by a deferred cleanup are local to that cleanup and suppressed.
They neither replace the enclosing scope's pending exit nor prevent an
earlier registered cleanup from running.

\section{Break, Continue, Return, Throw}
\ikw{break}\ikw{continue}\ikw{return}\ikw{throw}

\begin{lstlisting}
# break - exit a loop early
for item in $items {
    if ($item == "stop") { break }
    writeline $item
}

# continue - skip to next iteration
for item in $items {
    if ($item == "skip") { continue }
    writeline $item
}

# return - exit function with value
func find-first(items, predicate) {
    for item in $items {
        if ($predicate($item)) { return $item }
    }
    return null
}

# throw - raise an exception
func validate(value) {
    if ($value == null) {
        throw "Value cannot be null"
    }
}
\end{lstlisting}

\code{throw} also works as an \emph{expression} in any value position---the
false branch of a ternary, the right side of null-coalescing, or a match arm
body.  This lets you encode "this path must not be reached" inline:

\begin{lstlisting}
# Throw in a ternary: one branch produces a value, the other throws
var x = ($valid ? $value : throw "validation failed")

# Throw in null-coalescing: fail immediately if a required value is absent
var conn = $connectionString ?? throw "Connection string is required"

# Throw in a match arm body
var label = match ($input) {
    _ is int    => $"int: {$input}"
    _ is string => $"str: {$input}"
    default     => throw $"Unexpected type: {typeof $input}"
}
\end{lstlisting}


\section{Postfix Conditionals (\code{if} / \code{unless})}
\label{sec:postfix-conditionals}
\ikw{if}\ikw{unless}

A jump statement \textemdash{} \code{return}, \code{yield}, \code{throw},
\code{break}, or \code{continue} \textemdash{} may be followed by a
\emph{postfix conditional} that guards execution.  The form is:

\begin{lstlisting}
return 5  if   $x == 9
return 8  unless $ready
yield $i  if   ($i % 2 == 0)
throw "bad" unless (validate $input)
break     if   $done
continue  unless $found
\end{lstlisting}

Semantics:

\begin{itemize}
  \item \code{stmt if cond} executes \code{stmt} only when \code{cond}
        is truthy. It is exactly equivalent to
        \code{if cond \{ stmt \}}.
  \item \code{stmt unless cond} executes \code{stmt} only when
        \code{cond} is falsy. It is exactly equivalent to
        \code{if cond \{ \} else \{ stmt \}}; the original condition
        expression is preserved verbatim (no negation operator is
        inserted).
\end{itemize}

The condition is parsed as a single argument expression, so non-trivial
conditions should be parenthesised.  The postfix form is recognised only
when the \code{if} or \code{unless} keyword appears on the same logical
line as the jump statement (no implicit statement boundary in between);
this avoids ambiguity with a free-standing \code{if} block on the
following line.  Omitting the condition raises
\code{tosh.parser.expected\_postfix\_condition}.

Postfix conditionals attach \emph{only} to jump statements.  Regular
commands (\code{echo "hi" if \$x}) and assignments
(\code{var x = 1 if \$y}) are not supported \textemdash{} use a block
\code{if} instead.

\section{Arrow Functions (Wrappers)}

Arrow functions are single-expression functions. Inside arrow functions,
\code{\$1}, \code{\$2}, etc.\ refer to positional parameters:

\begin{lstlisting}
func double(x) => ($x * 2)

# Positional parameters
func add => ($1 + $2)
add 3 4      # 7

# As aliases
func cls => clear
func ll => ls -la
\end{lstlisting}

\section{Anonymous Functions (Lambdas)}

\begin{lstlisting}
# Expression lambda
var fn = func(x) => ($x * 2)

# Block lambda
var process = func(x) {
    var result = ($x * 2)
    return $result + 1
}

# Inline in pipelines
[1, 2, 3] | map func(x) => ($x * 2)   # [2, 4, 6]
\end{lstlisting}

\begin{aside}[Implicit Pipeline Lambdas]
In many pipeline commands, you can use block syntax with \code{\_} as the
current item instead of writing an explicit lambda:

\begin{lstlisting}
[1, 2, 3] | map { _ * 2 }        # Equivalent to above
ls | where { _.Size > 1mb }      # Block predicate
ls | sort { _.Modified }          # Block key selector
\end{lstlisting}
\end{aside}

\section{Typed Parameters}

\begin{lstlisting}
func connect(host: string, port: int) {
    writeline $"Connecting to {$host}:{$port}"
}

# Optional parameters (with ?)
func greet(name: string, title?: string = "friend") {
    writeline $"Hello, {$title} {$name}!"
}
greet "Alice"                 # Hello, friend Alice!
greet "Alice" "Dr."           # Hello, Dr. Alice!

# Rest parameters (with ...)
func print-all(items...) {
    for item in $items {
        writeline $item
    }
}
print-all 1 2 3 4 5
\end{lstlisting}

Parameters may also have default values.  Default expressions are evaluated
when the argument is omitted:

\begin{lstlisting}
func connect(host: string, port: int = 443) {
    echo $"{$host}:{$port}"
}

connect "example.com"                 # port defaults to 443
connect "localhost" 8080
\end{lstlisting}

\subsection*{Default-Value Semantics}
\label{sec:default-binding}

Defaults follow one protocol for functions, lambdas, methods, and
constructors:

\begin{itemize}
  \item A default is evaluated only when the caller supplies neither a
        positional nor a named argument for that parameter, and it is
        re-evaluated on every such call --- never captured once at
        declaration time.
  \item Defaults evaluate in the callable's own lexical scope, at call
        time, so a default that reads an outer variable observes that
        variable's value when the call happens.
  \item Evaluation proceeds left to right, and a default may reference
        any \emph{earlier} parameter that is already bound.  Referring
        to the parameter's own name, or to a later parameter, raises
        \code{tosh.runtime.unknown\_variable}.
  \item Overload resolution never evaluates a default; only the selected
        overload's defaults run, so a losing candidate produces no side
        effects.
  \item An evaluated default is converted through the parameter's
        annotation and refinement exactly like a supplied argument.  A
        default that cannot be converted raises
        \code{tosh.runtime.parameter\_default\_conversion\_failed}.
\end{itemize}

\begin{lstlisting}
func step(a: int, b: int = $a + 1, c: int = $b + 1) -> string {
    return $"{$a},{$b},{$c}"
}

step 1                     # 1,2,3   -- defaults chain left to right
step(1, c = 99)            # 1,2,99  -- named argument, b still defaults
\end{lstlisting}

\begin{notebox}
Because defaults evaluate at call time, a mutable default expression
produces a fresh value per call.  \tosh{func add(item, into = [])}
therefore starts from a new empty list on every call rather than sharing
one list across calls.
\end{notebox}

\section{Named Arguments and Callable Invocation}

Function calls can use command-style syntax, parenthesized call syntax, or
named arguments.  Named arguments use \code{name = value} inside the call and
may be supplied out of order.

\begin{lstlisting}
func deploy(host, port = 22, user = "root") {
    echo $"{$user}@{$host}:{$port}"
}

deploy "server"
deploy(host = "server", user = "alice")
deploy(user = "alice", port = 2222, host = "server")
\end{lstlisting}

Callable values can be invoked with \code{invoke} or postfix call syntax:

\begin{lstlisting}
var double = func(x) => ($x * 2)
invoke $double 21
$double(21)

var add3 = func(a, b, c) => ($a + $b + $c)
(curry $add3)(1)(2)(39)       # 42
\end{lstlisting}

\section{Return Types}

\begin{lstlisting}
func add(a: int, b: int) -> int {
    return $a + $b
}

func get-name() -> string { return "TōSh" }
\end{lstlisting}

\begin{notebox}[Implicit Pipeline Return]
A function does not need an explicit \code{return} to produce a value.
All pipeline output emitted by the function body is collected and yielded
as the function's result when the function exits normally.  If a
\code{return} is reached, its operands replace any buffered output:

\begin{lstlisting}
func doubled-items(items) {
    $items | each { _ * 2 }   # output flows out; no 'return' needed
}

var results = (doubled-items [1, 2, 3])   # [2, 4, 6]
\end{lstlisting}

Generator functions (those containing \code{yield}) stream values
progressively instead of buffering them---see
Section~\ref{sec:generators}.
\end{notebox}

\section{Function Overloading}

Functions can be overloaded by arity and typed parameters:

\begin{lstlisting}
func greet() { echo "Hello!" }
func greet(name) { echo $"Hello, {$name}!" }
func kind(value: int) { echo "integer" }
func kind(value: string) { echo "string" }

greet              # Hello!
greet "World"      # Hello, World!
kind 42            # integer
kind "hi"          # string
\end{lstlisting}

\section{Recursion Depth}

TōSh protects the host process with a limit on active ToastScript
execution frames. The default and highest supported limit are 128
frames. Functions, methods, lambdas, constructors, and nested
\code{eval}/\code{source} execution participate in the same
asynchronous-flow-local count; compiled ToastScript uses the same
protocol.

Exceeding the limit raises the stable
\code{tosh.runtime.recursion\_limit\_exceeded} diagnostic. It does not
terminate the process, and an interactive session remains usable after
the diagnostic is handled.

The limit may be lowered for a session or persisted in
\code{config.tosh}:

\begin{lstlisting}
$tosh.Config.Shell.MaxRecursionDepth = 64
\end{lstlisting}

Accepted values are 1 through 128. TōSh does not currently perform
tail-call elimination, so deeply recursive algorithms should be
rewritten as loops when practical.

\section{Operator Overloading}
\label{sec:operator-overloading}

Classes may overload binary operators by declaring methods whose names are
the operator symbol itself. The method receives the right-hand operand as
its single argument; \code{\$this} refers to the left-hand operand.

\begin{lstlisting}
class Vec {
    prop X: int = 0
    prop Y: int = 0

    func +(other) { var r = new Vec(); $r.X = $this.X + $other.X; $r.Y = $this.Y + $other.Y; return $r }
    func *(scalar) { var r = new Vec(); $r.X = $this.X * $scalar; $r.Y = $this.Y * $scalar; return $r }
    func ==(other) { return $this.X == $other.X and $this.Y == $other.Y }
}

var a = new Vec(); $a.X = 1; $a.Y = 2
var b = new Vec(); $b.X = 3; $b.Y = 4
$a + $b              # Vec { X: 4, Y: 6 }
$a * 3               # Vec { X: 3, Y: 6 }
\end{lstlisting}

The following operator symbols are accepted as method names:

\begin{center}
\begin{tabular}{l l}
\toprule
\textbf{Category} & \textbf{Symbols} \\
\midrule
Arithmetic & \code{+}, \code{-}, \code{*}, \code{/}, \code{//}, \code{\%}, \code{**} \\
Comparison & \code{==}, \code{!=}, \code{<}, \code{<=}, \code{>}, \code{>=} \\
Match      & \code{=\textasciitilde}, \code{!\textasciitilde} \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Resolution order}

When evaluating \code{a OP b} where either operand is a class instance:

\begin{enumerate}
    \item If the left operand defines an \code{OP} method, it is invoked
      with \code{b} as the argument.
    \item Otherwise, if the right operand defines an \code{OP} method, it
      is invoked with \code{a} as the argument (note: \code{\$this} is
      still the right operand).
    \item Otherwise, the standard built-in operator semantics apply, which
      typically raises a runtime error if neither side is a supported
      type.
\end{enumerate}

\subsection{Limitations}

\begin{itemize}
    \item Unary operators (prefix \code{-}, \code{not}) are not currently
      overloadable. Only the binary forms above are accepted as method
      names.
    \item Compound-assignment operators (\code{+=}, \code{-=}, etc.) are
      not overloadable directly; they desugar to the binary form, so
      defining \code{+} also covers \code{+=}.
    \item Indexer-style access (\code{a[i]}) is parser-level wired but
      not yet a spec-level guarantee; prefer named methods until indexer
      semantics stabilise.
\end{itemize}

\section{Generator Functions}
\label{sec:generators}
\ikw{yield}

A function that contains a \code{yield} statement is a \emph{generator
function}.  Each call returns a \code{LazySequence}---values are produced on
demand as the sequence is consumed.  A generator may yield any number of times
and may mix \code{yield} with normal control flow.

\begin{lstlisting}
func evens-up-to(n: int) {
    var i = 0
    while ($i <= $n) {
        yield $i
        $i += 2
    }
}

evens-up-to 10 | collect        # [0, 2, 4, 6, 8, 10]
evens-up-to 20 | first 4        # 0, 2, 4, 6
\end{lstlisting}

You can annotate the return type as \code{LazySequence} to make intent clear:

\begin{lstlisting}
func fibonacci() -> LazySequence {
    var a = 0
    var b = 1
    while (true) {
        yield $a
        var next = $a + $b
        $a = $b
        $b = $next
    }
}

fibonacci | first 8             # 0, 1, 1, 2, 3, 5, 8, 13
\end{lstlisting}

\begin{warnbox}[Known Limitation]
Generator functions with unbounded \code{while (true)} loops do not yet cooperate
with early-termination commands such as \code{first}.  The pipeline will run
indefinitely.  Use a finite upper bound in the loop condition, or reach for
built-in lazy sources (\code{iterate}, \code{recur}, \code{cycle}, \code{repeat},
infinite ranges \code{1..}) which do support early termination.
\end{warnbox}

\begin{tipbox}
Finite generator functions integrate naturally with the full pipeline command set:
\code{first}, \code{skip}, \code{where}, \code{map}, \code{collect}, etc.
\end{tipbox}

\section{Event Handlers}
\ikw{handles}

Functions can be registered as event handlers:

\begin{lstlisting}
func onDirChange(event) handles DirectoryChanged {
    writeline $"Changed to: {$event.NewDirectory}"
}

# With priority and guard
func onBigCommand(event) handles CommandCompleted priority 10
    when { $event.Duration > (timespan 1s) }
{
    writeline $"Slow command: {$event.Duration}"
}

# One-time handler
func onFirstStart(event) handles SessionStarted once {
    writeline "Welcome to your first session!"
}
\end{lstlisting}

The last value emitted by a \code{when} block is tested using the canonical
truthiness rules in Table~\ref{tab:truthiness}.  A block that emits no values
therefore has a falsy guard.

\section{Doc-Comments}

Functions, classes, properties, and methods accept documentation comments
immediately above their declaration.  A doc-comment line begins with \code{\#\#}
(double hash).  At runtime, \code{help <name>} renders the doc-comment:

\begin{lstlisting}
## Adds two numbers together and returns the sum.
## @param=a The first operand.
## @param=b The second operand.
## @returns The sum as an int.
## @example
##   add 3 4    # 7
func add(a: int, b: int) -> int {
    return ($a + $b)
}
\end{lstlisting}

The supported tags are:

\begin{tabular}{lL{8cm}}
\toprule
\textbf{Tag} & \textbf{Purpose} \\
\midrule
\code{@param=<name> <desc>} & Document a named parameter. \\
\code{@returns <desc>} & Describe the return value. \\
\code{@example} & Lines following this tag (still prefixed \code{\#\#}) are shown verbatim as examples in \code{help} output. \\
\code{@deprecated <message>} & Flag the item as deprecated; \code{help} renders a visible warning. \\
\code{@see <ref>} & Cross-reference another command or function. \\
\code{@since <version>} & First release in which the item appeared. \\
\code{@throws <type> <desc>} & Document an exception path the function may raise. \\
\bottomrule
\end{tabular}

\begin{tipbox}
All tags are optional.  A doc-comment containing only prose (no tags) is
perfectly valid and will display as the item's description.
\end{tipbox}

\section{Rune Definitions}
\ikw{rune}

Runes are macro-like shell commands whose arguments are captured lazily as
syntax thunks.  They are useful for control-flow helpers that should decide
when, whether, or how often to evaluate their arguments or body blocks.

\begin{lstlisting}
rune do-twice(body) {
    $body
    $body
}

do-twice { writeline "hi" }  # hi, hi
\end{lstlisting}

A rune can be invoked like any command, including with block arguments:

\begin{lstlisting}
rune retry(count, body) {
    for i in 1..$count {
        try {
            $body
            return
        } catch (err) {
            if ($i == $count) { throw $err }
        }
    }
}
\end{lstlisting}

\section{Rune Hygiene}
\ikw{sealed}\ikw{leaky}

Runes are \code{sealed} by default.  A sealed rune evaluates in a hygienic
scope so variables declared inside the rune do not leak back to the caller.
Mark a rune \code{leaky} when it intentionally writes bindings into the caller
scope.

\begin{lstlisting}
rune internal() {
    var hidden = 42
}

leaky rune export-var() {
    var visible = 42
}
\end{lstlisting}

\code{fixed} and \code{lazy} are accepted rune modifiers.  \code{lazy} is the
default evaluation mode; \code{fixed} marks the captured argument behaviour as
fixed for future expansion/runtime policy.

\section{Quote}
\ikw{quote}

\code{quote \{ ... \}} captures syntax as a first-class quoted value instead of
evaluating it immediately.  This is primarily useful inside runes for source
inspection and AST-like metaprogramming.

\begin{lstlisting}
rune show-source(expr) {
    var src = (quote { $expr })
    echo $src
}

show-source (1 + 2)          # contains "1 + 2"
\end{lstlisting}

\section{Built-In Runes}

The runtime currently provides \code{unless} as a built-in rune:

\begin{lstlisting}
unless false { echo "runs" }
unless true  { echo "skipped" }
\end{lstlisting}

\section{Using Statements}
\ikw{using}

Import CLR namespaces for shorter type references:

\begin{lstlisting}
using System.IO             # Import namespace
using System.IO = IO        # Aliased import
\end{lstlisting}

\code{using} is lexically scoped---it only applies in the block where declared.

\section{Require Statements}
\ikw{require}

Load scripts or modules:

\begin{lstlisting}
# Execute script in current scope
require "./utils.tosh"

# Import specific module
require Inventory from "./toastlib.tosh"

# With alias
require Inventory from "./toastlib.tosh" as Inv

# Multiple modules
require { Reporting, Utilities } from "./toastlib.tosh"
\end{lstlisting}

\section{Native Library Loading}
\ikw{bind}\ikw{callconv}

Load and bind native (unmanaged) libraries:

\begin{lstlisting}
require native "./libcrypto.so" as Crypto

bind Crypto {
    func sha256(data: byte-ptr, len: uint64) -> byte-ptr
}
\end{lstlisting}

Native bindings support \code{in}, \code{ref}, and \code{out} parameter modes
and an optional \code{callconv} override for specifying the native calling
convention.  Parameters default to \code{in} (pass by value).  \code{ref}
passes a managed reference; \code{out} captures a value written by the native
function into a new variable.

\begin{lstlisting}
require native "./libfoo.so" as Foo

bind Foo {
    # out parameter: value written by the native function
    func get-value(out result: int) -> bool

    # ref parameter: read/write managed reference
    func increment(ref counter: int)

    # custom calling convention (Cdecl, StdCall, ThisCall, etc.)
    callconv Cdecl
    func legacy-api(data: byte-ptr, len: int) -> int
}

var ok = false
var n = 0
$ok = (Foo.get-value out $n)   # $n receives the written value
\end{lstlisting}

\section{Module Definitions}
\ikw{module}

\begin{lstlisting}
module Utilities {
    shy func internal-helper() { ... }
    export func banner(title: string) {
        writeline $"=== {$title} ==="
    }
    func default-accessible() { ... }
}

# Usage
Utilities.banner("Report")
\end{lstlisting}

Modules can contain nested types:

\begin{lstlisting}
module Inventory {
    enum StockState { Healthy, Low, Out }
    record Item(Name: string, Quantity: int)
    class Shelf(label: string) { ... }

    func sample-items() {
        return [
            new Item("Widget", 100),
            new Item("Gadget", 5)
        ]
    }
}

# Access via dot notation
var items = Inventory.sample-items()
var state = Inventory.StockState.Healthy
\end{lstlisting}

\subsection*{Module-Qualified Command Dispatch}

Functions exported from a module may also be invoked in command position
using \code{module.function} syntax---no \code{\$} prefix, arguments
separated by whitespace like any other command:

\begin{lstlisting}
module Geometry {
    func area(r) { return 3.14159 * $r * $r }
}

Geometry.area 5            # 78.53975
\end{lstlisting}

This works for any module-name casing, including identifiers that contain
hyphens (\code{kebab-mod.hi}), underscores, or mixed case.  Nested modules
resolve segment-by-segment (\code{outer.inner.fn}).

\section{Class Definitions}
\ikw{class}\ikw{prop}

\begin{lstlisting}
class Point(x: double, y: double) {
    prop X: double = $x
    prop Y: double = $y

    # Computed property (evaluated on each access)
    prop Magnitude => (Math.Sqrt(($this.X * $this.X) + ($this.Y * $this.Y)))

    func Distance(other) -> double {
        var dx = $this.X - $other.X
        var dy = $this.Y - $other.Y
        return (Math.Sqrt(($dx * $dx) + ($dy * $dy)))
    }

    shared func Origin() { return new Point(0.0, 0.0) }
}
\end{lstlisting}

\begin{lstlisting}[title={Using classes}]
var p = new Point(3.0, 4.0)
echo $p.Magnitude              # 5
echo (Point.Origin())          # Point

var q = new Point(6.0, 8.0)
echo ($p.Distance($q))         # 5
\end{lstlisting}

Class features:
\begin{itemize}
  \item \textbf{Primary constructor}---parameters after the class name.
  \item \textbf{Stored properties}---\code{prop Name: Type = value}.
  \item \textbf{Computed properties}---\code{prop Name => (expr)} (type annotation is inferred).
  \item \textbf{Methods}---\code{func Name(params) \{ ... \}}.
  \item \textbf{Static methods}---\code{shared func Name(params) \{ ... \}} (also accepts \code{static}).
  \item \textbf{Self-reference}---\code{\$this} inside methods.
  \item \textbf{Visibility}---\code{shy} for private members.
  \item \textbf{Instantiation}---\code{new ClassName(args)}.
\end{itemize}

\subsection{Class Modifiers}
\ikw{sealed}\ikw{hollow}\ikw{hermit}\ikw{strict}\ikw{partial}

Class-level modifiers appear before the \code{class} keyword and control
the class's overall behaviour.

\begin{description}
  \item[\code{sealed}] Prevents the class from being inherited.
    A sealed class cannot appear as a base class.
  \item[\code{hollow}] Marks the class as \emph{abstract}.
    It cannot be instantiated directly; subclasses must override all hollow methods.
  \item[\code{hermit}] Marks the class as \emph{static-only}.
    All members are auto-promoted to shared; constructors are not allowed;
    the class cannot be instantiated.
  \item[\code{strict}] Makes every property in the class \emph{read-only}
    after initialisation, as if each were individually marked \code{fixed}.
  \item[\code{partial}] Allows the class definition to be split across
    multiple declarations.  All declarations must carry the \code{partial}
    modifier.  Properties and methods are merged; duplicate property names
    are silently skipped; methods support overloading.
\end{description}

\noindent Example:
\begin{lstlisting}
sealed class Config {
    prop Host = "localhost"
    prop Port = 8080
}

hollow class Shape {
    hollow func area() -> double { }
}

hermit class MathHelper {
    func square(x) { writeline ($x * $x) }
}
MathHelper.square(5)             # 25

strict class Point {
    prop X = 0
    prop Y = 0
}

partial class User { prop Name = "" }
partial class User { func greet() { writeline $"Hi, {$this.Name}" } }
\end{lstlisting}

\subsection{Member Modifiers}
\ikw{shy}\ikw{shared}\ikw{static}\ikw{fixed}\ikw{vital}\ikw{guarded}\ikw{overrule}\ikw{fading}\ikw{local}\ikw{raw}\ikw{proud}\ikw{public}

Member-level modifiers appear before \code{prop} or \code{func} inside a
class body.

\begin{description}
  \item[\code{shy}] Hides the member from public inspection and external access (private).
  \item[\code{shared} / \code{static}] Member belongs to the class rather than an instance.
  \item[\code{fixed}] Makes a property read-only after initialisation.
  \item[\code{vital}] Marks a property as required---construction fails
    without a value.
  \item[\code{guarded}] Restricts access to the defining class and its
    subclasses (protected).
  \item[\code{overrule}] Overrides an inherited method from a parent class.
  \item[\code{lazy}] Defers the property initialiser until first access;
    the result is cached.
  \item[\code{fading}] Marks the member as deprecated; emits a warning to
    stderr on use.
  \item[\code{local}] Restricts visibility to the defining assembly
    (internal).
  \item[\code{raw}] Marks a method for unsafe/native interop.
  \item[\code{proud} / \code{public}] Explicitly marks a member as public
    (no-op, members default to public).
  \item[\code{hollow}] (on a method) Declares an abstract method that subclasses must overrule.
    An empty body \code{\{ \}} is required: \code{hollow func name() \{ \}}.
\end{description}

\noindent \textbf{Canonical aliases.}  Every flavored modifier has an
equally-valid canonical alias drawn from the wider .NET / object-oriented
vocabulary; either form is accepted at parse time and produces identical
semantics.  Use whichever reads better in context.  The pairs are:
\code{shy}/\code{private}, \code{proud}/\code{public},
\code{guarded}/\code{protected}, \code{shared}/\code{static},
\code{fixed}/\code{readonly}, \code{vital}/\code{required},
\code{overrule}/\code{override}, \code{hollow}/\code{abstract},
\code{fading}/\code{obsolete}, \code{hermit}/\code{static} (class-level).
The same canonical/flavored equivalence applies to class-level modifiers
(\code{abstract}/\code{hollow}, \code{static}/\code{hermit}).

\noindent Example:
\begin{lstlisting}
class Product {
    vital prop Name: string
    fixed prop Id = 0
    lazy prop Metadata = load_metadata($this.Id)
    shy prop _cache = []
    guarded func validate() { echo "checking" }
    fading prop OldName = "use NewName"
}
\end{lstlisting}

\section{Generic Classes}
\label{sec:generic-classes}

A class declaration may introduce one or more \emph{type parameters}
inside angle brackets after the class name.  Type parameters can be used
anywhere a type annotation is accepted: primary-constructor parameters,
property types, method parameter and return types, and the
\code{extends} clause of a derived class.

\begin{lstlisting}
class Box<T>(initial: T) {
    prop value: T = $initial
    func unwrap() -> T { return $this.value }
    func set(v: T) { $this.value = $v }
}

var bi = new Box<int>(42)
echo $bi.unwrap()              # 42

var bs = new Box<string>("hi")
echo $bs.unwrap()              # hi
\end{lstlisting}

\subsection*{Instantiation}

\code{new ClassName<arg1, arg2, \ldots>(ctorArgs)} creates an instance
whose type parameters are bound to the supplied CLR types.  The
type-argument list must match the class's declared arity exactly;
mismatches \textemdash{} too few, too many, an empty
\code{<>} list, or omitting the angle brackets entirely on a class
that declares type parameters \textemdash{} raise an instantiation
error.

\subsection*{Strict (no-coercion) bindings}

When a constructor parameter, method parameter, method return value, or
property type is declared as a class type parameter (e.g.\ \code{x: T}),
the engine performs a \emph{strict} \code{IsInstanceOfType} check at
each use site against the bound CLR type --- it does \emph{not} run
the standard value-conversion path that applies to ordinary
annotations.  In particular:

\begin{itemize}
  \item \code{new Box<string>(42)} rejects with
    \code{tosh.runtime.annotation\_conversion\_failed} rather than
    silently stringifying \code{42} to \code{"42"}.
  \item \code{new Box<double>(9)} rejects rather than widening
    \code{int} to \code{double}.
  \item Reassignment to \code{\$this.value} where \code{value: T} is
    bound goes through the same strict check.
\end{itemize}

\noindent Type-parameters whose binding does \emph{not} resolve to a
known CLR type (rare; usually a forward-declared user type) are
treated nominally --- any value is accepted, and the binding only
participates in display.

\subsection*{Inheritance}

A subclass can pass type arguments through to its base, propagate its
own type parameters, or fix the base's parameters to concrete types:

\begin{lstlisting}
class _Point<T1, T2> {
    hollow prop X: T1
    hollow prop Y: T2
}

class Point2D<T1, T2> extends _Point<T1, T2> {
    overrule prop X: T1
    overrule prop Y: T2

    Point2D<T1, T2>(x: T1, y: T2) {
        $this.X = $x
        $this.Y = $y
    }
}

var p = new Point2D<int, int>(3, 4)
echo $p.X                      # 3
\end{lstlisting}

Bindings flow through the inheritance chain: when an instance of
\code{Point2D<int, int>} accesses an inherited member declared on
\code{\_Point}, the engine resolves \code{T1} and \code{T2} against
the base's type-argument list using the child's bindings.

\subsection*{Generic annotations}

Anywhere a type annotation is accepted, the form
\code{ClassName<arg1, arg2, \ldots>} refers to the user-defined
generic class \code{ClassName}.  Annotations with this shape are
recognised before falling through to the CLR type loader (where
multi-arg names like \code{Foo<int, int>} would otherwise produce a
\code{Type.GetType} error treating commas as type/assembly separators).
A value satisfies the annotation when it is a
\code{ToshClassInstance} whose definition (or any ancestor in the
inheritance chain) names \code{ClassName}; the per-instance type-argument
strings are not currently validated against the annotation strings.

\subsection*{Compiled mode}

Generic classes do not emit a CLR shell type at compile time.  Instead,
the compiler registers the class via source-replay and emits
\code{new}-expressions through a typed host overload\\
\code{ToshHost.NewObject(typeName, bareTypeName, string[] typeArgs, object?[] args)}\\
which delegates to the engine's reification path.  This means
generic classes behave identically in REPL and compiled execution.

\subsection*{Type-Parameter Constraints}

A \code{where T: <Constraint>[, <Constraint>\ldots]} clause may follow
the class header to restrict acceptable type arguments.  Built-in
constraints are summarised below; multiple \code{where} clauses may
follow one another to constrain different type parameters.  Unknown
constraint names are accepted conservatively (reserved for future
user-defined constraints).

\begin{center}
\begin{tabular}{L{3.6cm}L{9cm}}
\toprule
\textbf{Constraint} & \textbf{Satisfied by} \\
\midrule
\code{Numeric} / \code{Number} / \code{INumber} &
  \code{int}, \code{long}, \code{short}, \code{byte}, signed/unsigned variants,
  \code{float}, \code{double}, \code{decimal}, \code{Half}, \code{BigInteger} \\
\code{Add} / \code{Sub} / \code{Mul} / \code{Div} &
  Any numeric type, or any CLR type with a matching \code{op\_*} static method \\
\code{Comparable} & Any type implementing \code{IComparable} \\
\code{Eq} & Always satisfied (placeholder) \\
\bottomrule
\end{tabular}
\end{center}

\begin{lstlisting}
class Box<T>(initial: T) where T: Numeric {
    prop value: T = $initial
    func bump(amount) { $this.value = $this.value + $amount }
}

var bi = new Box<int>(10);     $bi.bump(5)     # 15
var bf = new Box<double>(1.5); $bf.bump(2.5)   # 4.0
# new Box<string>("hi")  -> rejected: 'string' does not satisfy 'Numeric'
\end{lstlisting}

The same constraint names also work as right-hand operands for the
\code{is} / \code{is-not} operators on values, so runtime checks reuse
the same registry as compile-time generic-parameter validation:

\begin{lstlisting}
var x = 42
$x is Numeric           # true
$x is Comparable        # true
"hello" is Numeric      # false
$x is-not Numeric       # false
\end{lstlisting}

\section{Inheritance, Interfaces, and Traits}
\ikw{extends}\ikw{fulfills}\ikw{implements}\ikw{uses}

Classes can extend another TōSh class, fulfill one or more interfaces, and use
one or more traits.  \code{implements} is accepted as an alias for
\code{fulfills}.  Parent constructors can be supplied in the \code{extends}
clause or called from the constructor with \code{\$super(...)}.
Construction proceeds exactly once per class layer, from the root base class
to the most-derived class.  The preferred form is
\code{extends Base(args)}.  A direct \code{\$super(args)} call is retained as
an alternative for an explicit constructor, but it must be that constructor's
first executable statement and must not be combined with arguments in the
\code{extends} clause.  If neither form is present, TōSh implicitly invokes a
matching zero-argument base constructor; a base that requires arguments
produces a diagnostic.

\begin{lstlisting}
interface Printable {
    func print()
}

trait Named {
    prop Name = "anonymous"
    func label() { return $this.Name }
}

class Report(title: string) fulfills Printable uses Named {
    prop Title = $title
    func print() { return $this.Title }
}

var r = new Report("Daily")
echo ($r is Printable)        # true
echo ($r is Named)            # true
\end{lstlisting}

\section{Interface Definitions}
\ikw{interface}

Interfaces declare required method signatures.  They cannot be instantiated.
When a class \code{fulfills} an interface, TōSh validates that the class has
each required method by name and arity.

\begin{lstlisting}
interface Runnable {
    func run()
    func stop()
}

class Job fulfills Runnable {
    func run()  { echo "running" }
    func stop() { echo "stopped" }
}
\end{lstlisting}

\section{Trait Definitions}
\ikw{trait}

Traits describe reusable requirements and optional defaults.  A trait may
declare required properties/methods, or provide default property values and
method bodies.  Classes using the trait must supply the required members; any
defaults not already present on the class are injected into the class.

\begin{lstlisting}
trait Timestamped {
    prop CreatedAt = date now
    func age() { return ((date now) - $this.CreatedAt) }
}

class Note uses Timestamped {
    prop Text = ""
}
\end{lstlisting}

\section{Union Definitions}
\ikw{union}

Unions define tagged variant types.  Unit variants (no fields) are accessed as
static members.  Variants with fields are constructed as static calls.  Every
union instance exposes \code{Variant} (also aliased as \code{Tag}) plus any
fields declared on its variant.

\begin{lstlisting}
union Result {
    Ok(value)
    Error(message)
    None
}

var success = Result.Ok(42)
echo $success.Variant        # Ok
echo $success.value          # 42

var failure = Result.Error("not found")
echo $failure.message        # not found

var empty = Result.None
echo $empty.Variant          # None
\end{lstlisting}

\subsection*{Pattern Matching on Unions}

Use \code{switch} on the \code{Variant} string to dispatch on the active
variant:

\begin{lstlisting}
func describe(r) {
    switch ($r.Variant) {
        case "Ok"    { echo $"Success: {$r.value}" }
        case "Error" { echo $"Failed: {$r.message}" }
        case "None"  { echo "No value" }
    }
}

describe (Result.Ok 100)        # Success: 100
describe (Result.Error "oops")  # Failed: oops
describe Result.None            # No value
\end{lstlisting}

\subsection*{Type Checking}

Union instances respond to \code{is} checks against their union type:

\begin{lstlisting}
echo ($success is Result)    # true
echo ($success is-not Result)# false
\end{lstlisting}

\section{Struct Definitions}
\ikw{struct}\ikw{fluid}

Structs are shell-defined value types with positional fields and optional class
style members.  By default, struct fields are read-only after construction.
Mark a struct \code{fluid} to make fields writable.  \code{partial} structs can
be split across declarations; every declaration must be marked \code{partial}.

\begin{lstlisting}
struct Point(x: int, y: int) {
    func sum() { return ($this.x + $this.y) }
}

var p = new Point(3, 4)
echo $p.x
echo ($p.sum())              # 7

fluid struct Counter(value: int)
var c = new Counter(0)
$c.value = 1
\end{lstlisting}

\section{Record Definitions}
\ikw{record}

Records are lightweight named types with positional fields:

\begin{lstlisting}
record Item(
    Name: string,
    Quantity: int,
    Category?: string = "General",
    Tint?: string = "White"
)

var widget = new Item("Widget", 50)
var custom = new Item("Gadget", 10, "Electronics", "Blue")
echo $widget.Name        # Widget
echo $custom.Category    # Electronics
\end{lstlisting}

Records feature value equality, optional fields with \code{?}, and default
values.

\section{Enum Definitions}
\ikw{enum}

\begin{lstlisting}
enum StockState { Unknown, Healthy, Low, Out }

enum Permissions : int {
    None = 0
    Read = 4
    Write = 2
    Execute = 1
}

var state = StockState.Healthy

    echo "Reorder needed"
}
\end{lstlisting}

\section{Event Definitions}
\ikw{event}\ikw{raise}\ikw{required}

Events are named message types with a fixed set of payload fields.  Any code
that can see the event name can \code{raise} it; any function in scope can
subscribe with \code{handles} (see Section~\ref{ch:functions}).

\textbf{Defining events:}

\begin{lstlisting}
event BuildCompleted {
    Project  = ""
    Duration = (timespan 0s)
    Success  = true
}

# Required event --- error if raised with no handlers registered
required event CriticalError { Message = "", Code = 0 }

# Local event --- automatically unregistered when the declaring scope exits
local event ScopedNotification { Text = "" }
\end{lstlisting}

\textbf{Raising events:}

\begin{lstlisting}
raise $BuildCompleted ({
    Project  = "MyApp",
    Duration = (timespan 5s),
    Success  = true
})
\end{lstlisting}

\textbf{Subscribing (in any visible scope):}

\begin{lstlisting}
func on-build(e) handles BuildCompleted {
    if ($e.Success) {
        writeline $"Build OK: {$e.Project} in {$e.Duration}"
    } else {
        writeline $"Build FAILED: {$e.Project}"
    }
}
\end{lstlisting}

Handler modifiers (\code{priority}, \code{when}, \code{once}) control
dispatch order, conditional execution, and single-fire semantics---see
Section~\ref{ch:functions} for the full syntax.

Fields not supplied in the \code{raise} payload keep their declared default
values.  Event fields are read-only inside the handler body.

\section{The Pipeline}

The pipe operator \code{|} connects command stages, sending the output of one
as input to the next:

\begin{lstlisting}
ls -la | where _.Type == file | sort Size | reverse | first 5
\end{lstlisting}

\begin{tipbox}
The current item in pipeline predicates and blocks is \code{\_}. This is
a special implicit variable---you do not need to declare it.
\end{tipbox}

Each stage in a pipeline receives objects (not text). Commands like
\code{where}, \code{sort}, and \code{map} operate on object properties
natively.

\section{Command Substitution}

Capture command output into a variable:

\begin{lstlisting}
var user = $(whoami)            # Capture as string
var count = $(ls | count)       # Capture pipeline result
var files = $(find . -name "*.cs" -type f)
\end{lstlisting}

\section{Subexpressions}

Parentheses group expressions and force evaluation:

\begin{lstlisting}
var result = (2 + 3)
echo (String.Join(" ", ["a", "b"]))
echo ($items | count)
\end{lstlisting}

\section{Ranges}
\iop{..}

\begin{lstlisting}
1..10             # 1, 2, 3, ..., 10 (inclusive)
1..2..10          # 1, 3, 5, 7, 9 (step of 2)
0..5              # 0, 1, 2, 3, 4, 5
10..1             # 10, 9, 8, ..., 1 (auto-descending)
\end{lstlisting}

Ranges are lazy \code{ToshRange} objects implementing
\code{IShellEnumerableObject}.

\section{Comprehensions}
\ikw{where}\ikw{let}

Comprehensions build collections from sequences using a concise
\emph{body}\,\code{<|}\,\emph{clause} syntax.  The clause specifies the
source, an optional filter, and optional intermediate bindings.

\subsection*{Collection Forms}

The opening and closing delimiters determine the output type:

\begin{center}
\begin{tabular}{lll}
\toprule
\textbf{Syntax} & \textbf{Result type} & \textbf{Evaluation} \\
\midrule
\code{[body <| clause]} & list (array) & eager \\
\code{\{: body <| clause :\}} & set (\code{HashSet}) & eager \\
\code{\{ key => value <| clause \}} & dict & eager \\
\code{(body <| clause)} & \code{LazySequence} & lazy / on demand \\
\bottomrule
\end{tabular}
\end{center}

\begin{lstlisting}
[$x * $x <| for x in 1..5]
# [1, 4, 9, 16, 25]

{: $x * $x <| for x in 1..5 :}
# {1, 4, 9, 16, 25}  -- duplicates removed automatically

{ $x => $x * $x <| for x in 1..5 }
# {1: 1, 2: 4, 3: 9, 4: 16, 5: 25}

($x * $x <| for x in 1..) | first 5    # lazy -- safe with infinite source
# 1, 4, 9, 16, 25
\end{lstlisting}

\subsection*{Clause Keywords}

\begin{description}
  \item[\code{for name in source}]
    Required.  Iterates \code{source}; the current element is bound to
    \code{name} (no \code{\$} prefix).  Inside the body and subsequent
    clause parts, refer to it as \code{\$name}.

  \item[\code{where condition}]
    Optional filter.  Only items for which \code{condition} is truthy are
    projected through to the body.

  \item[\code{let alias = expr}]
    Optional intermediate binding.  Evaluated once per item after the
    \code{where} filter.  Multiple \code{let} bindings may appear; each is
    visible in subsequent bindings and in the body.

\begin{lstlisting}
[$x <| for x in 1..20 where $x % 3 == 0]
# [3, 6, 9, 12, 15, 18]

[$label <| for x in 1..5 where $x % 2 != 0 let label = $"item-{$x}"]
# ["item-1", "item-3", "item-5"]
\end{lstlisting}
\end{description}

\subsection*{Multi-Clause Forms}

Three syntaxes extend a single \code{for} clause into a multi-variable iteration.

\paragraph{Cartesian product (comma \texttt{,})}
A comma after the source (or its modifiers) introduces a second clause.
Every combination of elements is produced---equivalent to nesting two
\code{for} loops:

\begin{lstlisting}
[($x, $y) <| for x in 1..3, y in ["a", "b"]]
# [(1,"a"), (1,"b"), (2,"a"), (2,"b"), (3,"a"), (3,"b")]

[$x + $y <| for x in [1, 2], y in [10, 20]]
# [11, 21, 12, 22]
\end{lstlisting}

The explicit nested \code{for} keyword produces the same result:

\begin{lstlisting}
[($x, $y) <| for x in 1..3 for y in ["a", "b"]]   # identical
\end{lstlisting}

\paragraph{Parallel / zip (\texttt{||})}
\code{||} between two clauses zips the sources together---one element from
each source per step.  Iteration terminates when the \emph{shorter} source
is exhausted:

\begin{lstlisting}
[$x + $y <| for x in [1, 2, 3] || y in [10, 20, 30]]
# [11, 22, 33]

[$x + $y <| for x in [1, 2, 3] || y in [10, 20]]   # shorter wins
# [11, 22]
\end{lstlisting}

\paragraph{Pattern destructuring (\texttt{(a, b, \ldots)})}
When the source yields tuples or lists, use a parenthesised name list to
bind each element to its own variable:

\begin{lstlisting}
[$a + $b <| for (a, b) in [(1, 2), (3, 4)]]
# [3, 7]

[$a + $b + $c <| for (a, b, c) in [(1, 2, 3), (4, 5, 6)]]
# [6, 15]

# Pairs produced by 'entries' work too:
{ $k => $v * 2 <| for (k, v) in ($myDict | entries) }
\end{lstlisting}

All three forms compose with \code{where}/\code{let} modifiers and work in
every collection form (\code{[...]}, \code{\{:~:\}}, \code{\{~\}}, \code{(~)}).

\section{Live / Streaming Output}
\label{sec:streaming-output}

Long-running commands that emit objects progressively (via \code{yield}
internally) are displayed incrementally in an interactive TTY session.
The REPL automatically promotes a pipeline to \emph{streaming mode} when it
detects a gap of roughly 250\,ms or more between successive output objects.

In streaming mode the REPL renders a live table:

\begin{itemize}
  \item The top border, header row, and mid-border are drawn immediately
        after the first object arrives.
  \item Each subsequent object is appended as a new row in real time.
  \item If a later object causes a column to widen, the entire table is
        redrawn from the top (using cursor-up escape sequences) to keep
        widths consistent.
  \item The closing bottom border is drawn when the command completes or
        is interrupted with \code{Ctrl-C}.
\end{itemize}

\begin{lstlisting}
ping -c 5 www.google.com    # rows appear one per second as replies arrive
tail -f /var/log/app.log    # new rows stream in as lines are written
\end{lstlisting}

Commands that complete quickly (e.g.\ \code{ls}) fall back to the standard
buffered renderer---the gap heuristic ensures short commands are never
artificially slowed. Streaming is automatically disabled when stdout is
redirected to a file or pipe (non-TTY).

\section{Glob Expansion}
\label{sec:globs}
\ikw{glob}

When a \emph{bareword} argument to an external process or one of the
builtin commands \code{echo}, \code{write}, \code{writeline}, or
\code{raw} contains the wildcard characters \code{*}, \code{?},
\code{[}, or the extended glob prefix \code{@(}, TōSh expands it
against the file system before the command is invoked.

\begin{lstlisting}
ls *.txt               # expands to all .txt files in $PWD
echo src/**/*.cs       # ** matches any number of path segments
rm build-?.log         # ? matches exactly one character
\end{lstlisting}

Glob expansion rules:

\begin{itemize}
  \item Only \textbf{bareword} arguments are expanded.  Quoted strings
        (\code{"*.txt"}, \code{'*.txt'}) and interpolated strings
        (\code{\$"*.txt"}) are \emph{never} expanded.
  \item If the glob matches no files the literal pattern is passed to
        the command unchanged (no error).
  \item Only commands that implement the implicit-glob contract perform
        expansion.  Pure shell built-ins such as \code{where}, \code{each},
        and \code{sort} do not expand globs---use \code{glob} or
        \code{find} to produce a file list first.
\end{itemize}

\begin{lstlisting}
# Use 'glob' to materialise a list from a pattern in a pipeline
glob "*.log" | where _.Size > 1mb | each { rm $_ }

# Quoted string - no expansion
echo "*.txt"           # prints the literal string *.txt
\end{lstlisting}

\endhead

\section{Picking Columns vs Rows}
\label{sec:get-row}

\code{get} and \code{row} form the canonical pipeline-slicing cluster.
\code{get} projects \emph{members} (columns); \code{row} selects
\emph{positions} (rows).  Both are variadic.

\begin{lstlisting}
ls | get Name Size              # column picker -- variadic field projection
ls | get Name                   # single column (yields scalars)
[10,20,30,40,50] | row 2        # row picker -- single index
[10,20,30,40,50] | row 4 0 2    # variadic, yields 50, 10, 30 in requested order
[10,20,30,40,50] | row [3,1,0]  # list literal works too
[10,20,30,40,50] | row 1..3     # contiguous range
\end{lstlisting}

\code{select} and \code{pick} are soft aliases for \code{get}.  Bad
indices in \code{row} throw \code{tosh.row.index\_out\_of\_range}.
\code{row} only materialises the prefix of the pipeline necessary to
satisfy the highest requested index, so it is safe on long but bounded
streams; infinite ranges (\code{row 0..}) are rejected.

\section{Structured Introspection}
\label{sec:introspection}

\code{members} and \code{methods} are the canonical introspection
commands.  Both accept first-argument keywords for filtering and
querying:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Subcommand} & \textbf{Effect} \\
\midrule
\code{has <Name>} & \code{true}/\code{false} for whether the named member exists. \\
\code{get <Name>} & Yields each matching member descriptor (zero-or-more). \\
\code{props}      & Filter to properties only (\code{members} only). \\
\code{fields}     & Filter to fields only (\code{members} only). \\
\code{methods}    & Filter to methods only (\code{members} only). \\
\code{events}     & Filter to events only (\code{members} only; reserved). \\
\bottomrule
\end{tabular}
\end{center}

The keyword may consume a trailing operand; any further arguments are
parsed as type targets, so the piped form and the named-type form are
interchangeable:

\begin{lstlisting}
$obj | members has Length        # bool from a piped instance
$obj | members get FullName      # descriptor record(s)
$obj | members props             # all properties of $obj's type
$obj | methods has ToUpper       # bool

members has Length string        # equivalent: type as trailing arg
methods get ToUpper string       # descriptor for String.ToUpper
\end{lstlisting}

\code{props} and \code{funcs} are top-level shortcuts for
\code{members props} and \code{methods}, respectively.

The verb-form CLR commands (\code{call}, \code{call-method},
\code{get-prop}, \code{get-props}, \code{get-methods}, \code{has-prop},
\code{has-method}, \code{set-prop}, \code{del-prop}) are deprecated
since version \code{26.05.0.10}; they remain registered for backward
compatibility but emit deprecation diagnostics.  Prefer the fluent
member-access syntax (\code{\$obj.Method(\$args)}, \code{\$obj.Prop},
\code{\$obj.Prop = value}) and the introspection cluster above.

\section{System Namespace}

The full \code{System.*} namespace tree is exposed via the CLR resolver
without an \code{import} statement.  This makes \code{System.IO.*} the
canonical handle API for file streams, paths, and binary IO:

\begin{lstlisting}
var fh = System.IO.File.OpenRead "/etc/hostname"
defer { $fh.Dispose() }
var bytes = System.IO.File.ReadAllBytes "/etc/hostname"
var leaf  = System.IO.Path.GetFileName $path
var b64   = System.Convert.ToBase64String $bytes
\end{lstlisting}

\section{Binder Pass}
\label{sec:binder-pass}

Between parse and evaluate, a static binder pass walks the AST and
emits \code{tosh.bind.unknown\_command} diagnostics for command names
that look like typos for registered builtins or aliases (Levenshtein
distance \(\le 1\) for short names, \(\le 2\) for longer).  Same-source
\code{func} declarations are recognised and never flagged.

Strictness depends on context:

\begin{center}
\begin{tabular}{ll}
\toprule
\textbf{Context} & \textbf{Default mode} \\
\midrule
Interactive REPL                 & \code{Warn} (stderr) \\
\code{tosh -c "\ldots"}          & \code{Strict} \\
\code{tosh script.tosh} / \code{source} & \code{Strict} \\
\code{profile.tosh} / \code{autoload/*} & \code{Warn} \\
\bottomrule
\end{tabular}
\end{center}

To bypass the binder entirely (recovery escape hatch; undocumented in
user-facing help), set \code{TOSH\_DISABLE\_BINDER=1}.

\chapter{Scripts and Subcommand Dispatch}
\label{ch:subcommands}
\ikw{subcommand}\ikw{flag}\ikw{arg}\ikw{eager}\ikw{hidden}
% =============================================================================

TōSh has a built-in system for turning a script into a structured CLI tool.
The \code{subcommand} block declares named commands with typed flags and
positional arguments; TōSh handles parsing, validation, and auto-generated
help text automatically.

\section{Subcommand Basics}

A \code{subcommand} block declares one named command.  Its body runs when
the user selects that command on the command line:

\begin{lstlisting}
subcommand greet {
    flag name: string = "World"
    echo $"Hello, {$name}!"
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh myscript.tosh greet            # Hello, World!
tosh myscript.tosh greet --name Alice  # Hello, Alice!
\end{lstlisting}

\subsection*{Arrow form}

A subcommand with parameters and a single-expression body may use the arrow
form.  Parameters in the arrow form are passed directly, not via flags:

\begin{lstlisting}
subcommand greet(name: string) => echo $"Hello, {$name}!"
\end{lstlisting}

\begin{warnbox}
Parameters declared with \code{()} in the arrow form require the
\code{=>} separator.  Using a block body with \code{()} parameters is a
parse error (\code{tosh.parser.subcommand\_params\_require\_arrow}).
\end{warnbox}

\section{Flags and Arguments}

Inside a subcommand body, \code{flag} declares an optional named option and
\code{arg} declares a required positional argument:

\begin{lstlisting}
subcommand deploy {
    arg  host: string
    flag port: int    = 22
    flag user: string = "root"
    flag dry-run: bool = false

    if ($dry-run) {
        echo $"[dry-run] ssh {$user}@{$host}:{$port}"
    } else {
        ssh $"-p{$port}" $"{$user}@{$host}"
    }
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh deploy.tosh deploy myserver
tosh deploy.tosh deploy myserver --port 2222 --user alice
tosh deploy.tosh deploy myserver --dry-run
\end{lstlisting}

\begin{itemize}
  \item \code{flag} values are set with \code{--name value} or \code{--name=value}.
  \item The CLI flag name is exactly the identifier as declared---no
        case folding or kebab-from-snake conversion.  A flag declared
        \code{flag dry-run} is invoked as \code{--dry-run}; \code{flag fooBar}
        as \code{--fooBar}; \code{flag MAX\_RETRIES} as \code{--MAX\_RETRIES}.
  \item Boolean flags may be set with \code{--name} (sets to \code{true}) or
        \code{--no-name} (sets to \code{false}).
  \item \code{arg} values are consumed from the remaining positional tokens in
        declaration order.
  \item \code{--} stops option parsing; all tokens after it are positional.
\end{itemize}

\section{Nested Subcommands}

Subcommands nest to build command trees.  Dispatch descends into the child
whose name matches the first positional token:

\begin{lstlisting}
subcommand git {
    subcommand commit {
        flag message: string = ""
        flag all: bool = false
        echo $"committing: {$message}"
    }

    subcommand push {
        arg remote: string = "origin"
        flag force: bool = false
        echo $"pushing to {$remote}"
    }
}
\end{lstlisting}

\begin{lstlisting}[title={Usage}]
tosh myscript.tosh git commit --message "initial"
tosh myscript.tosh git push origin --force
\end{lstlisting}

Flags are looked up leaf-to-root: a flag defined on a parent is available to
all its descendants.

\section{Subcommand Modifiers}

Modifiers appear between \code{subcommand} and the name:

\begin{description}
  \item[(none)] Body runs only when this is the chosen leaf of dispatch.
  \item[\code{eager}] Body runs even when execution descends into a child.
    Used for setup work (e.g.\ loading config before a child acts on it).
    May not be combined with \code{hollow}.
  \item[\code{hidden}] Excluded from auto-generated help and ``did you mean''
    suggestions.  Still fully callable.
  \item[\code{hollow}] Pure namespace---body must contain only nested
    \code{subcommand} declarations.  Cannot be instantiated directly.
  \item[\code{vital}] Throws a runtime error if children exist but the user
    did not choose one (instead of showing auto-help).
\end{description}

\begin{lstlisting}[title={eager parent}]
eager subcommand db {
    flag env: string = "production"
    writeline $"Connecting to {$env} database"   # always runs

    subcommand migrate {
        flag dry-run: bool = false
        run-migrations --env $env --dry-run $dry-run
    }

    subcommand seed {
        run-seed-data --env $env
    }
}
\end{lstlisting}

\section{Auto-Help}

Every subcommand automatically supports \code{--help} at any nesting level.
The help output is generated from the \code{flag} and \code{arg} declarations
at the current and ancestor levels.  To opt out of automatic help, declare your
own \code{flag help: bool = false}.

\begin{warnbox}[Doc-comments not yet included in auto-help]
Although \code{\#\#} doc-comments can be written above a \code{subcommand}
block, the current runtime does not attach them to the auto-generated help
output.  Only the structural information (flag names, types, and which
subcommands exist) is shown.  If you need richer descriptions today, write
them in the script body as \code{writeline} output guarded by
\code{if (\$tosh.Script.Help)}.
\end{warnbox}

\begin{lstlisting}[title={Invoking auto-help}]
tosh myscript.tosh --help
tosh myscript.tosh git --help
tosh myscript.tosh git commit --help
\end{lstlisting}

\begin{tabular}{L{7.6cm}L{5.6cm}}
\toprule
\textbf{Code} & \textbf{Trigger} \\
\midrule
\code{tosh.runtime.missing\_script\_flag} & Required flag not provided. \\
\code{tosh.runtime.missing\_script\_argument} & Required positional \code{arg} not provided. \\
\code{tosh.runtime.unknown\_script\_flag} & Unrecognised \code{--flag} on the command line. \\
\code{tosh.runtime.script\_option\_requires\_value} & Flag that expects a value was given without one. \\

% =============================================================================
\chapter{Overview \& Execution Model}
\label{ch:compile-overview}
% =============================================================================

TōSh runs in two modes: an \emph{interpreter} (\code{ToshEngine}) and an
\emph{ahead-of-time compiler} (\code{Tosh.Compiler}) that emits standard
.NET assemblies. The interpreter is the canonical semantics; the compiler is
a faithfulness-preserving lowering of those semantics onto the CLR. Both
modes share the same lexer, parser, binder, lowerer, and type checker —
only the back end differs.

\section{When each mode runs}
\label{sec:compile-when}

\begin{tabular}{l p{0.65\linewidth}}
\toprule
\textbf{Mode} & \textbf{Triggered by} \\
\midrule
Interpreter (REPL) & \code{tosh}, no positional source. \\
Interpreter (one-liner) & \code{tosh -c "..."}. \\
Interpreter (script) & \code{tosh path/to/script.tosh}. \\
Compiler (CLI) & \code{tosh --compile path.tosh -o out.dll} (\S\ref{ch:compile-cli}). \\
Compiler (MSBuild) & \code{<Project Sdk="Tosh.Sdk">} (\S\ref{ch:compile-msbuild}). \\
\bottomrule
\end{tabular}

\section{Compiler pipeline}
\label{sec:compile-pipeline}

\begin{enumerate}
  \item \textbf{Lex / parse.} Identical to the interpreter; produces a
        \code{ParseResult} with the same syntax tree.
  \item \textbf{Bind / lower.} Identical to the interpreter; produces a
        \code{BoundUnit} containing \code{BoundStatement}s and
        \code{BoundExpression}s.
  \item \textbf{Type check.} The same \code{TypeChecker} runs, but in
        \emph{compile mode} it emits an extra audit pass
        (\code{CheckCompileAnnotations}) for missing or implicit
        \code{dynamic} annotations (\S\ref{ch:compile-types}).
  \item \textbf{Emit.} \code{BoundUnitEmitter} walks the bound tree and
        emits IL into a \code{PersistedAssemblyBuilder}. Each shape is
        gated by a profile/tier check (\S\ref{ch:compile-profiles}).
  \item \textbf{Persist.} The assembly is written to disk; an optional
        reference assembly, apphost wrapper, and single-file bundle are
        produced as requested (\S\ref{ch:compile-cli}).
\end{enumerate}

\section{Parity contract}
\label{sec:compile-parity}

A program that compiles cleanly must, when run, produce the same observable
behaviour as the interpreter would for the same source. Observable here
means: stdout, stderr, exit code, files written by redirection, and values
returned to a hosting C\# caller. Internal scheduling, allocation, and
diagnostics-not-yet-promoted-to-errors are not part of the contract.

The conformance test layer (\S\ref{ch:compile-conformance}) is the
machine-checked expression of this contract.

\begin{tipbox}[Where to look]
The full pipeline lives under \code{src/Tosh.Compiler/} and
\code{src/Tosh.Compiler.Runtime/}. The bound tree the emitter walks is
defined in \code{src/Tosh.Language/Binding/BoundNodes/}.
\end{tipbox}


% =============================================================================
\chapter{Command-Line Interface}
\label{ch:compile-cli}
% =============================================================================

The compiler is invoked through the same \code{tosh} binary that runs the
shell. The first positional argument selects between shell and compile
modes:

\begin{lstlisting}
# Interpret a script.
tosh greet.tosh

# Compile a script to a managed assembly.
tosh --compile greet.tosh -o greet.dll
tosh -C greet.tosh -o greet.dll
\end{lstlisting}

\section{Flags}
\label{sec:compile-flags}

\begin{tabular}{>{\raggedright\arraybackslash}p{0.34\linewidth} >{\raggedright\arraybackslash}p{0.55\linewidth}}
\toprule
\textbf{Flag} & \textbf{Effect} \\
\midrule
\code{-o PATH}, \code{--output PATH} & Output assembly path. Required; the file extension does not have to be \code{.dll}. \\
\code{--profile NAME} & Compile profile (\code{permissive}, \code{runtime}, or \code{pure}). Default \code{permissive}. May also be written \code{--profile=NAME}. \\
\code{--compile-allow-dynamic}, \code{--allow-dynamic} & Suppress \code{tosh.compile.implicit\_dynamic} diagnostics. Equivalent to opting out of strict-mode for variables whose type the inferrer cannot pin down. \\
\code{--emit-refasm} & Also emit a sibling \code{*.ref.dll} stamped with \code{[ReferenceAssembly]} so C\# / F\# / Roslyn consumers can target the public surface without dragging in private members. \\
\code{--no-apphost} & Skip the native apphost wrapper (Windows: \code{.exe}; Unix: bare). The \code{.dll} is still written and remains runnable via \code{dotnet}. \\
\code{--publish-single-file} & Bundle the .NET runtime and all dependencies into a single self-contained executable. Implies an apphost. \\
\bottomrule
\end{tabular}

\section{Examples}
\label{sec:compile-examples}

\begin{lstlisting}
# Default profile -- accepts every shape the interpreter does.
tosh --compile script.tosh -o script.dll

# Strict -- reject source-replay (Tier 3) shapes.
tosh --compile script.tosh -o script.dll --profile=runtime

# Emit a refasm alongside the implementation assembly.
tosh --compile lib.tosh -o lib.dll --emit-refasm

# Single-file self-contained binary (~70 MB; bundles the runtime).
tosh --compile cli.tosh -o cli --publish-single-file
\end{lstlisting}

\begin{notebox}[Errors]
A \code{--compile} invocation with no source paths fails with
``\code{The '--compile'/'-C' flag requires at least one script path.}''.
Unknown options inside the \code{--compile} arg list fail with
``\code{Unknown option '...' for --compile.}''.
\end{notebox}


% =============================================================================
\chapter{Profiles \& the Tier Model}
\label{ch:compile-profiles}
% =============================================================================

Every compiled shape lives at one of three tiers. The \emph{profile}
selects how strict the compiler is about which tiers it accepts.

\section{Tiers}
\label{sec:compile-tiers}

\begin{tabular}{l p{0.7\linewidth}}
\toprule
\textbf{Tier} & \textbf{Definition} \\
\midrule
1 — native IL & Pure IL with no \code{ToshHost} call at runtime: literals, arithmetic, control flow, top-level user-function calls resolved at IL-emit time, real CLR module-type field reads. \\
2 — runtime-hosted & Real IL but calls into \code{Tosh.Compiler.Runtime.ToshHost} for builtin command dispatch, dynamic member access, qualified lookup, redirection scopes, etc. \\
3 — source-replay & The emitted assembly registers a span of the original tosh source and re-evaluates it through \code{ToshEngine} at runtime. Used for class / record / struct / union / enum / trait bodies, complex module bodies, and block-pipeline arguments. \\
\bottomrule
\end{tabular}

\section{Profiles}
\label{sec:compile-profiles-table}

\begin{tabular}{l c p{0.55\linewidth}}
\toprule
\textbf{Profile} & \textbf{Max tier} & \textbf{Use case} \\
\midrule
\code{permissive} & 3 & Default. Accepts every shape the interpreter does. The compile is guaranteed to succeed if the program parses, binds, and type-checks. \\
\code{runtime} & 2 & Real, redistributable .NET assembly that doesn't carry its own source for re-evaluation. Rejects user-defined types, complex module bodies, and block arguments. \\
\code{pure} & 1 & No \code{ToshHost} calls at runtime, no source replay. Today this is mostly aspirational — even \code{echo} is a Tier-2 builtin — but the profile exists as a forcing function for future ``lift this builtin into IL'' work. \\
\bottomrule
\end{tabular}

\section{\code{RequireTier} semantics}
\label{sec:compile-requiretier}

Internally, every shape emitter calls \code{RequireTier(int tier, string
feature)} before lowering itself. If the requested tier exceeds the maximum
allowed by the active profile, the emitter records a diagnostic of the form

\begin{lstlisting}
profile 'pure' rejects tier 2 feature: builtin command dispatch (statement)
\end{lstlisting}

Diagnostics are deduplicated per \code{(tier, feature)} pair: a program with
fifty calls to \code{ls} in pure profile reports the violation once, not
fifty times.

\section{Parity expectations}
\label{sec:compile-profile-parity}

A profile narrowing is \emph{always conservative}: any program that compiles
under \code{pure} also compiles under \code{runtime} and \code{permissive},
and any program that compiles under \code{runtime} also compiles under
\code{permissive}. Behaviour is identical across profiles when the program
compiles under all three.

\begin{tipbox}[Choosing a profile]
Pick \code{runtime} when you want a redistributable .NET library that does
not need to ship its own source. Pick \code{permissive} during development
or when the program uses class / record / module bodies the runtime profile
rejects today. Pick \code{pure} only in tooling contexts (refasm-only
builds, audit checks) where Tier-2 dispatch is itself the thing under test.
\end{tipbox}


% =============================================================================
\chapter{Type Discipline in Compiled Mode}
\label{ch:compile-types}
% =============================================================================

The type checker runs in every mode, but compile mode adds an
\emph{annotation audit} that the interpreter does not. The audit promotes
weakly-typed shapes to errors so a redistributable assembly cannot expose a
public surface that silently degrades to \code{dynamic}.

\section{The audit rules}
\label{sec:compile-audit-rules}

\begin{tabular}{>{\raggedright\arraybackslash}p{0.42\linewidth} >{\raggedright\arraybackslash}p{0.5\linewidth}}
\toprule
\textbf{Diagnostic} & \textbf{When} \\
\midrule
\code{tosh.compile.missing\_type\_annotation} & A \code{func} has no
return-type annotation, or a parameter has no type annotation. \\
\code{tosh.compile.implicit\_dynamic} & A \code{var} declaration has no
type annotation \emph{and} the inferrer cannot pin down a concrete type from
the initializer. \\
\bottomrule
\end{tabular}

\section{Explicit \code{dynamic} opt-out}
\label{sec:compile-explicit-dynamic}

The audit treats an explicit \code{: dynamic} annotation as an
intentional opt-out. Both of the following are accepted by the audit:

\begin{lstlisting}
func passthrough(x: dynamic) -> dynamic { return $x }

var f: dynamic = (ls)
\end{lstlisting}

The same source without the annotations would fail compile:

\begin{lstlisting}
func passthrough(x) -> dynamic { return $x }
# tosh.compile.missing_type_annotation: parameter 'x' is missing an
# annotation. Use `dynamic` to opt out explicitly.

var x = (ls)
# tosh.compile.implicit_dynamic: variable 'x' has no type annotation
# and the inferrer could not pin down a concrete type.
\end{lstlisting}

\section{The \code{--allow-dynamic} flag}
\label{sec:compile-allow-dynamic}

\code{--compile-allow-dynamic} (alias \code{--allow-dynamic}) suppresses
\code{tosh.compile.implicit\_dynamic}. It does not suppress
\code{tosh.compile.missing\_type\_annotation}: function signatures must
always be either typed or explicitly \code{dynamic}, because they form the
public CLR surface of the compiled assembly.

\section{Implementation note}
\label{sec:compile-types-impl}

The \code{AnnotatedDynamic} flag on \code{BoundVariableDeclaration} records
whether the source carried an explicit \code{: dynamic}. The Lowerer sets
the flag (case-insensitive on the type name); the audit consults it in
\code{CheckVarAnnotation}. Synonyms for explicit dynamic on parameters are
\code{dynamic}, \code{any}, and \code{object}.


% =============================================================================
\chapter{Public CLR Shape}
\label{ch:compile-clr-shape}
% =============================================================================

Compiled tosh source produces a single .NET assembly. The shape is designed
to be consumable from C\#, F\#, and reflection-driven tooling without
re-parsing the source.

\section{Top-level statements}
\label{sec:compile-clr-toplevel}

A top-level user function \code{func greet(name: string) -> string} becomes
a public static method on a class named after the assembly's main type.
Module bodies become nested static classes.

\section{Overloads}
\label{sec:compile-clr-overloads}

When a tosh function name is overloaded, every overload is emitted as a
separate static method under the same CLR name. Argument types come from
the parameter annotations, so overload resolution from C\# follows the
ordinary CLR rules.

\begin{lstlisting}
# tosh
func pick(a: int) -> string => $"one:$a"
func pick(a: int, b: int) -> string => $"two:$a+$b"
\end{lstlisting}

\begin{lstlisting}[language={[Sharp]C}]
// C# consumer
Greet.pick(1);        // "one:1"
Greet.pick(1, 2);     // "two:1+2"
\end{lstlisting}

\section{Name mangling}
\label{sec:compile-clr-mangling}

Tosh identifiers may contain characters the CLR-targeted languages reject —
hyphens are the common case (\code{func to-json}). The emitter rewrites
each illegal character to \code{\_} and prefixes leading digits, then
stamps the original spelling on the resulting member with
\code{[ToshOriginalName("to-json")]}. Tools such as the LSP, the MCP server,
and editor extensions read the attribute to present the original
identifier.

When two top-level types or functions mangle to the same CLR name a
\code{tosh.compile.name\_mangling\_collision} diagnostic fails the build.

\section{User-defined types}
\label{sec:compile-clr-types}

Compiled \code{class}, \code{struct}, \code{record}, \code{enum},
\code{interface}, \code{trait}, and \code{union} declarations are emitted
as public CLR types stamped with \code{[ToshType(Kind, SpanStart,
SpanLength)]}. The span identifies the original declaration in the
registered source so source-replay-backed types can rebind full interpreter
semantics through \code{ToshHost.RegisterTypeFromSource} when needed.

\section{Reference assemblies}
\label{sec:compile-clr-refasm}

\code{--emit-refasm} writes a sibling \code{*.ref.dll} stamped with
\code{[ReferenceAssembly]}. The refasm exposes only the public surface
(types, methods, signatures) and is the recommended target for downstream
C\# / F\# / Roslyn consumers — it isolates them from private-member churn
and reduces incremental rebuild scope.

\chapter{Pipelines \& Redirections Under Compile}
\label{ch:compile-pipelines}
% =============================================================================

Pipeline construction and stream redirection are emitted as IL that calls
into \code{Tosh.Compiler.Runtime.ToshHost} (Tier 2). The lowering preserves
both the lazy-by-stage semantics of the interpreter and the deterministic
disposal order of redirection sinks.

\section{Pipeline stages}
\label{sec:compile-pipeline-stages}

A multi-stage pipeline lowers to a chain of \code{RunStage} calls seeded by
either \code{EmptyInput} (top-of-pipeline) or \code{SeedFromValue} (when a
value-typed expression feeds the pipeline):

\begin{lstlisting}
ls -la | where _.Type == "file" | sort-by Size | head 10
\end{lstlisting}

becomes, schematically:

\begin{lstlisting}[language={[Sharp]C}]
var input = ToshHost.EmptyInput();
input = ToshHost.RunStage(ToshHost.ResolveCommand("ls"),     input, ["-la"]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("where"),  input, [_filter]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("sort-by"),input, ["Size"]);
input = ToshHost.RunStage(ToshHost.ResolveCommand("head"),   input, [10]);
ToshHost.DrainStatement(input);
\end{lstlisting}

Each stage is executed lazily: a stage's body does not run until the next
stage pulls from its async enumerable. \code{DrainStatement} (statement
context) and \code{DrainEnumerator} (value context) are the only points
that force evaluation.

\section{Stream redirection}
\label{sec:compile-redirection}

Output redirections (\code{out>}, \code{err>}, \code{o+e>}, and the
\code{>>} append variants) and input redirection (\code{in<}) all lower to
a single \code{ToshHost.BeginRedirection} call wrapping the pipeline body
in a \code{using} (try/finally + Dispose):

\begin{lstlisting}
echo hello out> "log.txt"
\end{lstlisting}

becomes, schematically:

\begin{lstlisting}[language={[Sharp]C}]
using (ToshHost.BeginRedirection(
        streams: [1],         // stdout
        modes:   [0],         // truncate
        targets: ["log.txt"],
        inputPath: null))
{
    /* pipeline body */
}
\end{lstlisting}

Output sinks are flushed and closed in reverse order during \code{Dispose};
\code{Console.Out} / \code{Console.Error} / \code{Console.In} are restored
to their pre-scope readers.

\section{Input redirection}
\label{sec:compile-input-redirection}

Input redirection installs \emph{both} a \code{Console.SetIn(...)} reader
(so commands that read \code{Console.In} — e.g.\ \code{read-line} — observe
the redirected file) and a thread-static input path consulted by
\code{EmptyInput()} (so commands that consume the pipeline input — e.g.\
\code{cat}, \code{wc}, \code{grep}, \code{read-lines} — observe the same
file as a sequence of lines).

\begin{lstlisting}
echo (read-line) in< "in.txt"          # reads via Console.In
cat in< "in.txt"                       # reads via pipeline input
\end{lstlisting}

\section{Nested redirection}
\label{sec:compile-nested-redirection}

\code{RedirectionScope} tracks per-scope state for the streams and sinks it
opened. Each scope only restores state it actually installed: an
output-only nested scope cannot clobber an outer scope's input path on
dispose, and vice versa.

\begin{warnbox}[Pre-existing footgun, now fixed]
The original implementation restored the thread-static input path
unconditionally on dispose. A nested output redirection inside an outer
input redirection would therefore wipe the outer scope's input path,
causing later pipeline-input consumers to see no input. The current
implementation gates the restore on a \code{\_trackedInputPath} flag set
only when the inner scope itself opened an input redirection.
\end{warnbox}

\chapter{Function References in Compiled Mode}
\label{ch:compile-funcrefs}
% =============================================================================

The \code{\&name} expression evaluates to an \code{IShellCallable}. In
compiled mode the value is a \code{CompiledMethodReferenceValue} bound
directly to one or more emitted \code{MethodInfo}s, not a late-bound name
lookup.

\section{Single-overload fast path}
\label{sec:compile-funcref-single}

When a function name has exactly one compiled overload the emitter loads
the \code{MethodInfo} via \code{ldtoken} / \code{MethodBase.GetFromHandle}
and calls \code{ToshHost.MakeFunctionReferenceFromMethod(method, name)}.
Invocation reorders named arguments to match the parameter list and calls
the method directly.

\begin{lstlisting}
func inc(n: int) -> int => $n + 1
var f = &inc
$f(41)                # 42
\end{lstlisting}

\section{Overloaded references}
\label{sec:compile-funcref-overload}

When a function name has two or more compiled overloads the emitter emits a
\code{MethodInfo[]} containing each overload and calls
\code{MakeFunctionReferenceFromMethods(methods, name)}. Invocation routes
through \code{InvokeUserOverload}, which scores each candidate against the
supplied argument list and dispatches to the best match.

\begin{lstlisting}
func pick(a: int) -> string => $"one:$a"
func pick(a: int, b: int) -> string => $"two:$a+$b"
var f = &pick
$f(1)            # "one:1"
$f(1, 2)         # "two:1+2"
\end{lstlisting}

\section{Named arguments through references}
\label{sec:compile-funcref-named}

Named-argument calls (\code{\$f(value=42, label="answer")}) are reordered
against the chosen overload's parameter list. Single-overload calls reorder
in \code{BindNamedArguments}; overload-set calls inherit the existing
\code{InvokeUserOverload} reorder pass. Missing optional parameters fall
back to their declared default; missing required parameters surface as the
ordinary arity-mismatch failure.

\section{Late-bound fallback}
\label{sec:compile-funcref-fallback}

For names that the compiler cannot resolve at emit time (e.g.\ a reference
to a builtin command or to a function loaded later through a host) the
emitter emits \code{MakeFunctionReference(name)} instead. The resulting
callable consults the runtime command table at invocation time.

\chapter{Other Bound-Shape Emitters}
\label{ch:compile-shapes}
% =============================================================================

Several language constructs lower to dedicated host helpers rather than
inline IL. They are summarised here so the implementation surface is
discoverable.

\section{Records}
\label{sec:compile-shape-records}

\begin{tabular}{l p{0.6\linewidth}}
\toprule
\textbf{Field shape} & \textbf{Lowering} \\
\midrule
\code{name: value} & Plain \code{Ldstr} key + value expression. \\
\code{(\$key): value} & Key expression evaluated, \code{ToString()}, then value (Tier 2). \\
\code{...\$source} & Call to \code{ToshHost.SpreadRecord} with the source on the stack (Tier 2). \\
\bottomrule
\end{tabular}

\begin{lstlisting}
var base = { name: "alice", age: 30 }
var ext  = { ...$base, age: 31, role: "admin" }
echo $ext.name $ext.age $ext.role     # alice 31 admin
\end{lstlisting}

\section{Tuple destructuring}
\label{sec:compile-shape-tuples}

A statement of the form \code{(\$a, \$b) = expr} lowers to one
\code{DestructureArray(value, count)} call followed by \code{count}
strongly-typed local stores. Missing slots collapse to \code{null}.

\begin{lstlisting}
var a = 0
var b = 0
($a, $b) = [10, 20]
echo $a $b           # 10 20
\end{lstlisting}

\section{\code{throw} as expression}
\label{sec:compile-shape-throw}

A \code{throw expr} in expression position lowers to a
\code{ToshHost.ThrowAsException(value)} call that returns \code{object} so
the rest of the surrounding expression typechecks.

\begin{lstlisting}
var port = $env.PORT ?? throw "PORT is required"
\end{lstlisting}

\section{Other helpers}
\label{sec:compile-shape-other}

\code{ToArray}, \code{IndexOrNull}, \code{IsTruthy},
\code{AsRedirectionPath}, \code{MakeMemberProjection}, and
\code{MakeFunctionReference[FromMethod[s]]} all live in
\code{Tosh.Compiler.Runtime.ToshHost} and are called from the
\code{BoundUnitEmitter} via cached \code{MethodInfo}s.

\chapter{Conformance Test Layer}
\label{ch:compile-conformance}
% =============================================================================

Two test surfaces in \code{tests/Tosh.Tests/CompilerFeatureMatrixTests.cs}
turn the parity contract from \S\ref{sec:compile-parity} into machine-checked
expectations.

\section{Feature matrix}
\label{sec:compile-conformance-matrix}

\code{FeatureCases()} yields one row per language shape with a flag per
profile saying whether the shape should compile cleanly under that profile.
The matrix is the executable form of \S\ref{ch:compile-limits}.

\begin{lstlisting}[language={[Sharp]C}]
yield return FeatureCase(
    id: "redirection.out-file",
    category: "redirection",
    source: "echo hi out> \"x\"",
    permissive: true, runtime: true, pure: false,
    note: "stream redirection requires Tier 2");
\end{lstlisting}

\section{Conformance cases}
\label{sec:compile-conformance-exec}

\code{ConformanceCases()} yields one row per shape that should produce a
specific stdout (and optionally a specific file) under the default profile.
The harness compiles the source, runs the resulting assembly, and asserts
on the captured streams.

\begin{lstlisting}[language={[Sharp]C}]
yield return ExecCase(
    id: "redirection.in-pipeline",
    source: "cat in< \"{TMPFILE}\"",
    stdout: "alpha\nbeta",
    note: "input redirection seeds pipeline-input commands like cat",
    seedFile: "alpha\nbeta\n");
\end{lstlisting}

\section{Adding a row}
\label{sec:compile-conformance-add}

Two-step recipe:

\begin{enumerate}
  \item Add a \code{FeatureCase} or \code{ExecCase} row alongside the
        implementation change. Runtime/Pure flags should reflect the
        \code{RequireTier} call the emitter makes for the new shape.
  \item Run \code{dotnet test tests/Tosh.Tests/Tosh.Tests.csproj
        --filter "FullyQualifiedName~CompilerFeatureMatrixTests"} and
        confirm the row passes for every profile its flags claim.
\end{enumerate}

\begin{notebox}[Console serialisation]
Tests that capture stdout/stderr or install \code{Console.SetIn} share the
xUnit collection \code{ConsoleSerialCollection} so xUnit serialises them.
Concurrent collections that touch \code{Console.\{Out, Error, In\}}
otherwise interleave output and produce flaky equality checks.
\end{notebox}

func browse(path?: string = ".") {
    var items = ls $path | get Name
    var choice = tui pick $"Contents of {$path}:" ...$items ".."

    if ($choice == "..") {
        browse (dirname $path)
    } else if (is-dir $"{$path}/{$choice}") {
        browse $"{$path}/{$choice}"
    } else {
        cat $"{$path}/{$choice}"
    }
}

func service-manager() {
    var services = systemctl list-units --type service
        | where _.Active == "active"
        | get Unit
    var choice = tui pick "Select service:" ...$services
    var action = tui pick $"Action for {$choice}:" \
        "status" "restart" "stop" "logs"

    switch ($action) {
        case "status"  { systemctl status $choice }
        case "restart" { systemctl restart $choice }
        case "stop"    { systemctl stop $choice }
        case "logs"    { journalctl -n 50 -u $choice }
    }
}
