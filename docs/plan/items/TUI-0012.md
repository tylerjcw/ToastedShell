## Problem

The TUI has never been measured. Two things are known to be wasteful by inspection and
neither has a number attached:

- Every frame clears the screen and repaints in whole (`TUI-0001`).
- `TuiRenderHelpers.ClipPlain` appends one character at a time and recomputes the
  visible length of the accumulated string on each iteration — quadratic in the line
  length, per line, per frame.

Live screens make both matter. A monitor at a one-second refresh now does this work
repeatedly against a terminal that may be 200 columns wide, and an idle screen polls
input every 15 ms.

Without a budget, `TUI-0001` cannot be called done: "diffed output" would be a design
note rather than a measured improvement.

## Acceptance

- [ ] A benchmark that renders representative screens at representative sizes
- [ ] A stated budget: frame build time, bytes written per frame, and idle cost per second
- [ ] Baseline recorded before `TUI-0001` so the change has something to be measured against
- [ ] Idle cost of a screen with no refresh interval is effectively zero
- [ ] A redraw that changes one row writes bytes proportional to that row, not to the screen
- [ ] The benchmark runs in `bench/` alongside the existing ones

## Notes

Take the baseline first. Once the string frames are gone there is nothing left to
compare against, and the number that makes the case for the rewrite will have been
thrown away.

Worth measuring separately: the cost of invoking a script handler through
`IShellCallable`, since `TUI-0002`'s `Custom` widget and `TUI-0008`'s bindings both put
script code on a path that runs repeatedly. The decision to keep handlers on the
refresh path rather than the frame path was made on reasoning, not measurement, and
should be checked.
