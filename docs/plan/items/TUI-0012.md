## Problem

The TUI has never been measured. Two things are known to be wasteful by inspection and
neither has a number attached:

- Every frame clears the screen and repaints in whole (`TUI-0001`).
- `TuiRenderHelpers.ClipPlain` appends one character at a time and recomputes the
  visible length of the accumulated string on each iteration — quadratic in the line
  length, per line, per frame.

Live screens make both matter. A monitor at a one-second refresh now does this work
repeatedly against a terminal that may be 200 columns wide, and an idle screen polls
input every 15 ms.

Without a budget, `TUI-0001` cannot be called done: "diffed output" would be a design
note rather than a measured improvement.

## Acceptance

- [x] A benchmark that renders representative screens at representative sizes
- [x] A stated budget: frame build time, bytes written per frame, and idle cost per second
- [x] Baseline recorded before `TUI-0001` so the change has something to be measured against
- [x] Idle cost of a screen with no refresh interval is effectively zero
- [x] A redraw that changes one row writes bytes proportional to that row, not to the screen
- [x] The benchmark runs in `bench/` alongside the existing ones

## The budget

- **A widget-tree frame at 120x40 builds in under 150 us.** Measured 90 us, or 108 us with
  twenty pull bindings re-asked. This is the path everything a script writes goes through.
- **A hand-rendered browser frame at 120x40 builds in under 300 us.** The help browser is
  239 us. The config browser is 1.08 ms and is the standing exception — `TUI-0014`'s
  territory, not rendering's.
- **A redraw writes bytes proportional to what changed.** Nothing changed writes nothing;
  one cell writes 9 bytes; one row writes 32. A full repaint is 5,088, so the diff is worth
  roughly 160x on the case it exists for.
- **An idle screen renders nothing and writes nothing**, however long it waits.
- **No frame path constructs a runtime, loads an assembly, or touches the filesystem.**

### The allocation line is revised

The proposed budget said "under 16 KB once buffers are reused". That is not reachable as
written and the number should not have been proposed without the arithmetic behind it: a
`TuiCell` is 32 bytes, so a 120x40 grid is **150 KB before anything is drawn into it**. The
widget tree's 187 KB is that buffer plus about 36 KB of actual work.

Pooling buffers would recover the 150 KB and is not worth doing. A TUI redraws on a
keystroke or on a one-second tick, not at sixty frames a second, so this is 150 KB of
short-lived Gen0 a few times a second — and the diffing writer needs the previous frame
kept alive, so a pool would be a swap chain with ownership rules threaded through the
failure path. The budget is stated as **under 2x the frame buffer** instead, which is the
thing actually worth watching: it says the drawing is cheap relative to the grid it draws
into, which is what went wrong below.

## What the measurement found

Two things, and neither was visible without it.

### A 40x regression nobody could see

The 2026-09-12 baseline recorded the help browser at 80x24 as **33.6 us and 129 KB**. When
this item was picked up, the same case measured **1,319 us and 3,200 KB** — forty times
slower, twenty-five times the garbage, arrived silently with the cell-buffer rewrite.

`TuiTextMeasure.EnumerateClusters` yields each grapheme cluster **as a string**, and
`TuiBuffer.DrawText` calls it for every string drawn. Painting one frame allocated a string
per cell. That is what the item was for and it is the reason to take a baseline before a
rewrite rather than after.

The fix is three things, none of them clever: a printable-ASCII fast path, because a
terminal is nearly always drawing printable ASCII and it is one column per character; a
`ref struct` walk that yields clusters as spans so a `foreach` allocates nothing at all; and
a table of the 128 single-character ASCII strings, so the string a cell holds comes out of an
array rather than the heap.

After: **156 us and 561 KB**. Still above the baseline's 33.6 us, and that is the honest
reading — a cell grid is not a string, and it buys the diffing, the clipping correctness and
the compositing that the string frames could not do.

### A fix that was a 13x regression

`ClipPlain` was the item's named suspect: it appended one character at a time and recomputed
the visible length of the whole accumulated string each pass. Replacing it with
`TuiTextMeasure.Elide` is the obvious move and made it **thirteen times slower** — 2.74 us
to 36.1 us — because `MeasureWidth` walked all 1,200 characters allocating a cluster string
each, where the quadratic loop had only ever run about eighty times.

The benchmark is the only reason that is known rather than believed. With the allocation
fix underneath it, the same call is **0.62 us and 368 bytes**: four times faster than the
code it replaced and fifty times less garbage.

Two more bugs fell out of writing its tests. `TrimOrPadPlain` padded by the code-unit length,
so a CJK label got three spaces after four columns of text and pushed the box's right border
out on exactly the rows with non-ASCII in them. And `TuiFormLayout` kept a second copy of
`ClipPlain` that cut with `text[..width - 1]`, splitting surrogate pairs — a label ending in
an emoji clipped to half an emoji, which a terminal draws as a replacement box.

## What keeps it

The benchmark records; tests enforce the parts that can be stated exactly.

`TuiIdleCostTests` drives the real loop with a host that reports nothing forty times and then
one key, and asserts the screen rendered **once** for the whole session and wrote one frame.
The wait slices live inside `WaitForSomething`, which returns only when something actually
happened — so a loop that redrew per slice would look identical on screen and fail here.

`TuiDiffCostTests` pins the byte counts by shape rather than by number: unchanged writes
nothing, one cell writes under 32 bytes, one row is under a tenth of the frame, a resize is
deliberately *not* diffed, and a run of one style is introduced once rather than per cell.

`TuiTextMeasureTests` pins the fast path — that it is taken only where it is right, that
both paths agree, and that an ASCII cell's string is the same instance every time, which is
the mechanism rather than a detail.

## Notes

Take the baseline first. Once the string frames are gone there is nothing left to
compare against, and the number that makes the case for the rewrite will have been
thrown away.

Worth measuring separately: the cost of invoking a script handler through
`IShellCallable`, since `TUI-0002`'s `Custom` widget and `TUI-0008`'s bindings both put
script code on a path that runs repeatedly. The decision to keep handlers on the
refresh path rather than the frame path was made on reasoning, not measurement, and
should be checked.
