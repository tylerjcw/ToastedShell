## Problem

This is the whole setup for the system monitor in `examples/system-monitor.tosh`:

```tosh
var screen = tui screen --title "System Monitor"
$screen | tui add-list $processes --id processes --display Name --prompt "Processes by memory" | ignore
$screen | tui add-text --id summary | ignore
$screen | tui layout horizontal --ratio "1:1" | ignore
$screen.RefreshInterval = 1s
$screen.OnTick = &Refresh
$screen | tui run
```

Seven lines before anything is on screen. Three `| ignore`s, because each builder
re-yields the screen. Two string ids that exist only so the tick handler can find the
widgets again, and a handler that exists only to push new values into them.

The target is the same screen as a value:

```tosh
tui run {|
    Title   = "System Monitor"
    Refresh = 1s
    Row = [
        {| List = &TopProcesses, Display = "Name", Title = "Processes" |},
        {| Text = &Summary |}
    ]
|}
```

No ids, because nothing needs naming. No tick handler, because `&TopProcesses` is a
*pull* binding: the widget asks for its value each refresh instead of being told. The
imperative form stays for the cases that need a handle.

This is expressible in the language today — nested `{| |}` records carry a `TimeSpan`
from `1s` and an `IShellCallable` from `&func` with no conversion. Verified by
evaluation, not by reading the grammar.

## Acceptance

- [x] A record tree builds a widget tree, with the key naming the widget
- [x] Pull bindings: a property set to a callable is re-evaluated on refresh
- [x] Push still works — hold the screen object and assign to a widget
- [x] Inter-widget binding needs no ids: a pull binding is handed every value, so a detail pane following a list is a function of the form's state
- [x] Handler properties (`OnSelect`, `OnChange`, `OnSubmit`, `OnPress`) take `&func`
- [x] A bad tree reports which widgets it could have named
- [ ] `examples/system-monitor.tosh` shrinks to the declarative form and still passes its pty check
- [ ] The builder subcommands are deprecated, then removed (`TUI-0015`)

## What landed

`TuiWidgetRegistry`, `TuiWidgetSpec`, `TuiTreeBuilder` and `TuiDeclarativeScreen`, and
`tui run` takes a record wherever it took a screen. `examples/reactor-block.tosh` is
written against it: fields on the left, the block on the right, recalculating as the
numbers are typed.

`TuiCustomScreen` is gone — 768 lines of switch over a six-value enum. Screens built by
the builder subcommands are adapted onto the same widget tree by `TuiScreenAdapter`, so
there is one screen implementation rather than two and the old form gains borders,
composable layout and real focus handling on its way out.

Pull bindings turned out to answer the inter-widget binding question as well. A binding
is handed every widget's current value as a record, so a pane that follows a list is
just a function of that record — which is less machinery than `--bind widget.property`
was, not more.

## Notes

No new file format. Record literals *are* the markup, and they are better than an XML
dialect would be here: values can be computed, a binding can be a function, and errors
arrive through the diagnostics that already exist. GtkBuilder XML exists because C
cannot express nested literals; ToastScript can. If a `.tui` file is ever wanted it
deserialises into the same tree, and it should not be built before anyone asks.

Last in the sequence on purpose. A declarative surface over a widget model that has not
been proven by `TUI-0003` would be a syntax for a shape nobody has used yet.
