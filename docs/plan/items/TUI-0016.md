## Problem

Two halves of the same gap.

**A handler cannot be attached at all in the object style.** A widget raises a CLR
delegate, and a script function is not one:

```tosh
$field.Changed = func(text) => (writeline $"now: {$text}")
```

> Cannot assign value of type 'Tosh.Language.ToshLambda' to member 'Changed' on type
> 'Tosh.Tui.Widgets.TuiTextField'.

The markup path had handlers because `TuiBuildContext.OnHandler` wraps the callable
itself; nothing equivalent existed for a property set directly, which is the whole of
the object style. This is not a TUI limitation — it is the last gap in the CLR bridge.
The FFI could already call back into a script (`raw callback`), and managed code could
not.

**So the result has to be read back afterwards.** With no way to answer an event, a
script finds out what happened by asking the screen for a dictionary:

```tosh
$answers = tui run $screen --title "Reactor Block" --result

if ($answers.Cancelled) { throw "Cancelled." }

$ReactorType = $"{$answers.Values["ReactorType"]}"
$Width       = Whole($answers.Values["Width"],    2)
$Height      = Whole($answers.Values["Height"],   2)
```

The widgets are in variables the script wrote moments earlier, and it goes looking for
them by name anyway: every value as text, every key unchecked, the outcome inferred
from a flag, and a `try`/`catch` around the lot because `tui run` is the only thing
that can fail.

## Acceptance

- [x] A script function assigned where a CLR delegate is wanted becomes one
- [x] A named function reference and an inline lambda both work
- [x] A handler that ignores its arguments need not declare them
- [x] A handler that must return a value converts what the script produced
- [x] A signature that cannot be expressed as objects is refused at assignment, not when the event fires
- [x] A form has `Submitted` and `Cancelled`, and says how it ended without being asked for a dictionary
- [x] A markup form reaches its values, having no variables to read
- [x] Both examples are written against it, in both styles

## What landed

`ISelfHostedCallable` and `ShellCallableDelegates` in `Toast.Runtime`, reached from
`TypeConversion.TryConvert`. Invoking a script function needs a `CommandContext`, which
only a command already running has — and a .NET type raising an event has none. A
function knows which engine defined it, so it builds that context itself; `ToshLambda`
and `FunctionCommand` implement the interface over the engine each already holds. No
ambient state and no install step, so nothing has to be wired up per host.

`TuiForm` on top of that: content, a title, `Submitted`, `Cancelled`, `Submit()`,
`Cancel()` and `Result`. It owns Enter and Escape, and both travel outwards from the
focused widget, so a multi-line field keeps its newlines. Handlers are handed the form
the way a Windows Forms event is handed its sender — a handler holding the widgets in
variables ignores it, and one built from markup reads `$form.Values.Width`.

```tosh
$form.Submitted = func() { $Width = Whole($wide.Text, 2) }

tui run $form

if ($form.WasCancelled) { throw "Cancelled." }
```

## Notes

The delegate is compiled rather than reflected, because it has to *be* the requested
signature — that is the point of handing it to a type that expects one. The native
callback thunks already work this way and the reasoning is the same.

Blocking while the handler runs is correct rather than convenient: the caller is a .NET
type mid-operation with nothing to await, and the engine stays single-threaded because
the handler runs on the thread that raised the event. The TUI's pull bindings already
called script functions from inside the render loop.

This closes the "callbacks are the only hard gap" note against GTK, SDL and Avalonia
from a script: a managed event can now be answered, not just a native one.
