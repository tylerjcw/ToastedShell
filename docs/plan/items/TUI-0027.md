## Problem

Filed as "the test engine and the shell disagree". They do not, and the real finding is
narrower and more useful.

```tosh
func Items() => ["alpha", "beta", "gamma"]     # the callable yields 1 value: a String[]
var rows = ["alpha", "beta", "gamma"]
func Items() => $rows                          # the callable yields 3 values: three Strings
```

Same host, same call site, same context. A collection *written* as an expression is a
sequence either way — that rule is `TOAST-0028` and `TOAST-0039` and it is not in question.
What differs is *delivery*. A bare variable reference whose binding replays as a pipeline is
expanded at the producer, so the callable yields the elements. A literal is yielded once,
marked spreadable, and expanded by whatever consumes it.

Downstream honours the marking, so at script level the two are indistinguishable:
`Items | collect` counts three either way, and `var x = Items()` is a three-element array
either way. Nothing a script author can write tells them apart.

A host enumerating the raw stream does not see the marking. `tui run`'s pull bindings are
such a host, which is how this surfaced.

## Acceptance

- [x] Establish which is intended: both are, and the language rule they follow is already written down
- [x] The two hosts agree, and a test pins the agreement
- [x] Find what differs — neither the engine, nor `IsInteractiveSession`, nor the statement path
- [x] Audit what else the difference could have hidden
- [x] Document the answer where a host author would look for it

## What it actually was

`ExecuteExpressionStageAsync` takes two routes. A `VariableReferenceArgumentSyntax` whose
binding has `ReplayAsPipeline` returns a `PreExpandedSequence` — already enumerated, and
marked so downstream does not enumerate it twice (`TS-P2-113`). Everything else returns a
`SpreadableSequence` — one value, marked as a sequence so downstream knows it may spread
(`TOAST-0028`).

Both are correct and both are load-bearing. The asymmetry is in when the expansion happens,
not in whether it does, and only a consumer that ignores the marking can tell.

## Why it looked like a host divergence

The probe that produced the original diagnosis changed two things at once. The failing case
used `func Log() => $lines`; the test written to pin it used `func Log() => [...]` — a
literal, because that is what one writes in a test. The literal yields one value, so the
test could not reproduce the failure, and the difference was attributed to the host rather
than to the spelling.

Which is the audit answer too: nothing else is hidden, because script-level behaviour is
consistent. The trap is narrower and worth stating plainly — **a test that writes the
collection as a literal exercises the other delivery shape**, so it cannot catch a bug in
the expanded one. `TuiCommandTests` now pins both, and reverting the invoker fails the
variable case and passes the literal one, which is exactly the asymmetry that caused this.

## What was done

Nothing in the language. The rule is already one sentence and already documented, the two
delivery shapes are each there for a recorded reason, and scripts cannot tell them apart.

The host contract is what needed saying: **a binding takes everything a callable produces**,
because a callable may hand over a collection whole or element by element and the caller
cannot tell which. `BuildArgumentInvoker` does that (`TUI-0008` made it so, for the wrong
stated reason), and the TUI guide now says why rather than merely that.
