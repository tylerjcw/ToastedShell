## Problem

**The reported flakiness did not reproduce, and looking for it found something else.**

The item as filed said single spurious failures appeared in 3 of 8 consecutive
full-suite runs on an unchanged tree, in two unrelated areas — `TtyCaptureTests` and
`GenericClassTests`. Ten consecutive runs were done on 2026-08-16 in an isolated
worktree to characterise it:

```
run 1: FAIL   15 failed, 5,309 passed
run 2-10:     0 failed, 5,324 passed   (nine consecutive)
```

One failure in ten, and it was not spurious. All fifteen failures in run 1 share one
cause:

```
CLI not built at .../src/Tosh.Cli/bin/Debug/net10.0/Tosh.Cli
System.ComponentModel.Win32Exception : An error occurred trying to start process
'.../src/Tosh.Cli/bin/Debug/net10.0/Tosh.Cli' ... No such file or directory
```

The worktree had been built `-c Release`. Fifteen tests — across `TtyCaptureTests`,
`ExecCommandTests`, `ExtensionCommandTests`, `ToshSdkBuildTests` and `EngineTests` —
spawn the CLI as a child process and look for it at a hard-coded **Debug** path.
Something during run 1 produced that binary, after which runs 2–10 found it and
passed, which is why the symptom looked intermittent rather than deterministic.

So the defect is a build-configuration dependency the harness does not declare or
create:

- `dotnet build -c Release && dotnet test -c Release` on a clean checkout fails fifteen
  tests, and the message points at a missing file rather than at the missing step;
- whether the suite passes depends on out-of-band build state rather than on the
  commit — which is the property that makes a suite unusable as evidence;
- **this is a plausible explanation for the original report.** Runs made while build
  state varied would show failures appearing and vanishing on an unchanged tree, in
  the same areas, exactly as described.

## The mechanism, found 2026-08-16

Not a guess. `EngineTests.Require_can_load_project_targets_for_following_using_statements`
executes `require <repo>/src/Tosh.Cli/Tosh.Cli.csproj`, and `require` on a project
**builds it** — in the default configuration, which is Debug. That is what produces
`src/Tosh.Cli/bin/Debug/net10.0/Tosh.Cli`.

So the chain is:

1. one test builds the Debug CLI as a side effect;
2. fifteen other tests hard-coded that Debug path;
3. xUnit runs tests in parallel, so their order varies between runs;
4. if the `require`-project test won the race, the binary existed and the fifteen
   passed; if not, they failed.

Unrelated areas failing intermittently on an unchanged tree — exactly as reported. It
was a **race against another test's build side effect**, not a defect in any of the
tests that failed.

Confirmed by observation: a fresh worktree built Release-only had no Debug output at
all, and one appeared under `bin/Debug` partway through the run.

## A second defect, found the same way — and fixed

The clean-checkout run was **stopped after 30 minutes** without completing, against a
warm run of 25 seconds. `dotnet build .../Tosh.Cli.csproj` was still going with 85
MSBuild node processes alive, because that `require` test triggered a from-scratch
Debug build of the entire dependency chain while the rest of the suite ran around it.

The cause was not parallelism. `require` passed **no configuration at all** to MSBuild,
so it always resolved and built Debug — output a Release test run had no reason to
have. Fixed in `a2dabc2` by taking the host's configuration; the Release output the
suite needs already exists, so nothing is built.

## Measured on a genuinely cold checkout, 2026-08-16

Fresh worktree, no build output of any kind, at `a2dabc2`:

| Phase | Time |
|---|---:|
| `dotnet build -c Release` | 15 s |
| `dotnet test --no-build -c Release` | 30 s |
| **total** | **45 s** |

Against 30+ minutes before, and no Debug output appeared anywhere during the run.
**The parallelism and serialisation fixes considered earlier are unnecessary for
speed** — the whole problem was the one unconfigured build. Slowest test is
`CommandIntrospectionTests.HelpTopics_builtin_commands_resolve_from_metadata_not_catalog`
at 19 s, which is not a build test and is the next thing to look at if the suite needs
to get faster.

**One failure did appear in that run**, and it is a real one:
`ToshSdkBuildTests.Dotnet_build_packaged_sdk_project_compiles_with_packaged_sdk`
failed at the *run* step — the packaged SDK built cleanly and the produced assembly
then exited **134 (SIGABRT)**. Re-run in isolation on the same cold worktree it passes
**3 of 3**, so this is contention under 8-way parallelism rather than anything about a
cold tree.

That is a genuine parallel flake, and a different one from the Debug-CLI race that
this item started as. It is rarer, it is in the SDK build tests, and those exercise the
compiled backend that Phase 0 freezes — so it is worth deciding whether to serialise
those tests or let them go with the component.

## Acceptance

- [x] The tests that need a CLI binary state the requirement clearly — `ToshCli.RequireBuilt` names the build command and configuration rather than a missing path
- [x] Configuration is not hard-coded — taken from the test assembly's own `AssemblyConfigurationAttribute`, so a Release run finds a Release CLI
- [x] A clean checkout builds and runs in 45 s with two documented commands, verified in a fresh worktree
- [x] `require <csproj>` no longer builds a second configuration as a side effect — it uses the host's, so the output already exists
- [ ] The remaining parallel flake resolved: `Dotnet_build_packaged_sdk_project_compiles_with_packaged_sdk` aborts (134) at the run step under load, passes 3/3 alone — serialise the SDK build tests, or retire them with the frozen compiler
- [ ] Ten consecutive runs pass in a **fresh** worktree, so the guarantee covers the state a new contributor is actually in — one full cold run has been done and found the flake above
- [ ] `GenericClassTests.Generic_class_user_interface_constraint_accepts_implementing_class` re-examined — it appeared in the original report and did **not** fail in any of the ten runs, so either it was collateral from the same cause or the report was imprecise

## Notes

Do not attribute this to the suite's memory use — that was measured and cleared. The
suite peaks around 2.8 GB.

The original filing named `TtyCaptureTests.An_interpolation_hole_does_not_yet_capture`,
and a standing note warns against misattributing that test's failures under load. Both
readings now look like the same underlying thing: those tests fail when the child CLI
is missing or slow to start, and neither symptom is about the test's own logic.

Worth doing before `TOAST-0005` and `TOAST-0006`. Those move thousands of lines with
"the suite passes unchanged" as their entire safety argument, and that argument needs
the suite to depend on the commit rather than on what happens to be in `bin/`.
