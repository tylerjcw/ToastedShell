## Problem

`UnixSystemServices.Statvfs` declared eleven `ulong` fields — **88 bytes** — while glibc's
`struct statvfs` on x86-64 is **112**. So every `statvfs()` call wrote 24 bytes past the end
of the buffer.

The field *offsets* were right: `f_files` at 40, `f_ffree` at 48, `f_flag` at 72,
`f_namemax` at 80, all matching the platform. Only the trailing `int __f_spare[6]` was
missing. So every reading the code took was correct, and only the memory *after* the buffer
was destroyed — which is why it survived so long and why nothing looked wrong.

It surfaced as:

```
Fatal error.
System.AccessViolationException: Attempted to read or write protected memory.
   at Tosh.Runtime.UnixSystemServices.TryGetInodeInfo(System.String)
```

**deterministically in the published single-file build, and never in a Release build of the
same source.** That difference is luck about what happens to sit after the buffer, not a
difference in correctness: the overflow was always there.

## Acceptance

- [x] The marshalled struct is the size the platform reports
- [x] The fields that are read keep their offsets, so completing the struct cannot have
      moved them
- [x] A published single-file build runs `examples/showcase.tosh` without crashing
- [x] A negative control: the size assertion fails with the shortened struct

## Resolution — 2026-08-17

Six trailing `int __f_spare` fields, bringing the type to 112 bytes.

**Verified against the platform rather than reasoned about.** A three-line C program
reports `sizeof(struct statvfs) = 112` and the offsets above; the test asserts
`Marshal.SizeOf` agrees. Asserted by *size* rather than by calling `df`, because the symptom
of getting this wrong is memory corruption — a test that merely called the function would
pass while corrupting whatever came next.

Proven in the shape that matters: the previously published artifact crashes 3/3 on
`examples/showcase.tosh`, and a single-file publish of the fixed source passes 3/3.

## Notes

**Found by checking whether the tree was safe to publish, and only because the check was
run against the published artifact rather than a Release build.** The earlier pass in this
session — profile loads, config files, examples — was run entirely against
`dotnet build -c Release` and would never have seen it. That is the lesson worth keeping:
"does it still work?" has to be asked of the artifact that ships.

`TryGetInodeInfo` backs `df`'s inode columns, so any script listing filesystems could hit
it. In an interactive shell it takes the whole process down.
