## Problem

Three projects reference SDK assemblies by absolute path into the *host* SDK and copy them
into the output:

```xml
<Reference Include="System.Reflection.MetadataLoadContext"
           HintPath="$(MSBuildSDKsPath)\..\System.Reflection.MetadataLoadContext.dll"
           Private="true" />
```

`$(MSBuildSDKsPath)` is the SDK of the machine doing the build, and `Private="true"` copies
that file into the publish output **whatever runtime is being targeted**. Publishing
`win-x64` from Linux therefore ships Linux binaries inside a Windows application.

Measured 2026-08-26 on a `dotnet publish -r win-x64 --self-contained` from Linux:

| File in the win-x64 publish | Machine type |
|---|---|
| `Tosh.Cli.dll` | x86-64 |
| `System.Linq.dll` | x86-64 |
| `System.Reflection.MetadataLoadContext.dll` | **`Unknown processor 0xfd1d`** |

That file is **byte-identical** to `/usr/share/dotnet/sdk/10.0.111/`'s copy.

## What it costs

Running the resulting binary under Wine, everything works — arithmetic, interpolation,
pipelines, classes, `ls`, `$env`, external process spawn, and two full example scripts —
until `--compile`, which dies:

```
System.BadImageFormatException: Could not load file or assembly
'System.Reflection.MetadataLoadContext.dll'. Format of the executable is invalid.
   at Tosh.Compiler.EmitterImpl..ctor(…) BoundUnitEmitter.cs:line 134
```

Unhandled, so the process aborts rather than reporting a compile failure. Wine surfaces it
as `0xE0434352`, which is the SEH code for a managed exception — the crash dialog is
reporting a .NET throw, not a Wine fault.

**It is not Windows-specific.** Any cross-RID publish is affected, including Windows to
Linux. It is simply invisible while every publish is same-RID.

## Affected references

| Project | Assembly |
|---|---|
| `Tosh.Cli` | `System.Reflection.MetadataLoadContext` |
| `Tosh.Compiler` | `System.Reflection.MetadataLoadContext`, `Microsoft.NET.HostModel` |
| `Tosh.Sdk.Tasks` | `System.Reflection.MetadataLoadContext` |

## The fix, and one thing measured about it

A `PackageReference` resolves the portable assembly instead of the host's crossgen'd copy.
Verified on `Tosh.Cli` alone: the shipped file became `PE32 … Intel i386` — plain MSIL — and
`BadImageFormatException` disappeared.

**A partial fix is worse than none.** With `Tosh.Cli` on the package and `Tosh.Compiler`
still on the SDK path, the two disagree about assembly version and the failure becomes
`FileNotFoundException: … Version=10.0.0.11`. All three projects move together, or none do.

`Microsoft.NET.HostModel` needs its own check: it is an SDK-internal assembly and its
published package versions do not track the SDK's the way the runtime libraries do.

## Resolution so far — 2026-08-26

`System.Reflection.MetadataLoadContext` moves to a `PackageReference` in all three projects
at once. The win-x64 publish audit now reads 108 x86-64 and 89 MSIL assemblies, with exactly
one file left carrying the host's machine type.

**A second defect surfaced the moment the first was fixed**, and it is the same assumption
wearing different clothes. `ToshPublisher` enumerates `*.dll` beside the application and
calls `AssemblyName.GetAssemblyName` on each. A self-contained *Windows* publish ships native
libraries — `coreclr.dll`, `clrjit.dll`, `Microsoft.DiaSymReader.Native.amd64.dll` — and
reading an assembly name out of one throws. Invisible on Linux, where the equivalents are
`.so` and never matched the `*.dll` pattern. A native library is not a managed dependency to
record in `.deps.json`, so `BadImageFormatException` there means *skip*, not *fail*.

With both fixed, `--compile` under Wine now writes `cout.dll`, `cout.deps.json` and
`cout.runtimeconfig.json` — emission completes — and fails only at the final apphost step.

**`Microsoft.NET.HostModel` cannot be fixed the same way.** nuget.org carries 22 versions of
it, the newest `5.0.0-preview.1.20120.5`; it ships only inside the SDK. So it keeps the
`$(MSBuildSDKsPath)` reference, keeps the host's machine type, and the defect narrows from
"every compile fails" to "the apphost and bundle step fails on a cross-published build". The
reference now carries a comment saying so.

Worth recording for whoever takes the rest: the emitted output is *complete and usable*
before that step — a `.dll` with its `.deps.json` and `.runtimeconfig.json` runs under
`dotnet cout.dll`. Failing hard there throws away working output, so degrading to a portable
artifact with a diagnostic looks better than the current unhandled exception.

## Acceptance

- [x] All three projects resolve `System.Reflection.MetadataLoadContext` through NuGet
- [x] `Microsoft.NET.HostModel` retention recorded with the version constraint that forced it
      — no package exists above `5.0.0-preview`
- [x] The full suite passes on Linux — 6,647, unchanged, and a native Linux compile still
      produces a running executable
- [x] A `win-x64` publish from Linux was audited mechanically by machine type; one file
      differs, and it is the one with no package
- [ ] `--compile` succeeds in that build under Wine — **emission does; the apphost step does
      not**, blocked on `Microsoft.NET.HostModel`
- [ ] A negative control
