## Problem

`TuiSparkline` draws a series in one row and `TuiBars` draws a set as rows or columns. Both
deliberately have no axis: a sparkline is a shape, and a bar chart's scale is the labels
beside it.

That covers what a shell script usually reports and stops short of what a script sometimes
needs — a series against a scale it can read. How long each build took over the last fifty
commits, memory against time, a latency distribution. Without an axis the reader has a
shape and no numbers, and a shape with no numbers is a decoration.

The pieces are here. The block ramp that draws a partial cell is shared already, the
scale-with-a-floor rule is written down twice, and `TuiTextMeasure` can size a label. What
is missing is the frame around them: a column of tick labels, a baseline, and the
arithmetic that picks ticks a person would have picked.

## Acceptance

- [x] A chart widget with a vertical axis: ticks, labels, and a baseline
- [x] Ticks are chosen for readability — 0, 25, 50, 75, 100 rather than 0, 33.3, 66.6
- [x] A horizontal axis where the series is long enough to need one
- [x] The plot area is a widget's worth of cells, so it composes in a row or a column like anything else
- [x] Braille sub-cell plotting for a line, where the terminal can draw it
- [x] A markup name, with the same binding vocabulary the other charts have
- [x] The guide says which of the four chart widgets to reach for and why

## Notes

Not `tosh-plot`. That library is written in Tōast and draws graphics; this is a C# terminal
widget and belongs with the rest of them. The two answer different questions and should not
be made to share code across a language boundary to prove a point.

Tick selection is the part with a right answer worth copying rather than inventing: a
"nice numbers" algorithm — round the range to a 1, 2 or 5 times a power of ten — is what
every plotting library uses and what a reader's eye expects.

Braille gives four times the vertical resolution and eight times the horizontal, which is
the difference between a line chart and a staircase. It is also the thing most likely to
render as boxes on a terminal without the font, so it wants the same fallback the spinner's
`ascii` style has.

## What landed

`TuiChart`, `{| Chart = … |}`, and two pieces underneath it that the other charts should
have been sharing already.

### The premise was one line out

"The block ramp that draws a partial cell is shared already" — it was not. There were two
copies, in `TuiSparkline` as `Blocks` and in `TuiBars` as `Eighths`, spelled the same and
named differently, which is how two widgets come to round a partial cell differently. A
third copy was where that would have started to bite, so it is `TuiBlocks.Eighths` now, with
the rounding decision made once: away from zero, because a chart whose smallest bar is
indistinguishable from no bar has lost the reader's smallest data point.

### Ticks

Heckbert's algorithm is the one the note pointed at, and it has a flaw worth naming. It
computes the spacing and then rounds it to the nearest of 1, 2, 5 — and 100 over four
intervals is exactly 25, which rounds *down* to 20 and then no longer fits in four
intervals. The acceptance box asks for 0, 25, 50, 75, 100 and plain Heckbert gives
0, 20, 40, 60, 80, 100.

Searching upward for the smallest candidate that does fit cannot make that mistake, and
costs a loop over a handful of numbers. `2.5` is in the candidate set, which Heckbert's is
not; matplotlib made the same addition, and a percentage is the single most common thing a
shell script charts.

Labels take their precision from the step and not from the value, so the column lines up —
and the precision is counted off the step rather than taken from its logarithm, because
`-log10(0.25)` says one place and 0.25 needs two. Tick values are counted from the minimum
rather than accumulated, because adding 0.1 ten times is 0.9999999999999999.

### Braille

`TuiBrailleCanvas` is 2×4 dots per cell. The bit layout is the one Unicode gave the block
and is not the obvious one: the fourth row of dots was added after the first three, so its
two bits sit above the others rather than in sequence. Getting it wrong draws a chart that
looks plausible and is upside down in its bottom quarter, which is why there is a test per
dot.

Two decisions in it. A point outside the canvas is **dropped, not clamped** — clamping piles
everything that overflowed onto the edge row, drawing a solid line along the top of a chart
whose scale is too small and hiding the fact that the scale is too small. And an empty cell
is a **space, not U+2800**: they look identical, and the blank is a character the ASCII
folding from `TUI-0009` turns into a mark, so an empty chart would have come out stippled.

Samples are joined vertically to the one before them, which is what makes it a line rather
than a row of disconnected dots.

### Fitting the series to the plot

`Stretch` is on, and differs from `TuiSparkline.PadLeft` on purpose: a sparkline is a live
shape and a chart with an axis is a report, and a report that leaves three-quarters of its
plot empty has misrepresented how much data there is. Off, the plot is a window onto the
newest samples, one per column, which is what a live meter wants.

Where there are more samples than columns each column takes the **largest** value in its
bucket. A mean is defensible and is wrong here: a chart that averages away the spike hides
the incident the reader opened it to find.

The axis is dropped before the plot is, and no row is held back for a horizontal axis that
then turns out to have no room — the first draft did, which left a blank line at the foot of
every narrow chart.

### A bug found on the way

`{| Spark = [1, 2, 3] |}` drew an empty chart, and always had. `TuiWidgetSpec.Numbers`
matched `IEnumerable<object?>` where `PrimaryItems` matches the non-generic
`System.Collections.IEnumerable`; the runtime's own list satisfies the second and not the
first. It went unnoticed because every example binds a function rather than writing the
numbers out. `Numbers` goes through `PrimaryItems` now, which fixes the sparkline as well as
the chart.

`spec.Number` also truncated to `int`, so a chart asked for `Max = 1.5` was told 1.5 seconds
was 1. There is a `double` overload now, picked by the type of the fallback — `0` reads a
count and `0d` reads a measurement — and the sparkline's `Scale` was quietly truncating the
same way.
