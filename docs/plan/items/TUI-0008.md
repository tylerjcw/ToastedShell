## Problem

Live screens landed in `0b2a2cc` with one event source: a `RefreshInterval` and a
`Tick` that fires when it elapses. That is polling, and for a system monitor it is the
right shape — CPU usage is a sample, not an event.

It is the wrong shape for most of what a shell has to show. A log being tailed, a build
emitting lines, a download reporting progress, a long pipeline producing rows: these
are streams that arrive when they arrive. Polling them means either a short interval
that burns work re-reading nothing, or a long one that makes the display lag the event.

TōSh already has jobs, channels and pipelines. A widget that consumes one is the
idiomatic version of a live screen, and it is the thing that makes a TUI genuinely part
of the shell rather than a separate world with a clock in it.

There is a second, sharper problem behind it. The tick handler runs on the render
loop's thread and the loop is blocked while it runs, so any handler that waits on
anything freezes the UI. `BuildTickInvoker` drains the callable synchronously with
`GetAwaiter().GetResult()`. A handler that does real work — reads a slow file, waits on
a job — stops input as well as drawing.

## Acceptance

- [x] A widget can be bound to a channel, a job's output, or an async stream
- [x] Arriving values mark the widget dirty and schedule a redraw, rather than waiting for an interval
- [x] The render loop never blocks on user code: handlers run off the loop or are given a deadline
- [x] A handler that throws is reported without tearing down the screen (`TUI-0010`)
- [x] Back-pressure: a source producing faster than the terminal can draw coalesces rather than queues without bound
- [x] `RefreshInterval` remains for genuine sampling, and the two compose on one screen

## Notes

This is the item that decides whether the TUI is a shell feature or a widget toolkit
that happens to live in a shell. A progress bar bound to a job is the demo.

Care needed around the existing channel receive race noted in the July 2026 review
round: a widget consuming a channel is a second consumer of that machinery and will
find the same bugs.

## Progress

`TuiWake` is the way in from another thread: `Post` runs work on the loop's thread between
frames and `Signal` just asks for a frame. The signal is a flag rather than a count, so a
thousand values arriving between two frames produce one frame — which is the back-pressure
answer. A drain runs at most `DrainLimit` items and leaves the signal raised if more are
waiting, so a source faster than the terminal cannot hold the loop and starve the repaint.

`TuiFeeds` hangs on a widget the way `TuiShortcuts` does, and for the same reason: a key is
a change the reader causes and a feed is one something else does, and both belong where the
thing they change is written. A source is a `ShellChannel`, an `IAsyncEnumerable`, a `Task`
or any sequence. `Feed = {| Source = $ch, Do = &Arrived, OnEnd = &Ended |}` in markup.

The run loop now waits for whichever comes first — a keystroke, posted work, or the
interval elapsing — in slices, because the console gives no way to wait on stdin and
anything else at once. A screen with neither a feed nor an interval still blocks on the
keyboard, so nothing that was free became expensive.

Driving `examples/live-feed.tosh` in a pty found a bug the unit tests could not have: a
pull binding kept only the *last* value its function produced, and a function returning a
collection yields its elements one at a time — so `Lines`, `List`, `Table`, `Spark` and
`Bars` had all been showing their final element and nothing else. `BuildArgumentInvoker`
now collects everything; one value is still that value.

### The deadline

A feed's *source* is read off the loop, which is the half that matters for a slow producer,
but the handler that folds a value into state runs on the loop's thread — deliberately,
because that is what makes it race-free and writable by someone who does not know there was
another thread.

I closed the paragraph above by saying a deadline would mean interrupting interpreted code
mid-statement, and that this was a language question rather than a TUI one. That was wrong,
and wrong in the cheap direction: the language already checks its cancellation token as it
iterates — it is how `Ctrl+C` stops a running script — so a handler given a token that fires
stops on its own, at the next thing it does. Nothing in the interpreter had to change.

`BuildArgumentInvoker` is the single door. Bindings, key handlers and feed handlers all
reach a script function through it, so the budget is one linked `CancellationTokenSource`
in one place. Linked, not standalone, so `Ctrl+C` still reaches a handler that is halfway
through something slow; and a cancellation that was *only* the deadline is translated into
a `TimeoutException` naming the budget, because a screen reports what it catches by type
and message and "A task was canceled" names neither the handler nor the reason.

Five seconds by default, `--budget 250ms` to tighten it, `--budget off` for a screen that
means to be slow. An unreadable value keeps the default rather than becoming `off`: a typo
that silently keeps the guard is found when a handler hangs, and one that silently removes
it is found when a terminal does.

What this catches is a script that loops, waits or polls forever. What it does not catch is
a handler blocked inside something that cannot be cancelled — a read on a pipe nobody
writes to. The alternative is running handlers on a thread and abandoning the ones that
overstay, which trades a stuck screen for two threads writing the same widget; a torn
screen is worse than a stopped one, and .NET cannot abort the thread anyway.

### One binding is not the frame

Doing this found that the guard from `TUI-0010` was coarser than it read. A binding that
threw was caught around the *whole frame*, so the frame was dropped and the last good one
kept — and on the first frame there is no last good one, which made a screen with one
misspelled property open as an empty rectangle with a banner under it.

`TuiBindings.Apply` now catches per widget: the widget keeps whatever it last showed, the
walk carries on to its siblings and its children, and the banner says what happened. Driven
in a pty against a binding that never returns, the title, the working bindings and the
footer all draw, the one bad line is blank, and `q` still quits. The frame guard stays
behind it for what gets past — layout, drawing, a widget's own arithmetic.

With nothing listening the exception is left alone, so a tree bound outside a screen — a
test, a script driving widgets itself — fails exactly where it always did.
