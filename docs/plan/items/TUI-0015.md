## Problem

`tui` has three jobs under one name.

**Asking a question inline.** `tui input "Name?" --cli`, `tui confirm "Sure?" --cli`.
A prompt at the cursor that returns a value. This is the most shell-like thing the TUI
does and the reason a command exists at all.

**Running a modal one-shot.** `ls | tui pick --display Name`. A pipeline stage that
filters through a human.

**Composing a screen.** `tui screen | tui add-list … | tui add-text … | tui layout … |
tui run`. Seven lines of scaffolding for two widgets, three `| ignore`s because each
builder re-yields the screen, and string ids whose only purpose is to let a handler find
the widgets again.

The third exists because there was no way to write a widget tree as a value. There is
one — nested `{| |}` records carry a `TimeSpan` from `1s` and an `IShellCallable` from
`&func` — so the builder subcommands are a workaround that outlived its reason
(`TUI-0004`).

A second problem sits underneath. `Tosh.Stdlib` cannot reach a terminal, so the modal
subcommands do not run anything: they yield a request object that `BufferingDisplaySink`
and `StreamingTableSink` intercept and run. Seven dispatch sites each construct their
own `new ConsoleTuiHost()`. That detour is what makes `var answer = tui confirm "…"`
store a `TuiConfirmRequest` instead of asking the question (`TUI-0013`).

## Acceptance

- [x] `ToshRuntime.TuiHost` exists as a service beside `ToshRuntime.InlinePrompts`, set once at startup
- [x] Modal subcommands run a screen and yield its result, rather than yielding a request
- [x] The request records stop being the public contract between the command and the shell
- [x] `tui run` accepts a record tree as well as a `TuiScreen`
- [x] `tui screen`, `add-list`, `add-text`, `add-input`, `add-picker`, `add-confirm`, `add-file`, `bind` and `layout` are deprecated, then removed
- [x] `--cli` inline prompts keep working exactly as they do
- [x] `help tui` describes two jobs rather than three

## What landed

`ITuiScreenRunner` answered the first three boxes under `TUI-0013` — declared beside
`IInlinePromptProvider`, assigned in `Program.cs`, so the modal subcommands run a screen
and yield the answer instead of yielding a request for a display sink to intercept.

The builder came out whole: nine subcommands, and the fourteen types that existed only to
carry what they built — `TuiScreen`, `TuiLayout`, `TuiLayoutConfig`, `ITuiWidget` and its
six config records, `TuiWidgetKind`, `TuiWidgetBinding`, `TuiRunRequest` and the
`TuiScreenAdapter` that translated them onto widgets. Around 1,100 lines, none of which
had a caller left: a widget tree can be written as a record or built with `new`, and both
reach the same builder.

`tui run` is one path now rather than three. It takes the first argument shaped like a
tree — a widget, a record, a dictionary — or the first one to arrive on the pipeline, and
everything else is an option. `TuiRequestProbe` lost the rule that tolerated the screens a
builder re-yielded, because nothing re-yields anything.

`help tui` describes two jobs.

## Notes

Keep the command. Narrow it: asking a question, and running a screen.

`ToshRuntime.InlinePrompts` is the precedent for the host — an `IInlinePromptProvider`
declared in `Toast.Runtime`, assigned in `Tosh.Cli/Program.cs`, consumed from the
standard library. A `TuiHost` beside it is the same shape and removes the reason the
request objects exist.

`tui` is the shell's façade, not the framework's API. A compiled Tōast program builds a
widget tree and runs it against `Tosh.Tui` directly, with no command involved — which is
why the framework had to move out of the executable in the first place.

Open question worth settling before scripts are written against it: once `tui run`
takes a tree, `tui {| … |}` reads better than `tui run {| … |}`.
