## Problem

`yazi` previews an image, a video and a PDF page in the terminal, at full colour and full
resolution, because Kitty, WezTerm, Ghostty and iTerm2 all accept pixels over the same
channel they accept text on. A terminal that can do that and a framework that cannot is a
framework that has decided a file browser's third pane is a list of bytes.

Nothing in the widget tree stops this. A surface is a grid of cells and an image is not
cells — but an image *does* occupy a rectangle of them, and the rectangle is something the
layout already computes. What is missing is a widget that reserves its rectangle, paints
nothing into the buffer, and emits its own escape sequence at the right cursor position
after the frame is written.

The protocols are the work. The Kitty graphics protocol is the good one and is what the
terminals worth targeting speak. Sixel is the fallback with the widest reach and the worst
colour. Half-block characters with a foreground and background colour give a passable
thumbnail on anything that does truecolour, and that is the floor: it needs no protocol
detection at all, degrades to a shape, and is what a plain-text snapshot can capture.

Video and PDF are not separate features once an image can be drawn. Both are a frame
extracted by something that is already installed — `ffmpeg` for one, `pdftoppm` or
`mutool` for the other — and the framework's part is caching the result and not blocking
the redraw while it is produced.

## Acceptance

- [x] `TuiImage` reserves a rectangle, and draws nothing into the cell buffer that would be overwritten
- [x] Half-block rendering with truecolour, as the fallback that always works
- [x] Kitty graphics protocol where the terminal answers that it speaks it, sixel where it does not
- [x] Protocol detection is asked once, cached, and overridable — a terminal that lies is the reader's problem to fix, not something to guess around
- [x] Scrolling or covering an image erases it, rather than leaving pixels over the widget that moved on top
- [x] A source that has to be produced (a video frame, a PDF page) is produced off the redraw and cached by path and modification time
- [x] `Image` is a markup name, taking a path or a byte source, with `Fit` deciding letterbox against crop
- [x] The plain-text twin renders a placeholder of the right size, so the golden masters still mean something

## Notes

TUI-0001 is done, so the cell grid and the frame diff this needs are already there. It
still wants TUI-0008 — the frame extraction is exactly the "fed by a job" case, and doing
it synchronously would stall the screen on every arrow key.

The erase problem is the one that makes or breaks this. Kitty images are placed by id and
persist until deleted, so a widget that has moved, been scrolled, or been covered by a
dialog has to delete its placement — which means the renderer has to know what was placed
last frame and is not placed this one. `TuiTerminalWriter.Present` already compares the
two buffers; placements are a second thing to diff alongside the cells.

## Progress

Half-blocks, which are the floor and the part that always works. One cell is two pixels —
an upper half block with the top pixel's colour in front and the bottom pixel's behind — so
a pane of *w* × *h* cells is a canvas of *w* × 2*h*. Nothing to detect, nothing to erase
when it scrolls (they are cells like any other), and a recognisable shape on anything that
does truecolour. Three of the boxes above are ticked by that alone: an image that is cells
cannot leave pixels behind, and a plain-text snapshot of one is a block of `▀` the right
size and shape.

The widget knows pixels and nothing else. `TuiPixels` is three bytes each, row-major, and
`TuiImage.Loader` is the hook that turns a path into them — the same pattern the table's
columns and the tree's glyphs use. So the toolkit has no image dependency, and a video
frame is the same kind of thing as a PNG.

The shell's loader asks `magick`, `ffmpeg` and `pdftoppm`, which are already installed on
the machine of anyone who wants this, and takes binary PPM back — a five-token header and
then the bytes, so the parser is forty lines instead of an image library. A format nobody
here has heard of works the day the reader installs something that reads it.

Two things were found by pointing it at real files rather than at fixtures. ImageMagick
writes **16-bit** samples by default, and the first parser refused them — which is a preview
pane that says "no preview" for every PNG on the machine. And `TuiImage` was missing from
the binding table, so `Image = &Chosen` silently never bound and the pane never changed;
the browser example is what caught it.

`examples/preview.tosh` is a file browser with a live preview pane. Driven in a pty against
`/usr/share/pixmaps`, the Arch Linux logo is legible in the capture.

## Real pixels

Kitty, which Ghostty and WezTerm also speak. Pixels do not fit in a cell, so they travel
beside the grid rather than in it: `TuiPlacement` is part of the frame like the cursor is,
the widget says where it wants a picture, and the writer decides how to ask.

The id is what makes a placement a thing rather than an event. A terminal keeps an image
until it is told to delete it, so a picture that moved, closed or was covered has to be
taken back, and only something comparing this frame against the last knows that happened.
`Present` now diffs placements alongside cells: gone ones are deleted, changed ones re-sent,
unchanged ones left alone — because a 4K frame down the wire every time a clock ticks is a
slideshow, not a preview. A screen that ends with a picture up deletes it on the way out, or
it would be painted over the shell the reader is handed back.

Detection reads the environment rather than asking. The protocol *has* a query — send a
one-pixel image, read the reply — but the reply arrives in the same stream as the keyboard,
so asking means racing the reader and risking a stray `ESC_G` being typed into whatever has
focus. `TERM_PROGRAM` is checked before `TERM` because a multiplexer rewrites `TERM`; and
inside `tmux` or `screen` it falls back to blocks, because a multiplexer does not know a
picture was sent and would leave it over whatever pane it had decided to put there.
`TOSH_TUI_GRAPHICS` is the override for a terminal that lies.

Two things came out of driving it rather than reading the spec. The first version sent the
**whole source** — a 1024-pixel photograph in a thirteen-cell box was 4.4 MB of base64 to be
scaled to two hundred pixels at the other end; capping at what a cell could generously be
worth made it 1.2 MB. And the fit was worked out treating a cell as **square**, which
stretched every picture vertically — a cell is about twice as tall as wide, so the geometry
is decided on the same half-cell canvas the blocks use. Switching protocols now changes how
a picture is drawn and not where it goes.

## Sixels

A second `Transmit` and a third value in the enum, as expected — and one thing that was not
expected and did reach the renderer.

A Kitty image is *placed*: it has an id, the terminal keeps it, removing it is a message. A
sixel is *painted into the screen* like text: no id, nothing to delete, and a picture that
goes away is removed by drawing the cells it covered again. The cell diff would never have
noticed, because those cells hold exactly what they held last frame — their content did not
change, only what the reader sees over them. `Present` now tracks the rectangles a picture
has vacated and forces them, and the whole thing turns on one predicate,
`TuiGraphics.Remembers`, rather than on a protocol check at each site.

The encoder is a 216-colour cube with run-length encoding. Median-cut would be better and
is a great deal more code for a preview pane; the cube is the same one the 256-colour
palette uses, so a picture and the coloured text beside it come from one family. It is also
far smaller on the wire than it looks: the preview that cost 1.18 MB as Kitty pixels is
43 KB as sixels.

Colours are percentages and not bytes, which is the one place this format quietly draws the
wrong thing, so there is a test that says so.

### How it was checked

Shape assertions say an escape sequence looks like a sixel. They cannot say the picture
survived, and an encoder whose bands are counted from the wrong end would pass every one of
them. So the guard is a **round trip**: a decoder in the test reads the encoding back and
compares pixels, on a four-quadrant picture where a band counted the wrong way or a column
swept the wrong way comes back visibly wrong.

It covers the two places sixel encoders classically break — a height that is not a multiple
of six, and two colours in one band, which is what the `$` return is for. Flipping the bit
order in the encoder fails it, which was checked rather than assumed.

### Producing off the redraw

Loading is cached by path, size and write time, so arrowing back up a list is instant. The
first read was the problem: a large video went through `ffmpeg` on the loop's thread with
only the five-second timeout bounding it, and five seconds is a very long time to hold a
terminal that cannot answer a keystroke.

The fix is not a `Feed`, which is what the note above expected. It is `TuiImage` learning to
*not* load. The `Path` setter used to read the file; now it records what was asked for, and
the load happens in the getter — which means a screen that has claimed its images can mark
them deferred and the getter stops loading on demand at all. `TuiDeclarativeScreen` reads
each pending picture on a task and posts the result back through the wake, so the widget is
written on the loop's own thread and nothing has to be thread-safe.

The placeholder is the reason this reads as a feature rather than as a delay: a widget that
is loading draws `Loading` (an ellipsis by default, `loading = "..."` in markup) where a
widget with no picture draws `Placeholder`. A preview pane arrowed down a directory shows
each picture arriving rather than freezing between them.

A result that comes back for a path nobody is asking for any more is dropped rather than
drawn. That is what makes arrowing *quickly* safe: without it, a slow decode of the file
three back finishes last and wins, and the pane ends up showing something the cursor left
long ago. `Accept` compares the path it was asked for against the path the widget currently
wants, and says nothing if they differ.

Proven by a test that blocks the loader on a `ManualResetEventSlim` and asserts `Render`
returns anyway — which is the property, stated in the only terms that cannot be satisfied by
a fast loader.
