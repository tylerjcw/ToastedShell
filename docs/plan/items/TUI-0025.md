## Problem

`yazi` previews an image, a video and a PDF page in the terminal, at full colour and full
resolution, because Kitty, WezTerm, Ghostty and iTerm2 all accept pixels over the same
channel they accept text on. A terminal that can do that and a framework that cannot is a
framework that has decided a file browser's third pane is a list of bytes.

Nothing in the widget tree stops this. A surface is a grid of cells and an image is not
cells — but an image *does* occupy a rectangle of them, and the rectangle is something the
layout already computes. What is missing is a widget that reserves its rectangle, paints
nothing into the buffer, and emits its own escape sequence at the right cursor position
after the frame is written.

The protocols are the work. The Kitty graphics protocol is the good one and is what the
terminals worth targeting speak. Sixel is the fallback with the widest reach and the worst
colour. Half-block characters with a foreground and background colour give a passable
thumbnail on anything that does truecolour, and that is the floor: it needs no protocol
detection at all, degrades to a shape, and is what a plain-text snapshot can capture.

Video and PDF are not separate features once an image can be drawn. Both are a frame
extracted by something that is already installed — `ffmpeg` for one, `pdftoppm` or
`mutool` for the other — and the framework's part is caching the result and not blocking
the redraw while it is produced.

## Acceptance

- [x] `TuiImage` reserves a rectangle, and draws nothing into the cell buffer that would be overwritten
- [x] Half-block rendering with truecolour, as the fallback that always works
- [ ] Kitty graphics protocol where the terminal answers that it speaks it, sixel where it does not
- [ ] Protocol detection is asked once, cached, and overridable — a terminal that lies is the reader's problem to fix, not something to guess around
- [x] Scrolling or covering an image erases it, rather than leaving pixels over the widget that moved on top
- [ ] A source that has to be produced (a video frame, a PDF page) is produced off the redraw and cached by path and modification time
- [x] `Image` is a markup name, taking a path or a byte source, with `Fit` deciding letterbox against crop
- [x] The plain-text twin renders a placeholder of the right size, so the golden masters still mean something

## Notes

TUI-0001 is done, so the cell grid and the frame diff this needs are already there. It
still wants TUI-0008 — the frame extraction is exactly the "fed by a job" case, and doing
it synchronously would stall the screen on every arrow key.

The erase problem is the one that makes or breaks this. Kitty images are placed by id and
persist until deleted, so a widget that has moved, been scrolled, or been covered by a
dialog has to delete its placement — which means the renderer has to know what was placed
last frame and is not placed this one. `TuiTerminalWriter.Present` already compares the
two buffers; placements are a second thing to diff alongside the cells.

## Progress

Half-blocks, which are the floor and the part that always works. One cell is two pixels —
an upper half block with the top pixel's colour in front and the bottom pixel's behind — so
a pane of *w* × *h* cells is a canvas of *w* × 2*h*. Nothing to detect, nothing to erase
when it scrolls (they are cells like any other), and a recognisable shape on anything that
does truecolour. Three of the boxes above are ticked by that alone: an image that is cells
cannot leave pixels behind, and a plain-text snapshot of one is a block of `▀` the right
size and shape.

The widget knows pixels and nothing else. `TuiPixels` is three bytes each, row-major, and
`TuiImage.Loader` is the hook that turns a path into them — the same pattern the table's
columns and the tree's glyphs use. So the toolkit has no image dependency, and a video
frame is the same kind of thing as a PNG.

The shell's loader asks `magick`, `ffmpeg` and `pdftoppm`, which are already installed on
the machine of anyone who wants this, and takes binary PPM back — a five-token header and
then the bytes, so the parser is forty lines instead of an image library. A format nobody
here has heard of works the day the reader installs something that reads it.

Two things were found by pointing it at real files rather than at fixtures. ImageMagick
writes **16-bit** samples by default, and the first parser refused them — which is a preview
pane that says "no preview" for every PNG on the machine. And `TuiImage` was missing from
the binding table, so `Image = &Chosen` silently never bound and the pane never changed;
the browser example is what caught it.

`examples/preview.tosh` is a file browser with a live preview pane. Driven in a pty against
`/usr/share/pixmaps`, the Arch Linux logo is legible in the capture.

### What is left

Real pixels: the Kitty graphics protocol where the terminal speaks it, sixel where it does
not, with detection asked once and overridable. That is the half that makes a preview look
like `yazi` rather than like a mosaic, and it is where the erase problem actually lives —
Kitty placements persist by id, so a widget that has moved or been covered has to delete its
own. `TuiTerminalWriter.Present` already compares two buffers; placements are a second thing
to diff alongside the cells.

And producing off the redraw. Loading is cached by path, size and write time, so arrowing
back up a list is instant, but the first read of a large video still happens on the loop's
thread with only the five-second timeout to bound it. The machinery to fix it landed in
`TUI-0008`: a handler sets the path from a `Feed` rather than from a binding. Worth doing
with the protocol work rather than before it.
