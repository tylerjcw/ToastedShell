## Problem

The CLR explorer draws a namespace tree with guide characters, expansion markers and
per-level indentation. The config browser draws a settings tree the same way. Both build
the rows themselves, flatten them into a list, and keep their own set of expanded paths.

A tree is a control. Rich has one, Ratatui has one in its ecosystem, and both browsers
would be shorter for it — but the reason to build it is that a script cannot show a tree
at all today, and a shell that walks filesystems, configuration and object graphs has
trees everywhere.

## Acceptance

- [x] `TuiTree` takes a root and a function from node to children, so it does not own the data
- [x] Expansion is the widget's own state, keyed by a stable id rather than by row index
- [x] Guides and markers are a swappable glyph set, defaulting to what the browsers draw
- [ ] The theme's `TreeStyle` picks the glyph set, so a tree follows the user's config
- [x] A node renders as a `TuiSpanLine`, so a caller styles what it likes
- [x] Selection, activation and scrolling behave as `TuiList`
- [x] Lazy children: a node's children are asked for when it opens, not when the tree is built

## Notes

Laziness is not a nicety here. The CLR explorer's root has every loaded assembly under it
and its leaves are every type in each; building that eagerly is the reason it caches
aggressively today.

`TuiList` already solved the "keyed by id, not index" problem for ticks, for the same
reason — a filtered list's indices mean something different after every keystroke.

## What landed

`TuiTree` takes a root and `ChildrenOf`, and that is all it knows about the data. Named
that way because `TuiWidget.Children` already means the widgets inside a widget, and two
properties called `Children` on one type is a member the CLR cannot bind — found by
assigning one from a script and being told the match was ambiguous.

Laziness needed one correction. Children are enumerated only when a node opens, but a
closed node still has to say whether it is a leaf or an unopened branch, or every leaf
draws with a collapse marker beside it. So a visible closed node is asked whether it has a
*first* child — one level, only for rows on screen — and `HasChildren` lets a caller who
already knows answer without being asked.

Expansion is keyed by `Identify`, so a tree rebuilt from fresh objects keeps what the
reader had open. Selection follows the node rather than the row number, so opening
something above it does not move it. Right opens and then steps in; Left closes and then
steps out; Enter toggles a branch and activates a leaf.

Still to do: reading the glyph set from the theme's `TreeStyle`, which the browsers do
today and a script cannot yet ask for.
