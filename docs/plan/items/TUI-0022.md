## Problem

`TuiShortcuts` carries a label and a description beside each action, and
`TuiShortcuts.Describe` builds a footer from them — so the help browser's footer can no
longer claim a key that does not work, which it had been doing for `/`, `[` and `]`.

That is half of it. The keys a screen answers *contextually* — `Enter`, `i`, the arrows,
`1`-`9` — are still a literal string in the footer beside a `switch` that implements them,
and the config browser's eight letter shortcuts are the same. The drift this removes is
only removed for the keys that happen to be in the table.

Bubbles' `key` and `help` packages are the shape worth copying: every binding carries its
own help, a screen exposes short and full help, and the help *is* a widget rendered from
the bindings rather than a string maintained beside them.

## Acceptance

- [x] Contextual keys are registered too, with the condition under which they apply
- [x] `TuiHelp` is a widget: a one-line summary, and a full view when asked
- [x] A binding that does not currently apply is dimmed or omitted rather than lying
- [x] The help browser's footer string disappears, replaced by a footer generated from the bindings
- [x] The config browser's does too
- [x] The generated footer is a row of segments (`TUI-0024`), so it can put a clock or a count on the right
- [x] A script can register its own bindings and get the same footer for free

## Notes

The condition is the interesting part. `i insert` only applies outside the search box, and
`1`-`9` only when the current topic has related topics — so a binding is a predicate as
well as an action, and the footer is a projection of which predicates hold right now.

## Progress

A condition is the other half of a binding, and it is the half that makes the rest work. A
key that does not apply is not described **and does not fire** — describing one and then
answering it anyway would be a footer that tells the truth about a screen that does not.

In code the condition wraps a group rather than being an argument to each key, because keys
that apply together are written together and repeating the predicate six times is how the
seventh comes to disagree. Conditions nest. One that throws is taken as "no": a footer is
not worth ending a screen over.

`TuiHelp` is a projection, not a list it was handed. The screen tells it *how to ask* —
the tables along the focus path, nearest the keyboard first — so what it shows changes when
a dialog goes up, without anything updating it. A chord bound twice is shown once, by
whichever binding would actually answer, because two lines for one key describes nobody's
screen.

`examples/help-keys.tosh` is the demonstration, and it was driven rather than trusted:

```
browsing   r rename   ? help   q quit   e edit
editing    r rename   ? help   q quit   ^S save   Esc stop
```

Pressing `e` makes `e edit` vanish and `^S save` and `Esc stop` appear. Nothing updates the
footer; it is asked.

The segments box is ticked by `TUI-0024` rather than by anything here: `Help` is an ordinary
widget, so a row of `auto`/`*`/`auto` puts it beside a clock or a count without either of
them knowing about the other.

## The help browser

Its footer is generated now, and the golden masters are the argument. The change is exactly
three removals and not one character else:

```
- focus:search  F1-F4 groups  / search  [ back  ] forward  q quit  Enter open/toggle  i insert  Left up  1-9 related
+ focus:search  F1-F4 groups  / search  [ back  ] forward  q quit
```

That is the search box. The old footer offered `Enter open/toggle` there — where Enter
*leaves* the search box — and `i insert` while the reader is typing, where `i` is the letter
i. It offered `1-9 related` on topics with no related topics and `Left up` outside the CLR
tree, which is the only place Left means "up" rather than "move to the list".

`F1`-`F4` moved into the table as four bindings with one description between them: nine
lines for one idea is not a footer, and neither is four. `Insert` stays in the switch as
`i`'s other name, deliberately unregistered — a footer that already spells a command once
should not spell it twice.

The conditions are three new predicates, each mirroring a guard that already existed:
`CanInsertSelection` (there is a sink and something to put in it), `HasRelatedTopics`, and
`CanNavigateClrUp`. They are read rather than called, because a condition is asked once a
frame to draw a footer and must not do anything.

## The config browser

I had deferred this as "a redesign of how that screen holds its state rather than a footer
change". Half right. The edit modes really are the conditions, and that half converted
almost mechanically once there was something to convert them *into*; what took the work was
the browsing footer, which was not a fifteen-branch problem at all but a lying one.

**What the old footer claimed.** `Space toggle` on every node in the tree, where the key
does nothing unless the node is an editable boolean — the same untruth the help browser told
with `1-9 related`. `e edit`, `s save`, `q quit`, `/ search` and five more offered while the
reader is typing in the search box, where every one of them types itself. `r revert` and
`R reset` on a screen with nothing selected.

All of those are conditions now, and the conditions are the ones the handler already had:
`GetSelectedNode() is not null` was a guard inside `RevertSelectedNode`, and the footer
simply never asked it.

**The switch is gone.** Nine keys moved out of `switch (key.Key)` and into the table, which
means they are dispatched from the same place they are described. The `when` clauses they
carried were doing double duty — `case ConsoleKey.R when RevertSelectedNode()` runs the
action to discover whether the key applied — so each one split into a predicate the footer
can ask and an action that no longer has to report whether it was allowed.

**Two things the table could not express**, both fixed in `TuiShortcuts` rather than worked
around in the screen:

`Shift+Tab`. `Matches` ignores Shift deliberately — it is how a capital arrives, so a table
treating it as a modifier could not register `r` and `R` as two bindings — and the cost is
that `Tab` and `Shift+Tab` are one binding. `On` now has an overload whose action is handed
the press, so one entry cycles both ways and the footer says `Tab switch panes` once.

`Note`. An editor's `Enter` is answered by the editor, and that is right: a `TuiTextInput`
owning its own keys is the design. A screen that re-registered them in its table to be able
to describe them would have two dispatchers for one key, which is worse than the footer it
was fixing. A note describes without dispatching. What it buys is that the *condition* is
the same expression `HandleEditorKey` switches on, so the footer cannot offer `b browse`
while the path editor is already browsing.

The mode labels ride along as notes too — `Note("editing", "text")` reads as `editing text`
— so the whole line after `focus:` and `dirty:` comes from one table.

**Escape moved.** It was a case in `TryHandleSearchKey`, which meant the one key that leaves
the search box was invisible to the footer. It is a binding now; control characters already
fell through to the table, so nothing else had to change.

### The diff

The goldens are the argument, and the search footer is the whole of it:

```
- focus:search  dirty:0  No validation issues.  / search  Enter expand/open  Tab switch panes  e edit  t raw-edit  Space toggle  a apply  s save  r revert  R reset  q quit
+ focus:search  dirty:0  No validation issues.  Enter leave search  Esc cancel search
```

Eleven keys removed, every one of which typed a letter instead of doing what it said.

Driven in a real terminal at 200 columns, because at the snapshots' 120 the end of the line
is clipped and a truncation reads as an absence:

```
focus:tree  dirty:0  No validation issues.  / search  Enter expand/open  Tab switch panes  e edit  t raw-edit  a apply  s save  r revert  R reset  q quit
focus:tree  dirty:0  No validation issues.  / search  Enter expand/open  Tab switch panes  e edit  t raw-edit  Space toggle  a apply  s save  r revert  R reset  q quit
```

The second line is the same screen with `SyntaxHighlightingEnabled` selected. `Space toggle`
appears where the key works and nowhere else, `l reload` and `i init` only on the startup
node, and `editing text  Enter stage  Esc cancel` is character-for-character what the old
string said — the modes were already telling the truth.
