## Problem

`TuiShortcuts` carries a label and a description beside each action, and
`TuiShortcuts.Describe` builds a footer from them — so the help browser's footer can no
longer claim a key that does not work, which it had been doing for `/`, `[` and `]`.

That is half of it. The keys a screen answers *contextually* — `Enter`, `i`, the arrows,
`1`-`9` — are still a literal string in the footer beside a `switch` that implements them,
and the config browser's eight letter shortcuts are the same. The drift this removes is
only removed for the keys that happen to be in the table.

Bubbles' `key` and `help` packages are the shape worth copying: every binding carries its
own help, a screen exposes short and full help, and the help *is* a widget rendered from
the bindings rather than a string maintained beside them.

## Acceptance

- [ ] Contextual keys are registered too, with the condition under which they apply
- [ ] `TuiHelp` is a widget: a one-line summary, and a full view when asked
- [ ] A binding that does not currently apply is dimmed or omitted rather than lying
- [ ] Both browsers' footer strings disappear
- [ ] A script can register its own bindings and get the same footer for free

## Notes

The condition is the interesting part. `i insert` only applies outside the search box, and
`1`-`9` only when the current topic has related topics — so a binding is a predicate as
well as an action, and the footer is a projection of which predicates hold right now.
