> Status as filed: Open — fixed 2026-08-17

## Problem

**A nullable annotation on a built-in type alias will not parse in a `var` declaration.** `var x: int? = null` and `var x: string? = null` both fail with `tosh.bind.unknown_command` — *"Command 'var' is not a registered builtin or function declared in this source"* — a message that never mentions the annotation and points at column 1. The boundary is specific and is what makes it look like a parser special-case rather than a missing feature: `var x: Nonexistent? = null` parses fine and reaches the runtime annotation check, and `func f(a: int?)` works in parameter position. So the form is understood everywhere except a `var` declaration naming a built-in alias. Found while writing the `TS-P2-119` corpus; reproduces identically on a build of `HEAD`, so it is not related to that work.

## Acceptance

Find where a `var` declaration's annotation is parsed and why a known type alias followed by `?` diverges from an unknown name followed by `?` — the likely cause is the `?` being taken as the ternary operator once the preceding token resolves as a type. A corpus should cover `var` and `const` declarations for a built-in alias, a user class, an unknown name, and the parameter and return positions that already work, plus the diagnostic naming the annotation rather than the statement keyword.

## Resolution — 2026-08-17

The item's hypothesis was that `?` was being taken as the ternary operator once the
preceding token resolved as a type. It was not. The lexer keeps a nullable suffix **inside
the bareword**, so `int?` arrived at `LooksLikePotentialTypeName` whole and failed
`IsValidIdentifier` on the `?`. That predicate now strips a trailing `?` before testing,
because a nullable suffix does not change whether a name *is* a type name.

**Why it looked specific to built-in aliases.** `Int32?` passed only because the CLR-name
heuristic accepts a capitalised word — nothing to do with `Int32` being known. The alias
spellings are lowercase, so nothing else would take them, and an unknown name like
`Nonexistent?` reached the runtime check for the same reason `Int32?` did.

**Why the diagnostic was so far from the cause.** The predicate decides whether `var` opens
a *declaration*. A false answer did not report a bad annotation — it fell through to command
dispatch and reported `Command 'var' is not a registered builtin`, at column 1, naming
neither the type nor the annotation. `var x: Nonexistent? = null` now reports as an unknown
*type*, which is the acceptance's second half.

11 tests; 5 fail with the predicate reverted, and the six that pass either way are the
parameter and property positions that already worked plus the type-enforcement controls —
`int?` still refuses `"abc"`, and a non-nullable `int` still refuses `null`, so `?` continues
to mean something.
