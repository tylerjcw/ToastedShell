## Problem

`examples/system-monitor.tosh` contains a `Bar` function that repeats `█` and `·` to make
a meter, because there is no widget that does. Every script that reports progress will
write that function again, and each one will get the rounding, the empty case and the
width arithmetic slightly differently.

Ratatui has `Gauge`, `LineGauge`, `BarChart` and `Sparkline`; Bubbles has `progress` and
`spinner`; Rich has a multi-task `Progress`. Between them they cover what a shell script
actually reports: how far through, how much of each, and what it has been doing lately.

## Acceptance

- [x] `TuiGauge` — a proportion, with an optional label drawn over it
- [x] `TuiSparkline` — a series in one row, from block characters
- [x] `TuiBars` — a labelled bar per value, horizontal
- [x] Vertical bars, for a set small enough to read across the screen
- [x] `TuiSpinner` — a frame sequence driven by the clock, not by a thread, with eight styles
- [x] Each takes a pull binding, so a script sets `Value = &Function` and writes no update code
- [x] `examples/system-monitor.tosh` loses its `Bar` function

## Notes

A spinner is the one that needs care: it has to advance on the screen's own tick rather
than owning a timer, or a screen with three spinners has three threads and a redraw storm.
`TuiDeclarativeScreen.Tick` is where that belongs.

Charts beyond this — axes, scatter, braille canvas — are a separate question, and the
answer is another TUI control rather than `tosh-plot`: that library is written in Tōast and
draws graphics, and it is not where C# terminal widgets go. Filed as `TUI-0028`.

## What landed

The gauge, the sparkline and the bars. `TuiSpinner` is still open, and so are vertical
bars: the spinner needs the screen's own tick, which the tree-run path does not expose, and
that is the same hole `TUI-0008` is about — a live screen fed by a job or a channel rather
than polling a timer. Worth doing together.

`TuiBars` shares two things across its rows on purpose. The labels share a column, so the
bars start at the same place; and every bar is measured against the same maximum, because
comparing bars drawn to different scales says nothing. The floor under that maximum is the
sparkline's, for the same reason.

The sparkline follows the one in `pidwatch`, whose two decisions are worth having taken
from it. The chart is a window onto the *tail* of the series, so a monitor pushes samples
forever and the widget draws the last however-many fit; and the scale has a floor, so a CPU
percentage is drawn against 100 even when it never exceeds 4. Without that floor a quiet
series of 1-2-1-2 scales to its own maximum and draws as a mountain range, which is
exactly the reading a monitor must not give.

`Capacity` caps the series in the widget rather than at the call site, because a script
sampling once a second for a day otherwise grows a list of 86,400 numbers to draw thirty of
them. `PadLeft` fills the empty part with a dim floor so a chart filling up reads as time
passing rather than as a shape that keeps changing.

`TuiGauge.Amount` is not called `Value`, for the reason `TuiTree.ChildrenOf` is not called
`Children`: `TuiWidget.Value` already means what a widget answers a form with, and a
property hiding it would leave a gauge reporting nothing while looking like it reported
something. `Value` answers with the amount.

`examples/system-monitor.tosh` lost `Bar` and `RepeatGlyph`, and gained live meters with
`pidwatch`'s heat colouring — dim, cyan, yellow, red by how far up the chart a sample
reaches. The sampling happens in the pull binding that was already being asked once per
redraw, which is exactly the cadence a chart wants.

## The spinner

The note above said the frame should advance on the screen's tick rather than owning a
timer. It ended up better than that: the frame is a **function of the clock**, so there is
nothing to advance at all. Two spinners on one screen cannot disagree about whose turn it
is, because neither is keeping a turn — and one shared stopwatch means they do not drift
apart by however long there was between constructing them.

What a spinner does need is redraws, and it *asks* for them rather than starting a thread.
`TuiDeclarativeScreen.RefreshInterval` is now the sooner of the screen's own interval and
any spinning spinner's, so `tui run {| Spinner = "Working" |}` animates with no `--refresh`
and no author knowing that a spinner has a pace. It stops asking the moment nothing is
turning, which is the property worth having: driving the example in a pty counts eight
frames while it spins and **none** after space stops it.

Eight styles, each carrying its own interval because the two are one choice — braille dots
read as motion at eighty milliseconds and as a flicker at forty. `ascii` is the one that
works anywhere: every other style is above U+2000 and is a row of boxes on a terminal
without the font, which is `TUI-0009`'s concern arriving early.

A style's width is its widest frame, and the text sits at that rather than at the current
frame's, so it does not shuffle as the spinner turns. Several of these characters are
ambiguous-width and draw as two columns on some terminals, which is exactly the case that
would have shuffled.

Building the example found something unrelated and worth having: `Key = " "` could not be
registered at all. A chord is trimmed before it is read, so a literal space is lost — which
left the one key every pause binding wants unusable. `"space"` now works, along with
`"esc"`, `"up"`, `"pgdn"` and their like, beside the enum's own names.

## Vertical bars

The same data and the same shared scale, drawn the other way — `Orientation` on the widget
that already had the values rather than a second one beside it. A row per value reads
further and takes a long label; a column per value compares a handful at a glance, which is
what a reader expects of a chart.

The top cell of a column is an eighth block, borrowed from the sparkline's ramp for the same
reason it has one: a column should end where its value does rather than at the nearest whole
row, which is the difference between a chart and a set of rounded-off stacks.

A bar is as wide as the widest label, so the labels fit underneath without rotating or
eliding them, and the whole chart is as wide as it needs. Values go above, labels below, and
both are dropped first when there is not room for them — a chart with no room for its
numbers is still a chart, and one with no room for its bars is not.

I had deferred this with the wrong reason attached: that a chart with an axis might belong
in `tosh-plot`. It does not. That library is written in Tōast and draws graphics; TUI
widgets are C# and live here. An axis chart is another control, and is now `TUI-0028`.
