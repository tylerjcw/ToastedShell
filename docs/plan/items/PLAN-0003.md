## Problem

`TS-P2-38` investigated memory exhaustion during development — runs reaching toward
128 GB — and cleared the test suite as the cause. That clearing was correct: the suite
peaks around 2.8 GB at eight threads, which was measured rather than assumed. The item
closed with **the actual cause unknown**, and nothing has been looking at it since.

A candidate turned up while measuring something else.

MSBuild keeps its worker nodes alive after a build so the next one starts faster.
Nothing reclaims them: `dotnet build-server shutdown` reports success and leaves them
running, and they have to be killed directly. Found resident on 2026-08-16, with no
build or test running:

```
110 MSBuild worker nodes, 19.4 GB, idle
```

That was one working session's worth. Measured contributions:

| Action | Nodes left behind |
|---|---|
| one `dotnet build` | several |
| one full suite run | 26 nodes, 4.21 GB |

Repeated builds each leaving gigabytes behind, never reclaimed, grows without bound —
which matches the symptom `TS-P2-38` describes, and would explain why the suite looked
innocent when measured in isolation. It *is* innocent. The builds around it are not.

This also corrupted a measurement taken today: peak memory during an unlimited-thread
suite run read 8.9 GB, of which roughly half was nodes accumulating during the run
rather than tests. With node reuse disabled the same run peaks at ~4.5 GB.

## Measured — 2026-09-12, on a 32-core machine

A live reproduction turned up without being asked for: **232 idle nodes holding 41.3 GB
of RSS** were resident after a working session of `dotnet build` and `dotnet test` run
directly rather than through `scripts/build.tosh`. `dotnet build-server shutdown` was
run against them and reported *"MSBuild server shut down successfully"* while reclaiming
**none** — confirming this row's central claim exactly.

### It plateaus, and then it expires

| experiment | result |
|---|---|
| 8 identical builds of one project | **1 node**, flat — reuse works as designed |
| 8 builds of *different* projects | 1 → 8, then flat |
| build + test of the test project, ×3 | **30 nodes** on the first build, then flat |

A pool is capped at roughly `nproc` (30 of 32 here). It does **not** climb without
bound.

And every node exits on an idle timer. Sampled once a minute from a 31-node pool:

| t | nodes | oldest |
|---|---|---|
| t+14m | 31 | 893 s |
| t+15m | 23 | 897 s |
| t+16m | 1 | 882 s |
| t+17m | **0** | — |

**~900 seconds of idle**, which is MSBuild's documented default. So the ceiling is
*(builds started within any fifteen-minute window)* × *(nodes per build)* — which is how
232 accumulated, and why none of those 232 was older than eleven minutes when found.

### Eliminated as the `TS-P2-38` cause, and real as a contributor

**A sum of RSS overstates this badly, including in the numbers above this section.**
Killing the 232 nodes returned system *used* from 51 GB to 33 GB: about **18 GB**, not
41. At this process count RSS charges every shared page once per process. The row's
earlier "19.4 GB" and "4.21 GB" figures are RSS sums and overstate in the same way.

PSS would settle it directly and `/proc/PID/smaps_rollup` is not readable on this
kernel, so the kill delta is the honest measure.

So the real transient cost is **~18–20 GB**, it self-clears in fifteen minutes, and it
cannot explain runs approaching 128 GB. **`TS-P2-38` stays open with its cause still
unknown.** What this row rules out is unbounded growth: nothing here accumulates without
limit, so the next investigation should not spend time on MSBuild nodes.

### The unguarded spawners, and one that was not

`ToshEngine.RunDotNetAsync` and `RunDotNetForOutputAsync` were unguarded as this row
predicted — and the leak is **shipped**, not merely a development annoyance. `require
<project.csproj>` against a project with a real dependency chain, measured from a zero
baseline:

| | nodes left | |
|---|---|---|
| installed binary, unguarded | **7** | 1.26 GB |
| with the guard | **0** | — |

`scripts/toshmem.tosh` spawned a build without it too, and now sets it.

`ToshPublisher` is **cleared**: it appears in a search for `"dotnet"` because it locates
the dotnet root, and spawns no build. The suspicion list in this row is corrected.

The environment variable rather than `-nr:false`, for the reason `scripts/build.tosh`
already measured: the switch reaches only the invocation it is written on, while the
variable reaches the nested `dotnet` processes a build spawns.

## Notes

**Mitigated already, which is not the same as explained.** `19c08e2` sets
`MSBUILDDISABLENODEREUSE=1` in `scripts/build.tosh` and in the test assembly's module
initializer, and both leave zero nodes behind afterwards. So the growth is stopped
where this repository controls it. That is why this is `research` rather than a defect:
the remaining question is whether it was *the* cause, not whether to fix it.

The gap worth checking is `ToshEngine.RunDotNetAsync`. It spawns `dotnet build` for
`require <project.csproj>` and does not disable node reuse, so a long-lived TōSh
session that requires projects accumulates nodes in the user's shell. TōSh is a logon
shell, which makes that the worst place for an unbounded leak. Whether the product
should set it is a real decision — it trades a slower rebuild for a bounded session —
and it belongs with whoever owns that call rather than being slipped in.

Do not re-blame the suite. It was measured at 2.8 GB and that number held up again
today; repeating that investigation would waste the work `TS-P2-38` already did.
