## Problem

`HelpBrowserScreen.HandleKey` and `ConfigBrowserScreen.HandleKey` both check the quit
key before they check where focus is:

```csharp
// HelpBrowserScreen
if (key.Key is ConsoleKey.Q or ConsoleKey.Escape)
{
    _shouldExit = true;
    return TuiScreenResult.Exit;
}

if (_focus == HelpBrowserFocus.Search && HandleSearchKey(key))
```

So a `q` typed into either search box quits the browser instead of typing. Searching
for `query`, `quote`, `quit`, `Queue`, `Requires` or `Sequence` is impossible — the
browser closes on the first `q`. The config browser guards its other letter shortcuts
(`e`, `t`, `s`, `a`, `r`, `l`, `i`) with `_focus != ConfigBrowserFocus.Search` and
simply missed `q`, which shows the intent was already the other way.

The help browser has a second symptom from the same ordering. `HandleSearchKey` has a
branch for `Escape` that returns focus to the list:

```csharp
case ConsoleKey.Escape:
    _focus = HelpBrowserFocus.List;
    return true;
```

It is unreachable. Escape is caught by the same early test and quits outright, so
there is no way to leave the search box without losing the browser — which is also
why the branch has never been noticed.

Reproducing takes two keys: open `help --browse`, press `/`, press `q`.

## Acceptance

- [x] `q` typed with focus in either search box inserts a `q` and does not exit
- [x] `Escape` with focus in the help browser's search box returns focus to the list
- [x] `Escape` with focus elsewhere still exits, as it does now
- [x] `q` with focus outside the search box still exits, and still prompts in the config browser when changes are staged
- [x] `TuiBrowserGoldenTests` characterisation tests for the current behaviour are inverted to assert the fixed behaviour

## Notes

Found while writing golden-master tests for the browsers ahead of splitting them up,
and pinned rather than fixed: those tests exist to hold behaviour still during a
refactor, so changing behaviour in the same breath would have defeated them. The two
tests that currently assert the wrong behaviour say so in their doc comments and name
this item —

- `The_help_browser_quits_when_q_is_typed_into_its_search_box`
- `The_config_browser_quits_when_q_is_typed_into_its_search_box`

— and the other snapshots deliberately search for `ping` and `prompt` to steer around
it. Inverting those two tests is the cheapest confirmation that a fix landed.

## What landed

The ordering, as `TUI-0006` describes: whatever holds the keyboard answers first, and the
browser's own keys come from a `TuiShortcuts` table asked afterwards. The config browser's
search handler had to start reporting what it *consumed* rather than returning a result,
so that `Enter` still leaves the box through the same handler every other pane's `Enter`
goes through.

Driving it in a pty found the reason nobody hit this outside the suite: `/` never opened
either search box. It was matched against `ConsoleKey.Oem2`, and .NET reports
`ConsoleKey.Divide` for `/` on a real terminal — as it reports `None` for `[` and `]`, so
back and forward were dead too. Three advertised keys did nothing, and the search box they
guard could not be reached, which made this defect unreachable as well. Registered as
characters now, which is what the reader actually pressed.

Five tests changed sides: the two golden characterisation tests, `HelpBrowserScreenTests`'
`can_quit_with_q_even_when_search_has_focus` — a name that describes the defect — and two
new ones pinning that `q` and `Escape` still work when the search box does not hold the
keyboard. The ten golden frame snapshots are unchanged, which is how we know only the
routing moved.
