## Problem

Every screen that wants a status line builds one the same way: a `$"..."` with spaces
counted by eye, in a `Text` widget pinned to one row. `editor-dialogs.tosh` does it, both
browsers do it, and the guide teaches it because there is nothing else.

That works until something has to sit on the right. A file name on the left and a position
on the right means measuring both and padding between them, which the script cannot do
correctly — it would have to know the terminal width and the display width of what it
wrote, and display width is not string length. So screens either put everything on the left
or hard-code a column.

`htop` and `btop` are the shape: segments, each with its own style, grouped left, centre
and right, and the middle absorbing whatever room is left. It is the same three-way split
a tool bar wants, and the same one the key bar along the bottom of `htop` wants — which is
TUI-0022's footer once the bindings can generate it.

## Acceptance

- [x] ~~`TuiBar`~~ A row of segments, grouped left, centre and right, each with its own style
- [x] Segments measure by display width, so a wide character or an emoji does not shift the right-hand group
- [x] A segment too long for the room is truncated with an ellipsis rather than wrapping the row
- [x] ~~`Bar` is a markup name~~ The idiom is documented, with the trap that catches people
- [x] A segment can be bound, so a clock or a position updates without the script rebuilding the bar
- [x] Both browsers' footers — moved to `TUI-0022`, which is where generating them lives

## Notes

The name collides with the existing `TuiBars` (the graphing widget, `TUI-0020`), which is
plural and draws quantities. Renaming that one to `TuiBarChart` before this lands is
cheaper than living with `TuiBar` and `TuiBars` meaning unrelated things.

Depends on TUI-0005 for display width to be right; until then a segment measures in the
same units everything else does, and the right-hand group drifts on the same input that
misaligns every other box.

## Closing

The premise was wrong, and checking it before building anything is what saved the work. A
row already is a status bar: `auto` on the outer two segments and `*` in the middle puts one
group hard left, one hard right and one centred between them, each an ordinary node with its
own style and its own binding. Nobody needs the terminal's width or the display width of
what they wrote. A `TuiBar` widget would have been a worse `Row` with a second layout
algorithm behind it.

What was actually broken was underneath, and was not about status bars at all.

**A long child starved every child after it.** `Distribute` satisfied fixed and auto
children in written order against what was left, so one child wanting more than the row took
all of it and every later sibling was arranged at zero width. A status bar whose path grew
past the terminal lost the position indicator at the other end entirely. Now each child is
measured against the whole line — how big a thing naturally is should not depend on who was
written before it — and when they do not all fit, everyone gives up the same proportion of
what they asked for above whatever minimum they declared. `Size = "auto 12.."` is how a
segment says it matters.

**A cut left no mark.** Text clipped by its surface was indistinguishable from text that
happened to end there, which is how a status bar shows half a path and reads as though the
file were called something else. `TuiTextMeasure.Elide` counts columns rather than
characters, so an emoji costs two and the mark is paid for out of the room available.

**One row of text is a label.** It is cut and marked rather than wrapped, whatever `Wrap`
says. Folding a path onto a second row that will never be drawn shows its first thirty-eight
characters and calls that the answer — which is exactly what a status bar did.

Four test expectations moved, all of them from silent clipping to a marked cut, with the
widths unchanged in every case. The browser golden masters did not move at all: nothing that
fits is affected.

### Moved rather than done

Two boxes went to `TUI-0022`. Both browsers still build their footers as strings, but there
is no widget to rebuild them *on* any more, so what is left of that is "generate the footer
from the bindings" — which is that item, not this one.

`TuiBars` keeps its name. Nothing collides with it now.
