## Problem

Rendering emits SGR sequences from theme config directly — `\e[2;90m`, `\e[1;96m` and
so on — with no step that asks what the terminal can show. A 16-colour terminal, a
`TERM=dumb` session, a CI log and a user with `NO_COLOR` set all receive the same
truecolor escapes.

The related gap is what happens when there is no terminal at all. `TuiApplication.Run`
refuses outright:

```
This interactive browser requires a real terminal.
```

That is correct for a full-screen application and unhelpful as the only answer. A
script that builds a screen and runs it in a pipeline has no way to say "render this
once, as text". The help browser has a non-TUI path (`help <topic>` prints a panel);
a user-built screen has nothing.

## Acceptance

- [x] Colour capability detected once: truecolor, 256, 16, none
- [x] Styles degrade rather than being dropped — nearest-colour mapping, bold and reverse as fallbacks
- [x] `NO_COLOR` honoured, and `FORCE_COLOR` or the equivalent for the opposite case
- [x] A screen can render one frame as plain text for a non-terminal destination
- [x] Box drawing falls back to ASCII where the encoding cannot carry it
- [x] Tests render the same screen at each capability level

## What landed

The note was right about where it goes. `TuiTerminalWriter` is the one place that turns
cells into bytes, so it is the one place that has to know what the bytes can be — and
because a `TuiStyle` holds its colours as the strings the theme wrote, nothing above the
writer had to change at all.

### Colour

`TuiColors.Detect` reads the environment, for the same reason `TuiGraphics.Detect` does: the
terminal can be asked, but the answer arrives in the same stream as the keyboard, so asking
means racing the reader. `COLORTERM` decides truecolor because `TERM` is `xterm-256color`
whatever the terminal can really do; `TERM` decides the rest; `dumb` and an unset `TERM`
mean none.

`NO_COLOR` is honoured for any non-empty value rather than for the string `1`. That is the
whole of the convention and it is worth getting right: a reader who exports `NO_COLOR=yes`
has said what they meant, and a program that demands a particular spelling has not listened.
`FORCE_COLOR` is the other half, at the levels the JavaScript ecosystem settled on, because
that is where readers will have met them.

**Degrading rather than dropping** is the part with judgement in it. A named theme colour is
already one of the sixteen, so most of a theme needs no reducing at all; a hex colour becomes
a palette index at 256 and the nearest of sixteen below that. With no colour, a background
becomes **reverse video** — a selected row is drawn with a background, and dropping it leaves
the reader unable to see what is selected, which is not a cosmetic loss.

Nearest-16 matches against xterm's values, not the pure ones: xterm's red is `205,0,0`.
Matching against `255,0,0` sends every mid-toned colour into the bright half of the palette,
which is how a dim theme comes out shouting. The assertion for `#ff8000` was written
expecting bright yellow and is yellow — the mistake those values exist to prevent, made
while writing the test that proves they work.

Nearest-256 tries the grey ramp as well as the cube, because the cube's greys are six steps
apart and a theme made of near-greys otherwise collapses into two of them.

Driven in a pty against the config browser: `[2;90m` and `[1;33m` become `[2m` and `[1m` —
the colour gone, the attributes kept.

### Characters

The same idea one layer along. Every border, guide, meter and spinner is drawn out of
characters above U+2000, and on a terminal whose encoding cannot carry them the result is
not a degraded screen but a screen made of replacement boxes.

`TuiGlyphs.Fold` is applied at the writer, so it catches everything drawn rather than only
borders — the tree's guides, the gauge's blocks, the spinner's braille. The set is knowable:
grepping the widget sources for non-ASCII gives about sixty characters, which is a table
rather than a heuristic.

Two rules keep it honest. **Only what the framework draws is folded** — a filename with a
CJK character in it is the reader's data, and mangling somebody's text to protect a border
is the wrong way round. And **a fold never changes a width**: replacements are one column
because the layout already reserved the columns, and a wide cluster is never folded at all.
`…` to `...` is the tempting version of this and would leave every row two columns short;
it folds to `.`, and a test walks the whole table asserting the widths match.

Detection defaults to *supported* unless something says otherwise — a locale naming a
non-UTF-8 encoding, or `TERM=dumb`. A great many correct setups leave `LANG` unset, and
folding those would make a working screen worse to protect one that was not broken.

Driven in a pty with `TOSH_TUI_ASCII=1 TOSH_TUI_COLOR=none`:

```
+ colour ------------------------------------------------------------+
|orange on default                                                   |
|white on blue                                                       |
|q quit                                                              |
```

### Without a terminal

`tui run --plain` renders one frame and answers with its text. It needs nothing: a screen was
already pure — `Render` takes a size and returns a buffer — so the only thing missing was a
way to ask. `--width` and `--height` set the size, defaulting to the terminal's if there is
one and 80×24 if there is not.

Asked for rather than inferred. A script whose output happens to be redirected today should
not silently do something different from what it did yesterday, so `--plain` is a flag and
not a guess about the file descriptor.

## Notes

The capability check belongs next to the terminal writer from `TUI-0001`, which is
already the one place that turns cells into bytes.

The plain-text path is worth more than it looks: it is what makes a TUI screen usable
in a script that might be piped, and it is the honest answer to "what does this do
without a terminal" other than an error.
