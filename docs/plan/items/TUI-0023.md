## Problem

A screen can offer a command two ways. It can register a key, which is terse and costs no
room but is invisible until someone reads the footer, and it does not scale — `msedit` has
five menus of a dozen commands each and there are not that many memorable chords. Or it
can put a button on the page, which is discoverable and costs a row of the document.

Neither is a menu. A menu bar is the third answer and the one every editor settled on: the
commands are named, grouped, and cost one row whether there are five of them or fifty,
because the group opens only when it is asked for.

The pieces are nearly all here. A drop-down is `TuiOverlay` with a `TuiList` in it,
positioned somewhere other than the centre. A menu bar is a `TuiStack` of labels with the
open one marked. What is missing is the anchoring — every overlay today is centred — and
the walk: Left and Right move between menus while one is open, Escape closes, and the
letter after `&` opens a menu without the mouse.

The same widget is a context menu (anchored to the caret or the pointer, no bar) and a
combo box (anchored to a field, the list replacing what it holds). Building three of these
separately is how a framework ends up with three that behave differently.

## Acceptance

- [x] `TuiOverlay` can anchor its modal to a rectangle rather than only centring it, and flips it when it would fall off an edge
- [x] `TuiMenu` is a list of commands, each a label, an optional key to display beside it, and an action
- [x] `TuiMenuBar` holds named menus, opens one at a time, and walks between them with Left and Right
- [x] A separator and a disabled item both draw and both refuse the keyboard
- [x] Escape closes the open menu and returns focus where it was, rather than to the first field
- [x] `Menu` and `MenuBar` are markup names, with the same `Do`/`Exit` vocabulary as `Keys`
- [x] A combo box is the same drop-down anchored to a field, not a second implementation
- [x] The guide documents all of it, and the surface test sees the new names

## Notes

Anchoring is the part with a design decision in it. An overlay currently measures its modal
against the screen and centres what comes back; an anchored one measures it against the
room on the side it opens towards, which is a different number above and below the anchor.
Flipping when it will not fit is what stops a menu near the bottom of the terminal from
being clipped to two rows.

Focus return is the other. `TuiFocus` seats the keyboard on the first focusable in scope
whenever the scope changes, which is right for a dialog and wrong for a menu: closing one
should put the keyboard back in the document, not at the top of it.

## Progress

Anchoring first, because it is the generic half and is worth having on its own — a tooltip,
a completion list and a colour picker all want it. `TuiOverlay.Anchor` is a *widget* rather
than a rectangle, so the popup follows what it came out of when the layout changes. It opens
below, flips above when below will not hold it, and is pulled back onto the screen rather
than clipped when it opens from the last name on a bar. No margin: a margin is what stops a
dialog looking painted onto the page, and an anchored popup is meant to look attached.

`TuiMenuTitle` exists because a menu cannot be its own anchor. It is arranged twice — once
as a name on the bar and once as the popup — and the second would overwrite the rectangle
the first has to supply.

Three things were decided by driving it rather than by design:

**A bar must not take the keyboard until something is down.** It sits at the top of the
tree, so a focusable bar takes focus *first*, and the letter a reader types at a screen that
has just opened opens a menu instead of being typed. `IsFocusable => Open is not null`, and
the bar is reached the way every editor reaches one: a key aimed at it, which `TUI-0026`
had just made possible (`Press = "menus"`).

**The selected command needs a marker, not just a style.** A band of bold spaces is
invisible on a terminal with no colour — the same reason a button draws one.

**Closing has to hand the keyboard back where it was.** Revalidation alone seats it on the
first focusable, so a reader who opened a menu from the third pane came back to the first.

The popup is the screen's to place, not the bar's, because a widget cannot paint outside
what it was given. A tree with a bar in it gets an overlay wrapped around it if it has not
got one, so the bar is written where it belongs — one row at the top of a column — instead
of the author having to say the same thing twice.

## The combo box

It is short, which is the whole point. The list is a `TuiMenu`, the layer is the one a menu
bar uses, and the anchoring is `TuiOverlay.Anchor` — so the only thing `TuiCombo` adds is
what a *field* does that a *bar* does not: show the chosen value, be as wide as its widest
option so a column of them lines up, and step through with Left and Right without opening
at all.

Getting there needed one generalisation rather than a second implementation. The screen
knew about `TuiMenuBar` by name; it now knows about `ITuiPopupHost` — what to show, what it
opens from, and how to take it down. A widget cannot draw a popup itself (it cannot paint
outside what it was given, which is the whole reason layers exist), so it says what it wants
and the screen puts it there. Escape closing a popup is the screen's, once, for both.

Once the list is up it holds the keyboard, because it *is* the modal on the layer. So moving
and choosing are the menu's, and `TuiCombo.OnInput` handles only what opens it. That is the
difference between reusing a drop-down and having two.

Driven rather than trusted: Enter opens on the item already chosen, Down Down Enter picks
the third, Escape closes without changing anything and hands the keyboard back, and Right
steps to the next without opening. The menus example still behaves exactly as it did after
the generalisation.

One thing that turned up on the way: `TuiHelp.Keys` hid `TuiWidget.Keys`. Every widget
already has a `Keys` — the keys it *answers* — and a property of the same name meaning the
keys it *describes* is two ideas wearing one word. Renamed to `Table` before it could become
the fourth time this codebase made that mistake.
