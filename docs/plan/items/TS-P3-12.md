## Problem

**Type highlighting misses real contexts, differently per surface.** Reported from a profile.tosh screenshot: `$this` renders harsh red in VS Code, `<T>` and declared classes uncoloured, `→ FileSystemEntry` return annotations plain. Three separate renderers are involved and each had different gaps. **REPL (fixed):** the type-context heuristic knew `->` but not `→` — and the Unicode arrow is what real profiles contain — and never treated `is`/`is not`/`as`/`where`/glued-`<` as type positions, so match arms and generic arguments went uncoloured; `SyntaxHighlighterTests` covers each context with a negative control. **VS Code (partly config, partly pending):** `$this` was scoped `variable.language.this`, which most themes render bright red — rescoped to `variable.other.member.this.tosh`, the member family the reporter asked for — and the family the grammar already uses for `variable.other.member.tosh`, which `variable.other.property` was not. **Corrected 2026-08-08:** the rescope was first written into `syntaxes/tosh.tmLanguage.json`, which is *generated* by `scripts/generate_vscode_grammar.py`, so the next regeneration silently reverted it and a reinstall showed no change. It now lives in the generator at the rule for `\$this`. Diffing a fresh regeneration against the working tree confirms the JSON is entirely generator output, so nothing hand-written was lost with it. The LSP already computes semantic tokens for *declared* type names (`GetVisibleTypeLikeSymbols`) but the extension contributed no `semanticTokenScopes`, so themes without direct semantic colours dropped them — mapping added. Both edits sit in the working tree alongside ~800 lines of the user's own uncommitted editor work, so they are **not committed here**; they ship with the user's next extension commit and need a vsix rebuild+reinstall to see. The screenshots may partly reflect the previously installed vsix, so `<T>` should be re-checked after reinstall before touching the grammar further — the working-tree grammar has rules that look correct for it. **Grammar audit, 2026-08-01, driven by tokenizing real code rather than reading rules.** A `vscode-textmate` harness over the users own profile and libraries measured **8,916 tokens, 2.3% unscoped**, and the clusters named the defects. **Fixed:** (1) *record and dict keys took whatever scope their spelling implied* — in one literal, `local` scoped as a storage modifier, `config` as a builtin command and `data` as a function call: three colours for three things of one kind. Records and dicts now have real begin/end contexts with a key rule, and that rule starts at the whitespace *before* the name so it beats the command rules, which is the tie-breaking trick `command-position` already documents for itself. (2) *`out`/`ref` scoped as control flow* though they are parameter directions — now `storage.modifier.direction`, so they read like `shy` and `raw` rather than like `if`. (3) *native marshalling types* (`cstring`, `cstr`, `buffer`, `handle`) fell through to the generic type rule — now builtins. (4) *success contracts* `-> ok` and `-> count` rendered as ordinary types, losing the distinction that makes a native signature readable; they now have `support.type.contract`, kept under `support.type` so themes that know only that still colour them. (5) *optional parameter markers* left `path?` entirely unscoped, because the name class excludes `?` and the rule demanded an immediate colon. \| **Remaining, and it is structural rather than a missing rule:** untyped parameters — `func +(o)`, `func f(other)` — stay unscoped, 38 occurrences in the users own code. The parameter rule requires a following colon, which is what stops it mis-scoping a command call inside parentheses: from a regex alone, `(o)` in a signature and `(greet)` in an expression are the same shape. The fix is a begin/end context for function signatures, `func <name>(` … `)`, inside which every bareword is a parameter — the same structural move that fixed record keys. Worth doing deliberately rather than as a regex widening, because signatures appear in class bodies, native binds, operator declarations and lambdas, and a bad block boundary would mis-scope all of them. **Grammar structure, 2026-08-15, measured not read.** The `vscode-textmate` harness was rebuilt and run over the user's libraries, the examples and their profile: **31,333 tokens, 2.22% unscoped**. Two entries this row already recorded as *fixed* — record and dict keys, and the `path?` optional marker — were **measurably still broken**, and the reason is the trap this row documents about itself: they were written into the generated `tosh.tmLanguage.json` and a later regeneration dropped them. The generator contained neither rule. All four gaps are now fixed **in the generator**: (1) *signature parameters* — the declaration rules open a region at their `(` and close it at the matching `)`, with a `nested-parens` rule so a parameter whose own type is a function (`cb: func(int) -> int`) cannot end the signature at its inner paren; this is what lets an untyped `func f(other)` be told from a call `greet(name)`, which no regex can do, and it subsumes `path?` by making the marker part of the name. (2) *record, dict and set literals* are regions with a key rule, so a key can be told from a defaulted parameter `func f(a, b = 2)` — the reason a `match` rule was not enough. (3) *type-alias right-hand sides* — `type IntPercent = int where …` left the base type unscoped in every alias. **Measured after: 528 unscoped, 1.69%**, and the residual `signature-parameter` count is the classifier's own false positives (a `func` line whose body contains `\| where Modified > $now`). Verified by tokenizing that the region closes on every shape — operator overloads, generics, splat parameters, a function-typed parameter, and the paren-less `func f => 1` — and, as the control that matters, that `var x = greet(name)` still leaves `name` unscoped. One deliberate imprecision: inside a function-typed parameter, `func(int)`'s positional `int` scopes as a parameter name, because a bare name there is genuinely ambiguous with an untyped parameter; it is coloured rather than invisible, which is the better of the two. **Guarded** by `EditorSurfaceParityTests`: the structural rules must exist in the checked-in artefact, and the parameter rule must not have regained its `(?=:` requirement — the specific regression that made it useless. Both were confirmed to fail when reverted. **Fourth pass, 2026-09-11, after the vsix rebuild and reinstall.** The harness was run against the *installed* grammar over the user's libraries and the repository's examples: **140,001 tokens, 1.04% unscoped**, already better than the 2.22% above. Four clusters named four defects, all fixed in the generator. (1) *The name a callback declares* — `callback` had just become a language word, but only the keyword coloured; `raw callback Comparator(...)` left `Comparator` bare while `trait Componentwise` scoped its name, and that name is what a `bind native` parameter is annotated with. (2) *Negative literals* — the arithmetic rule requires whitespace on both sides, so a sign glued to a digit matched nothing and rendered in the plain foreground beside its coloured digits: `Cancel = -6` in two colours, 98 occurrences. A glued sign belongs to the literal, which is the language's own rule (`TOAST-0115`, `TOAST-0121`); the lookbehind is the load-bearing half, since without it the rule claims the `-5` of `$a-5` and `f()-5`, which are subtractions. (3) *Hyphenated builtins* — `native` is a keyword and `native-free` a command, and a word boundary sits happily before a hyphen, so the keyword matched first and left `-free` scoped as nothing; both ends needed fixing, the keyword rule to decline a word touching a hyphen and the command rules' keyword exclusion to stop excluding a name it only prefixes. (4) *`catch (e)`* — the bound variable was scoped by nothing, once per error handler, 70 times; the parameter rule cannot claim it because it requires a following colon, so the binding needed its own rule ahead of control-flow. **Measured after: 1,210 unscoped, 0.87%.** All four are guarded in the checked-in artefact by `EditorSurfaceParityTests`, and each guard was confirmed to fail against the previous grammar. The residual clusters are single-word tokens in contexts a regex cannot tell apart — the loop variable of `for i in`, an untyped `&$this.Method` reference — which is the same structural class as the signature-parameter work above.

## Acceptance

**The GtkSourceView grammar was measured on 2026-09-11**, with a harness over the same corpus: **6.27% unscoped against VS Code's 0.87%**, and five defects, all fixed — no arithmetic operators at all in the `operators` context, unscoped dotted qualified names, only the last of a run of modifiers styled (GtkSourceView keeps one repetition of a repeated capture), a command position that demanded column zero so every indented call was missed, and no rule for a command reached through a dotted path. **2.54%**, and after five more — the type after `new`/`cast`/`is`/`as`, the name in front of a `:`, the name in front of a lone `=`, `catch (e)`, and an unquoted `require` path — **0.98%, level with the VS Code grammar's 0.87%**. One further defect was invisible to the measurement because it was a wrong colour rather than a missing one: `{|` opens a record, not a command position, so the first key of every literal was styled as a function call. Two regressions were introduced and caught by re-measuring: widening the command position without a keyword guard styled an indented `var` as a call, because GtkSourceView breaks a tie by earliest start rather than include order; and capturing the opening delimiter consumed it unstyled. Remaining there, and the same structural class as the VS Code work above: untyped parameters and loop variables, which need a signature region rather than a wider regex. **`<T>` and declared-class colouring were re-checked against the installed 26.9.7 grammar on 2026-09-11 and are correct** — `T` scopes `entity.name.type`, a declared class `entity.name.type.class`, `where T: Numeric` binds `entity.name.type.parameter`, and `$this` is `variable.other.member.this`, not the `variable.language.this` that themes rendered harsh red. That closes the part of this row that was waiting on a reinstall. **Fifth pass, 2026-09-11, both grammars measured against one corpus.** The two harnesses were re-run over the same 122 files (the repository's examples and scripts, and the user's libraries), which is what makes the two numbers comparable — the earlier VS Code figures were taken over a narrower root set. Starting from **0.89% unscoped** (VS Code) and **0.98%** (GtkSourceView), nine more defects were found and fixed, three of them shared by both grammars.

*VS Code.* (1) `&$this.OnSave` — the function-reference rule wanted a bareword after the `&` and so matched none of the handlers the libraries actually pass, leaving the operator uncoloured 37 times; `&greet` had always worked, which is why reading the rule did not show it. (2) `out value: int` — inside a signature *region* the keyword rules do not reach the direction word, so every `bind native` block that has one left it bare. (3) `require ./Graphics.tosh` came apart into four scopes for one literal: `.` an accessor, `/` nothing, `Graphics` a type, `tosh` a member. (4) *An inheritance clause names a list* and one regex can take only the first of it — worse, the type reference it used carries a comma for generic arguments, so `uses Polygonal, Shape2D, Enclosing, Transformable` scoped `Polygonal,` with the separator glued on and left the other three bare. It is a region now, ending at `{`, at `where`, or at the next clause keyword, because `fulfills IPoint<T> uses Componentwise where T: Numeric` is all three on one line. (5) *A command on the right of an assignment* — the opener alternation knew the start of a line, `;{(`, a pipe and `=>`, and not a plain `=`, so `var package = read-file $p` left `read-file` bare while the same word inside parentheses coloured. The whitespace in the new lookbehind is the load-bearing half: it separates an assignment from `==`, `!=`, `>=`, `+=` and `--flag=value`, each of which would otherwise scope the word after it as a call. (6) *Named arguments* were the one defect the measurement could not see, because it was a wrong colour rather than a missing one: in `new Facility(Name = $soname, Kind = "library")` the first name took the *function call* scope and the ones after each comma took nothing. **Measured after: 1,056 unscoped, 0.62%.**

*GtkSourceView.* (1) There was **no rule for `&` at all**, in any of its forms — not the function reference, not the background operator, and not `&&`, which was missing from the operator alternation entirely. (2) *The last name in every dotted chain* was scoped by nothing: `qualified-segment` claims only a segment with a dot after it, deliberately, so `using System.Drawing`, `ToastLib.Math.GeometryEpsilon` and the second and later calls of `$body.Replace(…).Replace(…)` all ended bare — the variable rule consumes `$body.Replace` whole and cannot span the closing paren. The new rule is included *after* `qualified-segment`, which starts at the same character for a mid-chain name, because GtkSourceView breaks that tie by include order. (3) The inheritance clause, as above, with `end-at-line-end` as the backstop so a clause that meets none of its enders cannot run away down the file. **Measured after: 773 unscoped, 0.54%.** Each new rule was probed for its guard cases as well as its subject — `&&`, `a == b`, `x += 1`, `--flag=value`, a doc comment containing the word `uses`, and the line after a clause.

All nine are guarded in the checked-in artefacts by `EditorSurfaceParityTests`, and all eleven new guards were confirmed to fail against the previous grammars. What remains in both is the same structural class named above: untyped parameters and loop variables, which need a signature region rather than a wider regex. The require-following work described here as outstanding was already complete, with `RequiredTypeVisibilityTests` covering the chain, the cycle, the depth bound and the URI form; the description below predates it.
