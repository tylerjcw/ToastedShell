## Problem

`build.tosh publish` does all of its work, prints its DONE banner, and then fails:

```
────────────[ DONE ]────────────
  ✓ Binary: …/artifacts/publish/linux-x64/single-file/tosh
  ✓ Version: 26.8.43.10
✖ error  tosh.runtime.return_type_conversion_failed
  Function 'Run' returned a value that could not be converted to 'Result'.
```

Exit code 1. Everything before the return is correct — the five projects publish, the bundle
is promoted, the version is written, and on the Arch path the packages are built and
installed. Only `Publish.Run`'s own return fails.

## Measured 2026-08-27

- **Both RIDs.** `--rid linux-x64` and `--rid win-x64` fail identically, so it is not
  cross-compilation.
- **Not a regression from current work.** The *installed* `/usr/bin/tosh`, dated 25 August
  and predating the session's changes, fails the same way on the same script.
- **The value is correctly shaped.** Instrumenting immediately before the return prints every
  field at its declared type — `Binary=System.String`, `Size=Tosh.Runtime.StorageSize`,
  `RID=System.String`, `Output=System.String`, `SelfContained=System.Boolean`,
  `Trimmed=System.Boolean`, `Duration=System.String`, `Version=System.String` — against a
  record declaring exactly those eight.
- **`type-of` says it *is* a `Result`.** The probe reports `built=Result`, and the value
  renders with all eight fields under their own names. A value the runtime calls a `Result`
  is then refused conversion to `Result`.

## Cause — found 2026-08-27

**A return annotation is checked against every value the function *produces*, not against the
value it returns.**

`ConvertFunctionReturnValue` is applied in two places: to each value the body yields
(`ToshEngine.cs:6560`) and to each `return` value (`:6578`). A body statement that produces a
value contributes it to the function's output, so a function that emits anything before
returning has its annotation checked against the emission too, and

```tosh
record R(A: string)
func Make() -> R {
    42
    return new R("v")
}
```

produces **two** values and fails. `Publish.Run` emits plenty — `dotnet` writes its build
output through it — so the `Result` it returned arrived behind a hundred lines of restore
output and was refused.

`§Refinement Types` describes `-> T where (_)` as a predicate over the **return value**,
which is not what happens.

### Every hypothesis before that was wrong, and each was cheap to kill

Recorded because the wrong ones cost more than the right one:

- **Three same-named `Result` records.** Renaming `Publish.Result` to `PublishResult` in the
  real file changed nothing but the name in the error.
- **A `StorageSize` field, nesting, module qualification, `defer`, sibling-module calls.**
  All reproduced nothing.
- **External commands.** `/usr/bin/true` was fine and bare `true` failed, which looked like
  command resolution and was actually the difference between a command and a *literal*.

What found it was bisecting the real function with an early `return` — ok after
`var artifacts = …`, failing after `dotnet …$restoreArgs`. Then the reduction: any statement
producing a value, including `42`.

## Why the fix is not obvious

Not checking emitted values would break the case the annotation exists for:
`func f() -> int { 42 }` has no `return`, so its emitted value *is* its result and checking it
is the annotation working. The ambiguity is a function that **both emits and returns** — the
emissions are output, the return is the return value, and only one is what `-> T` is about.

A rule that fits both: check emitted values only when the function contains no `return`.
That is a language semantics change and wants a decision rather than a patch.

## What was done — 2026-08-27

`Publish.Run` is annotated `dynamic`, with the reason recorded beside the record it used to
return. The release path exits 0. Piping the `dotnet` calls to `ignore` would have satisfied
the annotation and *lost the build log* — `ignore` suppresses external console output, not
just the values — which is the wrong trade.

Three tests characterise the behaviour, including the control that shows why the simple fix
is wrong: an emitted value with no `return` is still checked, and should be.

## The decision, and how it was implemented — 2026-08-28

**A return annotation describes the returned value.** When a function contains a `return` of
its own, the values it emitted on the way there are output, not the result, and the annotation
no longer applies to them. A function with no `return` is unchanged: its emitted value *is* its
result, so `func f() -> int { 42 }` still validates and `func f() -> int { "no" }` still fails.
A generator is also unchanged — its yielded values are its result by definition.

The distinction cannot be made where the value is emitted, because the `return` has not
happened yet and the values stream: buffering them would cost the short-circuiting that lets
`gen | first` stop an unbounded producer, which an earlier item measured at 800,000 wasted
values. So it is answered from the syntax once and cached on the definition, as
`FunctionDefinition.ReturnsExplicitly`.

That walk is reflective rather than a switch over the forty statement kinds, because a switch
would silently miss the next block-carrying statement someone adds and answer "no return" for
it — the same *must agree by hand* failure `TOAST-0002` is about. Statements that introduce a
body of their own are skipped, so a nested function's `return` is not mistaken for this one's,
and arguments are not walked at all, which puts a lambda's `return` naturally out of scope.

**The suite did not move: 6,651 before and after.** A semantics change to return annotations
altering nothing says the emit-and-return shape was only ever failing — there was no working
behaviour depending on the old rule.

The emitted values are still *produced*. Only the annotation stops applying, so a function that
emits and returns yields both, and `build.tosh` ignores its publish result as it always did.

## Acceptance

- [x] `build.tosh publish` exits 0 when it succeeds
- [x] A reduction that reproduces the conversion failure, small enough to live in the suite
- [x] The cause named — not the same-named records, which were tested and cleared: a return
      annotation is applied to emitted values as well as returned ones
- [x] A test covering it — three, in `FunctionTypeTests`, characterising current behaviour so
      that changing it is deliberate
- [x] **The language decision, taken 2026-08-28**: `-> T` checks only the returned value when
      a function contains a `return`. `Publish.Run` is annotated `-> Result` again
- [x] A negative control — the emitted-value-without-return case, which must keep failing
