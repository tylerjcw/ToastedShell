## Problem

Every width calculation in the TUI goes through one function:

```csharp
public static int GetVisibleLength(string text)
{
    ArgumentNullException.ThrowIfNull(text);
    return text.Contains('\x1B') ? StripAnsi(text).Length : text.Length;
}
```

`.Length` is UTF-16 code units. That is the right answer for ASCII and wrong for
everything else a terminal renders:

| Text | Columns | `.Length` |
|---|---|---|
| `日本語` | 6 | 3 |
| `😀` | 2 | 2 |
| `👩‍💻` | 2 | 5 |
| `é` as `e` + U+0301 | 1 | 2 |

Borders, padding, column alignment, clipping and the ellipsis all consume this number,
so a single CJK filename, an emoji in a commit message or a decomposed accent shifts a
pane's right-hand border and every line below it. A process list or a file picker
reaches this on ordinary input, not on a contrived case.

## Acceptance

- [ ] Width is measured in grapheme clusters, not code units or runes
- [ ] East Asian Wide and Fullwidth count as two columns
- [ ] Combining marks and zero-width joiners count as zero
- [ ] Clipping never splits a grapheme cluster, and never leaves a half-drawn wide character
- [ ] A wide character that does not fit in the remaining column is replaced rather than overflowing
- [ ] Tests cover CJK, emoji, ZWJ sequences, combining marks and the clipping boundary

## Notes

Cheaper to fix once `TUI-0001` lands. With string frames the answer is needed wherever
text is concatenated; with a cell buffer a cluster occupies one or two cells at the
point it is written, and every consumer is right by construction.

`ClipPlain` also has a performance defect worth fixing in the same pass: it appends one
character at a time and recomputes the visible length of the whole accumulated string
each iteration, which is quadratic per line.

.NET has `StringInfo`/`TextElementEnumerator` for cluster segmentation. It has no East
Asian width table, so that part is a table to embed and keep current with Unicode
releases.
