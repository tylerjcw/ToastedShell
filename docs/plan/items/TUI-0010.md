## Problem

`TuiApplication.Run` enters the alternate screen, hides the cursor and enables mouse
reporting, and restores all three in a `finally`. That covers an exception thrown
inside the loop. It does not cover:

- **A signal.** `SIGINT`, `SIGTERM` or `SIGHUP` terminates the process without running
  `finally`, leaving the terminal in the alternate screen with a hidden cursor and mouse
  reporting on. The user's next prompt is invisible.
- **A handler that throws.** Live screens now invoke script callables from inside the
  render loop. `BuildTickInvoker` drains the callable with no guard, so an ordinary
  scripting mistake — a null dereference in a tick handler — propagates out of the loop
  and ends the screen.
- **A panic mid-write.** An exception between writing the alternate-screen escape and
  the first frame leaves partial state.

TōSh is the user's login shell. A TUI that can leave their terminal unusable is a
different class of bug from one that draws a box wrong.

## Acceptance

- [x] Terminal state restored on `SIGINT`, `SIGTERM`, `SIGQUIT` and `SIGHUP`, not only on normal exit — implemented, but see the verification note below
- [x] A handler that throws is caught, reported on the screen, and does not end the session
- [x] Repeated failures from the same handler are rate-limited rather than reported every tick
- [x] Restoration is idempotent and safe to run twice
- [x] A test asserts the escape sequences that restore the terminal are emitted on each path
- [x] Signal-path restoration confirmed by a human pressing Ctrl+C in a real terminal
- [x] `tosh` recovers a terminal left in a bad state by an earlier crash

## Verification, and what could not be verified

Normal exit is confirmed end to end: running `examples/system-monitor.tosh` under a pty
and pressing Escape ends the output with exactly
`ESC[?1000l ESC[?1006l ESC[0m ESC[?25h ESC[?1049l` — mouse off, styling reset, cursor
shown, alternate screen left.

**The signal path is implemented but not demonstrated.** Sending `SIGINT` to the process
under a pty harness did not restore, and the reason turned out to be the harness rather
than the code: a standalone .NET program registering `PosixSignalRegistration` for
`SIGINT` also failed to fire, and its process was still running afterwards — the signal
was ignored, not mishandled. A background job started from a non-interactive shell has
`SIGINT` ignored, and the test inherited that. One earlier `SIGTERM` run under `script`
did restore correctly, which is consistent.

So this needs a person at a real terminal: start a TUI, press Ctrl+C, and check the
prompt comes back with a visible cursor. Until then the guarantee is argued, not shown.

Two implementation notes worth keeping:

- Restoration writes through `ITuiHost.WriteUrgent`, which goes straight to the file
  descriptor. An ordinary `Console.Write` from a signal handler waits on the console
  lock held by the render loop blocked in `Console.ReadKey`, and the process can die
  from the signal before the bytes leave.
- Calling `Environment.Exit` from the handler to make the ordering deterministic was
  tried and reverted. Running shutdown from a signal handler while other threads hold
  locks risks a hang, which is a worse failure than the one being fixed.

## Notes

Priority 1 because the failure lands on the user's shell rather than on the program
that caused it, and because the new tick path made it reachable from ordinary script
errors rather than only from TUI bugs.

`Console.CancelKeyPress` covers `SIGINT`, and `PosixSignalRegistration` covers `SIGTERM`
and `SIGHUP` on .NET. The handler must be installed by whoever entered the alternate
screen, and removed when it exits, or a later non-TUI crash emits escapes for a screen
nobody entered.

## Recovery, and how it was shown

A session restores on every path it can reach. It cannot reach `SIGKILL`, a machine that
lost power, or a runtime that dies before any handler runs — and after one of those the
reader is sitting in the alternate screen with no cursor, which is the whole point of this
item.

So a session leaves a note while it holds the terminal and removes it on the way out. A note
still there when TōSh next starts on that same terminal means the last one did not get out.
Keyed by the terminal rather than by the machine, because a crash in one window should not
make every other window repaint itself.

Blindly emitting the escapes at every start would also work, and would be wrong: a shell
should not write to the terminal on the chance that something is broken. That property is
the one worth defending, and it is tested both ways.

Shown end to end under a pty, which the signal path could not be. One shell starts a live
screen, the harness `SIGKILL`s it — no handler runs, nothing is restored — and the next
`tosh` on the same pty emits exactly the sane sequence before its first output. Two shells
in a row with no TUI between them emit nothing at all.

`tui reset` is the same repair on demand, for a reader who can already see their terminal is
wrong and should not have to convince anything of it. It deliberately does not go through
the "is there a terminal to draw a screen on" check that every other subcommand does: it is
the one you reach for *because* the terminal is in a state nothing can draw on.

The sane sequence now also deletes graphics placements. A picture the terminal was asked to
draw outlives the program that asked (`TUI-0025`), so a crash during a preview would leave
it painted over the shell — a new way to land exactly the failure this item is about, and it
arrived with the feature.

### Still wanted

The Ctrl+C confirmation, which needs a person at a real terminal: start a TUI, press Ctrl+C,
check the prompt comes back with a visible cursor. Until then that one guarantee is argued
rather than shown — though a reader who hits it now has `tui reset`, and the next shell on
that terminal repairs it by itself.

## Ctrl+C, at last

Confirmed by a person at a real terminal, and the confirmation found the rest of the bug.
The terminal *was* restored — the prompt came back with a visible cursor — and the job list
said:

```
[1]  Stopped                 tosh .../examples/preview.tosh
```

Stopped, not finished. Reproduced under a pty by writing `\x03` to the master, which is a
real Ctrl+C rather than a `kill`, and the capture says it plainly:

```
ESC[?1000l ESC[?1006l ESC[0m ESC[?25h ESC[?1049l    the restore
ESC[2;9H7 ESC[2;9H8 ESC[2;9H9                       the loop, still drawing
```

The handler restored the terminal and the process did not stop. The runtime does not apply
`SIGINT`'s default disposition once something has registered for it, so the loop carried on
painting frames over the shell it had just handed back, until the terminal driver stopped it
for reading in the background and left a suspended job behind. That is worse than not
restoring at all: the reader gets their prompt, types into it, and watches a dead program
scribble over the answer.

The earlier note argued against ending the program from the signal handler, and that still
holds. What was missing is that the handler does not have to: it sets a flag, and the loop —
on its own thread, where ending a program is safe — sees it and throws.

Which exposed the second half. A screen with no refresh interval blocked on the keyboard, so
it never got to look at the flag: the signal restored the terminal and the loop stayed asleep
in a read nobody was going to answer. The loop now waits in slices whatever the screen is,
which is what live screens already did.

And Ctrl+C is quiet. An error box reading "The operation was canceled" is the shell
explaining to the reader what they just did; the exit code is 130, the conventional
128 + `SIGINT`, so a caller can still tell.
