## Problem

Rendering one frame of `config browse` takes **676 µs and allocates 1.18 MB**, against
59 µs and 220 KB for the help browser at the same size — eleven times slower and five
times the garbage, measured by `TuiRenderBenchmarks`.

The cause is in the render path:

```csharp
private ToshRuntime CreateThemePreviewRuntime(params string[] pathPrefixes)
{
    var previewRuntime = ToshRuntime.CreateDefault(TextWriter.Null, TextWriter.Null);
    ...
}
```

Drawing the detail pane constructs a complete shell runtime so it can show the user
what their theme or prompt would look like. There are four call sites —
`BuildPromptPreviewEntries` and the table, syntax and TUI theme previews — and they run
whenever the selected node is under `Theme` or `Prompt`, which is most of the tree.

`ToshRuntime.CreateDefault` is not a cheap object. It loads the standard library,
registers every built-in shell type and command, and starts a background task that
walks the platform type index:

```csharp
WarmUpTask = Task.Run(DotNetTypeResolver.WarmUpPlatformTypeIndex);
```

So every frame — every arrow key, and every second once a refresh interval is set —
builds a runtime and spawns an index walk. The allocation figure understates it,
because work handed to a background task is not charged to the frame that started it.

## What it actually was — the first diagnosis was wrong

This item was filed blaming `ToshRuntime.CreateDefault`, called from the render path by
`CreateThemePreviewRuntime`. That call was real and wasteful, and caching it changed
nothing: the benchmark went from 676 us to 698 us, which is to say it stayed put.

Profiling per selection found the real distribution. The default selection lands on the
`Theme` group, which draws no prompt preview, so the benchmark had been measuring a case
that was never the problem:

| selection | before | after |
|---|---:|---:|
| a plain leaf | 0.15 ms | 0.16 ms |
| `Display.Style` | 0.24 ms | 0.16 ms |
| `Theme.Tables` | 1.38 ms | 0.53 ms |
| `Prompt` | **17.16 ms** | **0.52 ms** |
| help browser, for scale | 0.13 ms | 0.10 ms |

The cost is rendering the previews, not building a runtime to render them against.
`BuildPromptPreviewEntries` calls `ToshPromptRenderer.BuildPreviewLines` twice — two
complete sample prompts, which runs the prompt's own modules, including the one that
reads git state. Every frame. Every arrow key.

Confirmed against BenchmarkDotNet with a benchmark added for the selection that matters:

| | before | after |
|---|---:|---:|
| config browser on `Prompt`, 120x40 | 10.87 ms, 1.32 MB | **155.5 us, 495 KB** |
| config browser default, 120x40 | 676 us, 1.18 MB | 608 us, 1.16 MB |

Seventy times faster on the node that was slow, and the default improves a little
because the runtime caching still removes work.

## Acceptance

- [x] A preview runtime is built once and reused, not built per frame
- [x] The rendered preview is kept too, and re-rendered only when a staged value or the width changes
- [x] `config browse` renders within the same order of magnitude as `help browse`
- [x] No frame path calls `ToshRuntime.CreateDefault`
- [x] `TuiRenderBenchmarks` measures the expensive selection, not only the cheap one

## Notes

Found by writing the `TUI-0012` baseline rather than by reading the code — and then
*mis-diagnosed* by reading the code. The measurement said the config browser was slow;
the first explanation for why was the expensive-looking call in the render path, and it
was wrong. What settled it was measuring again after the fix and finding the number
unmoved.

The lesson is narrow and worth keeping: a profile that names a screen does not name a
line. The per-selection timings took two minutes to produce and pointed straight at the
prompt preview, which no amount of reading had suggested.

There is a second benefit. The preview was re-rendering live git state and the clock on
every frame, which is part of why these screens were hard to snapshot: the golden
masters scrub the prompt preview because it changed between frames. Cached previews
change only when the user changes something.

Independent of the cell-buffer work: the cost is in deciding *what* to draw, not in how
it reaches the terminal, so `TUI-0001` will not improve it and the two should not be
conflated when comparing before and after.

The preview is a good feature and worth keeping. It is a caching problem, not a reason
to remove it — the values it depends on change only when the user stages or applies
one, which is exactly the signal to invalidate on.
