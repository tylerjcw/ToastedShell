## Problem

The framework has widget *state* and no widget. `TuiListState`, `TuiScrollState`,
`TuiTextInputState`, `TuiFilePickerState`, `TuiCollectionEditorState`,
`TuiGroupEditorState`, `TuiPathEditorState`, `TuiOptionPickerState`,
`TuiOrderedToggleEditorState` and `TuiConfirmationDialogState` track selection, scroll
and editing between keystrokes. Not one of them draws. `TuiListState` contains no
`Render` at all.

So drawing belongs to whichever screen owns the state, which is why the two browsers
carry a thousand lines of rendering each, and why a script cannot be given widgets —
only a fixed menu of six `TuiWidgetKind` values interpreted by the 753-line
`TuiCustomScreen`.

Layout is four arrangements in an enum — `Single`, `SplitHorizontal`, `SplitVertical`,
`Stacked` — and they are not composable. Two panes side by side with a status bar under
both is not expressible, so a screen that wants it computes rectangles by hand.

## Acceptance

- [ ] A widget contract with `Measure`, `Arrange`, `Draw` and `OnInput`, and children
- [ ] Measure takes constraints and returns a desired size, so "as tall as its content" and "half the width" compose
- [ ] Containers as widgets: row, column, grid, dock, overlay
- [ ] The existing state types gain a drawing half, or are wrapped by widgets that have one
- [ ] Scrolling is a container (`TUI-0007`), not a field on nine types
- [ ] `TuiWidgetKind` retires in favour of a registry, so the set of widgets is open
- [ ] A `Custom` widget whose content comes from a script handler, called per refresh and never per frame
- [ ] The built-in set covers text, list, tree, table, input, checkbox, select, progress and tabs

## Notes

Depends on `TUI-0001`: `Draw` needs a surface to draw onto.

The decision recorded in `DECISIONS.md` is that built-in widgets are C# and compose
freely, with script-defined drawing available through one `Custom` widget on the
refresh path rather than the frame path. That keeps an `IShellCallable` out of the hot
loop while leaving the set open.

Two-pass measure/arrange is the part worth not skipping. A single-pass layout can do
splits and stacks, which is exactly what exists now; it cannot do intrinsic sizing, and
intrinsic sizing is what makes a form, a table with a fitted column, or a dialog sized
to its message work without arithmetic at the call site.
