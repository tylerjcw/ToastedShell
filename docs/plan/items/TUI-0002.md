## Problem

The framework has widget *state* and no widget. `TuiListState`, `TuiScrollState`,
`TuiTextInputState`, `TuiFilePickerState`, `TuiCollectionEditorState`,
`TuiGroupEditorState`, `TuiPathEditorState`, `TuiOptionPickerState`,
`TuiOrderedToggleEditorState` and `TuiConfirmationDialogState` track selection, scroll
and editing between keystrokes. Not one of them draws. `TuiListState` contains no
`Render` at all.

So drawing belongs to whichever screen owns the state, which is why the two browsers
carry a thousand lines of rendering each, and why a script cannot be given widgets —
only a fixed menu of six `TuiWidgetKind` values interpreted by the 753-line
`TuiCustomScreen`.

Layout is four arrangements in an enum — `Single`, `SplitHorizontal`, `SplitVertical`,
`Stacked` — and they are not composable. Two panes side by side with a status bar under
both is not expressible, so a screen that wants it computes rectangles by hand.

## Acceptance

- [x] A widget contract with `Measure`, `Arrange`, `Draw` and `OnInput`, and children
- [x] Measure takes constraints and returns a desired size, so "as tall as its content" and "half the width" compose
- [x] Containers as widgets: row, column, grid, dock, overlay
- [ ] The existing state types gain a drawing half, or are wrapped by widgets that have one
- [x] Scrolling is a container (`TUI-0007`), not a field on nine types
- [x] `TuiWidgetKind` retires in favour of a registry, so the set of widgets is open
- [x] A `Custom` widget whose content comes from a script handler, called per refresh and never per frame
- [x] The built-in set covers text, list, tree, table, input, checkbox, select, progress and tabs

## Notes

Depends on `TUI-0001`: `Draw` needs a surface to draw onto.

The decision recorded in `DECISIONS.md` is that built-in widgets are C# and compose
freely, with script-defined drawing available through one `Custom` widget on the
refresh path rather than the frame path. That keeps an `IShellCallable` out of the hot
loop while leaving the set open.

Two-pass measure/arrange is the part worth not skipping. A single-pass layout can do
splits and stacks, which is exactly what exists now; it cannot do intrinsic sizing, and
intrinsic sizing is what makes a form, a table with a fitted column, or a dialog sized
to its message work without arithmetic at the call site.

## Where this actually stands — 2026-09-20

Most of it shipped and the item was never updated, so it read 0/8 while seven of the eight
were done. Measured rather than assumed:

- **The contract exists.** `TuiWidget` has `Measure(TuiConstraints) -> TuiSize`, `Arrange`,
  `Draw`, `OnInput` and `Children`. `TuiCustomScreen` and `TuiWidgetKind` are gone — the
  enum retired in favour of `TuiWidgetRegistry`, which now answers 37 names.
- **Layout composes.** `TuiStack` gives row and column, and `TuiGrid`, `TuiDock` and
  `TuiOverlay` exist. Two panes side by side with a status bar under both is expressible.
- **Scrolling is a container**, `TuiScroll`, rather than a field on nine types.
- **The built-in set is covered** — text, list, tree, table, field, check, combo, gauge and
  tabs are all registered, and 34 widget classes exist.
- **Script-supplied content works**, through `TuiLines` and its `LinesSource`: a handler
  returns styled lines and the widget draws them, per refresh rather than per frame. It is
  not named `Custom`, which is the only part of that criterion left unmet, and the name is
  not the capability.

## What is left: the state types have no drawing half

The criterion asking that the existing state types gain one, or be wrapped by widgets that
have one, is **not** met and is most of the item's original complaint. Nine were named;
one still has no `Render` and no widget standing in for it:

| | lines | has a widget? |
|---|---|---|
| `TuiListState` | 134 | yes — `TuiList` |
| `TuiScrollState` | 63 | yes — `TuiScroll` |
| `TuiFilePickerState` | 309 | **yes — `TuiFilePicker`** |
| `TuiCollectionEditorState` | 242 | **yes — `TuiCollectionEditor`** |
| `TuiOrderedToggleEditorState` | 214 | **yes — `TuiArrange`** |
| `TuiGroupEditorState` | 152 | **yes — `TuiGroupEditor`** |
| `TuiOptionPickerState` | 134 | **yes — `TuiChoice`** |
| `TuiPathEditorState` | 89 | no |
| `TuiConfirmationDialogState` | 88 | **yes — `TuiConfirm`** |

So drawing for those still belongs to whichever screen owns the state, which is why
`ConfigBrowserScreen.cs` is 1,311 lines and `ConfigBrowserScreen.Detail.cs` another 1,235 —
the "thousand lines of rendering each" this item was filed about. The widget contract they
would be written against now exists; writing them against it is the remaining work.

## First one done — 2026-09-20: `TuiConfirm`

`TuiConfirmationDialogState` has a drawing half. The widget **wraps** the state rather than
restating it — the criterion allows either, and wrapping keeps the tested key handling and
the tested wording of the entries exactly as the config browser answered to them.

It is registered for markup, which is the point of the exercise:

```tosh
tui run {|
    Form = [ {| Confirm = "Delete everything?", Title = "Careful",
                ConfirmLabel = "Delete", CancelLabel = "Keep",
                OnAnswer = func(yes) { … } |} ]
|}
```

Driven in a pty: `y` answers true, `n` answers false, and the dialog takes itself down so
the script carries on. A script raises a question without knowing how a dialog is laid out.

Two decisions worth recording:

- **One `OnAnswer`, given the answer**, rather than `OnConfirm` and `OnCancel`. A dialog that
  is dismissed has been answered, and two handlers make it easy to write only the first and
  silently ignore a cancellation.
- **Answering ends the screen by default**, which is the opposite of `Button`'s `Exit`. A
  button rarely finishes anything; a dialog nearly always does, and one that stays up after
  an answer leaves the reader with no way out — `Esc` answers it too, so it would not even
  be an escape. `Exit = false` keeps one embedded in a larger form.

`TuiMarkupSurfaceTests.The_guide_documents_every_markup_name` caught the widget arriving
undocumented, which is the guard working: a markup name nobody can look up is a name nobody
can use.

## Second one done — 2026-09-20: `TuiChoice`

`TuiOptionPickerState<TItem>` has a drawing half, wrapping the state the same way. The
config browser built its enum picker a row at a time in the middle of a detail pane —
`"> (*) Name"` assembled inline — and that is now a widget, `{| Choice = [...] |}`.

It is deliberately *not* `TuiList`. A list is something you move through and activate; this
is a question with one answer, so the mark says which option **is** the value, and the
state's key keeps that answer across a redraw with the same options.

Three things the guards caught, each worth keeping:

- **`Every_widget_has_a_name_in_markup_or_a_reason_not_to`** rejected the first name. A
  markup name has to be a prefix of the type name — `spark` for `TuiSparkline` — and
  `choose` is not a prefix of `TuiOptionPicker`. Renamed to `TuiChoice`/`Choice`, which
  reads better in markup *and* follows the rule, rather than adding an exemption.
- **`The_guide_documents_every_markup_name`** rejected it again for arriving undocumented.
- A display-property test failed because the first implementation reimplemented labelling.
  `TuiList.FormatValue` is public and already asks shell records before reflection — a
  picker labelling its options differently from a list would be a difference nobody asked
  for, so it delegates.

`Exit` is opt-in here and on by default for `TuiConfirm`. A picker is usually one field
among several and a form with two that ended on the first would never reach the second; a
dialog exists to be answered and taken down.

Five to go. `TuiPathEditorState` (89 lines) is next by size but depends on
`TuiFilePickerState` and `TuiTextInputState`, so `TuiGroupEditorState` (152, over
`TuiListState` alone) is the cleaner one. `TuiFilePickerState` (309) has a second consumer,
`TuiFilePickerScreen`, and wants more care.

## Third one done — 2026-09-20: `TuiCollectionEditor`

`TuiCollectionEditorState<TItem>` has a drawing half — the rows, the cursor, and the input
line the config browser drew into a detail pane.

Chosen over `TuiGroupEditorState`, which is smaller, because the group editor's rows are
config-flavoured — `"{prefix} {marker} {name}: {value}"` with the marker read off a schema —
while "edit this list" is something a script actually wants: tags, exclusions, search paths.
Size was the wrong axis to pick on.

**It applies the edit itself**, which is the one place it departs from the browser's use.
The state reports *the reader submitted this text* and leaves the mutation to its owner —
right for a browser staging changes against a schema, wrong for a script, which would
otherwise have to implement add, replace and remove before it could ask for a list of tags.
`OnChange` is given the whole list rather than the delta, because a caller almost always
wants the result and one given only the change has to keep its own copy in step to find out
what it now holds.

## Fourth one done — 2026-09-20: `TuiGroupEditor`

`TuiGroupEditorState<TItem>` has a drawing half — rows of `name: value` with a cursor,
`Space` to toggle, `Enter`/`e` to edit, `t` to raw-edit, `Esc` to close.

The line it draws that `TuiCollectionEditor` does not: **it does not act on the rows.** A
collection is a list of values, where "add this one" means the same thing wherever it is
used, so the widget applies it. A group is a list of *settings*, and what toggling one means
belongs to whoever defined it — so this reports which row was asked about and the caller
decides. Two widgets over two states that look alike and are not.

`Row`, `Column` and `Box` remain how markup groups widgets on screen; `Group` is a list of
fields. The guide says so, because the name alone does not.

## Fifth one done — 2026-09-20: `TuiArrange`

`TuiOrderedToggleEditorState<TItem>` has a drawing half — boxes, a cursor, `Shift` with an
arrow to move the *entry* rather than the cursor, and a minimum below which a toggle is
refused.

The state asks for an `includedUpdater` returning a **new** entry carrying the new state.
That suits a record with an `Included` field and suits nothing a script is likely to hand
it: a list of strings cannot carry a flag. So inclusion is tracked beside the entries, by
key, and the updater returns the entry untouched — strings, records and dictionaries all
work, and the entries a caller passed in are the entries it gets back.

Two bugs of my own, both worth recording because neither would have been obvious later:

- `MinimumIncluded` was a plain property, and the state takes its minimum when *opened*. An
  object initializer runs after the constructor, so `new TuiArrange(entries) { MinimumIncluded
  = 1 }` kept the zero it was opened with and let the last entry leave. The setter re-opens.
- The re-open then passed `_state.Items` — the state's own list — and `Open` clears its list
  before refilling it from the argument, so the widget emptied itself. It snapshots.

## Sixth one done — 2026-09-20: `TuiFilePicker`

`TuiFilePickerState` has a drawing half. It was the one that already had one — but only as
`TuiFilePickerScreen`, a whole screen: usable from the shell, unusable as one field on
somebody else's form. The state assembles its own display through `BuildEntries`, so the
widget is mostly wiring.

Two details were not wiring, and both are the same mistake in different places: the state
sizes its page from the height it is *given*, and its key handling takes a page size
separately. Tell those two different numbers and `PageDown` moves by a different amount than
the reader can see. Both now come from the bounds the widget was arranged into.

Verified from a script, which is the point — `{| FilePicker = "…", Mode = "file", Start =
"…/alpha.txt" |}`, `Space`, and the handler is given the full path.

`Mode` decides what may be *chosen*, not what is shown: a file picker still walks
directories. Confirmed, because a picker that hid them would be unable to reach anything.

One to go. `TuiPathEditorState` (89), which needs this one and `TuiTextInputState` — a path
you can type or browse for.
