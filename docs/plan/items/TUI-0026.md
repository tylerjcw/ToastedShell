## Problem

`TuiShortcuts` binds a chord to an action, and the action is a script function. That covers
every command that changes state — save, open, quit, refresh — and none that change where
the keyboard is.

Which is half of what keybindings are for. `Ctrl+P` opens a palette *and puts the caret in
it*. `/` focuses the search box. `F2` moves to the second pane. `Tab` already does this,
but only in tree order, and a screen with three panes and a footer cannot say "this key
means that pane".

The script cannot do it itself because `TuiFocus` is not reachable from a handler. A
declarative screen builds one and keeps it private, which is right — a script should not be
holding a focus manager — but it leaves no way to say the thing at all. The object style is
no better off: the screen owns the focus manager there too.

The answer is not to expose the manager. It is to let a binding name what it wants, the way
the rest of the framework names things: by id.

## Acceptance

- [x] A shortcut can name a widget to focus, by id, instead of (or as well as) running a function
- [x] `Keys = [ {| Key = "/", Focus = "search" |} ]` in markup, `$keys.Focus("/", "/", "search", "search")` in code
- [x] A binding can activate a widget as well as focus it — press a button, submit a form, open a menu — without the script holding a reference to it
- [x] Focusing a widget that is hidden or out of scope is a no-op, not an exception
- [x] A handler can ask for the keyboard back where it was, which is what closing a menu or a palette needs
- [x] A background task started from a binding does not block the redraw, and the screen keeps answering keys while it runs
- [x] The guide's keybinding chapter covers all three kinds: run this, focus that, and start something

## Notes

Focusing by id is the same addressing the rest of the surface uses — `Id` already keys a
widget's value in a result — so it needs no new concept, only a lookup from the root and a
`TuiFocus.Focus` call the screen makes on the binding's behalf.

The background task half overlaps TUI-0008 and should not be built twice. A binding that
starts a job is a binding that hands the screen something to be fed by; the interesting
part here is only that the screen must not wait for it.

## Closing

`ITuiAim` is the answer to "not the focus manager, then what". A key that aims says what it
wants by id and the screen does it, so the manager stays private and a script never holds
one. Four spellings, and the difference between them is what a keybinding chapter is
actually about: `Do` runs a function, `Focus` moves the keyboard, `Press` does what Enter on
a widget would do *without* moving the keyboard, and `Back` puts it where it was.

`Press` needed one new thing: `TuiWidget.Activate`, which a button, a list, a table, a
tree, a field and a form each answer for themselves. Without it the screen would have had to
know what kind of thing every id named.

Two readings were worth getting right. An id written on a labelled field names the row,
because that is the node the author wrote, so aiming looks inside it for the input — the
same reading `TuiBindings.Attach` already takes. And reachability is the focus scope's
answer rather than the tree's: a field behind a modal is in the tree and out of reach, and a
key that jumped to it would put the caret somewhere the reader cannot see.

`examples/keybinds.tosh` exercises all of it, and was driven in a pty rather than trusted:
`/` moves to the search box while a list has the keyboard and types a slash when a field
does, `Esc` hands the keyboard back to the list, and F5 and Ctrl+R press Reload twice
without taking the caret out of what was being typed.

The background-task box is ticked by `TUI-0008` rather than by anything here: a handler that
wants to take time starts a job and lets its results come back through a `Feed`.
