## Problem

`build.tosh publish --rid win-x64` produces the right artifacts, and they run: measured
under Wine on 2026-08-26, the language, pipelines, classes, filesystem access, `$env` and
external process spawn all work, and `examples/collections.tosh` and
`examples/pattern_matching.tosh` run to completion. What does not exist is any way to
*install* the result.

Blocked on [`TOSH-0008`](TOSH-0008.md): until a cross-RID publish stops shipping the host's
SDK assemblies, an installer would package a build whose `--compile` aborts.

## What installing means, taken from what Linux actually does

`packaging/archlinux/PKGBUILD` is unglamorous, which is the useful part:

| Linux | Windows equivalent |
|---|---|
| five single-file executables into `/usr/bin`, renamed (`Tosh.Cli` → `tosh`) | the same five into `%LOCALAPPDATA%\Programs\Tosh\` |
| — | a user-level `PATH` entry, so no administrator is required |
| `tosh.install` adds `/usr/bin/tosh` to `/etc/shells` | no analogue; a Windows Terminal profile fragment is the nearest thing |
| `LICENSE` into `/usr/share/licenses` | beside the binaries |

No services, no daemons, no registry beyond `PATH`. The `/etc/shells` hook exists because
TōSh is a login shell, and that is the piece with no direct counterpart.

## Decision: extend `build.tosh`, do not write a separate installer

`build.tosh` does not install anything today — it publishes a validated bundle and hands it
to a platform packager (`makepkg` over the `PKGBUILD`). Windows needs a **second packager**,
not a second build system, so `packaging/windows/` sits beside `packaging/archlinux/` and
the install step dispatches on RID.

The alternative — a standalone installer project — would duplicate what `build.tosh`
already owns and has got right: CalVer bumping, `--targets` selection across the five
projects, `.tosh-publish-manifest` validation, the staging and rollback machinery, and the
cross-RID smoke-test skip that already exists for exactly this case.

## Decision: a zip and a PowerShell script first

It cross-builds from Linux with no new toolchain, is testable under Wine immediately, and
does what the Arch package does — place binaries, register a path.

`msitools` (`extra/msitools`, whose `wixl` authors MSI files on Linux) is the upgrade path
when Add/Remove Programs and a real uninstaller are wanted; it needs no Windows build
machine. `makensis` is not installed here and would have to be fetched.

## Acceptance

- [ ] `packaging/windows/` produces a zip of the five executables plus `LICENSE`
- [ ] An `install.ps1` places them under `%LOCALAPPDATA%\Programs\Tosh\` and adds that
      directory to the user `PATH` without requiring administrator
- [ ] `build.tosh publish --rid win-x64` invokes it, dispatching on RID the way the Arch
      path is dispatched today
- [ ] An uninstall path that removes both the files and the `PATH` entry
- [ ] Installed and run on real Windows, not only under Wine
- [ ] A Windows Terminal profile fragment, or a recorded decision not to ship one
