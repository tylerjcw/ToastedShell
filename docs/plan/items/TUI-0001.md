## Problem

`TuiFrame` is `record TuiFrame(string Content)`. A screen builds one string by
concatenation and the runtime prints it:

```csharp
host.Write(ClearScreenAndHome);
host.Write(frame.Content);
```

Four consequences, and they are not independent — they are all the same missing
abstraction.

**Every frame is a full repaint.** The screen is cleared and redrawn in whole, once per
render. That was invisible while the loop only redrew on a keystroke; now that screens
can set a refresh interval (`TUI` live screens landed in `0b2a2cc`), a one-second
monitor clears and repaints the entire terminal every second.

**Nothing can overlap.** A modal dialog, a dropdown, a tooltip or a floating status
cannot be drawn over the content beneath it, because there is no "beneath" — there is a
string, and whatever is in it is what there is. `ConfigBrowserScreen` has a confirmation
dialog today and it is rendered by the screen splicing lines into its own output.

**Mouse hit testing is hand-maintained.** `HelpBrowserScreen` keeps `_lastSearchRect`,
`_lastListRect` and `_lastDetailRect` as fields, assigns them during `Render`, and
consults them in `HandleInput`. Every screen that wants a mouse repeats this, and the
rectangles are correct only until someone changes the layout and forgets one.

**Width is wrong** — see `TUI-0005`. One place computes how wide text is, and it is
wrong there, but with string frames the answer is needed at thirty call sites instead of
one.

There is also a concrete cost in the clipping path. `TuiRenderHelpers.ClipPlain` appends
one character at a time and recomputes the visible length of the accumulated string on
every iteration, which is quadratic in the line length, per line, per frame.

## Acceptance

- [ ] A cell buffer type: a grid of (grapheme cluster, style) with a size
- [ ] Widgets draw into a sub-region of a buffer, and cannot draw outside it
- [ ] A compositor writes one buffer over another, so overlays and modals stop being the screen's problem
- [ ] The terminal writer diffs against the previously presented buffer and emits only the changed spans
- [ ] Cursor position and visibility are part of the presented frame rather than a side effect
- [ ] Hit testing answers "which widget is at this column and row" from the arrangement, not from fields the screen maintains
- [ ] `TuiFrame` either wraps a buffer or retires; `ITuiScreen.Render` returns one
- [ ] The golden-master snapshots render from the buffer, and the diff of the first conversion is read line by line rather than re-recorded

## Notes

This is first in the sequence because it is the only part that cannot be added later
without redoing the work above it. Widgets, containers and the declarative surface are
all additive over a buffer; none of them are expressible over a string.

Snapshots get better, not worse: a grid of cells serialises to something a person can
read without ANSI escapes in the way, which is an improvement on the escape-laden
snapshots recorded in `e5d1681`.

The performance target belongs to `TUI-0012`, which should be written before this is
called done, so that "diffed output" is a measured claim rather than a design note.
