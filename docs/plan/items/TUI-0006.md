## Problem

`HandleInput` hands the raw event to the screen, and the screen sorts it out. Each one
writes its own dispatch, and the order of the tests is load-bearing in a way nothing
enforces.

`TOSH-0011` is what that costs. Both browsers check the quit key before they check
where focus is:

```csharp
if (key.Key is ConsoleKey.Q or ConsoleKey.Escape)
{
    _shouldExit = true;
    return TuiScreenResult.Exit;
}

if (_focus == HelpBrowserFocus.Search && HandleSearchKey(key))
```

So typing `q` into either search box quits the browser, and the help browser's own
`Escape`-returns-to-list branch is unreachable. The config browser guards its other
letter shortcuts on focus and simply missed this one, which shows the intent was
already the other way — there was just nothing to make it so.

With a widget tree the question becomes structural: an event goes to the focused
widget, and bubbles outward only if unhandled. A text input handles `q` because it is
focused; the screen's quit shortcut never sees it.

## Acceptance

- [x] Events dispatch to the focused widget first and bubble to ancestors when unhandled
- [x] A widget declares whether it is focusable; focus moves in tree order
- [x] Focus scopes: a modal traps focus and the content beneath it stops receiving events
- [x] Screen-level shortcuts are registered rather than tested inline at the top of a handler
- [x] A text-entry widget consumes printable characters before any shortcut sees them
- [x] `TOSH-0011` closes as a consequence, and its two characterisation tests invert
- [x] Mouse events route by hit testing, not by rectangles the screen stores during render

## What landed

`TuiFocus` tracks the focused widget and routes events: the focused widget first,
then each ancestor, and what nothing consumes is left for the screen. Containers no
longer hand events to their children — `TuiStack` and `TuiBorder` used to offer every
event to every child in turn, which let an unfocused widget consume something meant for
the focused one.

`TuiTextField` is the widget that makes the original defect unrepeatable: while focused
it consumes printable characters, so a screen-level shortcut never sees a letter someone
is typing, and the screen does not have to know a text field exists for that to hold.
Asserted directly in `TuiFocusTests`.

What remains is the part that needs the browsers: modal focus scopes, registered
shortcuts, and inverting the two `TOSH-0011` characterisation tests. Those close when
the browsers move onto widgets in `TUI-0003`.

## What landed

`TuiWidget.FocusChildren` is the scope: almost every container answers with its children,
because almost every container shows all of them at once, and `TuiOverlay` with a dialog
up answers with the dialog alone. `TuiFocus.Focusable` walks that rather than `Children`,
so Tab cannot step behind a modal, and `TuiOverlay.HitTest` swallows a click aimed past
one.

`TuiFocus.Revalidate` is what makes it work when the scope changes without a key being
pressed — a handler putting a dialog up, a tick replacing a pane. The keyboard was seated
when the tree was built, and without re-seating it Enter went to the form the reader could
no longer see while the dialog in front of them did nothing. Only a widget that has gone
out of reach is rescued: nothing focused is a state a caller can ask for, and a screen
that wants every key for itself asks for it.

`TuiForm.KeepOpen` completes the pattern, which is Windows Forms' `FormClosing` with
`e.Cancel`: a cancel handler reads how the form ended and decides it has not, so Escape
can put a confirmation up instead of abandoning what the reader typed.

`TuiShortcuts` holds a screen's own keys in a table, asked once after the focused pane has
declined. The table is not what fixes `TOSH-0011` — asking it in that order is. What the
table removes is the possibility of asking it first by accident, which is what a line of
code in the middle of a method invites. Both browsers now register their quit key there,
and the three inverted tests assert that a letter typed into a search box is a letter.

Driving the browsers in a pty turned up a second defect underneath the first. `/`, `[` and
`]` were matched against `ConsoleKey.Oem2`, `Oem4` and `Oem6`, and .NET reports `Divide`
for `/` and `None` for both brackets on a real terminal — so search, back and forward were
dead keys everywhere except in tests that built their own key info. `TOSH-0011` was
therefore unreachable outside the suite as well: you could not open the search box to type
`q` into it. Registered as characters, which is what the reader actually pressed.

## Notes

Depends on `TUI-0002` for the tree, and on `TUI-0001` for hit testing.

The two tests named in `TOSH-0011` currently assert the wrong behaviour on purpose, so
that a refactor holds it still rather than changing it by accident. They are the
fastest confirmation that this landed: invert them and they should pass.
