## Problem

`TuiScrollState` exists, and then every widget that scrolls owns one and drives it by
hand. `TuiListState` holds a `Scroll` and calls `SetDimensions` and `EnsureVisible`
itself; `HelpBrowserScreen` holds a separate `_detailScroll` for its detail pane;
`TuiFilePickerState`, `TuiCollectionEditorState` and the text widget each do their own
version. Page size is recomputed from a height at each call site, which is why
`SetItems(items, pageSize)` takes a page size at all.

Scrolling is not a property of a list or a document. It is a relationship between a
viewport and content larger than it, which is what a container expresses.

## Acceptance

- [x] A scroll container that takes any child and scrolls it
- [x] The child measures at its natural size; the container clips and offsets
- [x] Scroll position survives content changes the way `SetItems` currently clamps selection
- [x] Keyboard and wheel scrolling handled once, in the container
- [x] Scrollbar rendering, where wanted, happens once
- [x] No *widget* keeps a `TuiScrollState`; the six that remain are screen state, not widgets

## What landed

`TuiScroll` measures its child with no height limit — how tall it wants to be is what
decides whether there is anything to scroll — then draws it into a buffer at that full
height and composites the visible rows out. That costs a buffer per frame for scrollable
content, which is what the compositor is for; the alternative is letting a child draw
outside its bounds, and a surface that cannot be trusted to clip is not worth having.

`ScrollIntoView` is how a child asks to be seen — a list keeping its selected row
visible — without reaching into the container's offset. The wheel scrolls whatever it is
over whether or not that has focus, which is what a wheel does; the keyboard scrolls only
the focused container.

The two unticked boxes both waited on consumers: a scrollbar had no one to draw for yet,
and the nine existing state types kept their own scroll fields until the screens using
them moved onto widgets in `TUI-0003`.

## Notes

Depends on `TUI-0002`.

Watch the selection-follows-scroll behaviour: a list keeps the selected row visible,
which is a relationship between the *child's* selection and the container's offset. The
container needs a way for a child to ask that a region be brought into view, rather
than the child reaching into the container's offset.

## Closing

Both remaining boxes came due once there were widgets that scroll.

**The scrollbar.** Four widgets had grown the same five lines: clip a column off the
surface if the content overflows, draw the content, then draw the bar into the column that
was clipped. Two conditions per widget that had to agree — `Scrollbar && count > height` to
reserve, and `Scrollbar` to draw — and they agreed only because `DrawVertical` happens to
draw nothing when everything fits. Two conditions that must agree, written out four times,
is a bug waiting for somebody to change one of them.

Reserving the column and drawing the bar are one decision, so they are one call now:
`TuiScrollbar.Fit` answers with the room left for the content and has already drawn. The
one thing that genuinely differs between widgets is that a table's bar runs beside its rows
and not beside its header, so `Fit` takes a first row and a visible-row count and nothing
else does.

Doing it found that `TuiTable` had inlined a dim style where the others had a
`ScrollbarStyle` property, and that `TuiTree` had borrowed its *guide* style for its
scrollbar — the same decision spelled three ways for four widgets. All four have the same
property now, defaulted the same way.

It also found a fault of my own making, which is the argument for the test: removing the
tree's draw call without adding its `Fit` left the tree with no scrollbar at all, and every
existing test passed. `TuiScrollbarTests` now asserts that each of the four reserves the
column it draws in, which is the invariant the two conditions were there to keep.

**The scroll state.** No widget keeps one. `TuiList`, `TuiTable`, `TuiTree` and `TuiLines`
each keep a plain offset and clamp it themselves, which is the right amount of machinery
for a widget that scrolls its own content and keeps a selection visible while it does.

`TuiScrollState` survives in six places and all six are *screen* state rather than widget
state: `TuiListState` and the five editors built on it, driving the config browser, the help
browser's sidebar and the file picker. Those go when those screens do, and the box as
originally written — "nine widgets' field" — describes a count that is now zero.

Moving a widget's offset into `TuiScroll` was considered and is the wrong trade: it would
mean `{| List = ... |}` stops scrolling until somebody wraps it, which is a worse surface
for the sake of a smaller class.
