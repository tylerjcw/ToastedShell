## Problem

**A lexical scope allocated ten collections it almost never used.** Measured with `GC.GetTotalAllocatedBytes`, an **empty** `for` iteration allocated **2,797 bytes** — and a scope is pushed per block, so per iteration. `LexicalScope`'s constructor eagerly built eight dictionaries and two hash sets — Commands, Classes, Modules, RefinementTypes, TypeImports, TypeAliases, NativeTypes, LocalEventNames, HushedCodes — of which a loop body uses none.

## Acceptance

**The tables are created when something is first put in one.** Every call site is unchanged, because `scope.Commands[name] = command` still reads the same; the cost is that a *read* of an empty table materialises it, which is acceptable since the table read on the hot path — variables — was always going to exist. **Measured: 2,797 to 2,187 bytes per iteration, and 1.50 to 1.16 µs**, a consistent 608 bytes saved per scope push across every shape measured. **What the measurement changed.** The working theory was "async-per-node": that the cost is async state machines. The numbers say otherwise — a bare `$s = $t` costs only 373 bytes over an empty iteration, while *parentheses alone* cost 5,472 (`$s = $t` 2,560 → `$s = ($t)` 8,032) and each further operator about 5,824. So the expense is concentrated in expression evaluation, not in the async machinery as such, and the remaining plan (`ValueTask`, then a synchronous fast path) should be re-aimed at that before it is written. **A caution about the profiler.** A `dotnet-trace` allocation profile named `ToshLexer.TryCreateIntegerToken` as 43% of allocations — code added the same day for `TS-P2-123`, which rebuilt a four-element suffix table on every call. Hoisting it to a static changed the per-iteration numbers *not at all*: the cost was parse-time, and the trace's sampling had misattributed it against a loop allocating gigabytes. The fix is kept because it is right — that table is rebuilt for every numeric-looking token in every file parsed — but it is not what the trace claimed. **Step 2: the cost was found by counting calls, not by sampling.** Temporary counters on each path answered what the profiler had not: a bare `$s = $t` never enters `EvaluateArgumentAsync` at all, `$s = ($t)` enters it twice per iteration, and `$s = ($t + 1)` three times — at roughly **2,545 bytes per entry**. That is far more than a `Task` (~80 B): it is the state-machine box of a ~1,000-line `async` method carrying locals from all 39 of its branches. Every expression node paid for the largest branch. **The fix is a synchronous pre-dispatch** in front of it — a non-`async` wrapper returning `ValueTask<object?>` that answers the shapes which cannot suspend (a literal, a resolvable variable, and parentheses around either) without entering the async method at all, which is steps 1 and 2 of the plan arriving together. **`$s = ($t)` fell from 8,034 to 2,825 bytes (-65%) and `$s = ($t + 1)` from 11,146 to 6,057 (-46%)**; end to end the million-iteration arithmetic loop went 1.455s to 1.272s and the annotated one 1.645s to 1.487s. The variable case is guarded to match the full one exactly — it falls through when the binding is declared-but-unassigned, holds a rune thunk, or is an out-of-scope constructor parameter — because answering those here would skip their diagnostics. The first draft used a plain value lookup and would have done precisely that; the guard was written after reading the case it replaces rather than after a test failed. **Widened to arithmetic, 2026-08-16.** Pure arithmetic over primitive numbers joins the synchronous path, and because the check recurses, a nested expression collapses entirely: `($t + 1 + 2 + 3)` now enters the async method zero times instead of three. **A/B against the previous commit: -15.1% on `$s = ($t + 1)` and -25.0% on the four-operator form**, the gain scaling with operator count exactly as it should when each avoided entry saves ~2,545 bytes. Comparison, membership, regex and string concatenation are deliberately excluded — each awaits — and either operand being a class instance means a user-defined overload that awaits too. Constant-folded operators are answered from the annotation the lowering pass already stamped. **Two measurement lessons.** A first reading showed the annotated loop 8% *slower*; an A/B against a worktree build of the previous commit put it at +0.5%, i.e. noise — the same trap as `TS-P2-122`, and the second time this session that a cross-run comparison nearly caused a wrong conclusion. And the two standing benchmarks showed no change at all for a good reason: they are built from `$x += 1` and `$x == N`, a compound assignment and a comparison, neither of which the fast path covers. A benchmark that does not exercise the change reports honestly that nothing happened. **The operator itself, 2026-08-16.** `EvaluateBinaryOperatorAsync` is now a non-async wrapper over its async core, taking the synchronous route when the operator is pure arithmetic and both operands are primitive numbers. Placed there rather than at the call sites so every caller benefits at once — a compound assignment, a chained comparison and an operator argument all arrive through it. **-3.2% on the `$x += 1` loop and -2.2% on the annotated one**, with the expression benchmarks unchanged because the argument-level path already covered them. **Two queued items were declined, and the reason is `TS-P1-24`.** A fast path for *comparison* would be a third implementation of equality: `AreEqualAsync` and `OperatorEvaluator.AreEqual` are the parallel pair that item was filed for, its own comment records that an earlier fix landed on only one of them, and the tail awaits `TryConvertForEqualityAsync` for both-direction coercion on top of enum equivalence, records-by-name and collection recursion. A fast path for *member access* has the same shape: `ReflectionObjectAccessor` already carries `GetValue` beside `GetValueAsync`, and routing through the synchronous twin would silently skip whatever the async one does for a computed property. The binary-operator shortcut was safe precisely because it is *not* a copy: it calls the same `OperatorEvaluator.EvaluateBinary` the async path reaches. That is the test worth applying to the remaining shapes — a shortcut to the existing implementation is safe, a second implementation of the same rule is the defect this project keeps finding.

## Where it stands — 2026-08-28

**The numbers above are out of date, and the third step was aimed at the wrong thing.**
Re-measured with the same method — `GC.GetTotalAllocatedBytes` around a 200,000-iteration
loop, best of three, after a warm-up pass over every shape:

| shape | bytes/iter | over empty |
|---|---:|---:|
| empty loop | **1,369** | — |
| `$s = $t` | 1,529 | 160 |
| `$s = ($t)` | 1,657 | 288 |
| `$s = ($t + 1)` | 1,825 | 456 |
| `$s = ($t + 1 + 2 + 3)` | 2,161 | 792 |
| `$x += 1` | 1,825 | 456 |
| `$s = ($t == 1)` | 1,745 | 376 |
| `$s = $r.Length` | 2,041 | 672 |

Against what this item recorded: `$s = ($t)` was 8,034 then 2,825, and is now 1,657.
`$s = ($t + 1)` was 11,146 then 6,057, and is now 1,825. **Expression evaluation is no longer
where the cost is.** It is now 160–792 bytes on top of an iteration that costs 1,369 before the
body runs at all — so between 67% and 90% of every row is the loop, not the expression in it.

That also settles the two shapes this item declined. Comparison now costs *less* per operation
than arithmetic (376 against 456), and member access, the most expensive shape measured, is 672.
Neither is worth a second implementation of equality or of member reading, and the reasons for
declining them are unchanged.

### What landed instead: the single-item fast path

Counting rather than sampling — the method this item vouches for — showed exactly one of each
per empty iteration: one `ExpandIterationItemsAsync`, one `ExecuteBlockAsync`, one scope push,
one body dictionary, one `MoveNextCapturingFailureAsync`.

The expansion is pure overhead for an atom. Every value from `1..N` is an `int`, and
`ExpandIterationItemsAsync` is an async iterator built to hand back the value it was given —
allocated, with its enumerator, once per iteration. `IsExpandableForIteration` is the predicate
already written to mirror the expansion's rule, so the loop asks it and skips the enumerable
when the answer is no. `alreadyExpanded` takes the same route; `SingleItemAsync` was one more
iterator for one value.

**1,617 to 1,369 bytes per iteration, -15.3%**, and because it sits beneath every loop the
saving applies to all of them — the "over empty" column is unchanged in both directions.

This passes the test this item lays down for its own fast paths: it is a *shortcut to* the
existing implementation, not a copy of its rule. It holds only while the predicate keeps
mirroring `ExpandCollectionLikeValue`, so `IterationFastPathTests` pins that agreement directly,
alongside the control-flow cases the restructured inner loop could have lost. The negative
control that forces the fast path unconditionally fails the nested-array case, where an outer
array must expand rather than bind whole.

### What is left is not this item's

The residual per iteration is the block's async iterator, the scope, and two dictionaries — one
for the loop bindings, one inside the scope. Reducing those means either pooling scopes, which
is unsafe while a closure in the body can capture one, or not building an iterator per block at
all. That is `TOAST-0009`'s bound-tree evaluator, and this item is closed rather than left
open against work that belongs there.

`MoveNextCapturingFailureAsync` was checked and needs nothing: it returns a
`readonly record struct` and its `async ValueTask` boxes only if it actually suspends.

### The measurement is a tool now

This item re-derived the same per-iteration allocation harness by hand three times, and its own
history records two occasions where a cross-run timing comparison nearly caused a wrong
conclusion. It lives in `bench/Tosh.AllocationProbe/` now, documented in `docs/BENCHMARKS.md`
with the numbers above. It is not BenchmarkDotNet and does not replace it — it answers one
question in seconds rather than minutes, which is the question this item kept asking.
