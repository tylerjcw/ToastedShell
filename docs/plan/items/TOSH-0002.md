## Problem

`tools/Tosh.DevCompanion/Tosh.DevCompanion.csproj` declares:

```xml
<PackageReference Include="Microsoft.Data.Sqlite" Version="9.*" />
```

A floating reference means two restores months apart can produce different builds
from the same commit, and nothing records which one was tested.

The old board carried a follow-up saying this project pulled
`SQLitePCLRaw.lib.e_sqlite3` 2.1.10, which has a known high-severity advisory
(GHSA-2m69-gcr7-jv3q), and asked for the package to be bumped. **Checked
2026-08-16: it now resolves to 2.1.12, so the advisory no longer applies.** No
action was ever taken — the float moved on its own.

That is the actual finding. The vulnerability resolved itself, which means it could
equally have appeared on its own, and the repository would have no way to know. A
security note that fixes itself invisibly is not a fix, it is an absence of control.

## Acceptance

- [x] The reference is pinned to an exact version, or floats only within a patch range
- [x] The version in use is recorded where a reader can find it without running a restore
- [x] The advisory is confirmed not to apply to the pinned version at the time of pinning
- [x] Any other floating `PackageReference` in the tree is found and given the same treatment

## Notes

Check the rest of the tree while pinning — this was found because it had a security
note attached, not because anything looks for floats, so others may exist unremarked.

`Tosh.DevCompanion` is a development tool rather than shipped shell code, which is
why this is priority 2 and not higher. That is also the reason it drifted: nothing
that ships depends on it, so nobody looks.

## Closed — 2026-09-20

`Microsoft.Data.Sqlite` is pinned to **9.0.20**, the version the float was resolving to.

The transitive set at the time of pinning is written into the csproj beside the reference, so
a reader can check it without running a restore: `Microsoft.Data.Sqlite.Core` 9.0.20, and
`SQLitePCLRaw.bundle_e_sqlite3` / `.core` / `.lib.e_sqlite3` 2.1.12. GHSA-2m69-gcr7-jv3q names
`SQLitePCLRaw.lib.e_sqlite3` 2.1.10 and does not apply to 2.1.12 — confirmed against
`project.assets.json` rather than assumed from the version string, and again after pinning.

**No other float existed.** All nine `PackageReference` elements in the tree now carry an exact
version, and none is missing one.

`PackageVersionPinningTests` is the control this item says was absent: the float was found by
following a security note, not by anything that looks for floats, so the next one would have
arrived the same way. It refuses a wildcard and interval notation both — `[9.0,10.0)` pins no
more than `9.*` does, it only spells the range out — and it carries a second test asserting the
path walk actually reaches the projects, because a walk that finds nothing passes an
"everything is fine" assertion silently.

Verified by reintroducing `Version="9.*"` and confirming the guard fails, then restoring the
pin. A guard that has only ever passed is not yet a guard.

## Not done, and deliberately

`NuGetAudit` is not enabled. It would catch the *class* of problem this item was filed over —
an advisory appearing on a transitive package with nobody looking — which pinning does not.
Turning it on changes what a restore does for every project, and this repository is the
author's login shell; that is a separate decision rather than a detail of pinning one
reference.
