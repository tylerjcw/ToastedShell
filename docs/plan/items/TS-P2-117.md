> Status as filed: Open — fixed 2026-08-17

## Problem

**A line beginning with a unary operator is absorbed into the previous line's expression.** `var r = true` followed on the next line by `not $r` reports `Variable 'r' was not found` at 2:5 — the binding never happened, because the two lines parsed as one expression continuing across the break. Measured on `HEAD` (`6351da8`) in a clean worktree, so it is older than `TS-P2-116` and independent of it: `var r = 5` then `not true` fails at **1:9**, the *first* line's right-hand side, and `var r = 5` then `+ 5` produces nothing at all. The boundary is strange and is the reason this is filed rather than folded in: a leading *binary* line is fine (`var r = 5` then `6 + 3` answers 9, and `var a = 1` / `var b = 2` / `$a + $b` answers 3), and the same two statements separated by `;` on one line are also fine (`var r = true; not $r` answers `False`). It appears to depend on what the previous right-hand side was — `var m = 12` then `bnot $m` answers -13, while `var r = true` then `not $r` fails.

## Acceptance

Decide first whether a leading operator is *meant* to continue the previous line, because that is a language question and not a parser bug: if it is, the ambiguity with a statement that opens with `not`/`-`/`+` needs a stated rule; if it is not, the continuation should stop at the line break unless the line ends with an explicit `\`. Either way the two-line form must stop silently discarding the binding. A corpus should cover both readings of `var r = true` / `not $r`, the `;` form that already works, the binary-leading lines that already work, and whatever explicit continuation the rule settles on.

## Resolution — 2026-08-17

**The rule needed deciding and turned out to be already decided.** The acceptance asks
whether a leading operator is *meant* to continue the previous line. Measuring what the
language already does answers it: a **trailing** operator continues (`1 +` then `2` is 3)
and so does an unclosed bracket. Continuation is signalled by the line that *ends*. A
leading operator continuing as well was simply inconsistent with that, so no new rule was
needed — only the existing one applied.

Six operator loops in `ToshParser.Expressions.cs` now refuse a bareword operator that begins
a line. An unclosed `(` or `[` exempts it, because there the expression genuinely is still
open and a leading operator is ordinary style — pinned, because a fix at the wrong level
would have broken it. Braces are deliberately **not** counted: a block holds statements, so
a line inside one begins a statement exactly as a line outside does.

`var m = 12` / `and $m` now reports `and` as an unknown command. That is the right answer —
a line beginning with `and` is a statement, and `and` is not one — and it is a large
improvement on silently discarding the declaration above it.

### The guard caught the fix

`OperatorStatementCorpusTests` listed `not` as a known failure owned by this item, with the
note that "an exemption that outlives its defect hides the next one". It failed the moment
the defect went away, naming this item and asking for the entry to be deleted. `KnownFailures`
is now empty.

13 tests; 5 fail with the parser reverted, and the eight that pass either way are the
continuation forms and the spellings that already worked.
