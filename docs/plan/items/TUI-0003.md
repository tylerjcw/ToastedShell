## Problem

`HelpBrowserScreen` and `ConfigBrowserScreen` are 6,800 lines that build their own
sidebars, detail panes, search rows, footers, dialogs and hit rectangles out of the 285
lines of primitives in `TuiRenderHelpers`. They are not duplicated code — a clone audit
measured 2% literal and 7% structural overlap, because both already call
`RenderDualPaneContent`, `RenderSearchRow` and `RenderFooterLine`. What they duplicate
is the *composition*: each one wires state objects to primitives by hand, because there
is no level above the primitives to work at.

Until they are ported, the widget layer is a claim. Porting them is the test: two apps
that are genuinely different — one navigates a catalogue, the other edits a config tree
with validation, staging and eight kinds of editor — should come out shorter and share
their furniture.

## Acceptance

- [x] Both browsers build a widget tree instead of concatenating lines
- [x] The sidebar, detail pane, search box and footer are shared widgets, not per-screen rendering
- [x] The confirmation dialog draws as an overlay rather than by splicing lines into the screen's own output
- [x] The `_lastListRect`-style hit rectangles are gone, replaced by hit testing against the arrangement
- [x] The CLR explorer's type pages and the config editors survive the move unchanged in output
- [x] `TuiBrowserGoldenTests` passes without re-recording, or every diff is read and explained

## Notes

The golden masters recorded in `e5d1681` exist for this item. Ten scripted sessions
snapshot every frame, including the CLR type page and the config value editors, so a
port that changes output says so. That is the whole reason they were written before
anything moved.

Expect the config browser to be the harder of the two: its editors mutate, its detail
pane renders live previews of the user's theme and prompt, and the prompt preview is
deliberately scrubbed from the snapshots because it embeds the working directory, git
state and the last command's duration.

`TuiCustomScreen` should come out of this too. Once widgets compose, the 753-line
interpreter over a closed enum has nothing left to interpret.

## What landed

Both browsers draw into cells. No screen in the shell builds a string frame any more, and
`TuiFrame.Content` has no producers left.

The drawing moved and nothing else did: the help browser's history, groups and CLR
explorer, and the config browser's schema, staging, eight editors, validation and live
previews are untouched, as is every key either answers.

  header  TuiBorder over TuiLines
  list    TuiList with a SpanSelector — a row of styled runs, which is what both
          sidebars were already building by hand
  detail  TuiLines, which keeps its own offset
  footer  TuiLines

Three things went with the port. `TuiScrollState` is gone from both browsers, because a
pane that scrolls owns its offset. The `_last*Rect` hit rectangles are gone, because a pane
that has been laid out knows where it is and a screen keeping its own copy has two answers
to one question. And the confirmation is a `TuiOverlay` rather than lines spliced into the
detail pane — spliced in, it hid whatever the reader was looking at when they pressed the
key that raised it, which is the one thing they need in order to answer it.

The recorded sessions were not left to chance. A plain-text twin of each snapshot was
recorded first, so the comparison survives the renderer's change of line breaks, and every
difference was read: the panes sit one column narrower, because a fraction is measured
against the space actually being divided; and the lists sit at different offsets in some
frames, because each keeps its selection in view by its own rule now. Checked frame by
frame that the selection is visible in every one. Nothing else moved.

`TuiWidgetKind`'s closed enum, `TuiCustomScreen`'s 753-line switch and
`TuiRenderHelpers`'s string builders are what this was for; the first two are already gone
(`TUI-0004`, `TUI-0015`) and the third now has only the browsers' own helpers calling it.
